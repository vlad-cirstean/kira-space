Agents needs an authenticated `claude` or `opencode` CLI. Kira finds it on your `PATH`, through your login shell, or in common install folders. Kira never writes your agent config, except when you click **Export**.

## Agent providers

Kira runs two agents: Claude Code and OpenCode. Pick the default in Settings, in the section named after the current agent. The **Agent** select runs new sessions and background steps. An agent whose CLI is missing shows `(not found)` and can't be picked.

- Per launch: the task launch menu (**New terminal or agent session**) lists one entry per installed agent, such as **Claude Code session** or **OpenCode session**. It does so when two or more are installed.
- Per step: the `agent` key, or **Agent** in the step's **Advanced** section. **Default provider** uses the setting.
- Order: the launch menu pick, then the step's `agent`, then the setting.

A conversation keeps its agent. Resume, Take over, Restart and Continue in terminal reuse it, even after the setting changes. No conversation moves between agents. If the agent is gone, Kira says that the agent that ran this conversation is no longer available.

| Feature | Claude Code | OpenCode |
|---|---|---|
| Interactive sessions, Take over, review rounds | Yes | Yes |
| Headless workflow steps | Yes | Yes |
| Smart scripts and smart steps | Yes | No: OpenCode can't cap cost |
| Memory calls | Yes | Run on Claude Code |
| Usage limits in the status bar | Yes | No |
| Activity and notifications | Hooks | A Kira plugin, no waiting-on-monitor state |

Every smart script has a budget, so OpenCode refuses each one. A plain agent step runs.

OpenCode learns its session ID after launch. Resume waits until the agent reports it. Kira passes no `-m` to an OpenCode session: set `opencode.model` in [agent settings](#agent-settings). Kira's own MCP servers install into OpenCode by a snippet that you paste into its config.

## Tasks and branches

A task owns branches across repositories. A branch is one of:

- `mine`: created here, with a name.
- `review`: another author's branch.
- `parked`: kept out of the merge order. The plan shows it as Not merging.

Another author's branch arrives as a review task. **Convert to work item** in its task menu makes it your own task: its branches become mine and get a worktree. It can't be turned back.

Paste a pull request or branch link into **Add > Existing branch** to add its branch. A fork's pull request arrives as `owner/branch`; another author's branch arrives as a review task. The repository must already be in your workspace with a remote for that repository.

A task has a status. The workflow sets it as the task moves between steps. You can also set it yourself, from the task menu or the status picker in the task panel. A manual move holds until the task changes step. A stuck or failed run shows a separate Blocked chip beside the status.

### Task statuses

The **Task statuses** row on the Workflows page edits the set. Add, rename, recolour (16 colours) and reorder statuses. A status is only a label: Kira reads nothing into its name, colour or order. Four selects set when a status changes by itself: where new tasks start, and what a step, a review and the finished workflow set. All but the first can keep the current status. Editing a status never changes the tasks that have it. Deleting a status asks where its tasks move. A new install has To do, In progress, In review and Done.

A new task lands in Today with no repositories, so it can start as soon as it has one. Add repositories or existing branches from the task panel, or let the agent declare them. Archiving asks for confirmation. Set, change or clear the estimate at any time, and rename the task in the panel title.

Backlog items stay off the plan until you promote them.

## Base branch and stacking

A task picks its base branch per repository: the repository's main, any branch, or another planner branch to stack on. A headless run rebases the branch when the base changes. **Change base…** and **Rebase onto** start that run.

No rebase starts on its own when a base moves.

## Workflows

A workflow is a YAML file in the `workflows` folder of the Space home, `~/.kira-space/workflows`. No workflow ships preinstalled. Sample files live in `apps/kira-space/internal/adeflow/testdata`.

The app watches the folder. A broken edit keeps the last valid version and reports the line.

A workflow lists its steps under `steps`, in order. Every step has an `id`, a `name`, a `kind` and a task `status` (a status id, such as `in-review`) while the task sits on it. Old files that name a status (`In review`) still load. A top-level `stages` key is refused: list every step under `steps`.

A step has one of four kinds:

- `agent`: the agent runs a `prompt` headless.
- `script`: one shell `command` runs in each branch worktree. Exit code 0 ends with `done`, any other with `failed`.
- `review`: the run waits for you. See [Review steps](#review-steps).
- `manual`: your own work. `session: true` opens an interactive agent session, with an optional `prompt` as its first message.

`agent` names the agent for an agent step, a review step or a manual step with `session: true`. Leave it out to use the setting.

An agent, script or review step runs `once`, for `each repo`, or `only <repo>`. It starts automatically or waits for your approval (`before: approval`). A step with `skip: true` is passed over; at least one step must stay unskipped.

```yaml
id: feature
name: Feature
steps:
  - id: spec
    name: Spec
    kind: manual
    session: true
  - id: impl
    name: Implement
    kind: agent
    runs_on: each repo
    prompt: Implement the spec for {repo} on {branch}.
  - id: release
    name: Release
    kind: script
    command: ./scripts/release.sh --branch {branch}
```

### Results and routes

An agent step can declare 1 to 12 results. Each result has an `id`, an `ok` flag and a `next` route. A script step has the fixed results `done` and `failed`; set only their `next`. A manual step has no results and moves to the next step when you finish it.

- `next`: the next step.
- A step id: that step. A later step skips the steps between. An earlier step makes a loop.
- `end`: the end of the workflow.
- `stop`: stop the task. Only a result that is not ok can use it.

A route to the step itself or an earlier step is a return. The step's `max_returns` limits them per task, step and branch. The count survives restart and Resume.

- Agent and script step: 1 to 10, default 3.
- Review step: 0 to 10, default 0. `0` means no limit.

At the limit the run stops with `Stopped: <step> reached its limit of <n> returns.` Retry the step to continue.

A run that ends with no report takes the step's `failed` result.

### Graph editor

The Workflows page edits a workflow as a graph or as YAML. Save with `Cmd+S`. Nothing saves automatically. Leaving with unsaved edits asks first.

Edit on the canvas. `+ Add step` under the graph adds a step of a kind you pick. The `⋯` menu on a step, or a right click, has Add step after, Move up, Move down, Make start, Skip and Remove. Move is off when it would turn a forward route into a return. Select a step to edit it in the inspector. The inspector shows the step number, name and kind switch on top, then four sections: **Action**, **Run**, **Sandbox** (agent, script and review steps) and **Results**. **Run** holds the repository scope, start gate, timeout, task status and agent. The status list is your set, with an **Edit statuses** link to the Workflows page. A step with no status of its own uses the default for its kind. **Advanced** holds allowed tools, agent settings and skip. Changing the kind clears the prompt, command or session prompt, after a confirmation.

A task follows the live file until its first run, session or move. After that it keeps a snapshot, and an updated file applies to new work only.

### Moving a task

The step block on a task offers Back and Next, and the task menu offers **Move to step**. Moving to an earlier step keeps the later runs as history; the step runs again. Moving to a later step passes over the steps between. **Done** finishes the task.

### Review steps

A step with a `review` block waits for you instead of running an agent. Put it after the step that wrote the code.

```yaml
- id: review
  name: Review
  runs_on: each repo
  timeout: 1h
  review:
    send_to: implementer
  results:
    - id: approved
      ok: true
    - id: rejected
      ok: false
      next: stop
```

`send_to` is `implementer` or `new`. `implementer` resumes the session of an earlier agent step, with its agent. `new` starts a review agent that keeps its own session across rounds. The optional `implementer` key names that step. Empty means the nearest earlier agent step. A review step takes no `prompt`, `allowed_tools` or smart script. `timeout` stays required.

The run enters the `review` state and the board shows **Waiting for review** and a **Review** item in Needs you. Open **Review code**, comment on the diff, then pick **Send to agent** in the **Workflow review** tab. The tab also holds the route and the finish buttons.

A comment is a **Change** or a **Question**. One send is one headless round. The agent answers each open comment with `reply_review_comment` and may commit. An answered comment turns **Addressed**. Reopen one and send again for another round. A round runs one at a time. A round resumed on the `implementer` runs with that step's `allowed_tools` plus `reply_review_comment`, so list `Edit` there if answers may change files. A `new` agent gets no `allowed_tools` list.

Finish with one of the step's results. The note you type (up to 2000 characters) reaches the step the result routes to. Open comments ask for a confirmation first.

If the implementer session is gone, the round moves to a new review agent and the tab says so. A round that a quit interrupted shows **Resume**. The review run itself stays in `review` across a restart.

### Sandbox

On macOS every agent, script and session step runs under a Seatbelt sandbox, unless its access is `off`. An agent or review step without a `sandbox` block gets the default: write the branch worktree, network on. A script step or manual session step without one runs with no sandbox, so existing steps behave as before.

```yaml
sandbox:
  access: write        # write | read | off
  read: [~/notes]      # extra read-only folders
  allow: [~/go]        # extra read-write paths
  network: true        # false: the agent's model API only
```

- `write`: writes the worktree and the scratch folder. Reads the worktree, tools and the `read` list. A home file outside them fails.
- `read`: same reads, no worktree writes.
- `off`: no sandbox, no other keys. The step badge shows `No sandbox`. This is the script and manual session default.
- A script step can set `sandbox` like an agent step. `read` fits a check that must not change files.
- A manual step with a session can set `sandbox` too. The session chip shows the policy and blocked actions. A sandboxed session cannot push or fetch, change agent settings or sign in again; push from the branch menu.
- Paths are absolute or start with `~/`. Keychain paths are refused.

Git inside the sandbox can stage, commit, amend and rebase in place. It cannot create branches, worktrees or tags, change config or hooks, write other branches, or delete objects. Use `request_branches` for a branch. Use `fetch_remote` and `push_branch` for the network; both run in the app. `push_branch` pushes the task branch only, never a protected branch, and a read step cannot push.

The SSH agent is blocked. With `network: false` only the agent's model API is reachable. With OpenCode, `network: false` reaches only a fixed list of model hosts. Sandboxed agents read the macOS keychain, so Claude Code signs in as usual. OpenCode reads its sign-in from its own data folder.

The run line shows a lock badge: `Write worktree`, `Read only`, `No sandbox`, or `N blocked` after denials. Click it for the policy, the first 50 blocked actions and the profile. A run that fails after a block says `Sandbox blocked <op> <path>.` Take over of an agent run opens an unsandboxed session.

### Outside the repositories

A step with `outside_repo: true` (agent, script or session) runs in the task folder, even when the task has branches. In the inspector, turn **Repository aware** off. The step has no repository scope. Its prompt or command may not use `{repo}` or `{branch}`; saving fails with a message if it does. Use it for work that touches no code, such as a notes or planning step. The run line reads `Task folder`.

```yaml
- id: notes
  kind: script
  command: ./notes.sh {task}
  outside_repo: true
```

Linux and Windows write the profile but do not enforce it. The badge says `Not enforced`. Claude permission rules still apply; they do not stop shell commands.

## Runs

A headless run starts `claude -p` or `opencode run` in the branch worktree. The agent reports through the `finish_step` tool. A run that ends without calling it fails with `no report: <agent> ended without calling finish_step`.

A run that came back shows `↩ n/N`: returns used of the limit. A step with no limit shows `↩ n`. The chip turns red when the limit stops the run.

Each run line shows its sandbox badge. See [Sandbox](#sandbox).

### Agent tools

Runs and task sessions get extra tools on the `kira-ade` MCP server. An agent creates branches and worktrees only with `request_branches`, and you approve each request in a dialog. An agent records what it made with `report_artifacts`. Finishing a step or a task returns every artifact of the task. See [MCP tools](../../reference/mcp-tools/).

Branches and repositories an agent adds carry an `agent` chip.

## Interactive sessions

Start an agent session in a branch worktree from the board. **Take over** turns a headless run into an interactive session. A taken-over run can still call `finish_step`.

A branch holds one session at a time.

Hover a session tab for its state and last activity. Right-click it to copy the agent's session ID, or to **Restart** an interactive session: Kira closes its terminal and resumes the same conversation.

Finished and stopped sessions sit behind the **Finished or stopped** dropdown at the right of the session tabs. Each keeps **Take over**; a background run's label opens its log. An archived task lists them inline.

## Agent context

The **Context** sub-tab of **Agent config** edits one Markdown file that every agent gets as extra system prompt: `~/.kira-space/agent/context.md`.

- Every module uses it: sessions, Take over, resume, headless steps, smart scripts and Continue in terminal. Memory calls do not.
- Up to 32 KiB. Empty or missing means no context. A broken file gives agents the last good text.
- A save applies to agents started after it. A running session keeps its text.
- A resumed Claude Code conversation keeps the context it started with until it compacts. OpenCode reads the new text on resume.
- The Studio modules have no editor. They read the same file.

## Agent settings

The **Settings** sub-tab of **Agent config** edits `~/.kira-space/agent/settings.yaml`. One file serves every agent. Kira renders it in each agent's own format. The file is up to 256 KiB, and an unknown key is refused with its line.

Common keys:

- `env`: variables every launch gets.
- `permissions`: `allow` and `deny` lists, in Claude Code tool names. `deny` beats `allow`.
- `mcp_servers`: a server per name. A stdio server has `command`, `args` and `env`. An http server has `url` and `headers`. `enabled` defaults to true. A server has a command or a url, never both. Names that start with `kira` are reserved.
- `hooks`: a hook per name, with `event`, `command`, `timeout` (1 to 600 seconds, default 60) and `matcher` for tool events. Events are `session_start`, `session_end`, `prompt`, `tool_start`, `tool_end`, `notification` and `turn_end`.

Each agent has its own section:

- `claude`: `model`, `permission_mode` (terminal sessions only), `status_line`, `hooks` with Claude Code event names, and `skip_hooks`.
- `opencode`: `model` as `provider/model`, `plugins` as `file:///` URLs, and `skip_hooks`.

```yaml
env:
  GITHUB_TOKEN: ${secret:gh-token}
permissions:
  deny: ["Bash(rm -rf:*)"]
mcp_servers:
  tracker:
    url: https://mcp.example.com/mcp
    headers:
      Authorization: Bearer ${secret:tracker-token}
hooks:
  lint:
    event: tool_end
    matcher: Edit
    command: ./scripts/lint-changed.sh
claude:
  model: sonnet
opencode:
  model: anthropic/claude-sonnet-4-5
```

References:

- `${NAME}` reads your login shell environment, then the app's. `${secret:name}` reads a stored secret. `$${` writes a literal `${`.
- They work in `env` values and in MCP `command`, `args`, `url`, `headers` and `env`. Hook and status line commands take none. Put the secret in `env` and read it as `$NAME`.
- A missing variable or secret fails the launch and names it.
- OpenCode refuses a value that holds `{env:` or `{file:`.

The **Secrets** section lists the secrets the file references. **Set value** stores a value sealed on this computer, shared with the Studio modules. Kira never shows it again. Deleting a secret warns that settings which reference it fail to launch until you set it again.

**Result** shows per agent the exact config it receives, with references as written, plus what Kira adds at launch. For OpenCode that is one JSON document in `OPENCODE_CONFIG_CONTENT`. No file is written.

- Kira's own hooks always run. Yours run in addition. `skip_hooks` drops a common hook for one agent. OpenCode applies no common hook yet.
- Settings apply to every terminal session, Continue in terminal, headless agent steps and review rounds. Smart scripts, smart steps and rebase runs choose their tools themselves.
- Resolved values live in a per-run file or the environment, removed when the agent exits. Headless step logs mask them. A live terminal shows what the agent prints.

## Import and export

Under each agent in the **Settings** sub-tab of **Agent config**, **Import from Claude Code** or **Import from OpenCode** reads that agent's user-level config. **Export to Claude Code** or **Export to OpenCode** writes Kira's settings and context into it.

- Claude Code files: `~/.claude/settings.json`, `~/.claude/CLAUDE.md` and the `mcpServers` of `~/.claude.json`.
- OpenCode files: `opencode.json`, `opencode.jsonc` or `config.json`, and `AGENTS.md`, in `$XDG_CONFIG_HOME/opencode` or else `~/.config/opencode`. `opencode.jsonc` wins over `opencode.json`.
- Project files are never read. A file over 4 MB is not read.

Import shows a preview first. Each item is **To add**, **Same** or **Differs**. A differing item is unchecked by default. Skipped keys are listed by name. The context file imports as **Replace** or **Append**. A literal credential becomes `${secret:<server>-<field>}` and a sealed secret on apply. Login keys such as `apiKeyHelper` are never listed.

Export merges by key and keeps other keys and JSONC comments. The dialog shows a diff with masked credentials, then asks to confirm. Kira keeps a backup named `<file>.kira-backup-<UTC time>` beside each changed file.

- A secret exports as a reference. Claude Code gets `${KIRA_SECRET_<NAME>}`. OpenCode gets `{env:NAME}`.
- The **Environment variables** list names each variable. **Copy export lines** copies lines without values. Set them where the agent starts.
- Claude Code servers go through `claude mcp remove` and `claude mcp add-json -s user`.
- Hooks export to Claude Code only.
- A preview lives 10 minutes and applies once. A file that changed since the preview aborts the export, and nothing is written.

:::caution
Export writes your user-level agent config. Kira keeps a backup beside each changed file.
:::

## Hermetic launches

**Hermetic agent launches** is on by default. Agents that Kira starts skip your own user-level agent config. Kira's agent settings and context apply instead. Project files still load.

It covers every launch: interactive, Take over, resume, workflow steps, headless runs and smart scripts.

Claude Code drops:

- User settings, hooks and permissions.
- MCP servers, skills, commands, agents and plugins.
- Your `~/.claude/CLAUDE.md`, claude.ai connectors and auto memory.

Claude Code keeps the project `CLAUDE.md`, `.claude/`, `.mcp.json`, local-scope servers and your login.

OpenCode drops your user `opencode.json`, the global `AGENTS.md` and `~/.claude/CLAUDE.md`. It keeps the project `opencode.json`, the project `AGENTS.md` and your login.

- The project `CLAUDE.md` does not load under OpenCode. The project `AGENTS.md` does.
- `~/.opencode` and user skills in `~/.claude/skills` and `~/.agents/skills` still load.
- Theme and keybinds in `~/.config/opencode` do not apply.

Kira can't isolate managed settings and policy, or variables that your shell profile exports. A sign-in kept in your user config, such as an API key helper or provider environment variables, needs the same variables in agent settings. Or turn this switch off.

For smart scripts, the MCP list shows the servers in agent settings. A ticked server missing there blocks the run. With the switch off, the CLI's own list and your user settings load. See [Smart scripts](../../shared/runs/#smart-scripts).

The Studio modules have no switch. Their launches are always hermetic.

## Config files

Workflows and agent config are plain files in `~/.kira-space`, in the `workflows` and `agent` folders.

- Each folder has a generated `AGENTS.md` that lists every option, so an AI agent can edit the files. Kira rewrites it at start. Edits to it are lost.
- The file bar on the Workflows, Context and Settings pages shows the path and status, with Open, Reveal, Copy path and **About these files**.
- Edit with any editor. Kira watches the folder. A broken edit keeps the last good version and names the line.
- Files hold secret references, never values.

## Review code

**Review code** opens the per-branch review in one step: `Cmd+Shift+R`.

The title bar's **Review** menu comments on, approves or requests changes on the branch's pull request, yours or a teammate's. GitHub does not let you approve your own. **Comment on PR** posts to the conversation. The button at the far right hides the agent pane (`Cmd+J`).

The right pane has two tabs when the branch has a review step: **Workflow review** and **Ask agent**. Without a review step it shows the review agent only.

## Notifications

A desktop notification fires when a session finishes, a session needs input, or a background run ends. Click it to open that session or task.

Configure each kind in Settings, in the agent's section (**Claude Code** or **OpenCode**). The same pane has the keep-awake switch.

The status bar shows Claude Code's five-hour and weekly usage for sessions that Kira starts. OpenCode reports none. Turn it off in the same section.
