### 1. `perf(harness): process hook events on one ordered worker`

Files:
- new `internal/harness/eventqueue.go`, new `internal/harness/eventqueue_test.go`;
- `internal/harness/hooks.go`;
- `apps/kira-space/internal/appwire/wire.go` (`shutdownTracker` only).

Today `Hooks` passes `opts.OnEvent` straight to each listener. Claude `handleHook` runs it before
`WriteHeader(200)` when no reply is due (`claude/hooks/http.go:170-176`). OpenCode always does
(`opencode/hooks/server.go:148-154`). OnEvent is `Tracker.HandleEvent`, `bridge.EmitAgentEvent` and
`notifier.HandleEvent` (`wire.go:120-124`): DB writes, emits, an `AppFocused` main-thread call, OS
notification.

Change:
- `eventQueue`: buffered channel (capacity 1024) of items. An item is an event, or a barrier carrying a
  `chan struct{}`. One goroutine calls `fn(ev)` in order and closes barrier channels.
  - `enqueue(ev)` blocks when the queue is full. This is backpressure: the HTTP handler waits, same worst
    case as today.
  - `barrier()` enqueues a barrier and waits for it.
  - `close()` stops intake, drains what is queued, then waits for the goroutine to exit.
  - A panic in `fn` is recovered and logged with `slog.Error`, so one bad event cannot kill the worker.
- `Hooks.Start`: when no queue runs, create one over the caller's `opts.OnEvent`. Hand each listener a copy
  of opts with:
  - `OnEvent = q.enqueue`;
  - `Reply` = a wrapper that calls `q.barrier()` first, then the caller's Reply, but only for
    `ev.AgentID == "" && (ev.Event == EventTurnEnd || ev.Event == EventPrompt)`. Other kinds call the
    caller's Reply directly.
  - Why the barrier: `Tracker.HookReply` sets `suppressIdle` for a block reply, and an earlier queued Stop
    must not consume it (sequence Stop1, Prompt, Stop2-with-block). Those are the only kinds a reply can
    carry (`Tracker.HookReply`, `tracker.go:1140`). Tool events, the bulk, never wait.
  - `ReplyFailed` passes through unchanged. It runs before that event's own OnEvent is enqueued, so order
    holds.
- `Hooks.Stop`: close listeners first (their `http.Server.Shutdown` waits for in-flight handlers that may
  still enqueue). Then `q.close()` and set `q = nil`. A later `Start` builds a fresh queue.
- New `Hooks.Flush()`: `q.barrier()` when a queue runs. It is the sync point for tests; production never
  calls it.
- `HookOptions` docs: OnEvent runs on the hub's single worker in arrival order, never after `Hooks.Stop`
  returns. The listener's own Close no longer implies that; the hub does.
- `shutdownTracker`: call `hooks.Stop()` before `tracker.Close()`. Drained events then still update
  `lastActive` before Close flushes it. Today the order is reversed.

Tests:
- `eventqueue_test.go` (concurrency earns it):
  1. events from 8 goroutines keep per-goroutine order; total count matches;
  2. `enqueue` blocks when full while `fn` is blocked, and unblocks after;
  3. `close` drains queued events, then returns; `fn` never runs after `close` returns;
  4. `barrier` returns only after every earlier event's `fn` returned;
  5. a panicking `fn` does not stop later events.
- Find tests that post a hook through a real hub and assert tracker or bridge state right after: run
  `codegraph_explore "postHook harness.NewHooks Hooks flowharness hooks"` and check
  `apps/kira-space/internal/flows/harnessflow/opencode_test.go`. Add `Hooks.Flush()` inside the shared
  helper that posts the hook (flowharness), never per test.
- `internal/harness/claude/hooks/server_test.go` drives the listener without the hub. It stays unchanged
  and must pass.

Acceptance:
- `go test -race ./internal/harness/... ./apps/kira-space/internal/flows/harnessflow/... ./apps/kira-space/internal/ade/...`
  is green.
- The listener packages have no diff.

### 5. `perf(appevent): flush coalesced batches outside the coalescer lock`

Files: `internal/appevent/coalescer.go`, `internal/terminal/service.go` (`coalesceMaxBytes`), new
`internal/appevent/coalescer_test.go` (or extend the existing one if `codegraph_explore "Coalescer test"`
finds it).

Change:
- Add `flushMu sync.Mutex`. Replace `flushLocked(done, final)` with `takeLocked()`, which stops the timer
  and swaps out the batch.
- Every flush site (Push over size, `onTimer`, Finish) does, while holding `c.mu`: take the batch, then
  `c.flushMu.Lock()`. Then `c.mu.Unlock()`, then `c.flush(batch, done, final)`, then
  `c.flushMu.Unlock()`.
- Flushes therefore start in the order their batches were taken. Push and the timer never wait on an emit
  in progress, except when a second flush queues behind the first (bounded to one).
- Lock order is always `mu` then `flushMu`, never the reverse.
- Finish sets `done` before releasing `mu`, so a late timer or Push is a no-op. Finish stays the last
  flush.
- `coalesceMaxBytes` 16KiB to 64KiB (`service.go:134-135`). A 32KiB PTY read no longer flushes on every
  read under burst output.
- Correction to audit: copies stay (read copy, concat, base64, JSON). Concat into one pre-sized buffer
  already happens (`service.go:185`). No pool: no evidence of allocator cost.

Tests (concurrency earns them):
1. A flush func that blocks: `Push` from another goroutine returns while it blocks.
2. 1000 pushes of sequence numbers from one goroutine with a 1ms interval: the concatenation of flushed
   batches equals the input order exactly.
3. `Finish` while a flush is blocked: the final flush arrives last, with `done=true`, exactly once.

Existing terminal, grpc and codeworkspace search tests must pass unchanged.

Acceptance: `go test -race ./internal/appevent/... ./internal/terminal/... ./apps/kira-space/internal/bridge/...` is green.

## Risks

- Ordering (B2-1): one worker keeps arrival order across all terminals. The Reply barrier keeps the
  `suppressIdle` handshake exact. `ReplyFailed` runs on the HTTP goroutine before the event is enqueued, as
  today.
- Hook delivery when replying before processing:
  - the agent gets its 200 before OnEvent runs;
  - an app crash between reply and worker loses that event's DB write;
  - accepted, since the event was lost on a 2s timeout before;
  - `lastActive` is flushed by `Tracker.Close` after `hooks.Stop` drains (commit 1 reorders shutdown).
- Backpressure: a full queue (1024) blocks the HTTP handler. Worst case equals today's synchronous path.
- Stale idle state (B2-1 + B2-7): `flushLease` runs on the worker after the TurnEnd that set idle. A Prompt
  still queued behind it marks busy later; `SendIfIdle` may type into a session that just got a prompt. Same
  window exists today between hook arrival and PTY write; `HasDraft` still guards typed text.
- Lock inversion: commit 2 removes `lease.mu` → `t.mu` nesting. Commit 5 fixes `mu` → `flushMu` order.
  Commit 12 workers take `repoMutex` (via `ensureWorktree`) while the parent holds `taskMu`, the same
  order as today (`taskMu` → `repoMutex`). No worker takes `taskMu`.
- Goroutine lifetime:
  - the hook worker ends in `Hooks.Stop`;
  - learn goroutines are waited on by `Tracker.Close`;
  - the registry change loop is waited on by `CloseAll`;
  - errgroup workers are joined before `finishBranchRequest` returns;
  - progress reporters live only for the call's ctx.
- Lost OnChange: the coalesced loop re-runs when a signal arrives mid-call, so the last change is always
  observed.
- Quick artifacts are older than live: a CR created seconds ago may be missing from the finish reply
  until the row syncs. The audit accepted this.
- `registered` gating: an agent that relied on the list each call must ask with `includeRegistered`. The
  prompt text says so; the real-claude ADE row checks agents still declare repos.
- Parallel branch creation: concurrent `startSetup`; commit 12 makes the implementer confirm its safety
  before landing.
