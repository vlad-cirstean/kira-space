# P701 plan: Restore after restart

Row: `SPEC.md` `## P701`. One dialog after a relaunch lists what was running when Kira stopped
(scripts, Docker when the engine restarted too, agents) and restores the selection with one button.
Planner discovery: `codegraph_explore` over scriptruns restore, docker restore tracker, ADE recover,
take over, resume, tracker, quit teardown; every hit re-read in this worktree.

## What exists (reuse, do not rebuild)

- **Scripts (P441 offer).** `scriptruns.Service.Recover` fails every running run with source `restart`
  (crash and quit alike: `Close` ends smart and headless runs with `endQuit`, terminal runs exit
  with `CauseQuit`). `restoreExpr` sets `script_runs.restore_pending`; `TakeRestore` moves the ids
  into the in-memory `restoreOffer` once per boot. `RestoreState`, `Restore` (per item, hash check,
  smart resume via `resumeLocked`, normal script via `Start`, `dropKey`) and `RestoreDismiss` serve
  it. UI: `RunsRestoreBanner` and `RunsRestoreDialog` in `packages/workbench/src/automations/restore/`.
- **Docker (P334).** `internal/docker` restore tracker runs from boot (`StartRestoreBound` in
  `appwire/dbmodule.go`), snapshots running containers per engine in `docker_restore_*`, detects a
  daemon restart by the default bridge network id (`detectRestart`), keeps the snapshot `pending`
  until Restore or Dismiss (survives relaunch). Bound `RestoreState` (ticks once, may block on an
  unreachable engine up to `callTimeout`), `RestoreContainers`, `RestoreDismiss`; push
  `kira:docker:restore`. UI: `docker-ui` `RestoreBanner` and `RestoreDialog`.
- **Shared dialog.** `packages/workbench/src/restore/RestoreDialog.vue` (presentational: rows,
  `excluded` model, Select all or none, unavailable collapsible, footer Dismiss plus primary
  `Restore {count}`), `RestoreRowItem.vue`, `types.ts`.
- **Agents.** `TaskBoard.Recover` (`ade/recover.go`): `RecoverRunning` turns running runs `stuck` and
  stores `launch_resume_id` for agent and review runs; `StopAllTaskRunning` stops every running
  session row. `ResumeRun` (`runs.go`) queues attempt+1 headless with `run.resume.line`.
  `TakeOver` (`launches.go`) opens any task session (headless run conversation or stopped TUI row)
  in a TUI: `Prepare` with `Resume` (TUI row, same cwd) or `Resumes` (conversation id), returns a
  `Launch`; the renderer opens the terminal (`useLaunchOpener`, `adeTakeOver` store).
  `PrepareArgs.Message` reaches `Compose`, which appends it with `agent.WithPrompt` (Claude and
  OpenCode both implement it), so a resumed TUI starts with that message submitted at the input.
- **Gap.** A clean quit leaves no trace of which TUI sessions were open: teardown runs
  `terminal.ShutdownBound` first and `Tracker.Reconcile` marks each row `stopped` while the DB is
  open (`appwire.go` teardown comment). Only a crash leaves rows `running` for boot recovery. P701
  adds the missing mark.

## What "was running when Kira stopped" means

| Kind | Clean quit | Crash or kill | Offered at boot |
|------|-----------|---------------|-----------------|
| Script run (terminal, headless, smart; any trigger) | Run ends with source `restart`, `restore_pending = 1` | Row left `running`; `Recover` ends it with source `restart`, same flag | `TakeRestore` ids, unchanged |
| Docker container or Compose project | Not Kira's to stop | Same | Only when the tracker's snapshot for the current engine is `pending` (daemon boot id moved). Not pending means Docker was not restarted: no Docker group |
| Headless agent run (step agent run, review run) | Row left `running` (engine cut by `TaskBoard.Close`) | Same | Runs `RecoverRunning` returned this boot for which `runResumable` holds |
| TUI agent session (task session, mode `tui`) | New: `Tracker.MarkQuit` sets `restore_pending = 1` and `restore_working` before PTYs die | Row left `running`; `StopAllTaskRunning` now sets `restore_pending = 1` on TUI rows it stops (`restore_working` stays 0: unknown) | `TakeRestoreSessions` ids, flags cleared in the same statement |

- A user stop, Close session, Restart, or window close never flags anything (same rule as scripts:
  only quit teardown and boot recovery mark). Closing the last window ends its sessions as a window
  close: not offered.
- Rebase runs, setup scripts, needs-input runs: no resume path today, not offered.
- One offer per boot. Marks are taken (cleared) at boot as `TakeRestore` does; the offer lives in
  memory until restored, closed, or the process ends.
- Dedupe: a stuck run whose agent session id equals an offered TUI row's (a taken-over run) is
  dropped; the TUI row wins.

### Quit mark

`Tracker.MarkQuit()` (`ade/tracker.go`): for every live record (`byRecord`), working is `turnBusy`,
a background count above 0, or open tool calls above 0; `turnInput`, `turnIdle` and `turnUnknown` are
not working (the agent waits for the user, or nothing is known). Calls
`Store.MarkRestore`; a failure logs a warning (quit never blocks). Called from `appwire.teardown`
immediately before `terminal.ShutdownBound` (one added line, with a comment why it precedes it).

## Restore actions per kind

All reuse existing paths. Each item succeeds or fails alone.

| Kind | Resume | Continue | Path |
|------|--------|----------|------|
| Script | row checkbox | n/a | `scriptruns.Service.Restore` (hash check, smart resume, `dropKey`), unchanged |
| Docker | row checkbox (Compose project = one row) | n/a | `docker` `RestoreContainers(engineId, ids)`, unchanged |
| Headless run, Resume + Continue | | on | `TaskBoard.ResumeRun(runId)`: background attempt+1 with `run.resume.line` (already ends "Then continue the task"), unchanged |
| Headless run, Resume only | on | off | Take over the run's session into a TUI with no message (`takeOverLocked`, `stopIfRunning` false), then clear the stuck run's launch spec as `resumeRun` does, so the board cannot resume the same conversation twice |
| Review run | on | always on (`continue: required`) | `ResumeRun` (routes to `resumeReviewRound`); Resume only has no meaning for a review round |
| TUI session, Resume only | on | off | `takeOverLocked` (`pa.Resume = rec.ID`, recorded cwd; moved worktree falls back to `Resumes`) |
| TUI session, Resume + Continue | on | on | Same, with `pa.Message = restore.continue.line`; `Compose` appends it with `WithPrompt`, so the session opens and the message is already submitted at its input |

- `takeOverLocked` gains a `message string` parameter (`""` from every current caller). Bound
  `AdeTaskService.TakeOver` and `adewire.TakeOverArgs` stay unchanged: the message is never renderer
  input. New `TaskBoard.RestoreAgent(ctx, item, cont bool) (AgentOutcome, error)` in new
  `ade/restore.go` holds the table above and takes `taskMu` like `TakeOver`.
- Sessions whose process is gone are the normal case here: every offered agent's process died with
  the old Kira. Resume needs the transcript under `~/.claude` (OpenCode: its own store). A lost
  transcript: headless gives `EndResumeLost` on the new attempt (existing, visible on the board and
  in Operations); TUI shows the CLI's "No conversation found" in its terminal (existing Take over
  behaviour). Unknown agent session id: `learnSessionID`, then `errSessionIDUnknown` as the item
  error.
- `continue` per item: `optional` (headless step run, TUI on a provider whose `WithPrompt` works with
  resume), `required` (review run), `unsupported` (provider without resume prompt; implementer
  checks OpenCode's interactive resume plus prompt and sets this only if it fails).

### Agent offer and availability

`ade/restore.go`:

- `type restoreOffer struct { mu sync.Mutex; items map[string]offerItem }`; one field
  `restore restoreOffer` on `TaskBoard` (zero value usable; `board.go` struct, one line).
- `Recover` fills it after `StopAllTaskRunning`: resumable runs from the `RecoverRunning` result,
  TUI rows from `TakeRestoreSessions`, dedupe by agent session id.
- `AgentRestoreState() []AgentItem`: per item, cheap checks only: task exists and not archived,
  branch still on the task, run still the latest attempt and `runResumable`, provider registered
  (`deps.Agent.For`). Failing one: `state: unavailable` with an i18n reason. Item id
  `run:<runId>` or `session:<sessionId>`.
- `AgentItem` (wire): `id`, `kind` (`run`|`session`), `runId`, `sessionId`, `taskId`, `taskTitle`,
  `branchId`, `branchLabel`, `step`, `provider` (label), `mode` (`headless`|`tui`), `working`,
  `continue` (`optional`|`required`|`unsupported`), `continueDefault`, `state`
  (`ready`|`unavailable`), `reason`.
- `continueDefault`: true for headless and review runs (they were mid-work by definition) and for TUI
  rows with `restore_working`; false for idle or input TUI rows and after a crash (unknown).
- `RestoreAgent` drops the item from the offer on success; `CloseAgentOffer()` empties it.

## Aggregator and bridge

New package `apps/kira-space/internal/sessionrestore` (Space only: agents exist only here):

```go
type Scripts interface { RestoreState() (scriptruns.RestoreState, error); Restore(scriptruns.RestoreArgs) (scriptruns.RestoreResult, error) }
type Docker interface { Current() docker.RestoreState; Restore(ctx, docker.RestoreArgs) (docker.RestoreResult, error) }
type Agents interface { AgentRestoreState() []ade.AgentItem; RestoreAgent(ctx, ade.AgentChoice) ade.AgentOutcome; CloseAgentOffer() }
```

- `State() (State, error)`: `{open, scripts []scriptruns.RestoreItem, docker docker.RestoreState,
  agents []ade.AgentItem}`. `open` is true while the auto-open claim is unused and the process is
  younger than `offerWindow` (2 min, option for tests).
- Docker's part uses a new non-blocking package func `docker.RestoreCurrentBound(b) RestoreState`
  (the tracker's last published `cur`; `none` when unreachable or the tracker is off). Never the
  bound `RestoreState`, which ticks and can block on a dead socket. The tracker's first tick runs at
  boot, before any window loads.
- `Claim(ClaimArgs{WindowKey}) (bool, error)`: compare-and-swap, true once per process and only while
  `open`. The window that wins opens the dialog; every other window does not.
- `Restore(Args) (Result, error)`: `Args{scripts []scriptruns.RestoreChoice; docker *{engineId,
  ids}; agents []{id, continue}}`. Order: scripts first (synchronous, so smart runs and headless
  scripts are running before agents start), then Docker and agents concurrently (an agent never
  waits up to 60 s on a Compose health wait), join. Result: `scripts []scriptruns.RestoreOutcome`,
  `docker *docker.RestoreResult`, `agents []{id, launch *adewire.Launch, runId, code, error}`.
  A `continue` on an `unsupported` or `unavailable` item: that item's `E_BAD_REQUEST`, others go on.
  An id outside the offer: that item's error (scripts keep their whole-call refusal from
  `scriptruns.Restore`; the aggregator pre-filters against `RestoreState` so a stale id becomes an
  item error, not a failed call).
- `Close() error`: marks the claim used and calls `CloseAgentOffer`. Script and Docker offers stay for
  their module banners.
- Bridge: `apps/kira-space/internal/bridge/sessionrestore.go`, `SessionRestoreService{Svc
  *sessionrestore.Service}` with `State`, `Claim`, `Restore`, `Close`; errors through `ipcerr`.
  Bound in `appwire.go` `Bound()` list. Wired in `appwire` after the board and the Docker service
  exist (scriptruns `w.runs`, `dbEmbedded.dockerSvc.BoundService`, `w.AdeBoard`). Without the Docker
  module (server build or tests without it) Docker is a nil adapter reading `none`.

## Edge cases

- **Nothing to restore** (no ready row in any group): no Claim, no dialog.
- **Only unavailable rows**: no dialog; the reasons stay reachable through board and banners.
- **Second window**: Claim returns false; no dialog. Reload of the claiming window after Claim: no
  dialog; banners and board remain.
- **X**: restores nothing, consumes the agent offer and the claim. The Runs banner and Docker banner
  keep their own offers (their Dismiss still drops them). Every agent stays reachable: stuck runs keep
  Resume on the board, stopped TUI rows keep Take over.
- **Restart while a restore is in flight**: items already started are running, so the next quit or
  crash marks them again and the next boot offers them. Items not yet started at that moment are
  lost from the offer (marks were taken at boot, as scripts do today) but stay reachable as above.
- **Restart while the dialog is open, untouched**: same as above; the offer is per boot.
- **Docker engine without default bridge**: no launch-time detection (existing Known open item); no
  Docker group then.
- **Agent row whose take over needs a worktree prepare** (`isPreparing`): item error with the
  existing catalog text; Take over from Sessions later waits as today.
- **Phone**: never shows the dialog.

## Decisions for the user (plan picks the first option)

1. Headless run, Resume without Continue: opens the conversation in a terminal and sends nothing
   (alternative: headless rows always continue in the background, Continue locked on).
2. Docker scope is the P334 snapshot: every non-tooling container running while Kira watched the
   engine, not only containers Kira started (Kira records no "started by Kira" for containers).
3. Auto-open only within 2 min of start; a later Docker restart shows only the Docker banner.
4. X keeps the Runs and Docker banners' offers; agents remain reachable on the board.
5. Continue defaults on for headless runs and TUI sessions busy at quit; off for idle ones and after
   a crash.
6. Continue text: "Kira restarted: continue where you left off."
7. Agents do not wait for Docker Compose health checks (Docker and agents restore concurrently, after
   scripts).
