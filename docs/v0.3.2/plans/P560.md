## What exists

### Server shapes

- `kira-ade`: loopback HTTP, one bearer token and one 0600 `--mcp-config` per run or session (`agentmcp.Server.Register`, `mcp.go:396`). Server name `agentmcp.ServerName` (`tools.go:6`), `Implementation{Name: ServerName, Title: "Kira ADE"}` (`mcp.go:241`). Shared servers keyed by `[6]bool` (run, space, outcomes, git, sandbox, handover); a per-run server when results are declared or a review grant exists. Per-run config files are rewritten each launch, so a rename needs no re-register.
- DB server, three identities:
  - user-scope `kira-db`, registered by the Settings Install button (`bridge/dbmcp.go:20` `dbMcpServerName`, `Installer.Install` = `claude mcp remove --scope user` then `add-json` with `headersHelper`);

### Who sees which `kira-ade` tool

- Step run (`ade/runs.go:868` `superviseAgent`, `allowedTools()`): finish_step, run_outcome, 9 Space tools; plus fetch_remote, push_branch when sandboxed. 11 or 13 tools.
- Review round: the above plus reply_review_comment.
- Rebase run (`ade/rebase.go` `rebaseTools`): git, finish_step, run_outcome; no Bash, isolated.
- Interactive session (`ade/launches.go:432` `prepareWithGrant`): run_outcome, 9 Space tools, plus finish_step with a run id or handover without one. 11 tools.
- Smart script (`scriptruns/smart_run.go:139`): finish_step; Space tools with a TaskID; fetch_remote, push_branch when sandboxed.
- Rule: finish_step and handover are never granted together (`handoverGranted` = TaskID set, no RunID).

## Use cases

Each use case below states the call path after P560. Before/after call counts in brackets.

`kira-space` (agent board):

- U1 Step run on a task branch. Read the prompt, then `task_info` only when the prompt lacks a repo or worktree. Work in the worktree. `report_artifacts` for a PR, doc or proof. `finish_step`. [3-5 calls, unchanged; the prompt already carries repo, branch and worktree.]
- U2 Step needs a second repo. `request_branches`, which blocks for user approval and adds the repo to the task. Then `task_info{repo, branch, waitSeconds}` waits for setup. [before: request_branches then branch_status polls; after: same count, one tool fewer to learn.]
- U3 Read-only look at another repo. `declare_repos`, then `task_info` for the path. [unchanged]
- U4 Sandboxed run. Work, then `push_branch` (and `fetch_remote` to rebase on the remote). [unchanged]
- U5 Review round. `reply_review_comment` per comment, then `finish_step`. [unchanged]
- U6 Rebase run. `git` loop, then `finish_step` with conflictedFiles or lastGitError. [unchanged]
- U7 Interactive task session. Same as U1, ending with `handover` (or `finish_step` when a run is attached). [unchanged]
- U8 Proof for a task. Before: proof_start_session, proof_add_step x N, proof_close_session, attach_proof (N+3 calls, two servers). After: one `proof_save` on the session server, which attaches to the task itself (D7). [N+3 to 1]
- U9 A git operation of the task hangs (a fetch in a branch setup). `operations` lists it, `operations{cancel}` stops it. [two tools to one]

`kira-studio` (databases):

- S1 Answer a question from data. `list_connections`, `list_children` to find the table, `describe` (one table, or a whole schema in one call), then `browse_table` or `run_query`. [before: describe_table and describe_schema overlapped; agents called both.]
- S2 Check a heavy query before running it. `run_query{explain: true}`. [one tool fewer]
- S3 Write or DDL. `run_query{mode: write|ddl}`; approval waits up to 10 min. [unchanged]
- S4 Run a saved script. `run_script` waits up to 50 s and, once ended, returns state plus the masked log tail. Longer run: `get_script_run{runId, waitSeconds, logs}`. [before: run_script, get_script_run, get_script_logs = 3; after: 1, or 2 for long runs.]
- S5 Diagnose a service in Kubernetes. `kube_list_clusters`, `kube_discover` (namespaces and kinds, one discover approval), `kube_list_resources`, `kube_describe` or `kube_pod_logs`. [before: two discover calls, possibly two approvals.]
- S6 Call an HTTP API. `api_list_environments`, `api_request`. [unchanged]
- S7 Stop a stuck query or script. `operations`, `operations{cancel}`. [two tools to one]

## Decisions

- **D1 Names.** `kira-ade` becomes `kira-space`: `agentmcp.ServerName = "kira-space"`, `Title: "Kira Space"`. DB server: user-scope and `Implementation.Name` become `kira-studio`, title `Kira Studio`; session server `kira-studio-session`, `SessionAllowTool = "mcp__kira-studio-session"`. Session and user-scope names stay distinct so a user-scope registration never shadows the audited session server (reason in `sessions.go`). Labels "Kira DB" become "Kira Studio" in UI text, errors and comments; "Kira ADE" becomes "Kira Space". Kept as is (default; NEEDS USER DECISION 1): Go packages `agentmcp`, `dbmcp`, `dbaudit`; workflow YAML key `db_mcp`; table `ade_db_audit`; bound service `DbMcpService`; token file `mcp-db-token.json`; `mcp-header-helper.sh`. Reason: none of them reaches an agent or a user label, and renaming `db_mcp` or the table would need a data move, which P557 rules out.
- **D2 finish_step and handover stay apart.** Guardrail: a run must end exactly once with a status from the run's own enum (`results` ids plus needs_input); a session hands over repeatedly with free notes. The grant never shows both, so the agent never chooses. Merging would put a status enum on sessions and a repeatable call on runs.
- **D3 git stays apart from fetch_remote and push_branch.** Guardrails differ: `git` runs only in a rebase run with no Bash, on any worktree in `GitGrant.Worktrees`, with an argument allow list (`CheckGitArgs`). fetch_remote and push_branch run outside the sandbox, on the run's own repo and branch only, with no free arguments; a read-only step refuses push. One tool would need both argument shapes and both rule sets.
- **D4 browse_table stays apart from run_query.** browse_table runs under the masked-access permission (no mode permission, no approval for read); run_query runs under the declared mode's permission and the plan check. Merging would let one tool switch permission families by argument.
- **D5 kube_list_clusters stays apart from kube_discover.** It needs no cluster id and no discover permission; it returns each cluster's permission groups, which the agent needs to pick the next tool.
- **D6 Operations: one tool per server.** `operations` with optional `cancel: <opId>`. No argument lists; `cancel` stops one listed op and returns `{opId, kind, cancelled}`; an unknown id keeps today's ToolError text, naming `operations`. Both servers keep their scope rules (`kira-space`: task's cancellable git rows, `CancellableRunning`; `kira-studio`: router ops on exposed connections plus `run:<id>` script runs). Default keep (NEEDS USER DECISION 2: drop from `kira-space` instead).
- **D7 Proof in one call.** `proof_save{name, summary?, reason?, steps[]}` replaces start, edit, add_step, close. No `reason` and a new name: create and close. `reason` and an existing closed name: edit (each step may carry `keepOrdinal` or `replacesOrdinal`; an old step left out is removed), returns `pending_review`. Steps validate first; any error rejects the whole call with `steps[i].<field>: <limit>` and leaves no draft. `data` per step is read from the raw request (`proofAddStep` reason: integer precision, key order), now `steps[i].data`. On the session server with a TaskID, a saved proof attaches to the task (same path `TaskBoard.AttachProof` uses) and the result says so; the external `kira-studio` server has no task and attaches nothing. `proof_list_sessions` becomes `proof_list`. Default (NEEDS USER DECISION 3: keep draft tools).
- **D8 attach_proof into report_artifacts.** New kind `proof`, `ref` = proof session name; the handler routes those items to `SpaceTools.AttachProof` and reports each like any other item. Covers a proof saved through the user-scope server in a task session.
- **D9 branch_status into task_info.** `task_info{repo?, branch?, waitSeconds?}`. No arguments: today's answer. With repo and branch: the answer gains `branch` (today's `BranchInfo`, with `next`), after waiting up to `waitSeconds` (0-600) for that branch's setup to leave running. `branchInfo.Next` and `request_branches` texts point at `task_info`.
- **D10 describe.** `describe{connectionId, path, refresh}` replaces describe_table and describe_schema. Path at a relation: today's describe_table answer (columns, PK, FKs, indexes, row estimate, `Tree.Describe`). Path at a container (schema or database): today's describe_schema answer (every relation's columns, `Tree.SchemaColumns`). The node kind decides; on engines with no tables, describe answers as describe_table did for a leaf and as describe_schema did for a container. Errors on an unknown path name `list_children`.
- **D11 explain into run_query.** `run_query{explain: true, includeRaw?}`: today's explain_query path exactly: SELECT or WITH only, read-mode permission plus prompt approval, masked plan stripping, nothing executed. `explain` with a `mode` other than read is refused with that text. `includeRaw` without `explain` is refused.
- **D12 Script logs.** `get_script_run{runId, waitSeconds, logs?: {from, lines, contains}}`; with `logs` it adds today's get_script_logs answer. `run_script` adds the masked last 50 lines when the run ends inside its wait.
- **D13 kube_discover.** `kube_discover{clusterId}` returns `{namespaces, restricted, fallback, kinds}`; one discover-group check and one approval for both lists.
- **D14 One DB server per headless run.** A headless step with `db_mcp` gets `kira-studio-session`; the user-scope `kira-studio` is left out of that run's `UserMCP` and `allowedMcpServers`, so the agent sees one set of DB tools and every call is audited. Interactive sessions load the user's own config and stay as they are. Default on (NEEDS USER DECISION 4).
- **D15 Text budget.** Every changed text gets a lower `budget.tsv` line; targets: `dbmcp.instructions` from 2423 to at most 1200 runes (drop text that repeats tool descriptions; keep the trust, mode and approval rules); `list_connections` 990 to 600; `run_query` plus explain 3358 to 2000; `proof_save` at most 2600 (four tools were 3743); `headless.space.instructions` and `headless.space.suffix` list the new tool set. Descriptions say what the tool returns and the next tool, nothing a schema enum already says.
- **D16 Registration replace, no back-compat code.** Install registers `kira-studio` only. Settings status checks `Registered("kira-studio")`, so an old install reads "Not installed" until the user clicks Install. The stale user-scope `kira-db` entry is removed by the user once: `claude mcp remove --scope user kira-db` (added to SPEC User to-dos and to `site/.../studio/database-mcp.mdx`). No boot re-register, no old-name lookup. Default (NEEDS USER DECISION 5: Install also removes `kira-db`).
- **D17 No change to `kira-memory`, the agent sandbox policy beyond one comment, or Keychain names (P557).**

## Capability map (every merged or dropped tool)

- branch_status (wait for setup, branch state, next hint): `task_info{repo, branch, waitSeconds}`, `branch` field.
- attach_proof (show a closed proof in the task chain): `report_artifacts` kind `proof`; automatic on `proof_save` through the session server.
- list_operations, cancel_operation (both servers): `operations`, `operations{cancel}`; same scope rules, same not-found text.
- describe_table (one relation detail): `describe` on a relation path.
- describe_schema (all relations' columns): `describe` on a container path.
- explain_query (plan without running, includeRaw, masked stripping, own approval): `run_query{explain: true, includeRaw}`.
- proof_start_session (create, name uniqueness, summary): `proof_save` without reason.
- proof_edit_session (edit closed proof, reason, side-by-side review): `proof_save` with reason; pending_review result kept.
- proof_add_step (views table, document, keyvalue, chart, diagram; languages; keepOrdinal, replacesOrdinal; per-value validation): `proof_save.steps[]`, same fields and validation.
- proof_close_session (notify user, closed or pending_review): implicit at the end of `proof_save`.
- proof_list_sessions: `proof_list`, same answer.
- get_script_logs (tail or head, lines 1-500, contains filter): `get_script_run.logs`; tail also inline in `run_script` once ended.
- kube_list_namespaces (namespaces, restricted, fallback): `kube_discover`.
- kube_list_kinds (kinds): `kube_discover`.

Nothing else is dropped.
