# P556 Experimental settings menu, Memory behind a toggle

Ask (verbatim): "Add an experimental menu in settings and hide memory module under a toggle."

Base: `chapter/v0.3.2` at `1f0435352`. Kira Space only: Kira Studio has no Memory module.

## Decisions

- **D1 Shape.** New settings section `experimental` with one boolean leaf per flag. First leaf: `experimental.memory`. Stored like every other leaf: one `settings` row `experimental.memory`, JSON `true`/`false`. A future flag is one Go field, one patch field, one read line, one upsert line, one zod field and one row in the pane's flag table.
- **D2 Default off.** `DefaultSettings().Experimental.Memory = false`, same in `defaultSettings` (TS). The ask says "hide ... under a toggle": hidden is the default.
- **D3 Off for everyone.** No boot-time write. Existing installs, including ones with a `memory.db`, read the default (off) until the user turns the switch on. User decision.
- **D4 Gate UI only, no backend gate.** The backend is already lazy. `NewMemoryService` (`apps/kira-space/internal/bridge/memory.go:69-74`) opens nothing. `service()` (`memory.go:77-93`) opens memory.db, the watcher and the backfill only on the first bound call. `appwire.go:516` states it: "memory.db opens on the Memory module's first call". No other startup path calls `w.Memory`, `w.MemoryImport` or `w.MemoryDistill` (grep of `internal/appwire`: construction, service registration and `CloseMemory` only). So with every UI caller gone, no memory work runs. Gating bound methods in Go would add an error path to every bound memory method and its flow tests for no behaviour change. The `kira-memory` MCP registration in the user's agent config is the user's own agent setup: Kira does not unregister it, and the `memory-mcp` subcommand keeps serving it (that path never reads Kira settings). ARCHITECTURE states this.
- **D5 What off hides.**
  1. Memory mode tab in the title bar (`ModeSwitcher` gets a filtered order).
  2. Memory settings section: not in the nav, and `MemoryPane` not mounted. Mounting matters: `SettingsShell` keeps every pane mounted (`v-show`), and MemoryPane's sections query `MemoryService.SemanticStatus`/`McpStatus`. `SemanticStatus` goes through `service()`, which opens memory.db and starts the backfill. A `v-show`-only hide would open memory.db on every Settings open.
  3. Editor "Distill selection" context action (`views/repo/distillSelection.ts`), which calls `setMode('memory')`.
  4. A window whose persisted mode is `memory` (`main.ts:126` hydrates it) falls back to `git`, Space's `WindowModes.Default`.
  5. A deep link `openSettingsAt('Memory')` while off opens the first section instead. Only caller is `memoryModule.ts:8`, reachable only from inside the module, but the guard keeps `SettingsShell.activeSection` from naming a section absent from its nav.
- **D6 Not hidden.** The Operations panel's `memory` module label (`OperationsPanel.vue:78`): op-log rows are history, and `memory-mcp` can still write them for an agent that has `kira-memory` registered. The `memory` entry in `MODES`/`AppMode` stays: the registry is a total `Record<AppMode, ModeDef>`; visibility is the order list's job.
- **D7 Section placement.** `Experimental` goes last in `sections`, after `Advanced`. `Memory` keeps its slot when on.
- **D8 Live apply.** Visibility reads the saved store value (`settingsStore.experimental.memory`), not the dialog draft. Save closes the dialog; the store update shows or hides the mode tab at once (reactive). The Memory section appears on the next Settings open. No restart.
- **D9 No new store, no new query.** The flag is settings state: it lives in the existing settings Pinia store and travels on `SettingsService.GetAll`/`Set`/`kira:settings:changed`. One composable reads it. No new bound service or method, so the flow coverage test, the bound-service count (`flowharness/harness_test.go:26`, 60) and the bindings surface stay as they are. Bindings still regenerate (`model.Settings` gains a field): `frontend/bindings` is gitignored and built by `scripts/setup.sh` (called from `scripts/prepare-worktree.sh`).
- **D10 One implementer.** Go model, repo, TS schema, pane, gate and specs form one dependency chain (the TS schema mirrors the Go model; specs read the Go contract). No stream split.
