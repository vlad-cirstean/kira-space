## Baseline construction and proof

Build, per DB (kira, review, memory), at the base commit before any deletion:

1. Scratch Go test (not committed; lives under the scratchpad or a `//go:build p557proof` file deleted in step 2) opens a fresh DB through the current chain.
2. Emit baseline SQL: `SELECT type,name,tbl_name,sql FROM sqlite_master WHERE sql IS NOT NULL AND name NOT LIKE 'sqlite_%' AND name <> 'schema_version'`. Order: tables in `rootpage` order (parents before children), then indexes, then triggers, then views. Skip FTS5 shadow tables (`<fts>_data`, `_idx`, `_content`, `_docsize`, `_config`): `CREATE VIRTUAL TABLE` creates them. Keep `sql` text verbatim, including quoted names such as `CREATE TABLE "ade_branch_marks"`; do not reformat.
3. Append seed rows the chain inserts on a fresh DB, as `INSERT` statements generated from the fresh DB (`ade_task_statuses` 0051, `ade_task_status_defaults` 0059, `custom_script_collections` 0023/0064 if non-empty, any `settings` row). Find them by dumping every table with rows in a fresh chain-built DB, not by reading SQL.
4. Write `apps/kira-space/internal/storage/migrations/0090_p557_baseline.sql`, `apps/kira-space/internal/gitreview/migrations/0008_p557_baseline.sql`, `internal/memory/migrations/0008_p557_baseline.sql`. Baseline does not create `schema_version`; the runner does. Header comment: one line naming v0.3.1.
5. Proof: build DB A through the chain and DB B through the baseline alone, then compare, all sorted (order-insensitive):
   - `SELECT type,name,tbl_name,sql FROM sqlite_master` (includes indexes, triggers, views, FTS5 shadow tables, autoindexes with NULL sql).
   - `PRAGMA table_list` (`strict`, `wr`, `ncol`) per table.
   - `pragma_table_xinfo`, `pragma_index_list`, `pragma_index_xinfo`, `pragma_foreign_key_list` per table and index.
   - Every row of every table, as an ordered dump (`SELECT * ORDER BY rowid` or by PK for `WITHOUT ROWID`), including `sqlite_sequence`.
   - `schema_version` equal (90/8/8).
   All must match exactly. Record the result (match, table and index counts per DB) in this file under "Proof result" in the commit that adds the baselines.
6. Real-data check, kira: at the base commit, extend the `TestP552Upgrade` seeding (`openAt82`, insert rows, migrate to 90), plus a flowharness-populated home if feasible, and save the DB to the scratchpad. After the swap, open a copy with the new code and assert: version 90, no migration ran, per-table row count and content hash unchanged, `PRAGMA integrity_check` = ok, `PRAGMA foreign_key_check` empty, schema dump equal to golden. - New `agentcfg.MoveSecretsFile(db *sql.DB, home string) error`, called from `main.go` after `storage.Open`, before appwire builds agent settings.
- `<home>/agent-secrets.db` absent: return nil.
- Open the file with `sqlitex.Open`, `PRAGMA wal_checkpoint(TRUNCATE)`, close. Then on one pinned conn of the kira pool: `ATTACH` it read-only (`file:...?mode=ro` URI), `BEGIN IMMEDIATE`.

- A crash after commit and before the rename re-runs the copy next boot: conflict skip, verify passes, rename.

### Keychain item rename

New: "Kira Space Secrets", "Kira Space", "Kira Space Secrets". The item holds the AES-256-GCM key sealing every value; a plain rename creates a fresh key and orphans them all.

- New `moveKeyIn(oldService, oldAccount, newService, newAccount string) error`; `loadOrCreateKey` calls it, then `loadOrCreateKeyIn(new...)`. Test seam: same parameterised style as `loadOrCreateKeyIn`.
- New item holds a 32-byte key:
  - Old absent: done.
  - Old equal (`subtle.ConstantTimeCompare`): delete old, done.
  - Old differs: return an error, delete nothing. Cipher reports unavailable with a reason naming both item names (no key data).
- New item absent:
  - Old absent or not 32 bytes: done; `loadOrCreateKeyIn` creates the new item (fresh install).
  - Old holds 32 bytes: `AddItem` new with the same data, new label, `SynchronizableNo`, `AccessibleWhenUnlockedThisDeviceOnly`; re-query new and compare constant-time; match deletes old; mismatch or error returns an error and keeps old. `ErrorDuplicateItem` on add re-enters the "new item holds a key" branch.
- A crash between add and delete leaves both equal: next boot deletes old.
- Never log or wrap key bytes; errors name the step and the keychain status only.
- Tests in `keychain_darwin_test.go` with test-only names ("Kira Space Secrets (test old)" etc.): old only moves; both equal deletes old; both different errors and keeps both; neither is a no-op. Real Keychain, darwin only: the Linux sandbox only compiles them (`GOOS=darwin go vet ./internal/secrets` if cgo allows, else note it). The orchestrator asks the user to run `go test ./internal/secrets -run Keychain` on the Mac before close.
- macOS may prompt once for the old item (read and delete) on first launch; install docs already warn of one prompt per build.
- Other Studio brand strings in this path: `keychain_darwin_test.go:21-22` test names, `cipher.go:83` home comment, `scope.go:25` comment (agent-secrets.db). `internal/shell` and `startupfail` test literals are window-title seams, unrelated.
