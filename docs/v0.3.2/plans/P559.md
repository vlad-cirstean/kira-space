### Why `~/.kira-memory` appears with Memory off

- Not the app boot. `NewMemoryService` opens nothing; `Store` construction is free; `removeRetiredModels` only `RemoveAll`s a missing dir. P556 hides every UI surface that would call `MemoryService`.
- The cause is `memory-mcp` startup. `memorycli.Run` (`run.go:64`) calls `openIngest` before serving, which calls `importer.Open` (`engine.go:39`), which calls `ms.DB()`, which `MkdirAll`s the home and creates and migrates memory.db (`store.go:60-70`). Claude Code spawns every registered stdio server at session start, so any Claude session (interactive, or an ADE run that loads user settings) recreates the folder, with no tool call.

## Decisions

- **D1 Path.** Memory home is `<Space home>/memory/`, default `~/.kira-space/memory/`. memory.db keeps its name: `~/.kira-space/memory/memory.db`, with `models/`, `distilled/`, `import-runner.log` and `import-runner.lock` beside it. Why a subfolder, not `~/.kira-space/memory.db`: memory owns several files (34 MB model, distilled docs, runner log and lock) that would scatter over the home root; the sandbox can allow one subtree (D5) without exposing `kira.db`, tokens or `mcp-db-token.json` at the root; `models/` at the root would read as app-wide. Not under `config/`: `config/` holds no DB and no secret so it can become a git repo (ARCHITECTURE "Config files").
- **D2 One env var.** Drop `KIRA_MEMORY_HOME` (default; NEEDS USER DECISION 1). The memory home always follows `KIRA_SPACE_HOME`. Tests isolate with one variable; child processes pass `KIRA_SPACE_HOME` instead.
- **D3 One resolver.** `internal/kirapaths` gains `SpaceHome()` (`Home("KIRA_SPACE_HOME", ".kira-space")`), const `MemoryDir = "memory"` and `MemoryHome()` (`filepath.Join(SpaceHome(), MemoryDir)`). `config.KiraSpaceHome()` returns `kirapaths.SpaceHome()`; `memory.Home()` returns `kirapaths.MemoryHome()`. Doc comments updated (package doc of `kirapaths` and `config` name the shared resolver). No other code joins a Space home and `"memory"`.
- **D4 No migration, no move.** Backward compatibility is dropped (P557). No code reads, moves or deletes `~/.kira-memory`. An existing `~/.kira-memory` is simply ignored; docs say it can be deleted. The user has no memory data to keep.
- **D5 Sandbox.** `agentsandbox.Runtime` gains `MemoryHome string`, set in `discover` to `filepath.Join(realPath(kirapaths.SpaceHome()), kirapaths.MemoryDir)` (resolve the Space home, which exists once Space ran; the memory dir may not exist yet, D6). `Profile` allows read and write on `sub(rt.MemoryHome)` when non-empty, replacing both `.kira-memory` lines. Never allow the Space home itself: `kira.db`, tokens and the DB MCP helper stay denied. `testRuntime` (`profile_test.go:17-25`) sets `MemoryHome: "/Users/ada/.kira-space/memory"`; regenerate the goldens with `-update` and review that the diff is only that path. If `discover` runs in an `agentsandbox` test binary without `KIRA_SPACE_HOME`, `kirapaths` panics (`requireTestHome`): add `TestMain` with `testx.RunWithTempHomes` there if needed.
- **D6 Lazy creation.** Nothing creates the memory home or memory.db until memory is used: a memory tool call, a Memory module call, or a model download.
  - `memorycli.Run`: replace the eager `openIngest` with a lazy `mcpserver.Ingestor` in `memorycli` (unexported `lazyIngest{store, available, mu, engine}`): `Create` and `JobWithFacts` open `importer.Open` on first call under a mutex; a failure is returned and not memoised (same pattern as `gitreview.Store.ensureOpen`, `gitreview/db.go:28`). `Close` closes the engine only if opened. Ingest tools stay registered whenever `--import-ref` is empty.
  - Effect: `memory-mcp` start (initialize, tools/list) touches no file under the memory home. Side effect, stated in ARCHITECTURE: an import job a dead runner left running resumes on the next ingest tool call or Memory module open, no longer on every MCP server start.
  - `appwire/wire.go:84-89` `removeRetiredModels`, its `go removeRetiredModels()` call (`appwire.go:523`), `modelstore.RemoveRetired` and `retired` (`modelstore.go:49-61`): delete, if P557 has not. A P224 one-time cleanup of a pre-v0.3.1 model, so P557's back-compat scope; it is also the only boot-time `memory.Home()` call.
  - Memory flag: no backend gate (P556 D4 stays; NEEDS USER DECISION 3). With the flag off and kira-memory still registered, an agent's tool call is use and creates the folder; a bare session start no longer does.
- **D7 Finalize server env.** `importer.ModelAgent.Home` (memory home) becomes `SpaceHome` (doc: the Space home the finalize MCP server resolves memory under). `mcpServer` (`finalize.go:54-60`) sets `{"KIRA_SPACE_HOME": spaceHome}`. Callers: `memorycli/ingest.go:49` (`kirapaths.SpaceHome()`), `tests/claude/memory_import_test.go:47`. Grep other `ModelAgent{` literals and `.Home` uses in `internal/memory/importer` and update.

## NEEDS USER DECISION

Defaults let the implementer start; the user overrides before implementation if wanted.

1. **`KIRA_MEMORY_HOME` (D2).** Default: drop it; memory always lives in `<Space home>/memory` and follows `KIRA_SPACE_HOME`. Alternative: `memory-mcp` reads `experimental.memory` from kira.db and serves no tools (or exits) when off, so a stale registration can never create memory data.
