# P571 Orchestrator tasks: spawn child tasks, passes, chain reads

Planner: Opus. Base: `chapter/v0.3.4` at `d7ae6f5f4`. Stream: own worktree, parallel to P569 and P570.

## Verdicts

- Pass mechanics need a small engine change. `SetTaskStep` from `done` to first step already works:
  `staleStep` passes, live run refuses, `since` bumps every step at or after target (old runs become
  history, nothing deleted), `syncStatus` re-slots. Missing pieces:
  1. `syncStatus` returns early unless kind is `task`. Orchestrator must sync too.
  2. Newest handover never reaches pass's first step: `handoverFor` returns text only when newest handed
     row has `ToStepID == stepId`. Previous pass ends with row `to = done`. New pass needs its own row.
  3. No action starts a pass: move plus start of first automatic step, one call.
  `ResetWorkflow` stays unused (deletes runs).
- P570 dependency: none. `create_task` takes base through existing `adewire.BaseChoice`,
  `TaskBoard.storedBase` and `CreateTaskArgs.Bases`, never P570's `BranchSpec.Base`. Overlap with P570
  is file-level only (table below), all additive or move-only hunks.
- Split: `P571 Part 1` (backend, wire, bindings, flow tests, docs) and `P571 Part 2` (frontend UI,
  UI specs). Orchestrator renames SPEC row to `P571 Part 1: …` plus `P571 Part 2: …` right after.
  Part 2 starts only once Part 1 is committed: Part 2 UI specs read contract files Part 1's flow tests
  write. This file holds both parts' plans in separate sections; each part gets own implementer pass
  and own Result.

  - `moveBranchKinds` runs only when branch kind really changes: skip for task to/from orchestrator.
- Creation: `adewire.CreateTaskArgs.Kind string` (`""` means task). `validateCreateTask` accepts
  `""`, `task`, `orchestrator`. Bridge patch validator (`bridge/adetask.go:273`) accepts orchestrator.

- Archive: children stay independent. Archiving parent keeps links, abandons its pending
  `task.create` items, refuses nothing. Archiving child changes nothing on parent. Restore works both

### Pass mechanics

- New `TaskBoard.NextPass(ctx, args adewire.NextPassArgs) (adewire.NextPassResult, error)` in new file
  `ade/orchestrator.go`. Args `{taskId, fromStepId?, notes *string, closeSessions bool}`. Result
  `{stepId, started bool}`.
  1. Under task mutex: `loadTaskCtx` (refuses archived), kind must be orchestrator
     (`ErrOrchestratorKind`), current step must be `done` (`staleStep` against `fromStepId`), no live run.
  2. Target: first non-skipped step of plan. Workflow with no steps refuses.
  3. Close stage sessions when asked (same path `SetTaskStep` uses).
  4. Bump `since` exactly as `SetTaskStep` does. Extract shared `passSince(tc, plan, targetIdx)` from
     `SetTaskStep` body (`runs.go:1565-1639`) so both call it; no behavior change for `SetTaskStep`.
  5. Pass handover: handed row `from = done`, `to = <first step>`, source `pass`. Body from new
     registry fragment `ade.pass.handover` with vars `{Message, Previous, PreviousFrom}`: message (if
     any) then previous pass's final handed row (newest handed row with `ToStepID == done`), capped
     at `maxHandoverBytes`. Row written only when body is non-empty. `FromStepName` = previous final
     row's `FromStepName`. Written through `SetEntryStep(taskID, firstStep, since, handoff)` so move
     and row land in one transaction. `applyHandoff` gains source `pass`: always inserts a handed row,
     never touches drafts.
  6. `closeHandoverPrompt`, `syncStatus`, `clearStepMessages`, `notifyBoard`, as in `SetTaskStep`.
  7. Release mutex. When first step is automatic (agent or script), call `StartRun` (`runs.go:295`)
     for it; `started = true` on success. `StartRun` error returns after the move; task sits on first
     step with its normal Run action. Manual first step: `started = false`.
- Older passes stay readable through `task_chain` (own chain). No Memory module.
- `SetTaskStep` from done stays valid for every work kind; only `NextPass` adds pass row and start.

### Child mirror

- Child finishes when a handed row with `ToStepID == done` is written, or entry moves to done with no
  row. Mirror hook lives in repo layer, same transaction:
  - `SetEntryStep`: when `stepID == done` and task has parent, after `applyHandoff`, insert mirror.
    `applyHandoff` returns the handed row body it wrote (`"", false` when none).
  - `RecordRunHandover`: when `ToStepID == done` and task has parent, insert mirror.
  - `recordRunHandoverLocked` early return with `to == done` and no row (no summaries, no draft):
    call new `Tasks.MirrorFinish(taskID, "", now)` so parent still sees the finish.
- Mirror row on parent: `state = note`, `source = child`, `from_task_id = child id`,
  `from_step_name` = child's last stage name, `body` = child's final handover body capped at
  `maxHandoverBytes` (empty allowed: UI shows "finished without handover"). Each finish mirrors again
  (child re-run, finish twice: two rows).
- `note` state keeps row out of `LatestHandover`, drafts and prompt handover. `Notes()` (prompt Notes
  input, `userNotes`) adds `source = user` filter so mirror rows stay out of prompts.
- `UpdateHandover` refuses child rows (`ErrHandoverReadOnly`, new): they copy another task's text.
- No wake: mirror only writes and calls `notifyBoard`.

### Brief

- Child's first handover: handed row `from = ""`, `from_step_name` = parent title, `to` = child's first
  non-skipped step, source `orchestrator`, body = brief. First step's prompt gets it through
  `handoverFor`/`handoverInto` unchanged. `applyHandoff` not used; inserted by `insertTask`.
- `repos.insertTask` gains `brief *model.AdeHandover` and `parentID`; new `CreateChildTask(t, branches,
  day, brief)` wraps it; `CreateTask` passes nil.

### Tools (`internal/agentmcp/orchestrator.go`, new)

- `OrchestratorToolIDs = []harness.MCPTool{create_task, list_tasks, task_chain}` in `tools.go`.
- Interface `OrchestratorTools` with `CreateTask`, `ListTasks`, `TaskChain(ctx, SpaceCall, input)`.
  `Options.Orchestrator OrchestratorTools`; `Grant.Orchestrator bool`.
- `Register` refuses `Orchestrator` without `Space` or without `s.orchestrator`.
- Shared-server key: replace `[6]bool` with comparable struct `toolSet{finish, space, outcomes, git,
  review, sandbox, handover, orchestrator bool}`; `buildMCPServer(ts toolSet, results)` replaces its
  seven bool params. Pure refactor plus one field.
- Grant rules:
  - Orchestrator kind, step run with Space (`superviseAgent`, `runs.go:868`, `space && l.smart == nil
    && tc.task.Kind == orchestrator`): granted.
  - Orchestrator kind, TUI launch or ad-hoc session (`prepareWithGrant`, `launches.go:417`): granted.
  - Rebase and review-round runs (`space` false), smart script steps (`smartstep.go`), automations
    (`automation.go` `Tools()`): never.
  - Task, review, parked kinds, and every child (parent set; always task or parked): never.
  - `allowedTools` (`runs.go:731`) and `prepareWithGrant` append `OrchestratorToolIDs` when granted.
- `create_task`:
  - Input: `title` (1..200 chars), `workflow` (id or name, required, must exist and have a step),
    `repos` (0..10 items `{repo, base?}`; `repo` = nickname, name or code repo id through
    `resolveRepoRef`; `base` = ref name, mapped to `adewire.BaseChoice{Ref: base}` and resolved by
    `storedBase`), `brief` (required, 1..`MaxHandoverBytes`).
  - Validation fails fast as tool error before any prompt (unknown workflow or repo, bad base).
  - Approval: kind `task.create` (`approvals.KindTaskCreate`), one item per call, id
    `task.create:<ref>`. Item: `Origin{Task, Step, Source: callSource}`, `Target{Name: child title,
    Kind: "task"}`, `Operation{Class: "create", Tone: "caution"}`, `Reason: "request"`, `Title` i18n
    `backend.prompt.taskCreate.title`. Payload `{parentTaskId, parentTitle, title, workflow{id,name},
    repos[{codeRepoId, name, base}], brief}`. Owner `taskCreateOwner.Answer`: approve or deny, no
    options. Registered in `NewTaskBoard` next to `branchOwner`.
  - Wait: `TaskBoardDeps.TaskRequestWait` (default 30 min, under `MCP_TOOL_TIMEOUT` 35 min).
    `ctx.Done` withdraws the item. Archive of parent withdraws (`abandonTaskRequests(taskID)` called
    where `abandonBranchRequests` is).
  - Run note while waiting: "waiting for task approval". Generalize run-note hold (see shared files):
    move `holdRunNote`, `releaseRunNote`, `restoreRunNote`, `setRunNote`, `runWait` from
    `branchrequest.go` into new `ade/runnote.go`; hold takes the note text; one hold per run counts
    every waiting call of any kind; restore compares with the note it set.
  - Approve: under parent's task mutex re-check parent live and orchestrator, create child through
    shared helper extracted from `TaskBoard.CreateTask` (`board_writes.go:125-182`) with
    `CreateTaskArgs{Title, CodeRepoIDs, WorkflowID, Bases, Day}`, parent id and brief. Day: parent's
    plan day; backlog parent puts child in backlog; no plan row puts child on today.
  - Result `{outcome: created|denied|timeout|failed, taskId, title, next}`; `next` text from registry
    tool-result entries.
- `list_tasks`: input `{state?: live|archived|all}` (default all). Output children of caller's task,
  newest first, cap 100, `more` flag: `{id, title, kind, workflow, status, step, finished, archived,
  createdAt, lastHandover}`; `lastHandover` = newest handed row body, first 500 bytes.
- `task_chain`: input `{taskId?, limit?, before?}`. `taskId` empty = own task; else must be a child of
  caller (tool error otherwise). Archived tasks allowed. Rows newest first, drafts included with state:
  `{id, from, to, source, state, body, createdAt, fromTaskId}`. `limit` default 10, max 50. `before` =
  row id: rows strictly older than it (created_at, rowid order, as `Handovers`). Body cap
  `MaxHandoverBytes` each with truncation marker; total cap 64 KiB stops early. Output `more`, `next`
  (cursor id).
- Repo reads: `ChildTasks(parentID, state, limit)`, `HandoverPage(taskID, before, limit)`.
