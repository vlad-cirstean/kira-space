# P569 Proof: JPEG screenshots, agent image steps, menu bar entry

Stream A of batch P569/P570. Own worktree off chapter base. Spec row: `docs/v0.3.4/SPEC.md` P569.

Three asks:

1. Proof window screenshots (copy, save active tab, save all tabs) encode JPEG.
2. `proof_save` gains an image step: JPEG only, inline or as a file path.
3. Proof window opens from the menu bar, outside any task.

## Decisions

### 1. Image step shape

- New view `image`: `proof.ViewImage = "image"` in `apps/kira-space/internal/proof/validate.go`.
- Input `data`, decoded with `decodeStrict` (unknown fields refused). Pass exactly one of these:
  - `{"path": "/abs/shot.jpg"}`
  - `{"base64": "<standard base64>"}`
- Both fields given, or neither, is an error: `data must hold exactly one of path or base64`.
- Stored payload: `{"width":W,"height":H,"bytes":N,"base64":"<canonical std base64 of the bytes>"}`.
  - Neither the path nor a mime type is stored.
  - The window needs only dimensions and bytes. A stored path would leak the agent's filesystem layout into the proof.
- A path source is read and its bytes are copied into `proof_steps.payload` at save. A later change or deletion of the file never alters the proof. Proofs are immutable records, and a path reference would break that.
- `query`, `language` and `source` keep their meaning. An image step usually has an empty query; that is allowed today.

### 2. JPEG check

Order in `checkImage`:

1. Read the bytes from the path or the base64 (`base64.StdEncoding`; refuse URL-safe and data-URL prefixes with `data.base64 is not standard base64`).
2. Apply the size cap.
3. Check the prefix `FF D8 FF`.
4. Run `jpeg.DecodeConfig` and apply the dimension caps.
5. Run a full `jpeg.Decode` for integrity. It is bounded by the pixel cap, so memory stays under about 100 MB worst case at 25 MP RGBA. Decode runs once per step at save, never at read.

- Any failure in steps 3 to 5 gives one message: `data is not a JPEG image (baseline or progressive)`.
- Uses stdlib `image/jpeg` only. No new dependency.
- Caps, consts in validate.go:
  - `maxImageBytes = 3<<20 - 1<<10` (3071 KiB). Base64 of 3071 KiB is about 4095 KiB, plus about 60 bytes of fields, so it stays under `maxPayloadBytes` (4 MiB). The existing per-step check after `json.Marshal` stays as a backstop.
  - `maxImageSide = 16384`. This is the WebKit canvas and `<img>` decode practical limit; larger images fail to draw.
  - `maxImagePixels = 25_000_000`. It bounds decode memory.
- Error messages name the limit:
  - `data is %d KiB; the limit is 3071 KiB per image`
  - `image is %dx%d; each side must be 1-16384 pixels and the area at most 25 megapixels`

### 3. Path source

- `filepath.IsAbs` is required. A relative path is refused with `data.path must be an absolute path`. The dbmcp server's cwd is the app's, not the agent's.
- `~` is not expanded. A leading `~` fails the IsAbs check.
- Symlinks are followed. macOS `/tmp` and `/var` are symlinks to `/private/...`, and agents write screenshots there. The opened file's `Fstat` decides, never `Lstat` of the name.
- Open with `os.OpenFile(p, os.O_RDONLY|syscall.O_NONBLOCK, 0)` so a FIFO or device cannot block the save.
- Then `f.Stat()`:
  - Refuse unless `Mode().IsRegular()`.
  - Refuse `Size() > maxImageBytes` before reading. A sparse 4 GiB file costs nothing.
- Read with `io.ReadAll(io.LimitReader(f, maxImageBytes+1))`, then recheck the length. The file may grow between stat and read.
- Not-found, permission, directory, FIFO and device errors all give one message: `data.path is not a readable regular file`.
  - The path is never echoed in the error or logged. A secret path name never reaches logs, and an agent cannot probe existence beyond what it can already do in its own shell.
- Sandbox interaction:
  - dbmcp runs inside the Kira Space app process on loopback HTTP, with the user's privileges. The agent's Seatbelt sandbox (macOS, `internal/harness/claude`) wraps only the agent process.
  - So the app can read a path the sandboxed agent itself could not.
  - Accepted, because:
    - (a) nothing returns image bytes to the agent: `proof_list` gives StepBrief only, and no tool reads payloads;
    - (b) only a file that fully decodes as a JPEG within the caps is stored;
    - (c) the stored bytes reach only the user, in the proof window.
  - Declined: restricting paths to `SessionIdentity.Cwd`. External MCP clients have no identity. Agents save screenshots under `/tmp` and tool output dirs outside the worktree. And (a) already removes the exfiltration channel.
  - Record this reasoning in ARCHITECTURE (see Docs).
- The repo builds for macOS and Linux only (no Windows target), so `syscall.O_NONBLOCK` compiles everywhere it needs to.

### 4. Caps

- Per step: the 4 MiB `maxPayloadBytes` is unchanged. An image step fits by the 3071 KiB file cap.
- Per session: `repos.ProofMaxSessionBytes` (32 MiB) is unchanged. It sums the stored `payload_bytes`, which is about 4/3 of the file size, so about 7 max-size images or many small ones fit. A path source counts the same as inline because the bytes are copied.
- HTTP body: `maxRequestBytes` (8 MiB, `apps/kira-space/internal/dbmcp/http.go`) is unchanged.
  - Inline base64 counts toward it. A path does not; its JSON is a few bytes.
  - So two max-size inline images in one call exceed 8 MiB, and paths are the way to send many.
  - Update only the comment above the const to say the request carries base64 images and that paths bypass the body cap.
- Steps: `ProofMaxSteps = 100`, unchanged.
- The tool text states all of this (see llmprompts).

### 5. Validate once, read the file once

Today `Service.Save` validates every step in a pre-check loop, then `AddStep` validates again. With a path source that reads and decodes the file twice. Worse, the file could change in between, so the stored bytes would differ from the bytes that were checked.

Refactor `apps/kira-space/internal/proof/service.go`:

- `Save` validates every step once into `[]checked` (plus each step's keep flag and the original `StepInput` for its ordinal fields). It refuses before any write, as today.
- Then it calls a new private `s.addChecked(draftID string, in StepInput, c checked, keep bool) error`, which holds the current body of `AddStep` after validation.
- `AddStep(in StepInput)` becomes `validate` plus `addChecked`. Its public signature is kept for `internal/flows/adeflow/proofchain_test.go:64`.
- No behaviour change beyond the single validation.

  4. `INSERT INTO proof_view_state_new SELECT <explicit column list> FROM proof_view_state;`
  5. `DROP TABLE proof_view_state;`

### 9. Screenshots: JPEG, quality, clipboard

- `apps/kira-space/frontend/src/studio/proof/screenshot.ts`:
  - Add `const JPEG_QUALITY = 0.92` and `canvasToJpeg(canvas): Promise<Blob>` using `toBlob(cb, 'image/jpeg', JPEG_QUALITY)`. 0.92 is the browser default for `image/jpeg`. It keeps UI text and table grid lines free of visible ringing at roughly a fifth of PNG size for screenshots with photos or charts. Lower values blur 11-12 px text.
  - JPEG has no alpha, so `captureElement` passes an opaque `backgroundColor`. Walk from the captured element up through its ancestors and take the first computed `background-color` with alpha above 0, falling back to the `--bg` token, so transparent areas never turn black.
  - `shotFileName` returns `NN-slug.jpg`.
  - `canvasToPng` stays, for copy only.
- `useProofScreenshot.ts`:
  - `saveActive` uses `canvasToJpeg` and `control.proofSaveJpeg(`${name}.jpg`, b64)`.
  - `saveAll` uses `canvasToJpeg` and `control.proofSaveJpegTo(folder.id, name, b64)`.
  - `copy` keeps `copyImageOrReportErrorLazy(shoot().then(canvasToPng))`.
- Clipboard decision: copy stays PNG. The spec allows this ("PNG may stay there if JPEG copy is unsupported").
  - The Async Clipboard API writes only `image/png` in WebKit (WKWebView, the app's webview on macOS, and the Playwright `ui` project's engine) and in Chromium. `ClipboardItem.supports('image/jpeg')` returns false in both.
  - The Wails v3 clipboard is text only.
  - A native JPEG clipboard would need a new Go/Cocoa path that pastes nowhere better: pasting apps re-encode anyway.
  - Implementer verifies once in the Playwright webkit project with a throwaway `page.evaluate(() => ClipboardItem.supports?.('image/jpeg'))`, not committed. The result goes in the commit message body of the JPEG commit. If it returns true there, still keep PNG: macOS WKWebView behaviour is the deciding target, and the spec permits PNG.
