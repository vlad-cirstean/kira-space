# P570 Agents choose the base of a requested branch

Stream B of `plans/batch-P569-P570.md`. Base commit: `d223aa2fd`. Own worktree.

## Ask

`request_branches` entries are `{repo, branch}` today. The base of a new branch comes only from the
row (user `SetBranchBase` / Change base, or the CreateTask base), else the repo's main. Give each
entry an optional base, validated through the existing `resolveChoice` path before any prompt, shown
in the approval dialog, applied to the worktree start point and echoed in the result.

## Decisions

### D1 Field: `base`, a branch name, optional

`BranchSpec` gains `Base string \`json:"base,omitempty"\``. One string, not a `BaseChoice` object:

- It maps to `adewire.BaseChoice{Ref: base}` and goes through `resolveChoice` unchanged. Naming a
  live planner branch (any task, same repo) already resolves to the stacked form (`BaseBranchID`
  set) through `sc.byName`, so the agent never needs a branch id.
- A `BranchID` form would only add the draft-parent case, and a draft parent is refused anyway
  ("parent not created yet"). Agents see branch names in `task_info`, never row ids.
- Omitted, `""` or the repo's main name: the repo's main (or the draft row's own base, D4).
- Short name only (`feat/api`, not `origin/feat/api`); remote-first resolution is automatic.

Arg text (new `arg` entry, field `branches.base`):
`Existing branch to start from, such as main or feat/api: short name, origin checked first. A branch of a task stacks on it. Omit for main.`

Tool default text stays as is (no default rewrite).

### D2 Validation before any prompt, per branch

In `planItem`, for the not-yet-created path, after the existing name checks and `branchExists`,
when `base != ""`:

1. Syntax: reuse the guards of `checkNewBranchName`. Split its first part into
   `branchNameRefusal(ctx, rec, name) (string, error)` (empty, spaces, length, `-`, `@{`, `HEAD`,
   `CheckBranchName`); `checkNewBranchName` keeps calling it, then `reservedBranchText`. The base
   calls only `branchNameRefusal` (main and integration branches are valid bases).
2. `sc := baseCtxFor(ctx, entry, codeRepoID)`; `t, err := resolveChoice(sc, self, nick,
   BaseChoice{Ref: base})` with `self` = the repo's draft row when one exists (cycle check against
   rows stacked on the draft), else `nil` (a row not stored yet has no children).
3. `ErrInvalidInput` from step 2: failed slot, text `Cannot use base <base>: <reason>.` via
   `toolMessage(err)`. A not-found reason gets the hint: `Give an existing branch; a branch asked for
   in this same call must be created first.` Any other error fails the call (git or DB fault), as
   today.
4. `t.reason == baseParentDraft`: failed slot, `Cannot use base <base>: it is not created yet.`
   (unreachable by name today; kept so the rule holds if `resolveChoice` changes).
5. Copy `t.base`, `t.baseBranchID` onto the row passed to the existing `newBranchBase` call, which
   then yields the display and the `baseMissing` refusal exactly as for a user base.

A failed slot raises no prompt; a call whose slots all fail answers at once (existing behavior).
Same-call stacking (child naming a parent asked in the same call) is refused by step 3 with the hint;
the agent asks for the parent first.

### D3 Storage on the row

The resolved choice travels on `requestSlot` (`base`, `baseBranchID`, plus `baseAsked` = raw text).
`createApproved` re-resolves under the task lock, since parent or ref may change during the wait:
`baseCtxFor` + `resolveChoice` again; an error or `baseParentDraft` fails that branch with the D2
text.

- Draft row path: `Tasks.SetBranchBase(draft.ID, t.base, t.baseBranchID, "")`, then set the same
  fields on the local `draft` struct before `createFor`, because `ensureWorktree` reads the struct.
- New row path: `AddBranch` with `Base` and `BaseBranchID` set in the struct; `insertTaskBranch`
  writes them in the insert.
- `BasePendingFrom` stays `""` in both paths: pending marks a stored base not yet reached by a
  verified rebase of a created branch. A fresh branch starts on its base, so nothing is pending.
- No base asked: no write, behavior unchanged.
- A failed `ensureWorktree` leaves the approved base on the row (the user approved it); the row is a
  draft again and Start uses that base.

`ensureWorktree`, `startPoint`, `newBranchBase` need no change: they read the stored base, resolve
remote-first and pass `StartPoint` to `worktreeAdd newBranch`.

### D4 Draft row with a user-set base

The repo's draft row may carry a base the user set (CreateTask bases, `SetBranchBase`). Rule:

- Agent gives no base: draft's base applies (unchanged).
- Draft base empty (main) or equal to the agent's resolved choice: agent's base applies.
- Draft base set and different: failed slot, `The task's <repo> branch starts from <draft base>,
  set by the user. Omit base, or use <draft base>.`

Reason: a user choice is never overwritten by an agent; the agent learns why. Same rule in
`createApproved` when the user changed the draft's base during the wait.

Compare by stored pair (`base`, `baseBranchID`), since `resolveChoice` stores main as `""`.

### D5 Existing branch with a different base: report, not refuse

A named row (branch exists in git, with or without worktree) keeps its base; git owns it. When
`base` is given and its name (main normalized to the main name via `sc.mainName`) differs from the
row's resolved base name (`sc.resolveBase(row).name`), the slot keeps its outcome (`existing`, or the
`worktree` item and later `created`/`existing`) and `Next` gets the prefix:
`This branch exists and keeps its base <current>; base <asked> was not applied. Ask the user to change it if needed. `

Reason: refusing would deny the agent its own worktree after a user Change base, and a retry with the
same args after a crash must stay idempotent. The base is not validated beyond syntax on this path
(it is not used). Concurrent calls for one branch with different bases end the same way: the first
create wins, the second reports.

### D6 Dedup

`cleanBranches` trims `Base` too; exact duplicates (repo, branch, base) collapse there.
`planBranchRequest` keys on resolved repo id plus branch (P517) and records the first entry's trimmed
base. A later entry with the same key and a different base string fails the whole call before any
prompt: ToolError `Branch <branch> of <repo> is asked twice with different bases.` Same base string:
skipped as today. `""` against the main name counts as different; the call is contradictory text
either way and the agent fixes it.

### D7 Approval dialog

No component or catalog change. The item's `Base` is the display from `newBranchBase` (D2 step 5),
so `BranchRequestBody.vue` shows `Create feat/x from feat/api`, or the main-branch label. A stacked
parent shows its branch name. Kind `worktree` items (branch exists) show no base: git fixed it (D5).
Frontend rules hold trivially: no new UI surface.

### D8 Result output

`agentmcp.BranchInfo` gains `Base string \`json:"base,omitempty"\``: the branch's base name, absent
for main.

- `branchInfo(sb, ...)` sets `Base: sb.Base` (stacked rows store the parent's name). This also fills
  `task_info` with `repo`/`branch` (`BranchStatus`), keeping one constructor.
- `noBranchInfo(nick, branch, base, next)` takes the base: the item's display for denied, timeout
  and post-approval failures (`outcomeBranch`), the asked text for plan-time failures.

### D9 Folder-run sandbox

No change. The worktree lands in `<home>/kira-space-wts/<repo>/wt_<id>` whatever its base;
`requestedWorktreeDirs` already pre-creates the folder per repo. `worktreeAdd` runs in Kira outside
the sandbox and reads the base from the main repo's refs.

## Out of scope

- A base for `rename_branch`, `declare_repos` or a branch that exists (Change base stays the user's,
  through Rebase).
- Same-call stacking (parent and child asked together); refused with a hint (D2).
- Tags, commit SHAs or `origin/`-prefixed refs as a base; `resolveChoice` takes branch names only.
- Any change to the dialog's layout, the board base marker or the CreateTask base picker.
