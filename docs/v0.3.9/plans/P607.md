## Evidence (run here, 2026-11-11, ClickHouse `26.3.58` unless noted)

1. Reproduced. `KIRA_TEST_MATRIX=1 go test ./internal/adapters/clickhouse/ -count=1 -timeout 3m -run
   'TestClickHouse_AuthMatrix/kira_ro1.*/statement_timeout'` panics at the 3m bound, stack at
   `authmatrix_test.go:200` (slow `Execute`). Same failure as release CI.
2. Query is really slow, not cheap. `SELECT sum(cityHash64(number)) FROM numbers(1e9)` takes 0.81s on
   4 cores here, so `numbers(1e12)` takes about 810s; CI's 976s is the query finishing. `Execute`
   returned nil because the query completed and returned its one row.
3. Nothing in the adapter times a `readonly=1` statement. Connect sets `noEngineTimeout`
   (`adapter.go:89-94`), `engineTimeoutSettings` then returns nil (`console.go:180-186`), and
   `withEngineTimeout` (`console.go:201-211`) runs the request with no limit. Same for `Read`
   (`adapter.go:309-321`). The only timer is the host backstop (`adapterhost/host.go:302-314`,
   armed by `data.go:218-221`, `browse.go:60-63`); the matrix test calls `a.Execute` directly, so no
   timer exists. The log line "app timer enforces limits" (`adapter.go:92`) promises an adapter
   behaviour that is missing. Spec context "works on `Read`" is wrong: no test ran a slow `Read` on
   `readonly=1`.
4. Server side, `readonly=1` user over HTTP (curl): client disconnect after 2s leaves the query in
   `system.processes` (elapsed 5.1s, still running); `max_execution_time=1` URL setting is refused
   with code 164; `KILL QUERY WHERE query_id = ... SYNC` sent by the same `readonly=1` user works and
   clears the row. So the app timer must be ctx deadline plus `KILL QUERY`.
5. Prototype (reverted, not committed): ctx deadline at `timeout` plus `KILL QUERY ... SYNC` by query id
   in the row-returning path made the failing subtest pass in 1.19s.
6. Row-cap kill (v0.3.8 R3) never worked for a late-emitting read, on any profile. No test covered it
   on `readonly=1`. Probe: `readonly=1` adapter, `Execute` of `SELECT number FROM numbers(10) UNION ALL
   SELECT sum(cityHash64(number)) FROM numbers(1000000000000)` with `Cap{Rows: 5}` hung past a 2m
   bound, stuck in `persistConn.roundTrip` (no response headers). Root cause: this server has
   `enable_http_compression = 1`, Go's `http.Transport` sends `Accept-Encoding: gzip` by default, and
   the server then buffers the compressed body: curl with `Accept-Encoding: gzip` gets no first byte in
   4s for that query (both `readonly=1` and `default` users), curl without it gets rows in 13ms. With
   `DisableCompression: true` on the transport (prototype, reverted) the same probe returned in 12ms,
   5 rows, `Truncated`, and `waitForProcessesClean` saw the query gone from `system.processes`.
   Without a kill a curl reader that stopped after 6 rows left the query running 94s later.
7. A user with `SELECT ON system.*` (kira) sees another user's row in `system.processes`
   (measured), so a `kira` side adapter can assert server-side cleanup of a `kira_ro1` query.
8. Rest of the ClickHouse suite passes. `KIRA_TEST_MATRIX=1 go test ./internal/adapters/clickhouse/
   -count=1 -timeout 9m -skip 'TestClickHouse_AuthMatrix/kira_ro1.*/statement_timeout' -v`: ok, 171
   PASS, 0 SKIP, on 26.3.58 (44.8s), db-compat min 25.3.14 (30.0s) and max 26.8.33 (68.3s). R4
   (`toString` catalog SQL: every Connect probe, `Describe`/`Read`/`Count` in `UInt64 max decodes
   exactly`) and R5 (UInt64 max read-back) ran and passed in all three. `read lane: cancel ends the
   query` on `readonly=1` passed.
9. `scripts/test-matrix.sh` is mode `100644` in git (`db-compat.sh` is `100755`); `release.yml:169`
   runs it with `sh`, so run it as `sh scripts/test-matrix.sh`. Not a defect.
10. Other kinds: blocked by a full shared disk, see "Other matrix kinds".

Verdict: product bug (no adapter app timer on `readonly=1`, row-cap kill unreachable through gzip
buffering) plus test bug (scenarios unbounded, so a regression costs 16 min instead of seconds).

## Changes

### C1 Adapter app timer (`internal/adapters/clickhouse/console.go`, `adapter.go`)

- Replace `withEngineTimeout` (`console.go:198-211`) with `withStatementTimeout`:

  ```go
  func withStatementTimeout[T any](ctx context.Context, h *Handle, timeout time.Duration,
  	nextQueryID func() string, log func(level, msg string),
  	run func(ctx context.Context, queryID string, extra map[string]string) (T, error)) (T, error)
  ```

  1. `timeout <= 0`: `return run(ctx, nextQueryID(), nil)`.
  2. `extra := engineTimeoutSettings(h, timeout)` non-nil: run with it. Not refused
     (`err == nil || !settingsRefused(err)`): return, mapping code 159 to
     `adapters.StatementTimeout(timeout, 0, err)` when `ctx.Err() == nil` (the mapping now in the
     `execute` defer, `console.go:215-220`, and `Read`, `adapter.go:315-318`; delete both copies).
     Refused: keep the `noEngineTimeout.CompareAndSwap` plus warn log, fall through.
  3. App timer: `tctx, cancel := context.WithTimeout(ctx, timeout)`, fresh `queryID := nextQueryID()`,
     `v, err := run(tctx, queryID, nil)`. If `err != nil && ctx.Err() == nil &&
     errors.Is(tctx.Err(), context.DeadlineExceeded)`: kill `queryID` (below) and return
     `adapters.StatementTimeout(timeout, 0, errAppTimer)`. Else return `v, err`.
  - `var errAppTimer = errors.New("app timer: statement stopped at its limit")`; test `WantCode`
    matches `"app timer"`.
  - Doc comment: one or two lines on why (readonly=1 refuses settings and cannot cancel on client
    close; `RunWithAbortRace` leaves the request running, so only `KILL QUERY` stops it).
- `killQueryBestEffort` (`console.go:147-157`): send `KILL QUERY WHERE query_id = {qid:String} SYNC`
  (add `SYNC`), keep the 5s bound. Both callers (row cap, app timer) then return only after the server
  stopped the query or 5s passed. Update its comment.
- `execute` (`console.go:214-253`): both branches call `withStatementTimeout(ctx, h, timeout,
  nextQueryID, log, func(ctx context.Context, queryID string, extra map[string]string) ...)`, passing
  `queryID` into `runRowReturning` / `RunCommand` instead of calling `nextQueryID()` inside.
- `Read` (`adapter.go:309-321`): same helper, `func() string { return seq.next(a) }`, `queryID` into
  `readPage`. Remove the post-call mapping block.
- `client.go:37-39` `noEngineTimeout` comment: the adapter's app timer enforces the limit (not "the
  host backstop alone"). `adapter.go:92` log text stays true after C1.
- Host and dbmcp stay as they are: `timeoutEnforcementOf` reports `session` for clickhouse, host grace
  stays 2s, adapter now stops at the limit itself.

### C2 Stream rows uncompressed (`internal/adapters/clickhouse/client.go:192-196`)

- Add `DisableCompression: true` to the `http.Transport`, with a one-line comment: the server
  buffers a gzip body, so a sparse or late-emitting read sends nothing and the row cap never fires.
- Trade-off accepted: responses are bounded by the console cap and page size, so uncompressed bytes
  stay bounded. No setting alternative: `enable_http_compression` cannot travel on `readonly=1`.
