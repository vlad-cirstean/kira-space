## Findings

- `scripts/test-matrix.sh --only <kind>` exists but takes one kind only, and does not filter pulls:
  it always pulls `go run .../testsupport/cmd/testimages` output, which is every pinned image
  (`testsupport.Images()`: postgres, mysql, mariadb, clickhouse, redis, mongo, kafka, localstack,
  elasticsearch, kibana; about 7.5 GB). Elasticsearch and kibana are used by no adapter package in
  the matrix. Script fix needed.
- `testimages` has no per-kind selection; `Images()` (one caller: `testimages`) returns a flat list.
- Per-package `go test -timeout 30m` equals the 30-min job timeout, so a hang is killed by the runner
  with no Go stack dump naming the test.
- Images each matrix package starts (fixture calls in its `*_test.go`; `StartPausableProxy*` is an
  in-process `net.Listen`, no container; `StartSqlite` starts none):
  postgres: postgres. mysqlfamily: mysql, mariadb. clickhouse: clickhouse. mongo: mongo.
  redis: redis. kafka: kafka (`StartKafka`, `StartKafkaSasl` both use `ImageFor("kafka", ...)`).
  sqs, s3: localstack. sqlite: none.
- `release.yml` `publish` has `needs: [tag, build, test-matrix, db-compat]`. `needs` keys on job id,
  so the aggregate job keeps id `test-matrix` and name `test-matrix (Linux)`; the matrix job takes a
  new id.
- Release `test-matrix` leaves Ryuk on (pulls `testcontainers/ryuk` from Docker Hub); `pr.yml`
  `go-containers` sets `TESTCONTAINERS_RYUK_DISABLED: "true"`. Runners are discarded, so the reaper
  buys nothing. Disable it in the group jobs too (also required locally: Hub blobs are blocked here,
  `docs/DEV_ENVIRONMENT.md` "Docker").
- Healthy sequential sum from v0.3.8 durations: about 2.5 min of tests plus ClickHouse plus 1.5 min
  pulls plus setup, under `build (macOS)`'s ~9 min. So a healthy release's critical path stays
  build-bound; the split's gain is failure behavior: a hang fails its own group at 8 min with a stack
  dump, other groups still report, and a rerun repeats one group, not nine packages.

## pr.yml assessment (from workflow definitions; no CI logs)

No split. `go-containers (Linux)` is the only container job. It runs one `go test` over all
container packages (`scripts/go-test-split.sh containers`), so packages run in parallel (`-p` =
GOMAXPROCS), not sequentially as in `test-matrix.sh`. No `-timeout`, so Go's default 10 min per test
binary fires before the 15-min job cap and names the hung test. `KIRA_TEST_MATRIX` is unset, so the
authmatrix scenarios (where v0.3.8's hang lived) skip. Images come from the cache tar. Other jobs:
`ui` already 8 shards; `checks`, `go`, `ui-extra`, `visual` start no container per package loop.

## Other release jobs

- `build (macOS)` (~9 min, 30-min cap): one sequential pipeline producing one artifact
  (package, verify, assert, hash, upload); each step needs the previous one's output. A second macOS
  runner adds setup (bun, wails3, bindings) and doubles macOS billing with nothing to parallelize.
  No split.
- `db-compat (Linux, min|max)` (~5 min each): already split. It keeps per-package `-timeout 30m` and
  a 30-min job cap, but runs without `KIRA_TEST_MATRIX`. Out of scope here; orchestrator decides
  whether to add a follow-up phase for its timeouts.
- `install smoke (macOS)` (15-min cap) and `publish` (10): short, sequential. No split.

Design notes:

- `rest` uses `--except`, so a kind added to `MATRIX` later runs there with no workflow edit (same
  "never a coverage filter" rule as `go-test-split.sh`). Spec's "small kinds" group is this `rest`.
- Aggregate `if: ${{ !cancelled() }}`: it runs after a failed or timed-out group and fails on any
  result but `success`. If it is skipped, `publish` is skipped too. Either way no release ships on a
  red group. "Re-run failed jobs" reruns the failed group and its dependent aggregate.
- Job cap 12 min: setup (Go restore, apt GTK) about 2-3 min, pulls up to 1.5, compile about 1, tests
  capped at 8 per package. In `rest` (six packages) a hang plus the healthy rest can pass 12; the
  8-min panic still prints the hung test before the runner stops the job.
