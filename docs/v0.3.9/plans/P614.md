## 2. Design (flat, no gating; reasoning in section 3)

### pr.yml new jobs

Three new job ids, appended after `go-containers`, each with no `needs` except the aggregate:

- `test-matrix-group`: name `test-matrix (Linux, <group>)`, four groups exactly as release, 12 min.
- `test-matrix`: name `test-matrix (Linux)`, aggregate, the one stable required name for the matrix.
- `db-compat`: name `db-compat (Linux, min|max)`, 12 min. Names are fixed by the two-value matrix,
  so no aggregate; both names become required.

Checkout uses the default ref (PR merge commit). Setup restores only (`cache-save: "false"`): six
jobs saving the same per-sha `go-ct` key as `go-containers` would only race for one reservation.
Ryuk off in all six (`TESTCONTAINERS_RYUK_DISABLED: "true"`; db-compat gains it, release lacked it).

### Image cache

Decision: one cache entry per matrix group, keyed on the group's exact image list (not on
`hashFiles(testsupport/*.go)`, which busts on any testsupport code edit). Restore-only in PR jobs;
saved in `main` scope by a new `cache-warm.yml` job on a miss, the go-containers pattern. db-compat:
no cache.

Sizes (uncompressed `docker images` here; mongo, kafka, localstack not on disk, estimated):
postgres 0.42 GB; mysql 1.12 + mariadb 0.46; clickhouse 1.19; rest: mongo about 0.8, redis 0.21,
kafka about 1.0, localstack about 1.2. Matrix total about 6.4 GB. db-compat min plus max about 12 GB
(mysql 8.0.46 1.10, clickhouse 25.3.14 0.92 and 26.8.33 1.20 measured, rest estimated). Existing
go-containers tar about 11.7 GB (adds elasticsearch 2.54, kibana 2.74). The user's "about 14 GB" is
in this range; exact compressed sizes are known only after `cache-warm` logs `du -h`.

Budget (10 GB per repo, least-recently-used eviction above it; `actions/cache` zstd on an
uncompressed `docker save` tar, assume 35 to 45 percent): matrix four entries about 2.5 to 3 GB,
go-containers entry about 4.5 to 5 GB, Go build/bun/Playwright/wails entries about 2 GB. Total about
9 to 10 GB: fits, at the line. db-compat would add about 5 GB, pushing past 10 GB so every merge
evicts something PRs restore. So db-compat pulls through the mirror (measured 3m23s to 3m45s per
extreme including pulls, inside 12 min).

Miss: the group pulls its own images through `mirror.gcr.io` (`--mirror`), exactly today's release
path. A miss is never a failure. Misses happen on the PR that changes a pinned tag (until its merge
warms `main`) and after an eviction.

Honest value: per measurements, cache restore plus load is about time-neutral against a mirror pull.
What it buys is independence from `mirror.gcr.io` availability and rate limits on shared runner IPs,
which is why `go-containers` caches too. Kept because the spec asks for it.

Key computation needs the image list from the one source (`testsupport` via `testimages`), filtered
per group by `test-matrix.sh`'s third MATRIX field. New script flags (real commits):

- `--print-images`: print the selected kinds' images, one per line, to stdout, nothing else on
  stdout, exit 0 (empty output for a selection with no images, e.g. `--only sqlite`).
- `--pull-only`: pull the selected images (honours `--mirror`) and exit 0 without running tests.
  `--pull-only` with `--no-pull`, or `--print-images` with either, exits 2.

```yaml

  # Complete auth/config permutation matrix (P25/P26) on every PR (P614), one job per weight group
  # (P608). `rest` is every kind the three heavy groups do not name, so a new adapter lands there
  # without a workflow edit. test-matrix.sh sets KIRA_TEST_MATRIX itself.
  test-matrix-group:
    name: test-matrix (Linux, ${{ matrix.group }})
    runs-on: ubuntu-24.04
    timeout-minutes: 12
    strategy:
      fail-fast: false
      matrix:
        include:
          - group: postgres
            args: --only postgres
          - group: mysqlfamily
            args: --only mysqlfamily
          - group: clickhouse
            args: --only clickhouse
          - group: rest
            args: --except postgres,mysqlfamily,clickhouse
    steps:
      - uses: actions/checkout@v7
      - uses: ./.github/actions/setup
        timeout-minutes: 10
        with:
          bun: "false"
          bindings: "false"
          go-cache: go-ct
          gtk: "true"
          cache-save: "false"
      - name: Resolve this group's images (the cache key is their exact pinned tags)
        id: images
        run: |
          set -eu
          LIST="$(sh scripts/test-matrix.sh ${{ matrix.args }} --print-images)"
          printf '%s\n' "$LIST"
          echo "key=matrix-images-${{ runner.os }}-${{ matrix.group }}-$(printf '%s\n' "$LIST" | sha256sum | cut -c1-16)" >> "$GITHUB_OUTPUT"
      - name: Restore this group's images (saved in main's scope by cache-warm.yml)
        id: image-cache
        uses: actions/cache/restore@v6
        with:
          path: ~/matrix-images.tar
          key: ${{ steps.images.outputs.key }}
      - name: Load the cached images
        if: steps.image-cache.outputs.cache-hit == 'true'
        run: docker load -i ~/matrix-images.tar
      - name: Complete matrix for this group (a cache miss pulls through mirror.gcr.io)
        env:
          # The runner is discarded: no reaper, no Docker Hub pull for it.
          TESTCONTAINERS_RYUK_DISABLED: "true"
          PULL: ${{ steps.image-cache.outputs.cache-hit == 'true' && '--no-pull' || '--mirror' }}
        run: sh scripts/test-matrix.sh ${{ matrix.args }} $PULL

  # One stable required-check name over the groups. Fails unless every group passed.
  test-matrix:
    name: test-matrix (Linux)
    needs: test-matrix-group
    if: ${{ !cancelled() }}
    runs-on: ubuntu-24.04
    timeout-minutes: 5
    steps:
      - env:
          RESULT: ${{ needs.test-matrix-group.result }}
        run: |
          echo "test-matrix groups: $RESULT"
          test "$RESULT" = success

  # Conformance against each kind's oldest and newest supported server (P16) on every PR (P614).
  # No image cache: the compat images (about 12 GB) would push the repo past its 10 GB cache limit.
  db-compat:
    name: db-compat (Linux, ${{ matrix.extreme }})
    runs-on: ubuntu-24.04
    timeout-minutes: 12
    strategy:
      fail-fast: false
      matrix:
        extreme: [min, max]
    steps:
      - uses: actions/checkout@v7
      - uses: ./.github/actions/setup
        timeout-minutes: 10
        with:
          bun: "false"
          bindings: "false"
          go-cache: go-ct
          gtk: "true"
          cache-save: "false"
      - env:
          TESTCONTAINERS_RYUK_DISABLED: "true"
        run: sh scripts/db-compat.sh --${{ matrix.extreme }} --mirror
```

`!cancelled()` on the aggregate: it runs when a group fails or times out (a timed-out job concludes
`cancelled`, so `RESULT` is not `success` and the aggregate fails). It is skipped only when the whole
run is cancelled (superseded push), whose checks belong to a sha that is no longer the PR head.

### Pattern

Cheap jobs considered for layer 1: `checks (Linux)`, `checks (macOS)`, `go (Linux)`. Heavy: the rest
plus the new matrix and db-compat jobs. Two candidate splits:

- Split A, layer 1 = both checks plus `go (Linux)`.
- Split B, layer 1 = both checks only.

Attempt-1 failure classes (what a gate decides on), runs 47-109:

- Split A: layer-1-only 11, layer-2-only 16, both 9.
- Split B: layer-1-only 3, layer-2-only 28, both 5.
- Runs 74-109 under split B: layer-1-only 0, layer-2-only 18, both 2.

Per run/sha outcome (a sha that never went green, versus green after a flake rerun), runs 47-109:

- Split A: red layer-1-only 6, red both 9, red layer-2-only 11; green after a layer-1 flake 5
  (all `go (Linux)`), after a layer-2 flake 5.
- Split B: red layer-1-only 3, red both 5, red layer-2-only 18; green after a layer-2 flake 10.

Hidden-failure check (a "both" sha whose next push on the branch failed a hidden layer-2 job again):

- Split A: 6 of 9 (runs 47, 48, 49 on v0.2.12; 89, 90 on v0.3.0; 106 on v0.3.7).
- Split B: 3 of 5 (runs 47 on v0.2.12; 89, 90 on v0.3.0).

Findings:

1. Most failures are heavy-only. Under split B, 28 of 36 red first attempts failed only in layer-2
   jobs; a gate never saves anything there and delays every one of them by layer 1's time.
2. A cheap-job failure alone is rare: 3 of 63 shas under split B, 0 of 36 in today's job shape. When
   `checks` fails, a heavy job usually fails too (5 of 8 shas), and in 3 of those 5 the heavy failure
   recurred on the next push, so a gate would have hidden a real failure.
3. `go (Linux)` is the most frequent failing job and the most flaky cheap one (5 shas green after a
   rerun). As a gate, its flake skips all of layer 2, and `gh run rerun --failed` (pr-rerun-flaky)
   reruns failed jobs with their dependents, so the rerun then runs layer 2 serially behind `go`:
   about 6.5 + 10.9 min instead of 6.5 min today. Split A makes flakes cost more, not less.
4. Push rounds under the CLAUDE.md rule (collect every failure of a run, fix, push once): flat CI shows
   every failure per run, so no added rounds. Gating adds about one round per "both" sha with a
   recurring hidden failure: 3 in 27 chapters (split B), 6 (split A). Each round is about 11 to 18 min
   of CI plus fix time.
5. Superseded pushes are common (runs 89, 90, 93, 97, 99 cancelled within minutes): CI reruns from
   scratch either way; gating changes nothing there.

### Cost of each option per PR

- Flat (today plus P614 jobs): green wall-clock median about 11 min (new jobs end by about 6 min).
  Runner time about 95 + 31 = 126 Linux min plus about 5.6 macOS. Peak 20 concurrent jobs at t0
  (GitHub Free cap: 20, macOS 5; above it jobs queue, never fail).
- Split B gate: green wall-clock about 5.6 (checks macOS median; p90 7.8) + 10.9 = about 16.5 min,
  p90 about 19. Saves about 110 Linux runner-min on a layer-1-only red attempt: 3 times in 63 shas.
  Delays 28 of 36 red first attempts by about 5.6 min. Adds about 3 push rounds per 27 chapters.
- Split A gate: green wall-clock about 6.5 to 8 + 10.9 = about 17.5 to 19 min. Saves about 100
  runner-min on 11 of 36 red first attempts, of which 5 were `go` flakes that then rerun layer 2
  anyway. Adds about 6 push rounds per 27 chapters.
- Minutes are free on this public repo (`docs/PACKAGING.md` §7), so runner-minute savings buy
  nothing billable; the costs are wall-clock and push rounds.

### Interactions any gate would have to respect

- Required checks: a job skipped because a `needs` failed reports "skipped", and a skipped required
  check counts as passing. Each gated group must sit behind an aggregate with `if: ${{ !cancelled() }}`
  asserting `result == 'success'` (as `test-matrix (Linux)` does), and db-compat would need its own
  aggregate. The 8 ui shard names, `ui-extra`, `visual`, `go`, `go-containers` would each need one
  too, or the ruleset list in `docs/PACKAGING.md` §7 changes to aggregate names.
- Auto-merge: fires when every required check passes; with aggregates it stays correct. Without
  them a skipped required job would let a red PR merge if the layer-1 job were ever dropped from
  the required list.
- `release.yml` `publish`: needs only `tag` and `build` after P614, independent of PR layering.
- `concurrency: pr-<ref>`, `cancel-in-progress: true`: a new push cancels both layers alike; a
  gate only shortens how much of a superseded run had started.
- ui and visual: today and in the recommended design they start at t0, independent of any layer.
  Under either gate they would move behind layer 1, which is where the wall-clock cost comes from.

### Recommendation

No gate: keep the flat design of section 2. The history does not fit a two-layer split: cheap-only
failures are 3 of 63 shas overall and 0 of 36 in today's job shape, while heavy-only failures are
the large majority and would all arrive about 5.6 min later. Cheap failures co-occur with real heavy
failures often enough (3 of 5) that a gate would add push rounds the standing CI rule exists to
avoid, and gating on `go (Linux)` turns its flakes into serial reruns of all of layer 2. The only
gain, about 110 runner-min on 3 PR attempts in 27 chapters, is free on this repo. ui, ui-extra and
visual stay layer-independent and start at t0, as today.

Revisit only on evidence the flat design lacks: if the 20-job concurrency cap queues runs in
practice, or once a few chapters show matrix/db-compat failing together with `checks`. Cheapest
fallback then: `needs: checks-linux` on `test-matrix-group` and `db-compat` only (ends at about
3.9 + 6 = 10 min median, under the ui critical path; p90 about 12 min, about 1 min over), plus a
`db-compat (Linux)` aggregate with the `test-matrix (Linux)` pattern, and the ruleset then requires
`db-compat (Linux)` instead of the two extreme names.
