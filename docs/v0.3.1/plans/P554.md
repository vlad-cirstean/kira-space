# P554 plan: GitOps for config files, shared config repos

Base: `chapter/v0.3.1` at `625a4c982`. Runs in batch with P551 (site) and P552 (schema), own worktree.

## Reading of current code

Discovery used `codegraph_explore`. Facts the design rests on:

- `<home>/config/<module>/` is the one layout (`internal/configfs/root.go`: `Root`, `ModuleDir`). Modules: `connections`, `api`, `runs`, `workflows`, `steps`, `repos`, `agent` (`context.md` via `internal/agentctx`, `settings.yaml` via `internal/agentcfg`), `prompts` (`llm-prompts.json`, `internal/llmprompts`, JSON, not a configfs module).
- Every module loads through `configfs.Folder` and its own fsnotify watch (`configfs.WatchDir`, 200 ms debounce). A write to the file is enough for a module to reload; no module needs a direct call. Hidden files and `AGENTS.md` are never read as config. `WatchDir` is not recursive and ignores entries whose parent is not the module dir.
- Files never hold a secret value: `x-kira-secret` schema fields must be exactly one `${secret:name}`; values live in DB `secret_values` or `agent-secrets.db`.
- `configfs.WriteAtomic` (renameio) writes one file atomically. Nothing writes several files atomically.
- P540 backup (`apps/kira-space/internal/configfold`): backup first to `<home>/backups/p540-<UTC ts>/`, `copyVerified` (copy to `.tmp`, `fsmove.VerifyTree`, rename), resumable marker. The marker lives in the DB `settings` table; P554 keeps its marker on disk instead (no DB).
- Git machinery: `gitclient.Run(ctx, runner, gitPath, Spec)` is the one spawn path (hygiene env incl. `GIT_TERMINAL_PROMPT=0`, `Setsid`). `wireGit` builds `oplog.NewRecordingRunner(gitclient.NewExecRunner(), opLog)` and `gitclient.Discovery`. `gitops.FetchRefspecsArgs`, `gitops.CoreAskPassArgs` build argv. `gitclient/catfile` reads blobs in batch. Credentials: `gitaskpass.Broker.WithOp(ctx, Prompter, fn)` plus `Broker.Env()`; prompts go to `gitcred.Relay.AskFrom(ctx, origin, source, req)` (window-routed). Auto-fetch (`gitsession/autofetch.go`) is credential-free by passing no askpass env, and stops on permanent failures.
- `gitsession.Registry`/`RepoEntry` assume a user repository (worktree, refs UI, undo slot). A config mirror needs none of that, so P554 calls `gitclient.Run` directly with the same runner, git path and broker.
- Windows: `HostViewService` opens an ephemeral native window: `Windows.Create(model.WindowRecord)` on the existing `WindowsRepo`, `OpenWindow`, `FocusWindow`, key prefix `hostview-`; `main.go` lists ephemeral prefixes in three predicates and `OnWindowClosing` forgets targets.
- Diff: `packages/workbench/src/editor/MonacoDiff.vue` (read-only two-text Monaco diff, debug attrs `data-kira-diff-original-text`/`-modified-text`), already reused by `AdePortExportDialog.vue` and `PromptDetail.vue`.
- Toast: no toast library in the app. The one toast is `packages/workbench/src/approvals/ApprovalsToast.vue` (`floatingSurface`, fixed top-right, `role="status"`).
- Settings: `apps/kira-space/frontend/src/workbench/SettingsDialog.vue` + `state/settings.ts` `sections`. Panes that own their data (not the DB settings draft) use their own TanStack Query, e.g. `CliToolsPane.vue`.
- App settings (`repositories.Settings.GetAll`) are a typed struct in `storage/model`. P552 owns `storage/**`, so P554 stores nothing there.
- Credential-shape rules exist only inside `internal/agentport/classify.go` (`nameIsSecret`, `valueIsSecret`, unexported).

## Decisions

### Scope and package

- New package `apps/kira-space/internal/configsync`. Pull only: Kira never commits or pushes to the shared repo. Publishing stays the user's job in their own git client.
- One shared repo per Space. Multiple repos declined: two shared layers need shared-vs-shared precedence and per-entry ownership across repos, a second design this phase does not need. Not half-built: the settings schema has one `repo` mapping, no list.

### Repo layout and manifest

- Shared repo root mirrors `<home>/config`: `<module>/<file>`, same file names and formats as local.
- Manifest `kira-config.yaml` at repo root, required:

  ```yaml
  version: 1
  modules: [agent, connections, api, runs, workflows, steps, prompts]
  ```

  Only listed modules are read. Missing manifest, unknown `version`, or unknown module name is a fetch problem shown in Settings; nothing is offered.
- Syncable modules: `connections`, `api`, `runs`, `workflows`, `steps`, `agent`, `prompts`.
- `repos` is never syncable: files are keyed by local absolute path, and they carry the worktree prepare script, which `model.GitRepoSettings` says must never come from a repo-carried source. A manifest listing `repos` is a problem naming that rule.
- Ignored in the shared tree: hidden files, `AGENTS.md`, `*.local.yaml` (per-machine, ARCHITECTURE says out of sync and git), anything outside listed module dirs, subdirectories inside a module dir.
- Caps: file 1 MiB (`configfs.MaxFileBytes`), 5000 tree entries. Over cap is a fetch problem.

### Local sync state: files under `<home>/config/.sync/`

No DB table. `.sync` is hidden, so no module reads it and no module watch fires on it.

- `.sync/sync.yaml`: user settings, written only by the service through `configfs.WriteAtomic`, decoded by `configfs.YAMLSchema` over `configsync/sync.schema.json`:

  ```yaml
  repo:
    url: https://github.com/acme/kira-config.git
    branch: main
  fetch_minutes: 30
  modules:
    agent: combined
    connections: shared
  deactivated:
    agent: ["settings.yaml#mcp_servers/github", "context.md"]
    connections: ["staging.yaml"]
  ```

- `.sync/state.json`: runtime state, app-written JSON (same class as `agent-usage.json`): `fetched` (sha), `applied` (sha), `fetchedAt`, `appliedAt`, `problem` (`kind`, `message`), `dismissed` (sha the toast was dismissed for).
- `.sync/base/<module>/<file>`: shared content as last applied. The merge base for three-way decisions.
- `.sync/repo.git/`: bare mirror. Bare means no worktree, no checkout, no hooks run on fetch.
- `.sync/apply.json`: apply journal, present only while an apply runs (see Apply).
- A missing `.sync/` means no repo configured.

### Modes and combine rules per module

Mode per module in `sync.yaml` `modules`. Default when a repo is added: every manifest module on its default below; nothing is written until a pull.

| Module | Unit | Modes | Default |
|---|---|---|---|
| connections, api, runs, workflows, steps | file | local, shared | shared |
| agent `settings.yaml` | entry | local, shared, combined | combined |
| agent `context.md` | file | follows agent mode (combined acts as shared) | |
| prompts `llm-prompts.json` | entry (prompt id) | local, shared, combined | combined |

- `local`: module ignored by sync.
- `shared` (override, file unit): a file is either local or shared. Shared files land under the same name; local-only files stay untouched. "Exclusive" in the spec maps here: no file is both. Deleting local-only files to mirror the repo was declined: it destroys local work with no conflict to show.
- `combined` (entry unit): local entries and shared entries live in one file. Entry ids: `settings.yaml#env/<NAME>`, `#permissions/allow/<rule>`, `#permissions/deny/<rule>`, `#mcp_servers/<name>`, `#hooks/<name>`, `#<provider>` (a provider section is one entry). Prompts: the prompt id.
- `shared` on agent/prompts treats `settings.yaml` / `llm-prompts.json` as one file unit.

Three-way rule, one table for both units (`ours` = current local, `base` = `.sync/base`, `theirs` = new shared minus deactivated):

| ours vs base | theirs vs base | result |
|---|---|---|
| equal (or both absent) | changed / added / removed | take theirs |
| changed | equal | keep ours |
| changed | changed, theirs == ours | no-op |
| changed | changed, theirs != ours | conflict |
| absent, never synced (no base) | present, differs from ours | conflict ("local file of same name") |

- After apply, base becomes theirs for every non-blocked unit, whatever the conflict choice. Keep-mine therefore stays quiet until shared changes again.
- Combined writes go through `configfs.EditYAML` (`NodeSet`, `Unset`) on the local text, so local comments and key order survive. A permissions list is set whole: local order kept, shared items appended, removed items dropped. Prompts write through new exported helpers in `internal/llmprompts/sync.go` (`DecodeOverrides`, `EncodeOverrides` keeping the document version and bumping `Revision`; shared texts validated with the existing prompt validation, invalid is blocked).
- Merged text is validated with the module decoder (`agentcfg.Store.Check` for settings, folder `Decode` for collections) before it is offered. An invalid merge result blocks that unit.

### Per-entry deactivate

- Stored in `sync.yaml` `deactivated[module]`, a list of unit ids (file name, or entry id). Local only; never in the shared repo.
- A deactivated unit is removed from theirs before the three-way rule. Effect: never applied; if applied earlier and ours == base, the next pull removes it locally; if ours changed, it is kept (theirs == removed, ours changed: conflict, default keep).
- Toggled from the review window and from the Settings resource list; every toggle rewrites `sync.yaml` and recomputes the preview.

### No secrets in the shared repo

- Repo URL with a password in userinfo is refused on save. Allowed transports: `https`, `ssh`, scp-like `user@host:path`, `file`. Every spawn sets `GIT_ALLOW_PROTOCOL=file:https:ssh` so `ext::` and similar never run.
- Each shared unit passes a gate before it can be applied; a failure blocks that unit and shows the line, never the value:
  1. module decode (schema incl. `x-kira-secret`, module rules);
  2. literal-credential scan over every string leaf that holds no `${`: value shape (`credshape.Value`) everywhere; name rule (`credshape.Name`) for map entries under any `env` or `headers` key.
- `credshape`: new package `internal/credshape` with `Name(string) bool` and `Value(string) bool`, moved out of `agentport/classify.go`; agentport calls them. No behaviour change in agentport.
- Secret values stay local. A shared file referencing `${secret:x}` that is unset locally applies; the review row notes the unset names (from each module's existing secret status).

### Fetch: interval and auth

- Mirror: `git init --bare .sync/repo.git` once; `git config remote.origin.url <url>` when the URL changes; fetch `gitops.FetchRefspecsArgs("origin", ["+refs/heads/<branch>:refs/remotes/origin/<branch>"])`. Read with `git ls-tree -r -z <sha>` and `gitclient/catfile` batch. All through `gitclient.Run` with the wired recording runner and `Discovery` git path.
- Interval: `fetch_minutes`, default 30, range 5 to 1440, 0 = off. First tick 60 s after start. One `time.Timer`; the next delay reads the setting fresh. Transient failures (`NetworkFailed`, `LockHeld`) back off with `github.com/cenkalti/backoff/v4` (already in `go.mod`) `ExponentialBackOff`, initial = interval, max 60 min, no elapsed limit. Permanent failures (auth, repo not found, bad manifest) stop the timer and set `state.problem`; a successful explicit fetch rearms it. Same verdicts as `gitsession/autofetch.go`.
- Background fetch is credential-free: no askpass env, so a credential prompt fails fast with `GIT_TERMINAL_PROMPT=0`; result `authRequired`.
- Explicit fetch (Settings Add, Fetch now) carries the calling window key: `Broker.WithOp` with a Prompter that calls `gitcred.Relay.AskFrom(ctx, windowKey, "Config sync", req)`, env `Broker.Env()` + op env, unless `Broker.ShouldInterpose(core.askPass)` says the user's own askpass wins. Stored credentials come from the user's git credential helper.
- CLI credentials never touched: Kira reads no token, config or credential file; git and its helper own them. Guard G5 extends to `apps/kira-space/internal/configsync` with the githost/issuetracker rule set (token commands, credential env names, auth headers, `net/http`, `os.Getenv`).
- "Changes available" = `fetched != applied` and the preview has at least one actionable unit. Emitted on `kira:configSync:changed` with the status.

### Conflict handling

- Conflicts come only from the three-way table. Each conflict row offers Keep mine (default, like agentport conflicts unchecked) and Take shared; delete conflicts offer Keep / Delete.
- Preview session (agentport pattern): 128-bit token, 10 min, single use; it stores the hash of every local target and the fetched sha. Apply re-hashes every target under the service mutex; any change, or a newer fetch, is `E_CONFLICT` and nothing is written; the UI re-previews.

### Apply: atomic with backup and rollback

1. Under the service mutex, validate token and hashes.
2. Backup (P540 approach): copy each target that exists to `<home>/backups/configsync-<UTC 20060102T150405Z>/<module>/<file>` via `fsmove.CopyVerified` (moved from `configfold.copyVerified` into `internal/fsmove`; configfold calls it).
3. Write journal `.sync/apply.json` (`WriteAtomic`): `state: applying`, `backup`, `commit`, `files: [{path, existed}]`.
4. Write each target with `configfs.WriteAtomic` or remove it. Write seam `Options.Write` for failure injection.
5. Write `.sync/base/...` for applied units, then `state.json` (`applied = commit`), then remove the journal.
6. Prune `configsync-*` backups beyond the newest 10.

- Any error in 4 or 5: roll back every journal file (existed: restore backup bytes with `WriteAtomic`; not existed: remove), remove the journal, return the error. Base and state stay at the old commit.
- Crash mid-apply: `configsync.Recover(home)` runs at boot in `main.go` right after `foldConfig`, before module stores start; a journal in `applying` rolls back. Rollback is idempotent.
- Watchers may see a short burst; the 200 ms debounce coalesces most of it. Per-file writes are atomic, so a module never reads a half-written file.
- Restore by hand: copy `<backup>/<module>/<file>` back into `<home>/config/<module>/`.

### Review window

- Native ephemeral window, hostview pattern: key `configsync-<id>`, one at a time (focus if open), title "Shared config changes". `bridge.IsConfigSyncKey` joins the three ephemeral predicates in `main.go` (fold them into one `ephemeralWindowKey(key)` helper there while editing all three). Window rows go through the existing `repositories.Windows` methods only.
- Frontend: `main.ts` asks `control.configSyncIsReviewWindow({windowKey})` (pure prefix check, like `openedFilesIsFilesWindow`); `App.vue` renders `ConfigSyncReviewWindow.vue` for it.
- Content: preview grouped by module. Row per unit: id, kind (add, modify, delete, conflict, blocked, deactivated, unchanged-hidden), badge "Runs commands" for `runs`, `steps`, `workflows`, agent hooks and stdio MCP servers, unset-secret note. Selecting a row shows `MonacoDiff` of current text vs text after pull for that file (combined files show the whole file's diff plus their entry rows). Conflict choice controls, deactivate switch per unit. Footer: commit short sha, Pull, Cancel. Pull calls `Apply(token, choices)`; success closes the window.
- Reuses `MonacoDiff.vue` as is. `useDiffEditor` declined: it is bound to repo URIs and the git read path.

### Toast

- `configsync/ConfigSyncToast.vue`, same pattern as `ApprovalsToast.vue` (`floatingSurface`, `role="status"`), fixed bottom-right so it never overlaps the approvals toast. Text "New shared config available" plus change count. Review opens the window (`ConfigSyncService.OpenReview`). Dismiss (X) calls `Dismiss(sha)`; it returns on the next new commit. Shown in workbench windows only (not review, host view, capture, files or proof windows).
- shadcn-vue Sonner declined: the app has no toast host, and Sonner's model is timed, auto-dismissing toasts; this notice must persist until acted on. The in-repo toast pattern meets the need.

### Settings UI

- New section `Shared config` in `state/settings.ts` `sections` (after `Git`) and `SettingsDialog.vue`; pane `workbench/settings/ConfigSyncPane.vue`. Own TanStack Query over `ConfigSyncService` (like `CliToolsPane`), not the DB settings draft. Tailwind + shadcn-vue primitives (`Input`, `Button`, `NativeSelect`, `Switch`, `Alert`, `Field*`).
- No repo: URL and branch fields, Add (validates, initial fetch with credential prompts routed to this window).
- Repo set: URL and branch (read-only, Change and Remove links), fetch interval, Fetch now, last fetch time, problem `Alert`. Status line "N changes available" with Review and Pull right there. Pull applies directly when the preview has no conflicts; with conflicts it opens the review window and says why. Module table: mode select per manifest module, entry count, deactivated count.
- Remove: confirm dialog; deletes `.sync/` (mirror, base, state, settings). Applied files stay as local files.

### Service surface

`bridge.ConfigSyncService` (bound): `Status`, `SetRepo{url, branch, windowKey}`, `RemoveRepo`, `SetFetchMinutes`, `SetMode{module, mode}`, `SetDeactivated{module, unit, off}`, `FetchNow{windowKey}`, `Preview` (token + rows + texts), `Apply{token, choices}`, `Dismiss{sha}`, `OpenReview`, `IsReviewWindow{windowKey}`. Event `kira:configSync:changed` carries `Status`. Errors through `ipcerr` catalog keys `backend.space.configSync.*`.
