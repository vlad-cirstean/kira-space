## 4. Overview carousel

Choice: pure CSS scroll-snap plus a small vanilla TS `<script>` in `site/src/components/BuildCarousel.astro`.
No island, no dependency. Reason (library rule): scroll-snap gives native touch swipe, momentum and
snapping in WebKit for free; the remaining work is arrows, dots and a timer. Embla (MIT) was
considered: it emulates swipe in JS and still needs custom code for off-screen and reduced-motion
pause, so it saves little and adds a dependency and an island.

Markup: `role="region"` `aria-roledescription="carousel"` `aria-label="Build with Kira in five steps"`.
Track: horizontal flex, `overflow-x: auto`, `scroll-snap-type: x mandatory`, scrollbar hidden.
Slides: `role="group"` `aria-roledescription="slide"` `aria-label="<n> of 5: <name>"`. Each slide is
one `<a href="#<anchor>">` with the step's lead window image and a caption bar "Step n. <name>".
Prev/next buttons (44 px, labelled) and five dot buttons (`aria-label="Go to step n: <name>"`,
`aria-current="true"` on the active one). No play/pause control.

No layout jump: every slide image is a window shot. Desktop: framed (all 2272 x 1504). Phone: the
detail crop (all 880 x 660). The track sets `aspect-ratio` per breakpoint; images carry width and
height.

Image markup: extract the `<picture>` block of `Shot.astro` into `ShotPicture.astro`, used by both
`Shot.astro` and the carousel. The carousel slide link goes to the section, not to the full image.

Active slide: an `IntersectionObserver` on slides (root = track, threshold 0.6). Arrows and dots
`scrollTo` the target slide; arrows wrap (5 to 1, 1 to 5). Keyboard: ArrowLeft/ArrowRight when
focus is inside the carousel; Tab reaches arrows, dots and slide links.

## 5. Autoplay rules

- Interval 6000 ms. Advances one slide, wraps from 5 to 1.
- Pause reasons, a set: `hover` (pointerenter/pointerleave on the carousel), `focus` (focusin;
  cleared on focusout when focus leaves the carousel), `touch` (touchstart; cleared on
  touchend/touchcancel), `offscreen` (IntersectionObserver on the carousel, under 50 % visible),
  `hidden` (`document.visibilityState !== 'visible'`). The timer runs only while the set is empty.
- Resume: when the set empties, the timer restarts with a full interval. Any manual move (arrow,
  dot, key, swipe) also restarts it.
- Reduced motion: `matchMedia('(prefers-reduced-motion: reduce)')`, live via its `change` event.
  When it matches, no timer ever runs and `scrollTo` uses `behavior: 'auto'`. Arrows, dots, keys and
  swipe still work.
- Live region: track `aria-live="off"` while autoplaying, `"polite"` while paused or under reduced
  motion (APG carousel pattern). Focus pause is the keyboard user's pause mechanism.

## 9. Shot generation speed

Measured in this sandbox (4 vCPU, WebKit at `/opt/pw-browsers`, worktree at `625a4c982`):

- `bun run build:test`: 10 s (Vite, bindings present).
- Current 6 tests / 8 shots, `--project=screenshots`: 32.9 s serial (per test 3.3 to 6.9 s);
  18.8 s at 2 workers; 16.1 s at 3 workers.
- Byte determinism: 3-worker output vs serial output, `diff -rq` over `framed/` and `crop/`: no
  difference.
- Per-operation split, from a throwaway timing spec (not committed) that booted the agents board
  once and timed each call with `performance.now()`: relaunch to first content 1.75 to 1.83 s;
  window shot (`captureShot`: two screenshots, frame context, two lossless WebP encodes) 1.79 to
  2.09 s; region crop (`captureCrop`) 0.31 to 0.33 s; one UI step (click plus settle) 0.32 s.
- Lossless WebP encode alone (`sharp`, effort 6): framed 2272 x 1504 0.26 to 0.80 s, detail 0.05 s.

Picks:

- One build and one browser per run: yes (already). One `build:test`, Playwright reuses a browser
  per worker; each `relaunch` is a new context.
- Several shots per session: yes, the main lever. Each section spec boots once per window kind and
  drives the UI through states, calling `shoot` at each. A boot costs about as much as a window
  shot, so 26 shots on ~7 boots instead of 26.
- FE-only mock bridge: yes (already the shot mode). Nothing real: board, approvals, review and proof
  data are fixtures.
- Shared storage state and seed: one fixture module (section 10); `relaunch({ storage })` for panel
  state such as agent panel on.
- Parallel workers: yes. `screenshots` project `fullyParallel: true`, `workers: 3`. Files and tests
  run in parallel; each test keeps its own serial session. Output files never collide
  (`shots-fill` already fails two ids on one file). Measured gain 2.0x at 3 workers; output
  byte-identical. If CI shows a flake at 3, drop to 2 and record it.
- CI shard matrix: declined. Cold setup with bindings (4 to 6 min) would repeat per shard and need a
  merge job; one shard fits the budget below.
- Per-shot cache keyed on its import closure: declined. The key already hashes
  `apps/kira-space/frontend/**`, so nearly every app change touches every shot's closure; per-shot
  entries would need a closure tracer and 34 cache entries to save about 3 minutes on a manual
  workflow. The existing whole-set key and last-good fallback stay. Extend the key with
  `apps/kira-space/tests/fixtures/**` and `apps/kira-space/tests/contract/**` (correctness gap).
- WebKit only: yes (already).
- Animation and font warmup: no change. `prepareCapture` already disables animations per
  screenshot and `fonts.ready` resolves in milliseconds after the first shot of a session. The
  measured cost sits in framing and encoding, which is P550 pipeline code; out of scope.

Expectations (from the measurements above):

- Per shot: window about 2 s, crop about 0.3 s.
- Per session: boot about 1.8 s, plus about 0.3 s per UI step.
- New specs, serial estimate: start-task 9 s, db-prompt 9 s, branches-handover 8 s, review 7 s,
  proof 12 s; about 46 s. With the existing 33 s: about 79 s serial, about 40 to 45 s at 3 workers.
- Local cold `bun run screenshots` (build plus capture): about 55 s.
- CI factor: the Pages comment records 2 to 3 min for build plus 8 shots, against 43 s locally, so
  about 3.5x. CI capture step (one shard, cold): about 3 to 3.5 min, under the 5 min target.
- CI job total, cold cache: setup with bindings 4 to 6 min, WebKit 1 to 2, capture 3 to 3.5, site
  1 to 1.5; about 10 to 13 min (timeout 30). Warm cache (exact key hit): no bindings, no WebKit, no
  capture; about 2 to 3 min.

How the implementer verifies: after all specs land, clear `screenshots/` except `assets/`, run
`time bun run screenshots` twice (second run for the determinism `diff -rq` against a copy of the
first), and record wall times plus the per-spec durations from `--reporter=list` in the Result. If
local capture exceeds 90 s at 3 workers, merge sessions before finishing. The Close check reads the
CI capture step time from the Pages run.

Workflow changes cannot be pushed from this sandbox: write
`docs/pending-changes/.github__workflows__pages.yml.patch` (cache key additions, updated timing
comment). No other workflow change.

Pages workflow patch file already exists (job pin to `ubuntu-24.04`, written before this phase). Extend it; never overwrite.

`site:shots:fill` must exit non-zero under `CI=true` when any shot needs a placeholder, not fill silently. Local runs keep filling. A placeholder-hidden capture failure broke Pages shots before.
