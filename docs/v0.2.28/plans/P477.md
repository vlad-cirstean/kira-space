### 4.2 What each long op keeps, unchanged

All of it lives below `handlers.Request`, so the bound path inherits it with no new code:

- Detach: `op.run`, `undo.run`, `remote.run`, `stack.restack` run under `context.WithoutCancel`.
  A cancelled Wails call ctx (promise `.cancel()`, window navigation) abandons the reply only; the
  write finishes. Reads (`remote.*Preflight`, every `preflight.*`, lists) stay on the call ctx.
- Op slots (the per-repo write locks): `RepoEntry.remoteOp` and `restack` `opSlot`s admit one op each;
  a second caller gets `OperationInProgress`. Local `op.run` writes are not slot-gated (git's own
  `index.lock`), as today (`TestLocalWriteAndRemoteOpAreNotMutuallyExclusive`).
- Op log: `ForConn.Request` wraps ctx in `oplog.WithOrigin(ctx, c.Origin())` (module git, label
  "Kira Space"); `startOp`/`finish*Result` unchanged. Op log cancel (`OpsService.Cancel` →
  `logOp.SetCancel(e.CancelRestack)` / remote killable phase) unchanged.
- Credential prompts: `RunRemote` passes the Conn as prompter. `Conn.AskCredential` ends the wait on
  the op ctx or `conn.done`; the route is `relay.AskFrom(ctx, windowKey, "Kira Space", req)` set once in
  `GitWindows.getLocked`. Bound and stream share that Conn, so routing is identical.
- Progress: `remote.progress` and `stack.progress` go through `Conn.Emit` → `EmitTo(windowKey,
  "kira:git:<event>")` (P476). Unchanged.
- Window close: `GitWindows.Close(key)` → `Conn.Close` closes `done` (pending credential prompt
  withdrawn, as a stream disconnect does today), releases holds. `Registry.release` starts the
  5 min linger (`defaultLingerFor`); `teardown` (and its `forceCancel` of the op slots) runs only after
  linger with zero refs. So a write in flight finishes; a remote op blocked on a prompt fails with its
  auth error and frees its slot (`TestDisconnectDuringCredentialPromptFreesTheSlot` semantics).

### 4.3 Wails call lifetime

- Long bound calls (a fetch, a restack, a credential wait up to 120 s) are fine: the Wails runtime
  call is a `fetch` with no timeout; native serves it in-process; the `-tags server` HTTP server sets
  no `WriteTimeout` (only `mobileweb` sets per-route deadlines). Implementer confirms with the
  native app once (fetch with a slow remote), no code change expected.

## 5. Cancel

### 5.1 Decision: explicit cancel methods, not binding cancellation

- `remote.cancel` → `RepoEntry.CancelRemote()` → `opSlot.tryCancel()`: answers `{cancelled:false}` when
  nothing runs or the phase is not killable (a push mid-delivery). Binding cancellation carries no
  answer and cannot express "refused"; the toolbar needs the bool.
- `stack.cancelRestack` → `CancelRestack()`, same shape. The op log's cancel button uses the same slot.
- Binding cancellation (`CancellablePromise.cancel()`, from `callBound` on abort or dispose) keeps the
  meaning the stream's `cancel` frame had: abandon the reply. Writes are detached, so it never kills one.
- Both cancel methods become bound (3.1). A cancel call runs concurrently with its in-flight
  `remote.run`/`stack.restack` call: Wails dispatches each runtime POST on its own goroutine; no
  ordering dependency on the stream remains.

### 5.2 Late progress after a bound reply

Today one stream carried responses and events in order. Now the reply (HTTP response) and
`kira:git:*.progress` (app event) travel separately, so a progress event can arrive after the reply.

- `packages/git-ui/src/state/ops.ts` (constructor, `remote.progress` handler): drop the event when
  `activeRemoteOp.value === undefined`. Without it a late event leaves `remoteProgress` set after
  `#runRemote`'s `finally` cleared it.
- `packages/git-ui/src/state/stack.ts` (constructor, `stack.progress` handler): drop the event when
  `!restacking.value`. Without it a late event of run N lands in `progress` after `restacking` went
  false; `StackDialog.vue` hides it (render gated on `restacking`), but it stays in the array.
- One test case each, in the existing `ops.spec.ts` and `stack.spec.ts` (ordering: an event after the
  reply settles is ignored). Earns its place under CLAUDE.md's concurrency bar.
