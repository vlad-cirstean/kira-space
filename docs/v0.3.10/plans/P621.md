### Multi-image clipboard per platform

Web: Async Clipboard API takes one `ClipboardItem` with `image/png` in WebKit and Chromium; several
image items are rejected. Wails v3.1.0 `app.Clipboard` is text only. So multi-image copy is native,
from Go.

- **macOS: possible.** `NSPasteboard` holds an ordered array of `NSPasteboardItem`s
  (`-writeObjects:`, 10.6+). Each item carries its own types. Write one item per tab with
  `public.png` data plus `public.file-url` (`NSPasteboardTypeFileURL`, 10.13+; app minimum is
  14.0) pointing at the PNG on disk. Readers that take all items (`-readObjectsForClasses:` with
  `NSImage` or `NSURL`: Finder, Mail, Notes, Messages, Slack) get every image. A reader that takes
  one image gets the first item, unchanged. No stitching anywhere. macOS default becomes copy-all;
  the brief's guess that macOS cannot do it is wrong.
- **Windows: not possible as images.** One clipboard holds one block per format; `CF_DIB`,
  `CF_DIBV5` and the registered `PNG` format each carry one image. Several items exist only as
  `CF_HDROP` (a file list), which is files, not images. App also has no Windows build
  (`docs/PACKAGING.md`: darwin only). Capability false; default stays save.
- **Linux: not possible as images.** X11 `CLIPBOARD` and Wayland data offers have one owner with a
  set of MIME targets, one payload per target, so at most one `image/png`. Several items exist only
  as `text/uri-list` or `x-special/gnome-copied-files` (file references). Linux is a dev build only.
  Capability false; default stays save.
- Rule used: capability means several images, each with its own image data, on the clipboard.

Runtime decision: Go reports `multiImage` through `ProofService.ShotClipboard`. The darwin shim
probes `NSPasteboard` at runtime; every other build answers false. UI reads it through TanStack
Query and picks the primary action.

### 2. Native package `apps/kira-space/internal/imageclip` (new)

- `imageclip.go` (no tag): package doc; `type Clipboard struct { invoke func(func()) }`;
  `func New(invoke func(func())) *Clipboard`. `invoke` runs a func on the AppKit main thread:
  production passes `application.InvokeSync`, the darwin test passes a direct call.
- `imageclip_darwin.go` (`//go:build darwin && cgo`), cgo
  `-x objective-c -fobjc-arc`, `-framework AppKit -framework Foundation`:
  - C `kira_can_write_images(void) int`: 1 when `[NSPasteboard generalPasteboard]` and
    `[NSPasteboardItem class]` are non-nil.
  - C `kira_write_images(const char *name, const char **paths, int n) int`: `@autoreleasepool`;
    `name == NULL` means general pasteboard, else `+pasteboardWithName:`. Per path:
    `NSData dataWithContentsOfFile:` (nil returns 1), new `NSPasteboardItem`, `setData:forType:
    NSPasteboardTypePNG`, `setString:[[NSURL fileURLWithPath:p] absoluteString] forType:
    NSPasteboardTypeFileURL`. Build all items first, then `clearContents` and `writeObjects:`
    (NO returns 2). 0 on success. Clipboard stays untouched when any file fails.
  - `MultiImage() bool`: `sync.Once` caching `kira_can_write_images()` run through `invoke`.
  - `WriteImages(paths []string) error`: empty slice is an error; `C.CString` each path, free with
    `defer`; call through `invoke` with `name == nil`. Map 1 and 2 to distinct errors.
  - Unexported `writeImagesTo(name string, paths []string) error` shared by `WriteImages` and the
    test.
- `imageclip_other.go` (`//go:build !(darwin && cgo)`): `MultiImage()` false, `WriteImages`
  returns `errors.ErrUnsupported`. Comment names the Windows and Linux reasons above in one line
  each.
- `imageclip_darwin_test.go` (`darwin && cgo`), `TestWriteImagesPrivatePasteboard`: writes 3
  small valid PNGs (`image/png` encode) to `t.TempDir()`, calls `writeImagesTo` on a unique
  pasteboard name (`kira.test.<pid>.<nanos>`), then C helpers read back: item count 3, each item
  has `public.png` bytes equal to its file and `public.file-url` equal to its URL, in order. A
  missing file returns the read error and leaves the previous content. Cleanup:
  `releaseGlobally`. Never touches the general pasteboard. Earns its keep: the only check of the
  native write, on real AppKit.
- No pure-Go/purego path: `ebitengine/purego` is indirect only, and the repo's darwin shims are
  cgo (`localauth`). cgo file is compiled and linted by PR CI's macOS job.
- Declined: `NSPasteboardItemDataProvider` (lazy data). All PNGs are on disk already; eager write
  is simpler and the pasteboard server copies the data either way.
