Root causes:

- (a) Handover race. `internal/ade/handover.go` `RecordHandover` runs `UpsertHandoverDraft`, then
  `openHandoverPrompt(tc)`, and only then `b.notifyBoard()`. The prompt event reaches the window
  before the board-changed event. The frontend draft comes from the board snapshot
  (`adeStageDialog.ts`: `draft = card.task.handoverDrafts.find(...)`), and the board refetch is heavy
  (git work per repo). So the dialog opens with empty notes and the text arrives one board refetch
  later. Two aggravating factors:
  - `AdeHandoverPrompt` calls `store.open` in `onMounted`, so the first frame has no dialog content.
  - `AdeNotesEditor`'s model watch drops an outside change while the editor is focused and editable
    (`ed.isFocused && !props.readonly`). A late prefill landing after focus is lost.
- (b) Proof ready. `taskTitle` comes from `useProofSessions()`, fetched after mount.
- (c) `FlushEditor`. `MonacoHost` already paints a `<pre>` preview while `loadMonaco()` loads, but
  `FlushEditor` sets `height = max(contentHeight, lineHeight)` with `contentHeight = 0` until Monaco
  emits `update:contentHeight`. The preview is clipped to one line until Monaco is loaded and laid
  out.
- (d) TipTap. `@tiptap/vue-3` `useEditor` (3.32.2) creates the `Editor` in `onMounted`, and
  `EditorContent` appends its DOM in a `nextTick`. Read-only brief text appears at least one frame
  after the dialog.
- (e) Handover link strip. `AdeLinkStrip` calls `useTaskLinks`, whose `useTaskArtifacts(taskId)` and
  `useTaskIssue` fetch after open; strip shows `Skeleton` first.
- (f) `BranchRequestBody` reads holder titles from `useBoard()`; falls back to "New task" until the
  board is cached. Usually cached in the Space window; verify in measurement.

## 6. Approval dialog: one prompt, fixed layout, full room

Requirements (user, added mid-planning):

- Exactly one prompt per dialog. Others queue; the next shows once the current one is answered.
- Fixed layout: Approve/Deny sit at the same screen position whatever the statement or request
  length. Fixed footer; content area fills the rest.
- Statement/request text gets maximum room: larger dialog, content `flex-1`, scroll only on real
  overflow.

### Root cause: two prompts in one dialog

Not a backend or router bug. `internal/approvals/queue.go` `Put` opens one router prompt per item
(`approval:<id>`); `internal/prompts/router.go` keeps one entry per id. `PromptHost.vue` already shows
one routed prompt at a time (`head`), and `ApprovalsSurface` turns into the toast while
`promptShown`, so routed prompts and approvals never stack.

The stacking is by design in `packages/workbench/src/approvals/ApprovalsDialog.vue`: `ApprovalsSurface`
passes every approval targeted at this window (`mine`), and the dialog renders all of them
(`<ApprovalItemCard v-for="(item, i) in items" ...>` in one `DialogBody`, `divide-y`), with
`focusId` only scrolling to one. Any two approvals pending together (two db.query calls from one
agent, a task.create plus a branch.request) show in one dialog.

Layout causes:

- Each `ApprovalItemCard` has its own Deny/Approve row (`approval-footer`) under its body, so the
  buttons move with content length.
- `DialogContent size="2xl" fixed-height` is `w-225 h-160 max-h-[85vh]`; `FlushEditor` caps each
  editor at 12 lines (`MAX_LINES`), so long statements scroll inside a small box even when the
  dialog has free room.

`TextPromptDialog` (`packages/workbench/src/prompt/TextPromptDialog.vue`) is the generic rename
input prompt, not MCP-triggered; out of scope.
