## 2. Design

### 2.1 Semantics

Every request gets one verdict from the rules plus the new default.

- A deny rule matches: refused. Deny wins over allow; order is irrelevant (unchanged).
- An allow rule matches (and no deny rule): sent without the approval prompt, whatever `apiApproval`
  and `agentAutoApproveReads` say.
- No rule matches: the default decides.
  - `ask`: follows `apiApproval` and `agentAutoApproveReads` exactly as today. It waits with
    `always` and is sent without asking with `never`.
  - `deny`: refused.

Outcome table. Refused: an error to the agent, no approval item. Asks: an approval item, except a
body-less GET/HEAD/OPTIONS in an environment with `agentAutoApproveReads`, which runs. Runs: sent
without an item.

| Rule match | Default | `apiApproval: always` | `apiApproval: never` |
| --- | --- | --- | --- |
| deny | ask or deny | Refused | Refused |
| allow | ask or deny | Runs | Runs |
| none | ask | Asks | Runs |
| none | deny | Refused | Refused |

The default applies with zero rules too. Zero rules plus `deny` refuses everything, and the UI warns
(section 2.7).

Under this model `apiApproval` means "what happens to requests that match no rule while the default is
ask". The approval control stays where it is, and its copy is unchanged. The rules section hints say
how the two combine (section 2.8).

Race between plan and send: `Send` re-plans. `apiRequest` passes `&plan` to `Send` in both branches
(today it already does). `Send` returns `ErrPlanChanged` when `approved.AllowedByRule` is true and the
re-plan is not. That way, an allow rule removed in the gap between plan and send cannot send an
unprompted request that now needs a prompt.

### 2.2 Redirect hops

The hop check is `Policy.CheckHop(method, next)`, run with the request's own method as today:

- A deny rule matches: refused.
- An allow rule matches: followed.
- No rule matches: refused. The one exception is a policy that allows everything (zero rules plus
  `ask`), which follows the hop as today.

Why: an allow rule skips the prompt, so an allowed host must not be able to redirect to an unvetted
host unprompted. The exception keeps installs without rules unchanged
(`TestApiRequestRedirectNoCredential` guards it). Consequence: with rules present and default `ask`, a
prompted request (no rule matched) also cannot follow a hop to an unmatched host. Its approval covered
only the first URL. Under `deny` the hop rule is the same as today.

`redirectGuard` (resolve.go:435-450) uses `access.AllowsAll()` for its fast path and calls
`CheckHop`. The error stays `redirect to <host> blocked: <reason>`. The reason for an unmatched hop is
`"<M> <scheme://host> matches no allow rule in Kira Space's database MCP settings, and a redirect must go to a host an allow rule matches"`.

### 2.3 Existing installs

- No stored rules: the leaf is absent and reads as `ask`. Same as today: every request follows
  `apiApproval`, and redirects are followed.
- Stored rules: migration 0096 writes `deny`, so unmatched requests stay refused, as today.
- Deliberate behavior change, approved by the user: an install with allow rules and `apiApproval:
  always` stops prompting for requests its allow rules match. Under P580 those requests still waited
  for approval. This is the point of the user's decision. The plan states it in ARCHITECTURE.md, the
  site page and the SPEC Result line. No migration rewrites allow rules to keep the old prompting;
  the user chose the new meaning.
