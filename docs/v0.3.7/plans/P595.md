## 2. Design

### 2.1 Semantics

Two questions, two controls, as today. The phase adds one setting to the first question only.

1. May the request run? Rules plus the new default.
   - Deny rule matches: refused. Deny wins over allow, order irrelevant (unchanged).
   - Allow rule matches: may run.
   - No rule matches: the default decides. `ask`: may run. `deny`: refused.
2. Does it wait for the user? `apiApproval` plus the environment's `agentAutoApproveReads`, unchanged,
   for every request that may run.

Outcome table (Refused: error to the agent, no approval item. Asks: approval item, except a
body-less GET/HEAD/OPTIONS in an environment with `agentAutoApproveReads`, which runs. Runs: sent
without an item):

| Rule match | Default | `apiApproval: always` | `apiApproval: never` |
| --- | --- | --- | --- |
| deny | ask or deny | Refused | Refused |
| allow | ask or deny | Asks | Runs |
| none | ask | Asks | Runs |
| none | deny | Refused | Refused |

The default applies with zero rules too. Zero rules plus `deny` refuses everything; the UI warns
(section 2.4).

Why "ask" means "may run; the approval setting applies", not "always prompt":

- The user's sentence frames "ask for everything" as the approval setting ("if the default is ask for
  everything"). The complaint is that a rule list silently converts unmatched requests from "ask" to
  "refused". With `apiApproval: always`, default `ask` gives exactly "ask for everything except what a
  deny rule refuses".
- It keeps P580's stated rule: rules gate approval, never replace it. An allow rule never skips
  approval; it only matters when the default is `deny`. One concept per control: rules plus default
  say "may it run", approval says "do I get asked".
- It preserves every existing install with no new value (section 2.2). A forced prompt for unmatched
  requests would change installs with no rules and `apiApproval: never`, which today send everything
  silently. Avoiding that would need a third default value (`allow`) the user did not ask for.
- Cost: with `apiApproval: never`, default `ask` does not ask. The UI says so in plain words next to the
  control (section 2.4). Open question 1 offers the alternative.

Redirect hops follow the same `Check`. Under `ask`, a hop to a host no rule matches is followed (same
as a no-rule install today; a credential still never leaves its own host list, resolve.go:440-444).
Under `deny`, it is refused as today. A deny rule refuses a hop in both. No second approval mid-flight:
the approval item already shows the URL and the follow-redirects flag.

### 2.2 Setting, migration, validation

- New leaf `dbMcp.apiDefault`, values `ask` | `deny`. Fresh install default `ask`.
- Existing installs, one data migration, `internal/storage/migrations/0096_p595_api_default.sql`
  (P593 claimed 0095; if 0095 is not on the chapter branch at landing, renumber to 0095):

  ```sql
  -- P595: requests no API access rule matches were refused once any rule existed. Installs with stored rules
  -- keep that as an explicit default; installs without rules keep the new default, ask.
  INSERT INTO settings (key, value)
  SELECT 'dbMcp.apiDefault', '"deny"'
  WHERE EXISTS (
    SELECT 1 FROM settings
    WHERE key = 'dbMcp.apiRules'
      AND NOT (json_valid(value) AND (json_type(value) = 'null' OR (json_type(value) = 'array' AND json_array_length(value) = 0)))
  )
  ON CONFLICT (key) DO NOTHING;
  ```

  Rules present (or stored but unreadable, which already refuses everything): `deny`, same as today.
  No leaf, `[]` or `null`: no row, reads as `ask`, same as today's empty policy. Add the entry to
  `internal/storage/migrations/embed.go` (`{Version: 96, Name: "p595_api_default", File: ...}`).
  Confirm modernc's SQLite has JSON1 (it does in the version vendored; the test below proves it).

  default the moment a no-rule install saves its first rule. A one-time write fixes the value once.
