## Ask

- Tool text: a proof is about functionality and behavior, not code.
- Proof window: the explanation gets more space and a bigger font by default. It is the most important
  part of a proof.
- Tool text: keep the explanation terse but clear.

## Design

### 1. Tool text (`internal/llmprompts/registry.go`)

Keep every existing clause, numbers and negations verbatim. Replace only the opening and two argument
texts.

`dbmcp.tool.proof_save` default: replace the opening
`Save proof that your work is correct: one call creates and closes it, and the user reviews it in a window. Steps show in order. `
with
`Save proof that your work is correct. Prove functionality and behavior, not code: show what the system does (query results, responses, screenshots), not source or diffs. One call creates and closes it, and the user reviews it in a window. Steps show in order; each step's description is the explanation the user reads first. `
The rest (from `Pick each step's view …` to `… names steps[i] and the limit.`) stays byte-identical.
Rendered size 835 to about 1032 runes.

`steps.description`:
`The explanation, shown large above the data: one terse, clear line, ideally under 120 characters, at most 200. Say what the step shows and what that proves. Required unless keepOrdinal is set.`
(about 192 runes, from 96).

`summary`:
`Which behavior it proves: 1-3 terse, clear sentences, up to 500 characters. Shown above the steps. New proofs only.`
(about 115 runes, from 54).

`proof_list`, `name`, `reason`, `query`, `data` and the rest: unchanged.

Length decision, with evidence:

- Keep the hard limits (200 runes, one line; summary 500). The description doubles as tab title,
  screenshot file name and image/chart region label (see above); a longer or multi-line description
  degrades all of them, and the 200-rune cap already enforces terseness. No schema, migration or
  validation change.
- Add a soft hint, "ideally under 120 characters": at 13 px (`text-kira-lg`) a 120-character line
  wraps to at most 2 lines in a normal centre pane and about 3 in compare mode's half pane, which keeps
  the explanation band short. A hard cap at 120 would refuse existing-style descriptions; the hint
  guides without breaking edits of stored proofs (a `replacesOrdinal` step resubmits text).
- No filler words (style guard list: please, just, simply, very, make sure, note that, …): checked
  against the drafts above.

Budget: set the three `budget.tsv` lines (`dbmcp.tool.proof_save`,
`dbmcp.tool.proof_save.arg.steps.description`, `dbmcp.tool.proof_save.arg.summary`) to the exact rune
counts `go run ./internal/llmprompts/cmd/promptsizes` prints after the edit (ratchet: visible diff,
no slack).

### 2. Proof window: explanation larger and with room

Step description (`ProofStepView.vue`, header block at lines 146-170):

- Header row from fixed `h-control-lg … items-center` to `flex min-h-control-lg shrink-0 items-start
  gap-2 px-3 py-2`. Icon and badge stay on the first line (`items-start`; give the icon `mt-0.5` or
  equivalent so it aligns with the first text line, implementer checks visually in the spec run).
- Description span: drop `truncate`, use `min-w-0 flex-1 text-kira-lg font-medium leading-snug
  break-words` (wraps to as many lines as needed; 200 runes is at most about 4 lines in compare
  mode). Keep `data-testid="proof-step-description"`.
- Source `Badge` keeps `shrink-0`. No other change in the file.

Proof summary (`ProofWindow.vue`, centre section, lines 147-170):

- Inside the `QueryState` default slot, before the tab strip `div` (line 149), add
  `<p v-if="data.summary" class="max-h-32 shrink-0 overflow-y-auto whitespace-pre-line break-words
  px-3 py-2 text-kira-lg leading-snug" :aria-label="t('studio.proof.summary.aria')"
  data-testid="proof-summary">{{ data.summary }}</p>`.
- Session-level, so above the step tabs. `whitespace-pre-line` because summary validation allows
  newlines. `max-h-32` with scroll bounds a 500-rune summary so the step body keeps its room.
- It sits inside `centre`, which `useProofScreenshot` captures (`ProofWindow.vue:122`, `target:
  centre`), so copied and saved screenshots carry the summary. Static text: no readiness signal
  needed.
- New i18n key `studio.proof.summary.aria` = `Proof summary` in `packages/theme/src/i18n/en.json`
  (additive hunk). Implementer runs `bun scripts/copy/check-copy.ts` and `check-catalog.ts --unused`.

Font size: `text-kira-lg` is the only size above body text on the guarded scale that fits a paragraph
(`text-kira-xl` is a fixed 20 px heading size). With `font-medium`, `leading-snug`, wrap and padding,
the explanation becomes the most prominent text in the step. No new token, no guard change (see Open
questions).

Frontend rules: Tailwind utilities only, no scoped `<style>`; no new primitive, composable, store or
query: the summary already arrives in the `useProofSession` TanStack Query result; nothing else
needed.

Out of scope: P597 (screenshot export to a Desktop folder; `useProofScreenshot.ts`,
`ProofScreenshotMenu.vue`, `screenshot.ts`) and the task chain entry (`AdeProofEntry.vue`). Not touched.

## Open questions

- Font step: `text-kira-lg` is 13 px against 12 px body text (+1 px, plus `font-medium`, wrap and
  padding). A clearly larger size (say 15 to 16 px) needs a new token and a `check_font_scale` change,
  which is a design-system decision. This plan stays on the guarded scale; raise it if the user wants
  more.
- Summary band: the summary ("what it proves") is not shown in the proof window today. The plan reads
  it as the proof-level explanation and shows it. Drop the band if the user meant only the step
  description.
