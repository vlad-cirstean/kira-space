## 3. Placement rule

- Engine capability (does the engine honor what the adapter sends?) goes in the adapter suites, as a
  `ts.Scenario` wired into each engine's `*_test.go` and the least-privilege `Then` row of its
  `authmatrix_test.go`. Items 39-43.
- MCP option against a real engine (does the gate, limit, mask, lane produce the right MCP answer on
  this engine?) goes in `flow`, complete suite, one table-driven top-level test per area iterating
  engines. Items 1-31 where an engine differs.
- Engine-independent MCP behavior stays where it is; only the two `api_request` gaps are added.
- Keep `TestDbMcpReadLanePostgres`, `TestDbMcpExpensiveQueryPostgres`,
  `TestDbMcpBrowseExpensiveQueryPostgres` unchanged: they own contracts (`dbmcp-expensive-query`)
  and their own container. New engine tables skip pg only for the exact steps those tests cover;
  every other step runs pg too.

### 4.1 `ts.ExplainPlan` (new `ts/explain.go`)

```go
type ExplainPlanCase struct {
	Path        []string // lane-readable table: the seeded big_rows
	FullScan    string   // statement whose estimate must reach MinRows
	Point       string   // selective statement whose estimate stays under MaxPointRows
	MinRows     int64
	MaxPointRows int64
}

```

- `Requires`: `caps.SQL`. `Run` skips when `!queryplan.Supported(cfg.Kind)`.
- Compose with `queryplan.StatementsFor(kind, stmt)`, run each on the lane adapter
  (`laneAdapter` in `ts/readlane.go`, so it proves EXPLAIN works on the read-only session), parse
  with `queryplan.FromPages(kind, pages, threshold)`.
- Assert: parse returns no error; pg/my/ma/ch `HasRowEstimate` true, FullScan estimate `>= MinRows`,
  Point estimate `< MaxPointRows`; sl `HasRowEstimate` false and parse still yields a plan.
- Wire: pg `FullScan "SELECT * FROM app.big_rows"`, `MinRows 500000`, Point `... WHERE id = 1`,
  `MaxPointRows 1000`. my/ma same on `kira_test.big_rows`. ch: Point bound `MaxPointRows 100000`
  (estimate is granule-based, 8192 rows per granule). sl on the seeded table, no estimate.

## 6. Docker absence and confidence

This sandbox has no Docker. Every container test skips here (fails only under
`KIRA_FLOW_DOCKER=require` or with `KIRA_TEST_MATRIX=1`). CI's complete suites run them.

Confidence without running:

- `CGO_ENABLED=1 go vet ./internal/adapters/... ./internal/flows/dbmcpflow/`.
- Compile every test binary: `go test -count=1 -run '^$' ./internal/adapters/... ./internal/flows/dbmcpflow/`.
- `go test -list 'TestDbMcpEngine|TestApiAccessRulesHostPort|TestApiRequestTLSVerified' ./internal/flows/dbmcpflow/`
  and `-list` on each adapter package: new names present.
- Run the general-suite additions for real (§5.7 and any sqlite subtest reachable without Docker:
  temporarily drop `RequireDocker` locally for the `sl` subtests, run them, restore before commit).
- `golangci-lint run` on touched packages.
- Read each engine's SQL against its docs and the existing passing scenarios in the same file; reuse
  their statements where one exists (`slowRows`, `LaneCancel` statements).

Flake avoidance:

- 1 s limits against 5 s statements; assert `< 4 s` upper bounds, never tight windows.
- `flowharness.WaitUntil` for post-cancel row checks and lane close, never `time.Sleep`.
- Unique scratch names per test and engine; cleanup drops even on failure.
- No `t.Parallel()` in engine tables.
- Expensive thresholds an order of magnitude from both estimates (1M full, at most 8192 point).

Runtime: containers are memoized per test binary. Kibana start (about 2 min) is the largest cost in
`flow`. After the first CI run, compare the package time to `test:flows:complete`'s 20 min timeout;
raise the script timeout in the same phase if the package exceeds 15 min.
