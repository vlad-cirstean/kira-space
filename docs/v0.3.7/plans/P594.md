# P594 Open GitHub links inside the app: fix

Stream B of batch 2 (P593, P594, P595). Worktree `/home/user/ws-p594`, branch `stream/p594`.

Ask: "Opening GitHub links in the app itself is broken." Paths below are under `apps/kira-space/`
unless noted.

## 1. Where a GitHub link is clicked and routed

In-app route (PR view window, `HostViewService.Open`, `internal/bridge/hostview.go:176`):

- Details tab link row title: `frontend/src/ade/v2/details/AdeDetailsLink.vue:29-34`. Kind
  `changeRequest` calls `useOpenHostView` (`frontend/src/hostview/queries.ts:71-73`, bridge
  `frontend/src/bridge/index.ts:295`); any other kind calls `control.openExternal`. The row's URL is
  the pasted text: task host slot (`linkGroups.ts:68-78`) or stored row (`linkGroups.ts:34-47`).
- Branch panel PR row "View": `frontend/src/ade/v2/panel/AdeBranchPanel.vue:176-179`.
- Main tab PR chip: `frontend/src/ade/v2/panel/AdeMainBranches.vue:49-54`.
- Jira only (not GitHub): `AdeTaskIssueLine.vue:44-51`, `hostview/IssueSidebar.vue:19`.

Browser route (`LinkService.OpenExternal`, `internal/bridge/link.go:22`, `internal/shell/link.go:20`;
never fails silently, `packages/workbench/src/bridge/openExternal.ts:7-18` announces):
`AdeLinkOpenExternal.vue` (P586 button), `AdeTimelineEntry.vue:17-20`, `AdeArtifactList.vue:37`,
`AdeArchivedPanel.vue:113`, `AdeNotesEditor.vue:80`, `useTaskMenu.ts:124`, `AdeBranchPanel.vue:180-183`,
PR view's own links (`hostview/MarkdownBody.vue:21`, `HostViewSidebar.vue:61`).

Two GitHub parsers decide the in-app path, and they disagree:

- Classification, when a link is pasted (`internal/ade/linkclassify.go:151`, `board_writes.go:767-776`)
  and for the host slot's kind (`internal/ade/artifacts.go:173`): `githost.Registry.ParseLink` ->
  GitHub `ParseLink`, `internal/githost/github/provider.go:124-136`. Regex
  `^https://github\.com/([^/\s]+)/([^/\s]+)/(issues|pull)/(\d+)` has no end anchor: any suffix after
  the number is a change request.
- PR view: `HostViewService.Open` -> `Registry.ParseChangeRequestLink` (`githost/registry.go:140`) ->
  GitHub `ParseChangeRequestLink` (`github/detail.go:148-154`) -> `ParseBranchLink`
  (`github/links.go:19-67`). After `/pull/<n>` it allows nothing or exactly one of `files`, `commits`,
  `checks` (`links.go:16`, `links.go:52`). Everything else misses, and `Open` answers bad request
  (`hostview.go:188`, `notViewable`).

The click result is then dropped: `fireAndForget` (`packages/workbench/src/bridge/fireAndForget.ts`)
"logs and shows no UI". The user sees nothing happen.

## 2. Reproduction

No UI here, so reproduced at the parser, the layer the IPC call ends in. Probe test run against
current `github.Provider` (temporary file, deleted):

```
https://github.com/acme/api/pull/12                  view=true  classify=changeRequest
https://github.com/acme/api/pull/12/                 view=false classify=changeRequest
https://github.com/acme/api/pull/12/changes          view=false classify=changeRequest
https://github.com/acme/api/pull/12/files/abc..def   view=false classify=changeRequest
https://github.com/acme/api/pull/12/commits/abc123   view=false classify=changeRequest
https://github.com/acme/api/pull/12/files#diff-1     view=true  classify=changeRequest
```

`/pull/<n>/changes` is the URL of GitHub's current "Files changed" page, so a link copied from the
browser's address bar on that tab, a single-commit page or a range diff, or one with a trailing slash,
renders as a change request title that does nothing on click. Existing tests never cover these:
`github/links_test.go:20-33` only has `/files`, `/commits?x=1#a`; `TestHostViewGitHub`
(`flows/githostflow/hostview_test.go:256`) uses `/pull/7/files`; `TestDetailsOpenExternal` and
`ade-v2-details-open.spec.ts` use the `forge.test` fake host. `go test ./internal/flows/githostflow
-run 'HostView|IssueView'` is green today.

Same parser feeds `linkedChangeRequest` (`internal/ade/review.go:107-123`): a task host link of these
forms also loses the review window's linked PR (Review menu "Comment on PR", approve).

Git history: P586 (v0.3.6, `f16f8c264`) only added `AdeLinkOpenExternal` and touched no routing; the
title click still routes in-app (`AdeDetailsLink.vue:32`). No commit since v0.3.0 touched
`github/links.go` or `hostview.go` routing; the break is the parser gap meeting newer GitHub URLs,
not a regression in this repo. P577, P581, P583 do not touch link routing.

## 3. Ranked candidates

1. Fixed here (most probable). PR links with any path past `/pull/<n>` other than the three tabs
   classify as change requests but the PR view refuses them; refusal is swallowed. Evidence in §1/§2.
2. GitHub Enterprise Server PR links. `ParseLink` hardcodes `github.com` (`provider.go:124`), so a
   GHES PR link files as kind `link` and its title opens the browser, never the PR view, though
   `Open` would accept it (`Claims`, `provider.go:69-79`). Not a dead click. Not fixed here:
   `ParseLink(raw)` has no context for `Claims`, a signature change across three providers and the
   capture flow (`bridge/capture.go`). Separate phase if the user confirms GHES.
3. Timeline artifact entries, archived panel, notes and the stage dialog list open GitHub PR links in
   the browser (`AdeTimelineEntry.vue:17-20` etc.); PR view markdown links too. By design (P586
   kept only the Details title in-app; ARCHITECTURE "Pull request view"). Not a break.

User question that disambiguates: "Which link did you click (Details row, branch PR row, timeline,
or inside the PR window), and what is its URL? Did nothing happen, or did a window open with an
error?" A URL ending past `/pull/<n>` confirms 1; a non-github.com host means 2.

## 4. Design

Backend, `internal/githost/github/links.go` `ParseBranchLink`:

- Drop one trailing empty segment before the length check (`/pull/12/`, `/issues/5/`,
  `/tree/main/`). `tree/` alone still has no ref and misses.
- `pull`: after the number, nothing, or one tab from `pullTabs`, now
  `files`, `commits`, `checks`, `changes`. `files`, `commits`, `changes` may carry further non-empty
  segments (`/files/a..b`, `/commits/<sha>`, `/changes/<sha>`); `checks` may not. Unknown tab still
  misses (`/pull/12/foo` stays refused: no guessing at arbitrary paths).
- `issues`: number then nothing, as today (after the trailing-slash trim).
- Update the doc comment. No change to `ParseLink`, Azure or the fake host.

This makes `ParseChangeRequestLink` (`detail.go:148`), `HostViewService.Open`/`ChangeRequest`,
`linkedChangeRequest` (`review.go:111`), `ResolveHostLink`/`AddHostLink` (`hostlink.go:132`) and
branch classification (`linkclassify.go:156`) accept the same forms. `Open` already stores the
canonical `ChangeRequestURL` as the target (`hostview.go:266`), so the window and its identity
(`hostview.go:154`) are the same for every form: `/pull/12/changes` focuses the `/pull/12` window.

Frontend, a click that the PR view refuses opens the browser instead of nothing:

- `frontend/src/hostview/queries.ts`: add `useOpenChangeRequest()`, a TanStack `useMutation` whose
  `mutationFn(url)` calls `control.hostViewOpen(url)`; on any rejection it logs (`logWarn` from
  `@workbench/bridge/log`, scope `hostView.open`, code and message) and calls
  `control.openExternal(url)` (already announces its own failure). Returns `HostViewOpen | null`.
  Doc comment: change request links only; issue keys keep `useOpenHostView` (a bare Jira key has no
  URL to fall back to).
- Use it in `AdeDetailsLink.vue` (`open`, kind `changeRequest`), `AdeBranchPanel.vue`
  (`viewChangeRequest`) and `AdeMainBranches.vue` (`openPr`). The latter two pass index URLs, which
  parse today; same helper keeps one rule for every PR click. `AdeTaskIssueLine` and `IssueSidebar`
  stay on `useOpenHostView`.
- No new strings: fallback is silent beyond the browser opening; `openExternal` failure already has
  `common.error.openLink.announce`.

Library check: TanStack Query mutation (existing), no new dependency. No Pinia state.
