# P592 Jira: faster loading

Stream C of batch 1 (P590, P591, P592). Worktree `/home/user/ws-p592`, branch `stream/p592`.

Ask: "Jira is still very slow. Consider a more efficient approach." Earlier speed work: v0.2.27 P460
(issue view: saved copy 30 s fresh, 10 min kept with `Stale`, coalesced read, window-open prefetch).
That fixed the issue window only. The task panel issue line, the Details artifacts and the tracked
updates watcher still pay a blocking `acli` spawn per issue. P592 removes those waits; it does not
redo P460.

## 1. Where time goes (code evidence)

Paths below are under `apps/kira-space/` unless noted. Every Jira read is one `acli` process: spawn,
acli's own auth and config load, one HTTPS round trip to Atlassian (`jira/runner.go:21`,
`toolexec.RunIO`). No real Jira is reachable here, and no acli timing is recorded in repo docs
(`docs/PERF.md` has no tracker entry). Plan therefore counts spawns on the critical path; a spawn is
the unit of cost.

1. Issue result cache is a hard 60 s TTL, no stale serve. `internal/issuetracker/jira/client.go:20`
   (`resultOKTTL = 60s`), `client.go:98-107` (`cached` deletes and misses past `until`),
   `client.go:74-96` (miss blocks the caller on a coalesced fetch). One minute after any read, the
   next caller waits for a full `workitem view`.
2. Issue line and Details artifacts both block on that cache. `internal/ade/issuetracker.go:84`
   (`TaskIssue`, 10 s budget), `ade/issuetracker.go:54` (`trackerSource.Artifacts` under
   `artifactSourceTimeout = 5s`, `ade/artifacts.go:26,96`). Frontend shows a skeleton until it
   returns (`frontend/src/ade/v2/panel/AdeTaskIssueLine.vue:28-29,56-58`); a slow acli turns the
   Details row into a timeout gap.
3. Every board push refetches both. `frontend/src/ade/queries.ts:81-85` invalidates
   `artifactsPrefix` and `issuePrefix` on `onAdeTaskBoard`. Past 60 s each push costs a blocking
   spawn per open panel. `useTaskIssue` (`frontend/src/ade/v2/queries.ts:597-603`) has
   `staleTime: 60_000`, matching the backend TTL; switching to a task read over a minute ago always
   waits.
4. Saved issue details are ignored by the Issue path. `jira/detail.go:117-129` (`saveDetail`) copies
   a detail into the Issue cache with the same 60 s TTL, and `detail.go:92-107` keeps the detail
   10 min (`detailKeepFor`, `detail.go:38`). `client.issue` never reads `c.details`; a 9-minute-old
   detail still forces a spawn for the line.
5. Status probe sits on the critical path every 5 min. `jira/status.go:18` (`okTTL = 5m`),
   `status.go:42-68` probes inline; `probe` (`status.go:70-107`) runs `acli --version` then
   `acli jira auth status`, sequentially. Every read goes through `client.ready`
   (`client.go:126-139`). So every 5 min the first read pays 3 sequential spawns.
6. First read per site discovers the Development field with `*all` (`client.go:25,156-170`); on
   overflow it re-reads (`client.go:166-169`). Cold start: probe (2) + discovery (1-2) sequential.
7. Watcher reads one full detail per task. `internal/ade/updates.go:385-427` (`issueObservations`):
   per due task one `IssueDetail` with comments, description, attachments (`detail.go:18-21`,
   heavy, up to the 1 MiB cap), fan-out 2 (`updates.go:31`). `readIssue` (`updates.go:430-442`)
   adds a second read when the saved copy is older than `JiraInterval` (10 min, `updates.go:29`).
   N linked tasks = N heavy spawns every 10 min and on every Refresh (`fresh` forces all,
   `board.go:771`).
8. Watcher reads issues only after all git host reads. `updates.go:200-207`: branch observations,
   then change request observations, then issues, sequentially. At app start (`updates.go:80-88`)
   the Jira warm-up waits behind every `gh`/`az` call.
9. Nothing batches. Each key is its own `workitem view` (`client.go:221-229`). acli offers
   `jira workitem search --jql ... --fields ... --json --limit N`, unused.

Net effect for a user with N live Jira tasks: after app start, each task's line waits for its own
spawn (plus probe and discovery for the first); after 60 s idle, every panel open and every board
push waits again; the watcher spends N heavy spawns per 10 min.

## 2. Options weighed

- Stale-while-revalidate on the Issue cache (and the status probe). Gain: removes the wait from every
  repeat view. Risk: low, in-memory only; mirrors P460's detail pattern. Chosen.
- Batch reads via `workitem search --jql "key in (...)"`. Gain: N spawns become ceil(N/50); warms
  every line in one call. Risk: medium, acli search flags and JSON shape are documentation-only here.
  Contained by a per-key fallback and a backoff. Chosen, scoped to the watcher pass.
- Watcher change detection by `updated`. Gain: steady-state and Refresh passes skip the heavy detail
  read for unchanged issues. Risk: low; relies on Jira bumping `updated` on comment add (it does in
  Jira Cloud). Chosen.
- Issue reads beside host reads in the watcher. Gain: startup warm-up no longer waits on `gh`/`az`.
  Risk: low (disjoint data). Chosen.
- Bounded parallel pool for detail reads (raise fan-out 2). Declined: after batching only changed
  issues need detail reads; acli gives no rate-limit signal (ARCHITECTURE "No breaker"), so more
  concurrency risks throttling for little gain.
- Persistent cache table across restarts. Declined: needs a migration, and the startup batch warms
  every line within one search spawn. The tracked snapshot (`ade_tracked_items`) already persists
  what change detection needs (section 3.4).
- REST through the CLI's own library. Declined: acli is a closed binary, not an importable library;
  Kira code must never read its token (CLAUDE.md "CLI credentials", guard G5 under
  `issuetracker/`). No library path exists that keeps the rule.
- Long-lived acli process. Declined: acli has no server or batch-stdin mode.
- Hover or panel prefetch. Declined: the startup batch plus stale serve already makes the line
  instant; prefetch would add spawns for issues never opened.
- Persisting the Development field id per site. Declined: one discovery spawn per app start, now off
  the UI path (watcher does it in the background).

## 3. Design

### 3.1 Issue cache: stale-while-revalidate (`jira/client.go`)

`Provider.Issue` gains `fresh bool`: `Issue(ctx, ref, fresh) (Issue, error)` in
`internal/issuetracker/issuetracker.go:83`, mirroring `IssueDetails.IssueDetail`. Only Jira implements
`Provider` (grep: `jira/jira.go:83`); callers are `ade/issuetracker.go:54,84`.

`issuetracker.Issue` gains `Stale bool` (a kept copy past the fresh window).

`resultEntry` becomes `{issue, okAt, err, errAt}` (keep last good copy beside the last error).
Constants: `resultOKTTL = 60s` (fresh window, unchanged), `resultErrTTL = 15s` (unchanged), new
`issueKeepFor = 30 * time.Minute`.

Rules for `client.issue(ctx, ref, fresh)`:

- Not fresh, good copy younger than `resultOKTTL` and no newer error: return it.
- Not fresh, error younger than `resultErrTTL` and newer than the copy: return the kept copy with
  `Stale` if one is younger than `issueKeepFor`, else the error. Start no revalidation.
- Not fresh, good copy younger than `issueKeepFor`: return it with `Stale = true`; start one
  background revalidation through the existing singleflight key (`c.sf.DoChan(key, ...)` on
  `context.WithoutCancel`, bounded by `c.bound`), result discarded by this caller.
- Otherwise, or `fresh`: blocking coalesced fetch, as today. On failure, if a good copy younger than
  `issueKeepFor` exists, return it with `Stale = true` and the error both (caller decides).
- `store` on success sets `issue, okAt`, clears `err`. On a stored error kind it sets `err, errAt` and
  keeps `issue, okAt`. `ErrUnavailable`, `ErrUnauthenticated`, `ErrOtherSite` stay unstored.
- `saveDetail` (`detail.go:117-129`) sets `okAt = now` as today.
- `forget` (`client.go:144`) unchanged.

Return contract for the fresh-failure case: `(issue with Stale, err)`. Callers: `TaskIssue` fills
title, status and summary from the copy and sets `Reason`; `trackerSource.Artifacts` keeps its
current error branch (static row plus gap), since it only reads non-fresh.

`detailKeepFor` (`detail.go:38`) rises from 10 min to 30 min, same as `issueKeepFor`, so the issue
window opens from a saved copy for any live task the watcher read in the last 30 min. `Stale` marking
and the frontend's one fresh follow-up (`frontend/src/hostview/queries.ts:60-66`) are unchanged.

### 3.2 Status probe: stale-while-revalidate (`jira/status.go`)

- OK entry younger than `okTTL` (5 min): return (unchanged).
- OK entry younger than new `okStaleFor = 1 * time.Hour`, `refresh` false: return it and start one
  background probe (a `probing bool` under `d.mu` keeps it to one). The background probe runs on
  `context.Background()`; `versionTimeout` and `authTimeout` already bound it. Its result replaces
  the entry, OK or not.
- Not-OK entries, `refresh`, or older entries: blocking probe (unchanged), so a fresh login is still
  noticed within 30 s.
- New `discovery.forget()`: drops the entry. `client.view` and `client.commentList` call it when
  `classify` returns `ErrUnauthenticated`, so a logout found by a read makes the next read re-probe
  inline instead of trusting a stale OK.

Effect: the 3 sequential spawns every 5 min leave the read path.

### 3.3 Batch read via `workitem search` (`jira/batch.go`, new)

New optional role in `internal/issuetracker/issuetracker.go`:

```go
// IssueBatch is optional: one tracker call reads many issues.
type IssueBatch interface {
	// Issues reads refs in as few calls as the tracker allows and refreshes what Issue answers.
	// The result maps Ref.Key to its issue; a key the tracker could not read is absent.
	Issues(ctx context.Context, refs []Ref) (map[string]BatchIssue, error)
}

// BatchIssue is an issue plus the fields a change check needs.
type BatchIssue struct {
	Issue
	Priority  string
	Assignee  string // tracker account id
	UpdatedAt int64  // unix ms; 0 when the tracker did not say
}
```

Jira implementation (`Provider.Issues` delegates to `client.issues`):

1. `ready` once (skip refs whose site differs from the signed-in site).
2. Development field: when unknown and not inside the `noDevTo` window, run one `c.issue(ctx,
   refs[0], true)` first (existing discovery path, `client.go:156-170`).
3. Chunks of `batchMax = 50` keys. Per chunk one call:
   `acli jira workitem search --jql "key in (K1, K2, ...)" --fields summary,status,priority,assignee,updated[,<devID>] --json --limit <n>`
   with `searchTimeout = 20 * time.Second`. Keys come only from `ParseRef`, which accepts only the
   Jira key pattern, so JQL holds no user text; argv never passes a shell.
4. Parse: accept a top-level array or an object with `issues` (shape unverified, so take both). Each
   element goes through existing `parseIssue` (`jira/parse.go:54`) plus `fields.updated`
   (`parseJiraTime`, `detail.go:349`), `fields.priority.name`, `fields.assignee.accountId`, and
   `parseDevSummary` when the dev field is present. Missing dev field keeps the cached summary.
5. Each result is stored into the Issue cache (`okAt = now`) with Ref URL and Site filled as in
   `fetch` (`client.go:183-189`).
6. Chunk failure:
   - `ErrUnauthenticated` or `ErrUnavailable`: return it (caller keeps previous snapshots).
   - `ErrNotFound` (Jira rejects a whole `key in` list when one key does not exist) or
     `ErrOutputTooLarge` or timeout: read that chunk per key through `c.issue(ctx, ref, true)`,
     fan-out `batchFallbackFanOut = 2`; per-key failures leave the key absent.
   - Any other failure (unknown flag, unreadable output): set `noSearchTo = now + noDevTTL`
     (10 min), `slog.Warn` once, read per key as above. While inside that window, skip search
     entirely.
7. `discovery.forget()` on `ErrUnauthenticated`, as in 3.2.

Effect: one spawn per 50 linked issues instead of one per issue; the op log shows one
`workitem search` row (`oplog/toolrunner.go:53-68` derives the kind) instead of N `workitem view`.

### 3.4 Watcher: batch, change check by `updated`, beside host reads (`ade/updates.go`)

- `updates.IssueSnap` (`internal/updates/snapshot.go:25-34`) gains
  `Updated int64 \`json:"updated,omitempty"\``. Version stays 1: old snapshots decode with 0, and
  `diffIssue` (`updates/diff.go:110-122`) ignores it, so no concept fires from it.
- `pass` (`updates.go:159-207`): start `issueObservations` in its own goroutine before
  `branchObservations`; join before the upsert loop. They share only `prev` (read-only) and
  `w.jiraAt` (under `w.mu`).
- `issueObservations`: build the due list exactly as today (`updates.go:390-397`). Group due tasks
  by provider. For a provider implementing `issuetracker.IssueBatch`, call `Issues` once under
  `updatesBatchTimeout = 45 * time.Second`. Then per due task:
  - Batch has the key, the previous snapshot (`prev[...].CurrentJSON`, `updates.DecodeIssue`) has
    `Updated != 0` and equal to `UpdatedAt`: build the snapshot from the previous one, refresh
    `Title`, `Status`, `Priority`, `Assignee` from the batch, `Linked` from `Summary` when
    `Summary.Known` (else keep), keep `Comments` and `Updated`. No detail read. Set `jiraAt`.
  - Else: `readIssue` as today, passing `fresh` only when the pass is fresh; snapshot gains
    `Updated: d.UpdatedAt`.
  - Batch error: fall through to `readIssue` for every due task (today's behavior).
- Same rule for fresh (Refresh) passes: the search is itself a fresh tracker read.

Effect: startup pass = probe (2) + discovery (1) + ceil(N/50) searches, run beside host reads; detail
reads only for issues whose `updated` moved, or snapshots without `Updated` (first pass after
upgrade only). Steady state: 1 search per pass instead of N heavy reads. Every live task's Issue
cache entry is fresh after each pass, so the panel line and Details answer without a spawn.

  goes stale).
- `AdeTaskIssueLine.vue`: no template change. A fresh failure arrives as copy plus `reason`; the
  existing gap row shows the reason under the kept title.

No i18n change.

### 3.6 Expected effect (spawns on the UI path)

- Open the Details tab of a task read 1 to 30 min ago: before 1 blocking spawn (plus 3 when the
  status is past 5 min), after 0; line renders from the copy, one background spawn refreshes it.
- First open after app start: before 1 blocking spawn per task (plus probe and discovery), after 0
  once the startup pass ran (one search for all tasks).
- Board push with the Details tab open: before 1 blocking spawn past 60 s, after 0.
- Watcher, N live linked tasks: before N heavy detail spawns per 10 min and per Refresh, after
  ceil(N/50) light searches plus one detail spawn per changed issue.
- Issue window for a live task: saved copy kept 30 min instead of 10.
