# P593 Database MCP: customizable explain threshold

Ask: explain threshold cannot be customized. Base: `chapter/v0.3.7` at `d959e7ea7`.

## 1. Current behavior

One number exists, app-wide. It is already editable, but in a place nobody looks for it, and no
connection can have its own.

- Leaf: `advanced.expensiveQueryRows`. Go `model.AdvancedSettings.ExpensiveQueryRows`
  (internal/storage/model/settings.go:31-32), default 100,000 (settings.go:242), bounds 1,000 to
  1,000,000,000 (`validateAdvancedSection`, settings.go:394-396). TS mirror
  `advancedSettingsSchema.expensiveQueryRows` (frontend/src/state/settingsDomain.ts:158-164),
  `EXPENSIVE_QUERY_ROWS_RANGE` (settingsDomain.ts:52).
- Unit: estimated rows read, never rows returned, never engine cost (ARCHITECTURE.md:1166,
  model comment settings.go:31). Per kind (`queryplan`):
  - postgres, mysql, mariadb: largest single scan estimate, `maxEstimatedRows(scans)`
    (postgres.go:158, mysql.go:217, mariadb.go:170). Comes from table statistics, ignores LIMIT.
  - clickhouse: sum of `EXPLAIN ESTIMATE` rows over the parts it would read (clickhouse.go:188-206).
    Runs higher than the others for a comparable query.
  - sqlite: no estimate (`HasRowEstimate`, statements.go:65-69). No check.
  - Comparison: at or above (`isOverThreshold`, issues.go:131).
- Editor: Settings, Advanced (`AdvancedPane.vue:133-160`, testid `settings-expensive-query-rows`),
  draft/Save. Settings, Database MCP pane has nothing. A standalone "Takes effect after restart."
  note sits directly above the field (AdvancedPane.vue:131), so the field reads as restart-only. It
  is not: the server reads it fresh.
- Connection MCP tab (`ConnectionMcpTab.vue:200-230`): switch `mcp.auto_explain` ("Check agent
  queries against the row threshold") plus `rowsWho` text showing the number read-only
  (`settingsStore.advanced.expensiveQueryRows`, line 212). Nothing says where to change it.
- Server: `bridge.DbMcpService.explainThreshold` (bridge/dbmcp.go:264-271) reads settings on every
  call, wired as `dbmcp.Config.ExplainThreshold` (dbmcp.go:146). Read sites in `internal/dbmcp`:
  `listConnections` (tools.go:38, 50), `resolveVerdict` (tools.go:545, feeds `rv.threshold` into
  `limitCall`, limits_gate.go:68, and `expensiveQueryLimit.Check`, expensive.go:18-31),
  `explainQuery` (tools.go:859), `planBrowseCall` (browse.go:486). Connection summary is
  re-resolved per call (`resolveEnabled`), so a connection-file edit is live on the next call too.
- Console: `autoExplainCheck` (views/console/state.ts:232) and the Explain action (state.ts:619)
  pass `useSettingsStore().advanced.expensiveQueryRows` to `parseExplainPages`;
  `ExplainResultView.vue:54` prints the same store value in the verdict.
- Deliberate P530 decision (ARCHITECTURE.md:3385): "No second per-connection number, so the console
  warning and the MCP refusal agree."

## 2. Design

Scope: both. Keep the app default, add an optional per-connection override, and make both findable.

Why per connection: a fixed rows number means very different things per database. 100,000 is a tiny
scan on an analytics ClickHouse (whose estimate also sums parts) and a large one on a small
Postgres. One app-wide number forces a choice that is wrong for one of them. Why keep the app
default: most users want one number; the override is opt-in.

Parity with P530 is kept per connection: the override is a connection-level key (sibling of the
console `auto_explain`), not an `mcp.` key. It drives console explain, console auto-explain and
every MCP path for that connection. Console warning and MCP refusal still agree for any given
connection.

### 2.1 Connection file and model

- File key: top-level `explain_threshold_rows` (int). Absent = app default. Allowed: 1,000 to
  1,000,000,000 (same bounds as the app setting). 0 is not written; `ToFile` omits it.
- Go model: `ConnectionFields.ExplainThresholdRows int \`json:"explainThresholdRows"\`` (0 = app
  default). Constants in model/connection.go: `ExplainThresholdRowsMin = 1_000`,
  `ExplainThresholdRowsMax = 1_000_000_000`, `ValidExplainThresholdRows(v int) bool` (0 or within
  bounds). `validateAdvancedSection` (settings.go:394) uses the same two constants instead of its
  literals: one source for both bounds.
- Column: migration `0095_p593_explain_threshold.sql`:
  `ALTER TABLE connections ADD COLUMN explain_threshold_rows INTEGER NOT NULL DEFAULT 0 CHECK (explain_threshold_rows >= 0);`
  First-class column, not `options_json`, for the 0045 reason (a safety limit must not be settable
  by pasting a URI). Regenerate `internal/storage/testdata/schema.sql` and
  `internal/kiraschema/kiraschema_gen.go` (`go test ./apps/kira-space/internal/storage -update`,
  then `-run TestKiraSchemaGenerated -update`).
- `connfiles/file.go`: `File.ExplainThresholdRows int \`json:"explain_threshold_rows,omitempty"\``
  after `ThrottlePerSec`; `Fields()` copies it; `ToFile` writes it when non-zero.
- `connfiles/validate.go`: out of range gives
  `bad("/explain_threshold_rows", "backend.studio.connection.explainThresholdRange.body", nil)`,
  beside the `throttle_per_sec` check.
- `connfiles/connection.schema.json`: property `explain_threshold_rows` (integer, minimum 1000,
  maximum 1000000000, description "Estimated rows read at or above which this connection's explain
  warns and agent queries are refused. Absent uses advanced.expensiveQueryRows."). Update
  `mcp.auto_explain`'s description to say "the connection's threshold".
- `connfiles/projection.go`: `configColumns` and `configArgs` gain the column, after
  `ThrottlePerSec`.
- `storage/repos/connections.go`: `connectionSelectColumns` and `scanConnectionRow` gain it; an
  invalid stored value is coerced to 0 with a `slog.Warn`, same shape as the timeout coercion
  (connections.go:105-107).
- `connections/service.go` `zeroExemptFields` (around line 585): `f.ExplainThresholdRows = 0` plus
  its clause in the comment. Without it, editing the threshold counts as a destination change.
- `datagrip/apply.go`: no change (zero value is the default).
- TS: `packages/shared/domain/connection.ts`: `EXPLAIN_THRESHOLD_ROWS_RANGE = { min: 1_000, max:
  1_000_000_000 } as const` (comment: mirrors model constants), summary field
  `explainThresholdRows: z.number().int().min(0).max(max).refine(v => v === 0 || v >= min).default(0)`,
  and pure `explainThresholdOf(rows: number | undefined, appDefault: number): number` (override when
  > 0, else app default). `settingsDomain.ts:52` becomes
  `export const EXPENSIVE_QUERY_ROWS_RANGE = EXPLAIN_THRESHOLD_ROWS_RANGE;` (one source).
  `packages/shared/domain/connectionConfig.ts` `ConnectionFileModel`: `explain_threshold_rows?: number`.
- Wails bindings: regenerate with `wails3 task common:generate:bindings` (DEV_ENVIRONMENT.md:377);
  never hand-edit `frontend/bindings/.../model/models.ts`.
- Typecheck fallout: object literals typed `ConnectionSummary` (e.g. `NewConnectionDialog.vue:73`,
  `packages/db-fixtures/support/*.ts`) add `explainThresholdRows: 0` if typecheck demands it.

### 2.2 Server

- `internal/dbmcp/expensive.go`: `func (s *Server) thresholdFor(c model.ConnectionSummary) int` returns
  `c.ExplainThresholdRows` when > 0, else `s.cfg.ExplainThreshold()`.
- Replace every `s.cfg.ExplainThreshold()` read with `s.thresholdFor(summary)`: tools.go:545
  (`rv.summary`), tools.go:859 (`summary`, after the approval re-resolve so a mid-wait edit counts),
  browse.go:486 (`rv.summary`), and `listConnections`: drop line 38, compute per connection on line

  effective number). No new wire field.
- No restart and no cache: settings and connection summary are both read per call. Saving the
  connection file updates the projection row; the next call sees it.
- `bridge/dbmcp.go` unchanged (still the app default source).

### 2.3 Console

- state.ts:232 and :619: threshold = `explainThresholdOf(record?.explainThresholdRows,
  settings.advanced.expensiveQueryRows)` where `record` is the tab's connection from
  `useConnectionsStore()` (lookup by `tab.connectionId`). Store nothing new in a store: one pure
  helper plus existing stores.
- `ExplainResultView.vue:54`: print the threshold the verdict was computed with, not the store
  value. Carry it with the plan result: `pushPlanResult(tabId, statement, plan, thresholdRows)`
  stores it beside the plan; `getPlan` returns it; the view reads it. The verdict and its number can
  then never disagree.
