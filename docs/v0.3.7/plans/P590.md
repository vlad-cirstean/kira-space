# P590 plan: no approval prompt when the database connection cannot be established

Ask (user): Kira Studio prompt must not show if the database connection cannot be established.
Acceptance (SPEC): a request against a connection that cannot connect returns the connection error
without raising an approval item. Stream: P590 (batch 1, worktree `stream/p590`).

## 1. Current behavior (evidence)

Every DB approval in `internal/dbmcp` already sits behind a connect step, so a connection that has
never connected and fails its connect gets no prompt. The prompt still shows in three cases.

Existing connect gate:

- `run_query`: `resolveVerdict` (tools.go:515) calls `connectForQuery` (tools.go:547) and refuses a
  non-`connected` state (tools.go:552-555) before `awaitApproval` (tools.go:259, raise at 654).
- `run_query` explain: `explainQuery` connects at tools.go:779-785, raises at tools.go:802.
- `browse_table`: connects at browse.go:403-409, raises via `awaitApproval`/`awaitExemption`
  (browse.go:435, 438).
- Exempted call: `awaitExemption` raises at limits_gate.go:141, after the same `resolveVerdict`.
- `connectForQuery` (access.go:54-59) returns early when `StateOf` says `connected`; otherwise
  `ConnectContext` runs a full connect (pre-connect script included, connections/service.go:662,
  787-795). `connectStateError` (access.go:65) words the failure.

Gaps (prompt raised, connection fails after the human answers):

1. Stale `connected` state. `connectForQuery` trusts `StateOf` (access.go:55). Nothing notices a
   server that went away (DB restarted, container stopped, VPN dropped, tunnel target down): the
   adapter Interface has no liveness method (adapters/adapter.go:33-100), postgres `Acquire` only
   drops a socket pgx already marked closed (postgres/client.go:313-319), mysql only one the driver
   flagged bad (mysqlfamily/client.go:431-435). The approval is raised, then `Execute` fails
   (tools.go:311-313). This is the case a user hits: a never-connected failing connection already
   gets no prompt.
2. Read lane opened after approval. Mode `read` (and `masked`, and explain) runs on the read lane
   through `Router.ExecuteRead` (adapterhost/readlane.go:131-150). The lane opens lazily on first use
   (`acquireLane` readlane.go:153, `openLane` readlane.go:167-197) inside `executeAndRender`
   (tools.go:311), after the approval. A lane that cannot open (server gone, read-only session
   refused, lane idle-closed after 10 minutes and server now down) fails after the prompt. Exception:
   `planForCall` (tools.go:634) opens the lane for its EXPLAIN when `mcp_auto_explain` is on and the
   class is read, so that subset already fails before the prompt (via `checkLimits` fail-closed).
3. Stale open lane: an open lane on a dead server, same as gap 1.

Approval subjects and whether they apply:

| Subject | Raised at | Needs DB connection | In scope |
|---|---|---|---|
| `db.query` (run_query, browse_table, explain) | tools.go:654, tools.go:802 | yes | yes |
| `db.exemption` | limits_gate.go:141 | yes | yes |
| `db.response` | tools.go:399 | statement already ran on a live connection | no |
| `script.run` | script_tools.go:261 | no (a script, not a connection) | no |
| `api.request` | api_tools.go:130 | no (HTTP) | no |
| `kube.read` | kube_tools.go:157 | no (Kubernetes cluster, not a DB connection) | no |

Both servers share the handlers: the external server and the session pool build `dbmcp.Config` from
one `serverConfig` (bridge/dbmcp.go:129-153, `Query: s.Deps.Router`, `Conns: s.Deps.Connections`;
sessions.go:150-183). One change covers both.

## 2. Design

"Cannot be established" means any of:

- the connect attempt ends in a non-`connected` state (existing gate, unchanged);
- the read lane cannot open (mode read, masked, explain on a lane kind);
- the connection the statement would run on does not answer a ping (stale state).

Rule: right before raising a `db.query` or `db.exemption` approval, probe the connection the
statement will run on. A failed probe returns the error and raises nothing. Calls with verdict
`allow` are not probed: no prompt exists to suppress, and execution reports the failure itself.

### 2.1 Adapter liveness: optional `adapters.Pinger`

New file `apps/kira-space/internal/adapters/ping.go`:

```go
// Pinger is the optional liveness check: one cheap round trip on the connection Execute uses.
// It never resolves secrets and never dials beyond what the adapter's own pool already does.
type Pinger interface {
	Ping(ctx context.Context) error
}
```

Optional, type-asserted like `StatementClassifier` and `Discoverer`; no change to `Adapter`. An
unconnected adapter returns `adapters.New(CodeEngineDown, "not connected", nil)`. Errors go through
each adapter's own `mapError`, so codes are `CodeConnect`, `CodeEngineDown`, `CodeTimeout`,
`CodeAuth` or `CodeCancelled` as for any op.

Implementations (each on the kind's existing handle, no new connection):

- postgres: `connSet.Primary(ctx)`, `conn.Ping(ctx)`, release. A failed ping leaves pgx's conn closed,
  so the next `Acquire` redials (client.go:315).
- mysqlfamily (mysql, mariadb): `connSet.Primary(ctx)`, `entry.PingContext(ctx)`, release.
- sqlite: `assertFileExists(file)` then `db.PingContext(ctx)`. An open handle survives an unlinked
  file, so the file check is what makes "file gone" fail.
- clickhouse: the connected handle's `Ping(ctx)`.
- mongo: `client.Ping(ctx, readpref.Primary())`.
- redis: `client.Ping(ctx).Err()` (same call Connect uses, redis/client.go:197).
- kibana: `GET /api/status` through `h.request` (Connect's first request, kibana/adapter.go:82).

Kafka, S3, SQS: no `run_query` or `browse_table` approval reaches them (no SQL caps); no Pinger.

### 2.2 Router probe

New file `apps/kira-space/internal/adapterhost/probe.go`:

```go
// ProbeError is a failed probe. Primary is true when the connection's main adapter itself failed.
type ProbeError struct {
	Primary bool
	Err     error
}

func (r *Router) Probe(ctx context.Context, connectionID string, lane bool) error
```

Constants: `probeTimeout = 10 * time.Second` (matches postgres `connectTimeout`), `confirmTimeout =
5 * time.Second`.

Steps:

1. `requireLiveAdapter(connectionID)`; failure returns `ProbeError{Primary: true}`.
2. `lane` and `laneKinds[cfg.Kind]` (cfg from `r.lanes.config`):
   - Check out the lane under `r.lanes.open` lock. Missing: `openLane` (the open is the probe; the
     lane then serves `ExecuteRead`, so no second connect). Present and used only by this probe:
     `Ping` it. Present and busy (`inflight > 1`): skip the ping, an op is using it.
   - Ping failure on an existing lane: discard and tear it down (`discard`, `teardownLane`), then
     open once more (one fresh dial; heals a lane whose socket died on a server restart).
   - Release with `r.lanes.release` so the idle timer arms as today.
   - Lane failure with a connection-class code (`CodeConnect`, `CodeEngineDown`, `CodeTimeout`,
     `CodeAuth`): confirm on the primary (step 3, `confirmTimeout`). Primary fails too: return
     `ProbeError{Primary: true, Err: primaryErr}`. Else `ProbeError{Primary: false, Err: laneErr}`.
     Other codes: `ProbeError{Primary: false, Err: laneErr}`.
3. Primary (`!lane`, or a kind without a lane):
   - Adapter without `Pinger`: return nil (state is the only evidence, as today).
   - Busy primary (any running op with this connection id and no `OpSpec.Adapter`, new
     `Host.busyOnPrimary(connectionID) bool` over `h.running`): return nil. The op in flight shows the
     connection in use, the statement would queue behind it, and a ping would wait on the pinned
     connection's lock (postgres/mysql `guard.Lock`).
   - Ping; on failure ping once more (pg/mysql redial a socket the first ping found dead). Second
     failure returns `ProbeError{Primary: true, Err}`.

The ping runs outside `RunOp`: no op-log row, no throttle slot (one round trip per approval-bound
call). The lane open keeps its existing `RunOp` "connect" op labelled MCP (readlane.go:174). Probe
never calls `connections.Service`, so no secret resolve, no keychain access, no pre-connect script
run.

### 2.3 Connection marked lost

A failed primary probe means the `connected` state is false. Leaving it would keep the tree showing
`connected` and probe-fail every later call. New `connections.Service.MarkLost(id, detail string)`
(service.go, beside `Disconnect` at 874):

- No-op unless `states[id].Status == "connected"` and no attempt is in flight or tearing down (a
  concurrent connect or disconnect wins).
- Same teardown as `Disconnect` (`beginTeardown`, `Preconnect.Stop`, `Backend.Disconnect`), then
  `emitState` with `Status: "error"` and message `i18n.T("backend.studio.connection.lost.error",
  {"detail": detail})`.

The next MCP call then reconnects through the existing `connectForQuery` path: a server that came
back connects (one connect, pre-connect script included, exactly as a user click); one still down
fails the connect and raises nothing.

### 2.4 dbmcp gate

New file `apps/kira-space/internal/dbmcp/reach.go`:

```go
// reachProber is the optional QueryRunner half that probes a connection (*adapterhost.Router).
type reachProber interface {
	Probe(ctx context.Context, connectionID string, lane bool) error
}

// lostMarker is the optional ConnectionsReader half that drops a connection found unreachable.
type lostMarker interface {
	MarkLost(connectionID, detail string)
}

// ensureReachable probes the connection the statement will run on, right before an approval is raised.
func (s *Server) ensureReachable(ctx context.Context, summary model.ConnectionSummary, mode string) (res *mcp.CallToolResult, out any, err error, done bool)
```

- `lane := mode == modeRead || mode == modeMasked`; explain passes `modeRead`.
- `s.cfg.Query` without `reachProber` (unit-test fakes): no-op, existing tests unchanged.
- Failure: if `ProbeError.Primary`, the code is connection-class and `ctx.Err() == nil` (a client
  that went away proves nothing), call `MarkLost` when `s.cfg.Conns` implements `lostMarker`.
- Result text (app-authored, no row data, so unmasked like `connectStateError`):
  - primary: `connection %q is not reachable: <err>. Nothing ran and no approval was asked.`
  - lane: `connection %q could not open its read-only session: <err>. Nothing ran and no approval was asked.`
  Use `adapters` error message (`errorMessage`-style: the `*adapters.Error` message, else
  `err.Error()`).

Call sites (one line each):

- `awaitApproval` (tools.go:649): after the `verdict != "prompt"` return, before `RequestChoice`.
  Covers `run_query` and `browse_table`.
- `awaitExemption` (limits_gate.go:140): first statement. An exempted call always asks.
- `explainQuery` prompt branch (tools.go:801): before `Approvals.Request`.

Order stays: every existing gate (mode, tables, column review, exemption claim, EXPLAIN, limits) runs
first, so a refused statement spends no probe. The exemption id is claimed before the probe; a probe
failure spends it, same as any other refusal after the claim (limits_gate.go:33-35 rule).

### 2.5 Not done (scope kept out)

- `kube.read`, `script.run`, `api.request`, `db.response`: no DB connection to establish (table §1).
- No probe on `allow` verdicts: a failure there already returns its error with no prompt.
- No change to the approval broker, items, payloads or UI components.

### 4.1 Flow test (backend half)

`newFixture` (sqlite, write prompt) with `flowharness.WithWindowFocus()` and a `w1` window, like

- `f.queueLen(t) == 0` and `f.app.Focus.Keys()` empty (no item, no window raise);
- `Connections.StateOf(connID).Status == "error"` with the lost message (primary failure);
- restore the file before the next subtest.

Entries:

1. `run_query` mode write (verdict prompt, primary probe).
2. `run_query` mode read with read set to prompt (lane open fails; primary confirm fails).
3. `run_query` explain with read prompt (lane path).

5. Exempted call: `newExemptionFixture` limit refusal gives an id, file renamed, retry with
   `exemption` (`runQueryWithExemption`); no `db.exemption` item (`assertNoItem`).
6. Never connected: file renamed before any connect; write call returns `connect failed`, no item
   (regression guard for the existing gate).
7. Recovery: after case 1, restore the file and repeat the write call: the connection reconnects

- `ApprovalsService.List`: `[]`;
