## 1. Current model, plain

What is masked: values of a column whose **name** matches a rule, ignoring case. A rule masks that
name in every table of the connection. The rule's `table` field has no effect on masking:
`maskrules.Service.MaskSetFor` (`internal/maskrules/service.go:164`) folds rules by lowercased column
name only; two rules on one name fold to the stricter (`mask.Stricter`).

Who sees masked values:

- The AI agent, through Kira's database MCP tools only (`run_query`, `browse_table`, held result
  review). Security boundary: `internal/dbmcp/render.go`. Masked columns also can't be filtered
  (only is-empty) or sorted in `browse_table`, and an alias or expression over one is refused.
- The user, only when they turn on the grid toolbar's masking preview (`views/grid/maskPreview.ts`).
  Normal grid, console and editors show real values. Stored data never changes.

What a masked value looks like (`internal/mask/mask.go`, TS twin `packages/shared/domain/mask.ts`):
six kinds. name keeps initials and word lengths, email keeps domain and first letter, text keeps a
bucketed length, number keeps order of magnitude, date keeps the year, redact keeps nothing. "Keep
initials/domain/year" (`keep_hint`) toggles the hint. "Correlate" appends a tag (`#K3F9QZ`): HMAC of
the real value under a per-connection key, so equal values tag equal across tables and joins work.
number never tags.

Who decides:

- Rules: the user. Two entry points write the same `masks:` list in the connection file: Privacy tab
  (draft, saved with the dialog) and grid header menu "Mark column as sensitive"
  (`views/grid/menu.ts:580`, immediate `MaskRulesService.Upsert`).
- Column review (P534, optional, off by default, `mask_review:` key): a safety net for columns nobody
  thought about. When on, a column that no rule covers and that is not in the reviewed list is
  **withheld**: dropped from `run_query`/`browse_table` results (name told to agent, never values),
  and a "masking" prompt asks the user to review. Only postgres, mysql, mariadb, clickhouse, sqlite.
  Checked on connect, Refresh, after MCP writes, and at most 30 s stale. Withholding matches by
  name: a pending `log.note` also withholds a reviewed `users.note`.

Controls on the Privacy tab today (`frontend/src/studio/project/connection/ConnectionPrivacyTab.vue`,
`ConnectionMaskReview.vue`), top to bottom:

1. Intro line (`cd.privacy.intro.description`).
2. Enforcement paragraph (`cd.mcp.enforceMasking.body`): name match, table ignored, aliases refused,
   best effort.
3. Rule list: `table.column`, kind select, keep-hint checkbox (name/email/date), Correlate checkbox,
   remove. Empty: "No masking rules yet."
4. Add row: table input (placeholder `*`), column input, kind select, Add; kind explanation below.
5. Column review: title, checkbox "Withhold new columns until reviewed" (turning on marks all current
   columns reviewed), three enforcement paragraphs, status + refresh, search, filter, "Confirm all as
   reviewed", list (tick, ref, type, state badge Masked/Marked reviewed/Needs review, Mask button).
6. "Regenerate correlation key" (or save-first hint), key error, insecure-keychain warning.

## 2. Why it confuses (findings)

1. **Model inconsistency (real bug).** The table field is asked for and shown, but masking ignores
   it. Column review honours it (`maskreview.Covered`, `internal/maskreview/diff.go:33`; TS
   `maskRuleFor`, `packages/shared/domain/maskReview.ts:43`): a rule covers only when its table is `*`
   or equals the bare table name. The grid menu writes the qualified name (`public.users`,
   `qualifiedNameForPath`), which never equals the bare name. Result: a column masked from the grid
   shows "Needs review" in the Privacy tab, stays pending, opens the prompt, and is withheld from the
   agent even though its rule masks it. The UI says one thing, the MCP does another.
2. The review "Mask" button only prefills the add row far above, with kind redact; nothing is added
   until the user scrolls up and clicks Add.
3. "Correlate" is unexplained; the key that drives it sits at the bottom, detached.
4. Four dense enforcement paragraphs (internals: 30 s, aliases, exemptions) sit before any control.
5. No statement of the model: who sees what, that the user's own views are unmasked, that the tab
   does nothing while MCP is off.
6. Review vocabulary: "Withhold new columns until reviewed" plus "Marks every current column as
   reviewed"; a disabled tick for masked rows; "Marked reviewed" vs "Masked".
7. No preview of what a rule produces.

## 3. Decisions

- D1. One matching rule everywhere: **a rule matches by column name in every table.** Review coverage
  follows masking (name only). Masking is not made table-aware: result columns carry no reliable
  source table (aliases, joins, views), which is why render matches by name. Safety: a column covered
  by name is masked by that same rule, never returned raw.
- D2. The Privacy tab drops the table input. File key `masks[].table` stays valid (old files, hand
  edits); a rule with a table other than `*` shows a "Table ignored" badge with tooltip. No migration,
  no file rewrite.
- D3. Grid menu writes `*` for a new rule; finds an existing rule by name only (first match), so
  re-marking edits it in place.
- D4. Review row actions add directly: "Allow" (= reviewed) and "Mask as" dropdown (adds a rule to
  the draft with that kind). No prefill.
- D5. Rename for meaning, keep file keys and IPC unchanged: Correlate → "Matching tag"; Column review
  → "New columns"; reviewed → "Allowed"; pending (review on) → "Hidden from agent"; pending (review
  off) → "Not masked".
- D6. Example of effect per rule, computed client-side with `applyVisible` from
  `@shared/domain/mask` on a fixed sample per kind (catalog `.example` keys), plus a sample tag when
  matching tag is on. No key needed, no IPC.
- D7. Enforcement detail moves into one collapsed "How masking is enforced" section (shadcn
  `Collapsible`), reworded to four short bullets.
- D8. Backend change is limited to D1 (Covered) plus one validation message (§5.3). No schema,
  migration or bridge change.

## 10. Open questions for the user (defaults applied)

1. Name-only matching (D1): a rule now covers a column of that name in every table, also for column
   review. Default: yes, it is what masking already did. Alternative (table-aware masking) is not
   reliable for computed results.
2. Old rules with a table (D2): shown with a "Table ignored" badge, file untouched. Default: no
   automatic cleanup.
3. Wording: "Matching tag" for Correlate, "New columns" / "Allowed" / "Hidden from agent" for column
   review. Default: as listed; file keys (`correlate`, `mask_review`) unchanged.
