# P698: Toasts: drop operation progress and success toasts the ops panel and task already show

User request: "When deleting worktrees (and in some other circumstances) there is a persistent toast and
then it says success. Drop it. I can see the progress in the ops panel and in the task itself. The toast
is irrelevant."

Frontend only. No IPC, Go or bridge change, so the IPC-split test rule has no backend half: the adeflow
flow tests these UI specs pair with (`TestTaskReposAndBranches`, `TestArchiveRisk`,
`TestAgentBranchRequest`) stay as they are. The updated UI specs are the proof. Line numbers are from
worktree head `973964eb7`; find symbols by name if they moved.

  mirrors backend agent ops (`track`/`settle`, fed by `adeOpMirror.ts` from the op log). `TOAST_POLICY`

  times out, flips to success by id: the user's "persistent toast then success"); `slow` for the 17 other
  client kinds (loading toast past `TIMING.slowOp` 2 s via `slowNotice`, success only if loading showed);
  `never` for backend kinds, whose `settle` (293-300) toasts success or error past 2 s.
- Progress is already on screen without the toast: `ops` map drives `AdeOpStatus.vue` (Badge + Spinner +
  `opLoadingText`, `data-testid="ade-op-status"`), rendered by `AdeTaskCard`, `AdeBranchRow`,
  `AdeSessionStrip`, `AdeSessionsRow`, `AdeWorkflowReviewPanel` (10 call sites), per task, branch or

  closed, lease badge) and the op's Operations panel row.
- Failure: `fail()` (232-236) writes `ui.actionError[taskId]` when the op has a task. That Alert renders
  only in `AdeTaskPanel`, `AdeBranchPanel`, `AdeArchivedPanel` (the open task), and lease and attach ops
  without a task have no other surface. So the error toast stays for every client op: no op loses its
  only failure signal.
- `slowNotice` (`state/slowNotice.ts`) has one caller (`adeOps.ts` 249) plus its unit spec
  `tests/unit/ade-v2-slow-notice.spec.ts`. Both die. `TIMING.slowOp` stays: `settle` and
  `refusalTiming.ts` `timedCall` read it.
- `opDoneText` (147-202) is the only reader of the 25 `space.ade.ops.<kind>.status` keys and of
  `AdeOp.name` ("named in the toast", 46-47). Both die. `opLoadingText` stays (`AdeOpStatus`).
- Corner chips are not progress or success toasts: `ApprovalsToast`, `PromptsToast` (`PendingToast`: work
  waiting for the user, Review/Show) and `ConfigSyncToast` (only signal of a new shared-config commit,
  Review/Dismiss). Copy feedback is `CopyIconButton`'s icon swap, not a toast. No success toast is the
  only feedback of an action.

## Rule applied

- D1: drop a loading or success toast whose op shows progress as a chip (task, branch, session) or
  pending button, and its result on the board and in the Operations panel.
- K1: keep every error toast. Task ops also set the task action error, but that shows only in the open
  task's panel; lease and attach-without-task ops have nothing else.
- K2: keep corner chips (actionable waits, not results).

   - `run` becomes:

     ```ts
     /** Starts `fn`; resolves true on success. A second run of a live id is ignored (resolves false); `OpAborted` ends it silently (false). A failure toasts its error. */
     async function run(input: AdeOpInput, fn: () => Promise<unknown>): Promise<boolean> {
       if (ops.has(input.id)) return false;
       const op: AdeOp = { ...input, source: 'client' };
       ops.set(op.id, op);
       if (op.taskId) delete ui.actionError[op.taskId];
       try {
         await fn();
       } catch (err) {
         ops.delete(op.id);
         if (err instanceof OpAborted) return false;
         toast.error(fail(op, err), { id: op.id });
         return false;
       }
       ops.delete(op.id);
       return true;
     }
     ```
