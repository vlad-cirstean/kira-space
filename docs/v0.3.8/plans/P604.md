## 1. ClickHouse: a `readonly=1` profile user cannot connect

### 1.1 Root cause (measured)

Every request (`query.go:61` `buildURL`) sends `fixedSettings` (`client.go:32`) as URL settings, plus
`readonly=2` when `Handle.ReadOnly` (lanes, read-only connections), plus per-call extras
(`cancel_http_readonly_queries_on_client_close=1` on console reads, `console.go:104`;
`max_execution_time`/`timeout_overflow_mode` when a statement timeout applies, `console.go:164`).

ClickHouse `readonly=1` refuses any setting change, but accepts a setting sent with the value it
already has. Measured per parameter on 26.3.58, one request each, profile `readonly=1` user (ro1)
and profile `readonly=2` user (ro2):

| URL parameter | ro1 | ro2 |
|---|---|---|
| `database`, `query_id`, `param_*`, `default_format=JSONCompactStringsEachRowWithNamesAndTypes` | ok (HTTP params, not settings) | ok |
| `output_format_json_quote_64bit_integers=1` | 164 READONLY | ok |
| `output_format_json_validate_utf8=1` | 164 READONLY | ok |
| `show_table_uuid_in_table_create_query_if_not_nil=0` | ok (equals default) | ok |
| `date_time_output_format=simple` | ok (equals default) | ok |
| `readonly=2` | 164 `Cannot modify 'readonly' setting` | ok |
| `readonly=1` | ok | 164 |
| `cancel_http_readonly_queries_on_client_close=1` | 164 | ok |
| `max_execution_time=5`, `max_block_size` (via `SETTINGS`) | 164 | ok |

So H1 (P602) holds in a wider form: not only lane reads but every request, Connect's probe first,
fails for a `readonly=1` profile. `default_format` is safe (HTTP handler sets it on the context).

Further facts, measured with ro1:

- `SELECT toString(getSetting('readonly'))` returns `1` (ro1), `2` (ro2), `0` (normal user over POST).
- Writes are refused by the profile itself: `INSERT` with an INSERT grant gives
  `Code: 164 ... Cannot execute query in readonly mode. (READONLY)`. ro2 likewise. So the lane's
  write refusal holds without sending `readonly=2`.
- `KILL QUERY WHERE query_id = '<own id>' SYNC` works for ro1 (HTTP 200, the query ends with
  `QUERY_WAS_CANCELLED`). Cancel and the host timeout backstop stay functional.
- `EXPLAIN PLAN json = 1, indexes = 1, description = 1 <sql>` and `EXPLAIN ESTIMATE <sql>` work for
  ro1 (EXPLAIN options are not settings).
- Without `cancel_http_readonly_queries_on_client_close`, a streaming read whose client hangs up
  stops server-side anyway (write to the closed socket fails; `system.processes` empty 2 s later).
  A non-streaming aggregate keeps running until done or killed. The console cap stops only after a
  row arrives (streaming), so the cap path loses nothing that matters; Cancel uses KILL QUERY.
- `FORMAT JSON` without `output_format_json_quote_64bit_integers` renders UInt64 as a bare number
  (`{"id":18446744073709551615}`); `FORMAT JSONStrings` quotes it but renders NULL as `"ᴺᵁᴸᴸ"`.
- Without `output_format_json_validate_utf8`, invalid UTF-8 arrives raw (`"a\xffb"`); with it the
  server emits `"a�b"`. Go's `encoding/json` replaces invalid UTF-8 with U+FFFD on decode, so
  every adapter path (all decode through `json.Unmarshal`) ends with the same text either way.

### 1.2 Decision

Two parts. Defaults applied are marked.

1. **Drop two settings the adapter does not need (all users).**
   - `output_format_json_quote_64bit_integers`: catalog decode becomes number-tolerant instead
     (below). Only `RunCatalogQuery` (`FORMAT JSON`) depended on it; the streamed
     `JSONCompactStringsEachRowWithNamesAndTypes` path never did.
   - `output_format_json_validate_utf8`: redundant with Go's decode (measured above).
   Rejected alternative: `toString(...)` in each catalog SQL. Fragile (an alias `position` shadows
   the column in `ORDER BY position`, sorting `"10"` before `"2"`), and every future catalog query
   would need to remember it.
2. **Detect the profile's `readonly` at Connect and send only what it permits.**
   - `Handle` gains `profileReadonly` (atomic, values 0/1/2) and a `probed` flag. Until probed,
     `buildURL` sends no settings at all (only `database`, `query_id`, `default_format`, `param_*`).
   - Connect's probe (`adapter.go:67`) adds `toString(getSetting('readonly')) AS readonly` to its
     existing single query; nothing else changes about the probe. Store the value on the handle
     before Connect returns. Parse failure of that cell: `adapters.Contract(...)`, Disconnect,
     return the error (same posture as "connect probe returned no rows").
   - `buildURL` policy after the probe:
     - `profileReadonly == 0`: as today minus the two dropped settings (`show_table_uuid...=0`,
       `date_time_output_format=simple`, `readonly=2` when `readOnly`, per-call extras).
     - `profileReadonly == 2`: same, but never `readonly` (sticky 2 already; sending it is
       pointless and `readonly=1` would be refused).
     - `profileReadonly == 1` (locked): no settings at all, including per-call extras. Fixed
       settings with default values would pass today, but a profile that changes them (with
       `readonly=1`) would then fail every request; sending nothing is the only rule that always
       holds. Consequence: `date_time_output_format` and UUID display follow the profile.
   - Locked handle sets `noEngineTimeout` at Connect so `withEngineTimeout` (`console.go:185`) never
     sends the timeout settings; statement timeouts on such a connection are enforced by the host
     backstop only (KILL QUERY works). Log once at Connect: `clickhouse: profile is readonly=1;
     engine timeout and per-request settings disabled, app timer enforces limits` (`a.deps.Log`,
     `warn`). The existing reactive 164/452 retry stays for `readonly=0` profiles with constraints.
   - Cancel (`adapter.go:365`) is unchanged: it already sends `readOnly=false` and no settings;
     under the new policy it still sends none for a locked handle.
   - Enforcement label: `list_connections` stays `session` for clickhouse. With `readonly=1` or
     `readonly=2` profiles the engine still refuses writes (measured), so the label stays true.

Rejected: reactive retry on 164 for every request. The failure would hit Connect first, and per
request there is no safe point to know which setting to drop without parsing error text for each.

## 2. MySQL 9.7: composed EXPLAIN yields no row estimate

### 2.1 Root cause (measured)

`mysql:9.7.2`: `SELECT @@explain_json_format_version` = `2` (8.0 has no such variable; 8.4
defaults to 1). `EXPLAIN FORMAT=JSON` then returns the iterator-tree schema
(`"json_schema_version": "2.0"`), root key `query_plan`, not `query_block`:

```json
{"query": "...", "query_plan": {"operation": "Table scan on b", "table_name": "b",
 "access_type": "table", "schema_name": "t", "used_columns": ["id","v"],
 "estimated_rows": 1000.0, "estimated_total_cost": 101.0},
 "query_type": "select", "json_schema_version": "2.0"}
```

Point read by primary key: `{"operation": "Rows fetched before execution", "access_type":
"rows_fetched_before_execution", "estimated_rows": 1.0, "estimated_total_cost": 0.0, ...}`.
Joins nest children under `inputs` (Filter, Nested loop inner join, Aggregate using temporary table,
Sort, index lookup with `index_name`, `lookup_condition`, `condition`). Non-leaf wrappers such as
`Sort` and `Table scan on <temporary>` may carry no `estimated_rows`.

`queryplan/mysql.go:190` `parseMysqlPlan` reads only `query_block`, so on 9.7 it finds no table and
`EstimatedRowsRead` is nil. The parser is wrong for 9.7, not the P602 scenario. The TS console
parser (`frontend/src/studio/views/console/planParsers/mysql.ts`) has the same gap, so console
Explain on 9.7 shows an empty plan too. The MCP expensive-query check (`dbmcp/expensive.go`) on 9.7
therefore passes every query as "no estimate".

### 2.2 Decision

Parse schema 2.0 in both parsers (Go mirrors TS; parity fixtures pin both). Rejected:
`SET explain_json_format_version = 1` per session (unknown variable on 8.0, changes the user's own
console session, v1 is the legacy direction) and a `SET_VAR` hint injected into the user's SQL
(rewrites agent SQL, `WITH` statements complicate placement).

v2 mapping (both languages, identical):

- Detection: top-level object has `query_plan` (object) → v2; else the existing v1 path, unchanged.
- Node from a v2 object `n`:
  - `label` = `n.operation` (server text, verbatim) or `"?"` when absent.
  - `relation` = `n.table_name` when present.
  - `detail` = `n.condition` ?? `n.lookup_condition`.
  - `estimatedRows` = `n.estimated_rows` when a number.
  - `cost` = `{ total: n.estimated_total_cost }` when a number.
  - `metrics` = every other key except the typed set {`operation`, `table_name`, `condition`,
    `lookup_condition`, `estimated_rows`, `estimated_total_cost`, `inputs`}, stringified the same
    way v1 untyped metrics are (arrays joined with `, `), sorted by label (Go already sorts; TS
    order follows the existing fixture convention, check `mysql-*.expected.json`).
  - `children` = `n.inputs` mapped recursively.
  - Issues: `full-scan` (existing i18n key) when `access_type == "table"` and `table_name` is
    present and does not start with `<` (a `<temporary>` scan is not a base-table scan);
    `filesort` (existing table-less key `studio.console.plan.issue.filesort.description` /
    Go equivalent) when `access_type == "sort"`; `temp-table` (existing key, relation `?` when no
    table) when `access_type` is `temp_table_aggregate` or `materialize`. Nothing else: v1 flags
    only these plus `unused-index`, which v2 cannot express (no `possible_keys`).
  - Scans: every leaf (no `inputs` or empty) with a numeric `estimated_rows` is a scan;
    `pushWideScanIssue` runs on those, `estimatedRowsRead` = max (existing `maxEstimatedRows`).
    Same meaning as v1's per-table `rows_examined_per_scan` max: leaves are the access paths.
- Root: synthetic Query root (existing label key), one child = node(`query_plan`), `cost` and
  `nativeCost` (`mysql-cost`) from `query_plan.estimated_total_cost` when a number, else none.
- `Raw` = verbatim text; `kind` = `mysql`.
