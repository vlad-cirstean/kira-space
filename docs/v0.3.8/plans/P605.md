## Failure 1: `TestHermeticSession/hermetic`: user MCP server in hermetic list (the SPEC title)

- Output: `hermetic_test.go:103: MCP servers = [user-probe proj-probe kira-space kira-studio-session], want
  proj-probe and kira-space, not user-probe`.
- Root cause: test, not product. P588 flipped `agent.hermetic` default to off (`settingsDomain.ts`
  `hermetic: false`, Go `DefaultAgentSettings`). The subtest calls `f.SetHermetic(t, false)` only for the
  control case and never turns hermetic on, so the "hermetic" case runs non-hermetic and loads
  `~/.claude.json` user servers. Same bug d959e7ea7 fixed in `smartscript_test.go` (v0.3.7). The product
  path is sound: `settingSources` gives `project,local` under `Hermetic` (`internal/harness/claude/headless.go:47`),
  hermetic env added in `RunHeadless`.
- Proof: with the one-line fix below applied locally, `go test -run 'TestHermeticSession/hermetic'` passed (43 s).
- Fix: `apps/kira-space/tests/claude/hermetic_test.go:80-82`, replace
  ```go
  			if !hermetic {
  				f.SetHermetic(t, false)
  			}
  ```
  with `f.SetHermetic(t, hermetic) // off by default since P588`.
- Also grep the module for other subtests that assume hermetic on without setting it
  (`grep -n "hermetic" apps/kira-space/tests/claude/*_test.go`). Fix any found the same way. The full run showed none failing.

## Failure 2: `TestDbMcpBrowseThroughClaude`: agent refuses to browse

- Output: `dbmcp_test.go:170: no browse_table tool use in the stream`. Fails about 2 runs in 3 alone.
- Stream of failing runs (captured with a temporary dump, reverted): haiku calls `list_connections` before
  loading any other tool schema (CLI defers MCP tool schemas behind ToolSearch). The payload says
  `permissions.read: deny`, `access.read: {allowed:false, reason:"permission denied"}`, `access.summary:
  "none"`. Haiku answers "read access denied, I didn't try to read through another route, since that
  would get around the connection's policy". It never sees `browse_table`'s description ("Needs the
  connection's masked access"). In the passing run it loaded all schemas via ToolSearch first, then browsed.
- Root cause: product. The connection allows masked reads (`access.masked.allowed: true`), but nothing
  in the read-denied answer tells the agent so. `summary` "none" and reason "permission denied" read as
  "no reading at all". The run_query refusal already carries this hint (`gateMode`, `tools.go:593`:
  "Rows can still be read with browse_table (masked)"). `list_connections` lacks it.
- Fix (one place, `accessOf`, `apps/kira-space/internal/dbmcp/permissions.go:213-252`): after `a.Masked` is set,
  when `!a.Read.Allowed && a.Read.Reason == "permission denied" && a.Masked.Allowed`, set
  `a.Read.Reason = "permission denied; read rows with browse_table (access.masked)"`. Keep `Summary`
  unchanged: it lists run_query modes only and is mirrored by `accessSummaryOf` in
  `packages/shared/domain/dbmcp.ts` (UI). Add a short comment saying why: the agent reads the payload
  before any tool schema.
- Blast radius checked: no contract fixture under `apps/*/tests/contract/` has read denied with masked
  allowed (script scan). The only Go assertion on a reason string is `dbmcpflow/mode_test.go:202`
  (`DDL.Reason`), which is unaffected. `gateMode` and `recheckAfterApproval` refusals use `Summary`, not
  `Read.Reason`. The frontend does not render `access.read.reason`.
- Docs: `docs/ARCHITECTURE.md` "Masked browse (P535)" bullet on `list_connections` (about line 3452):
  add that `access.read.reason` names `browse_table` when read is denied and masked allowed.
- Escalation, only if verification below still fails: also add a sentence to the `DbmcpInstructions` default
  (`internal/llmprompts/registry.go:1415`, server instructions are in the prompt from the start):
  "Read denied but `access.masked` allowed: read rows with `browse_table`." Then regenerate goldens
  (`go test ./internal/llmprompts -run TestGolden -update`) and run the prompt-registry row of
  `docs/DEV_ENVIRONMENT.md` "Real `claude` tests". Never weaken the test prompt or assertion instead.

## Failure 3: `TestAdeSandbox`: run has no sandbox

- Output: `sandbox_test.go:70: sandbox row = {Access:off Enforced:false ...}, want write access, enforced only on macOS`.
- Root cause: test. Since v0.3.6 a step without a `sandbox` block is unconfined (`adewire.DefaultSandbox`
  is `access: off`, `apps/kira-space/internal/bridge/adewire/wire.go:180`; `defaultSandbox` in
  `frontend/src/ade/v2/board/stepSandbox.ts` mirrors it). The test passes `""` for the block, so the
  run stores an off row. `TestAdeSandboxReadOnly` sets `access: read` and passes.
- Proof: with the fix below applied locally, `go test -run 'TestAdeSandbox$'` passed (19 s).
- Fix: `apps/kira-space/tests/claude/sandbox_test.go:60`, pass `"    sandbox:\n      access: write\n"` as
  `sandboxStep`'s third argument instead of `""`. Also update the doc comment above `TestAdeSandbox`
  (line 53) to say the step declares write access.
