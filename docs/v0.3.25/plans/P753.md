# P753: Proof window shows that its proof is stale

SPEC row: an open proof window shows when its proof changed after the window loaded it: a clear stale
marker and a reload action. It never reloads by itself, so what the owner reads or screenshots never
changes underneath. Plan picks the signal and states the cost. Flow test asserts the signal, UI spec
asserts marker and reload.

## Signal

Choice: emit `kira:proof:changed {sessionId}` on every change of a proof's accepted or pending content,
and give `proof.Detail` a `version`. The window compares the version it shows against a fresh read,
fetched only when an event names its session.

Why:
- The event already exists, is app-wide and carries the session id; the window already listens.
- The event alone gives false positives (the window's own accept or reject, `RaiseReady`). The version
  compare makes the marker mean exactly "what you see differs from what Kira holds now".
- Rev alone misses a replaced pending edit. A content hash needs step payloads that `Session` never
  reads. `proof_sessions.updated_at` is already written by every content write: `Create`
  (`proofcache.go:119`), `Propose` (`:170`), `DropPending` (`:193`), `Accept` (`proof.go:309`), `Reject`
  (`proof.go:342`). `MarkSeen` and `SetViewState` leave it alone, so opening or scrolling never
  stales a window.

Version: `fmt.Sprintf("%d.%d.%d", currentRev, pendingRev or 0, updatedAt)`. Two content writes in the
same millisecond on one proof cannot happen in practice: saves debounce at 300 ms and a write takes a
transaction. Rev in the token guards that anyway for accepts.

Coverage:
- Agent edit of the newest proof: `unitApply` hook (new).
- User edits on disk: P750's idle watcher pushes the board only, nothing changes in the cache, no
  marker. Accept on the banner runs `Adopt` -> `unit` -> same hook. Discard drops a pending edit through
  `RestoreProof` -> hook (new). A save while an agent watcher runs goes `SyncTaskFiles` -> same hook.
- Deleting the folder, accepted: `unitGone` -> hook (new). Window probe gets `E_NOT_FOUND`.
- Pending raised, replaced or withdrawn: existing `RaiseReview` / `WithdrawReview` emits.
- Accept or reject in the window, delete in the header: existing emits.

Cost:
- Go: one extra `Emit` per accepted proof unit, at most one per debounced save per task.
- Each open proof window of that session: one `ProofService.Session` call per event (session row, two
  revision reads, link, title: five small SQLite reads). Windows of other proofs drop the event on the
  id check, no IPC.
- Main window: `onProofChanged` already invalidates `TaskProofs` (`ade/queries.ts:95-97`); the board
  push does too. TanStack dedupes the in-flight refetch; worst case one extra `TaskProofs` read.
- Contracts: every `ProofService.Session` snapshot gains `version`; masked, so a one-time rewrite.

Reload behaviour (what stays):
- Active tab: `store.activeId` stays; a rev bump drops the id and `activeId` falls back to the same
  ordinal (`ProofWindow.vue:52-58`), else the first tab.
- Side and compare: `store.side` and `store.compare` stay. A vanished pending revision falls back to
  current (`:31-34`); compare needs a pending revision.
- Scroll and highlight: a rev bump remounts `ProofStepView` (key `${rev}:${ordinal}`). `Accept` copies
  view state of unchanged steps to the new rev (`repos/proof.go:283-290`), so they restore; changed
  steps start at the top. Same rev: steps refetch in place, view state untouched.
- Expanded documents: P736 auto-expand applies again on remount.
- Screenshot: Reload is disabled while `capturing`; nothing reloads on its own, so a capture never
  changes mid-batch.

Screenshot rule: the marker sits inside the captured `centre` pane and renders only while `state` is
`'changed'` or `'removed'`, which needs a confirmed version mismatch or a confirmed not-found after an
event for this proof. So a screenshot carries the marker only when its content is truly stale, and then
always does, so a shared image cannot pass for current. The Reload button never appears in a capture
(`data-shot-skip`). A batch keeps the marker state from its start (freeze above), so all images of one
batch agree.

Deliberate behaviour change: a pending edit raised while the window is open no longer swaps the window
to the proposed side. The marker shows; Reload shows the edit and its change panel.
