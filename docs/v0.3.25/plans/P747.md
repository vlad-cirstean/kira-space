# P747: Run restarted after app restart: fresh script timeout

SPEC row: a run restarted after an app restart fails at once with the script timeout. Restart is a new
run: reset its timeout clock and any other elapsed-time state. Plan finds where the original start
time survives the restart.

## Root cause

### Finding: no stored start time feeds any timeout

Every timeout path was traced. Each one arms a fresh `context.WithTimeout` at launch, from a context
with no deadline. No path reads a persisted `StartedAt`/`CreatedAt` to compute a deadline.

- Script runs (`internal/scriptruns`):
  - Smart: `launchSmart` builds a fresh ctx (`smart_run.go:87`) and takes the timeout from the
    plan (`smart_run.go:170-174`). The harness arms it (`internal/harness/claude/headless.go:196`,
    `internal/harness/opencode/headless.go:285`).
  - Headless: `startHeadless` uses `WithCancel(Background)` (`headless.go:87`) and arms the timer at
    `headless.go:149`.
  - `newRun` (`headless.go:27-49`) sets `StartedAt=now`. For a waiting row it keeps only `ID` and
    `CreatedAt`, and `CreatedAt` reads nothing timeout-related.
  - Restore: `restoreOne` (`restore.go:274-304`) calls `s.Start` with a fresh plan.
  - Resume: `resume` (`resume.go:26-88`) calls `startSmart` with a fresh plan.
  - Scheduled: `fireScript` (`scheduler.go:223-263`) and `startScheduled` (`schedule.go:72-98`) do
    the same.
- ADE runs (`apps/kira-space/internal/ade`):
  - `startRun` (`runs.go:689-806`) sets `StartedAt=now` (`:713`) and reads `timeout` from the step
    definition (`:786-789`).
  - Its ctx comes from `beginLive` (`:790`), which wraps `b.ctx` (`live.go:43`). `b.ctx` has no
    deadline (`board.go:289`).
  - `ResumeRun` runs under `joinOp`. `joinOp` uses `WithoutCancel` (`opdedupe.go:18-38`), so no IPC
    deadline leaks into the run.
  - `startSetup` (`setup.go:326-384`) and `planSmartStep` (`smartstep.go:35-65`) are fresh too.
- Session restore (`sessionrestore.go:171-268`) passes the caller ctx through and adds no deadline.
  `OfferWindow` gates only the dialog's auto-open.
- Lease and tracker clocks are monotonic and new per process (`ARCHITECTURE.md:877`). They are not
  script timeouts.
- The frontend enforces no timeout. `RunElapsed.vue`, `ScriptProgress.vue` and `runText.ts`
  `runElapsedMs` only display elapsed time.

So the phrase "original start time survives restart" names no real site in today's tree. The plan
says so plainly rather than inventing one. Two real defects remain that can each make a restarted run
fail at once with a timeout-shaped error. Both are fixed here, and a repro test gates the work.

### Defect A: parent cancel misread as "timed out"

Three runners mark a run timed out whenever `runCtx` holds `DeadlineExceeded`, without checking
that the run's own timer fired:

- `internal/harness/claude/headless.go:246`
- `internal/harness/opencode/headless.go:330`
- `apps/kira-space/internal/gitprepare/runner.go:144`

Each one runs `timedOut := errors.Is(runCtx.Err(), context.DeadlineExceeded)`.

When the parent ctx carries a deadline that ends first, this reads as `TimedOut`. `decide` then maps
it to `EndTimeout` (`smart_run.go:342-343`), and the message is "timed out after <the step's full
timeout>". The run fails with the script timeout message even though its own clock never ran out.

`internal/scriptruns/headless.go:183` already guards this correctly:
`... && ctx.Err() == nil`. The other three runners must match it.

### Defect B: restored terminal script's launch token ages from Restore, not tab open

- `restoreOne`, through `s.Start`, calls `startTerminal`. That stamps `created: now`
  (`launch.go:38-55`).
- `useOpenRestoredRun` (`packages/workbench/src/automations/restore/rows.ts:46-72`) opens one tab per
  restored terminal script. Only the active tab mounts.
- `useTerminalMount` sends the token on first mount only (`useTerminalMount.ts:101-132`).
- A second restored script, or one restored into another workspace, mounts when the person opens
  it. If that happens more than 60s later, `takeLaunch` refuses the token (`launch.go:65`). `Begin`
  then fails the run at once with `backend.core.scriptRun.expired.body`, "This run expired. Start it
  again." (`service.go:150-153`).
- That is elapsed-time state that the restart hands to the restored run: a clock started by the
  restore click, not by the run.

## Changes

### Step 0: repro test, first commit

Before any fix, add the flow tests below and run them against the unfixed tree.

- If a test shows a restarted run reporting "timed out" for a reason other than A or B, stop.
  Root-cause it and fix it at that site in this phase.
- Record what reproduced in this plan's `## Result`, which the implementer appends.

### A: only the run's own timer reports timed out

- `internal/harness/claude/headless.go:246-247`:
  ```go
  timedOut := errors.Is(runCtx.Err(), context.DeadlineExceeded) && ctx.Err() == nil
  cancelled := !timedOut && ctx.Err() != nil
  ```
- `internal/harness/opencode/headless.go:330-331`: same change.
- `apps/kira-space/internal/gitprepare/runner.go:144-145`: same change.

Effect: a parent ctx that ends first now ends the run as `Cancelled`, never as `TimedOut`. Callers'
existing cancel paths (`decide`, `agentEnd`, `endAgentRun`) already handle `Cancelled`. Confirm with
`codegraph_explore` on each `RunHeadless` caller that none relies on the old misread.

### B: restore-issued launch tokens outlive LaunchTTL

- `internal/scriptruns/launch.go`:
  - Add `ttl time.Duration` to `launch`.
  - Add a package var `RestoreLaunchTTL = 30 * time.Minute` next to `LaunchTTL`. It is a var so a
    flow test can shorten it.
  - `startTerminal(p)` sets `ttl` to `RestoreLaunchTTL` when `p` came from restore and to `LaunchTTL`
    otherwise.
  - Both the sweep (`:48`) and `takeLaunch` (`:65`) compare against `l.ttl`.
- `internal/scriptruns/restore.go` `restoreOne`: mark the plan as restore-issued with an unexported
  `planned.restored bool` field, set before `s.Start`'s terminal branch. Thread it through the
  existing `planned` struct; add no new public API.
- The token stays single-use and in memory. Close and quit already drop it. 30 min bounds how long a
  person can leave a restored tab unopened. The 60s TTL for a fresh Start is unchanged.
- Declined: having the frontend eagerly open every restored session at restore time with no
  mount. `useTerminalMount` reads size from the mounted renderer (`:114`). An unmounted pty would
  start at a guessed size and then redraw on first mount. That changes behavior for every script
  terminal, which is a wider change than this row needs.

## Tests

The split is at IPC: backend flow tests assert the result, and a UI spec asserts the same result
for the half with UI. No unit tests: each change is a one-condition guard.

### Backend flow tests

- `apps/kira-space/internal/flows/termflow/restore_test.go`, new
  `TestRunsRestoreRestartedSmartFreshTimeout`:
  1. Use `WithSmartTimeout(2s)` and a fake provider that holds the run.
  2. Start the smart run, wait 1.5s, then `Restart()`.
  3. Restore the run, then wait 1.5s more.
  4. Assert the run is still `running`.
  5. Let it finish and assert its end is not `EndTimeout`.
- Same file, new `TestRunsRestoreTerminalTokenOutlivesLaunchTTL`:
  1. Set `LaunchTTL = 50ms` and `RestoreLaunchTTL = 5s`.
  2. Restore a terminal script and wait 200ms.
  3. Open its terminal with the token, which calls `Begin`.
  4. Assert the run starts with no `expired` error.
  5. Control: a fresh `Start` token, after the same wait, still fails with `expired`.
- `apps/kira-space/internal/flows/adeflow/resume_test.go`, new `TestResumeAfterRestartFreshTimeout`:
  1. Give a workflow agent step `timeout: 2s` and start it.
  2. Wait 1.5s, `Restart()`, then `ResumeRun`.
  3. Wait 1.5s and assert the run is still live.
  4. Call `finish_step` and assert the run is `done`, not "timed out".
  - Reuse `TestResumeAfterRestart`'s setup.
- Defect A, harness level: in the same termflow test, add a case where the parent ctx is cancelled
  through the service's stop path while a smart run holds. Assert the end is cancelled, not
  `timed out after`.

### UI spec

UI half applies to B only. A has no UI.

`packages/workbench` restore dialog spec, beside the existing `RunsRestoreDialog` specs:

1. Restore two terminal scripts.
2. Assert both tabs open, each carrying its own token.
3. Activate the second tab after the first.
4. Assert its terminal opens with its token and shows no `expired` message.

The bridge mock returns the same results the flow test asserts. Run only this spec locally; the UI
suites run in PR CI.

## Migration

None. There is no schema, stored-data or config change. Launch tokens are in-memory only. The
minor-bump rule does not apply: this is a patch with no legacy path.
