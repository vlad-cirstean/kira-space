## Audit: what the dialog shows today, top to bottom

Dialog (`packages/workbench/src/approvals/ApprovalsDialog.vue`, card
`ApprovalItemCard.vue`, footer `ApprovalItemActions.vue`, kinds
`apps/kira-space/frontend/src/studio/approvals/kinds.ts`):

   and, when queued, "N of M" (`ApprovalsDialog.vue:79-87`).
2. Line 1 (`ApprovalItemCard.vue:104-159`), all one size, one row, wrapping:

4. Body, indented (`:167-183`): statement (Monaco, formatted/as-sent tabs) or API path only
   (`ApiRequestBody.vue:85-88`: host and method sit on line 1, apart from the path), body.
5. Details rows inline under the body, always open: API headers, variables, options

6. Footer row 1: "Deny all" row, `invisible` for a single item but still takes its height

Not shown at all: how a read is enforced (`payload.enforcement`: `session` = database read-only

(`studio.dbMcp.approval.enforcement.*`). API read vs write: backend gives `class: request` for every
method and only the tone differs (`api_tools.go:462` `methodTone`), so no "Read" word appears.

## Ranking (what decides Approve or Deny)

1. Effect class: read, write, schema change, delete. Must read at a glance.
2. Bound on the effect: read-only connection, read-only session (database-enforced), Kira-checked
   read, unenforced read; for API, credential sent.
3. Target: connection or environment name, its colour, kind and location.
4. Statement or request: the thing itself, highlighted.
5. Warnings: rows estimate, plan issues (with their message), kept values, scripts, truncation.
6. Secondary: headers, variables, options, reason, statement echo of a result review.
7. Who asked: client, folder, task.

## Design

One layout for every kind; DB and API differ only in what the kind function returns.

1. Verdict row (top of the card, replaces line 1). A large tone badge first: icon plus word.
   - DB `read` green "Read" (eye), `masked` "Masked read", explain "Explain"; `write` amber "Write"
     (edit); `ddl` red "Schema change"; unknown amber "Unclassified"; exemption amber "Lift limit".
   - API by method: GET/HEAD/OPTIONS green "Read", DELETE red "Delete", other methods amber "Write".
   - Result reviews (`db.response`, `api.response`): neutral "Result" (table), fact "Not sent yet"
     or amber "Already ran".
   Then fact badges, same height: green "Read-only connection" (lock) when `target.readOnly`; read
   enforcement from `payload.enforcement`: green "Read-only session" (shield), neutral "Read checked
   by Kira", amber "Read not enforced", each with the existing enforcement sentence as tooltip; API
   "Sends <credential>" (key; amber on a write, neutral on a read; tooltip names hosts). Then a
   divider, a colour swatch (connection or environment colour, replaces the band), target name,
   kind and location muted, countdown right.
2. Focus block: the statement or request in one framed box (`rounded-kira-sm border border-border
   p-3`), not indented. DB: Monaco statement as today with Formatted / As sent. API: one request
   line `METHOD scheme://host/path?query` (method coloured by `methodTextClass`, origin muted, kept
   ranges marked as today), then the body (Monaco JSON as today), user inputs and kept panels as
   today.
3. Warnings list under the box: one line each, icon plus full text (plan issue shows its message,
   not `warn`/`info`). Same `ApprovalRisk` data; read-only and credential move up into facts.
4. Details, collapsed by default (shadcn `Collapsible`, `link-meta` trigger with chevron): the kind's
   `details` component (headers, variables, options, exemption reason, response statement) and an
   "Asked by" row (origin). Open state is per item, not remembered.
5. Footer: one row. Left: "Deny all (N)" as `link-meta` only when N > 1 (no invisible spacer), then
   the kind's footer action (Review result). Right: Deny as neutral `dialog` outline (the safe
   choice, no alarm colour), Approve tinted by verdict: `dialog-approve` for read and result,
   new `dialog-warn` for write, `dialog-danger` for schema change and delete. Shortcuts unchanged:
   Mod+Enter approves, Mod+Backspace denies (kbd hints stay on both buttons). Kind labels stay
   (Send / Don't send, Send to AI / Withhold, Lift for this query / Keep the limit).
6. Header: title plus "N of M" badge on the title row when queued; drop the lone count badge.

Data review (`apps/kira-space/frontend/src/studio/approvals/PendingResponse.vue`, used by
`DbResponseBody.vue`; `ResultReview.vue` hosts it with the scripted views):

7. Row resize: each row gets a drag handle along its bottom edge, the existing `ResizeHandle`
   (`packages/theme/src/components/ui/resizable/ResizeHandle.vue`, `usePaneResize` axis `y`:
   pointer drag via VueUse `useDraggable`, ArrowUp/Down keyboard step, Home/End, ARIA separator).
   No grid in the repo has row resize today (grep: none); the column/pane handle is the behaviour
   to reuse. Min = single row height (`useRowHeight`), max 480 px. Double-click resets the row.
   Heights live per held result in component state (`Record<row, px>`) and feed
   `useVirtualRows({ rowHeights })` (`packages/workbench/src/behaviour/virtualRows.ts:31`), which
   already supports exact per-row heights and re-measures on change. A taller row wraps its cells
   (`whitespace-pre-wrap break-words`, clipped to the row height); an unset row stays one line.
   One handle per cell, all bound to the row, so the grab area spans the full row (a positioned
   `<tr>` does not anchor an absolute child in WebKit; seen in the prototype); only the first
   cell's handle is in the tab order.
8. Full value: hover shows an expand button at the cell's top right (`screen-full`); click,
   double-click or Enter on the focused cell opens one shared shadcn `Popover` anchored on that cell
   (`PopoverAnchor :reference`, the `KeyValueEditPopover.vue` pattern): header "column · row N",
   character count, Copy (VueUse `useClipboard`), the value in the data font, pretty-printed when
   it parses as a JSON object or array, scrolling at `max-h-80`. NULL cells get no button.
   `TruncatedText`'s hover tooltip on these cells goes (it covered the expand button in the
   prototype); the popover replaces it.

Declined: Studio data grid (`SlickGridHost`/cheetah) inside the dialog. It needs the page cache,
tab id and selection stores of a data tab; the held result is a plain JSON blob capped at a few
hundred rows. The shadcn table plus virtual rows meets the need; the grid's cell editor dock is the
same full-value idea, not reusable without a tab.

## Backend

None. Every fact the design shows is already in the item: `target.readOnly`, `operation.class`,
`payload.mode`, `payload.enforcement`, `payload.method`, `payload.credentials`,
`payload.alreadyRan`. The IPC split rule therefore adds no flow test; Result says so. Note: API
`operation.class` stays `request`; read/write is derived from the method in the frontend, same rule
as `methodTone` and `isRead` (`kinds.ts:187`).

## Open questions (for the user)

1. API read-only: there is no read-only flag for an API environment today. Want one (environment
   setting "agent may only read", enforced by the backend, shown as a "Read-only environment" fact)?
   That is backend work with a flow test plus UI spec; proposed as its own phase, not in P715.
2. Approve tint by verdict (green read, amber write, red delete/schema) vs one neutral primary for
   all. Proposal tints.
3. Origin ("Asked by") inside Details vs kept small in the footer. Proposal: Details.
4. Row heights: per review only (gone when the item is answered), or remembered per column across
   reviews? Proposal: per review.
5. Verdict words: "Schema change" for DDL and "Delete" for HTTP DELETE, or keep "DDL" / method name?
