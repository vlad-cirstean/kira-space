## Answers from code

### "Read-only connection" vs "Read-only session"

- Read-only connection is the user's setting on the connection (`readOnly` in its file,
  `internal/storage/model/connection.go:14`). It governs the whole connection: Studio's own console
  and grid (`model/connection.go:44-45`), the Postgres main session runs
  `SET default_transaction_read_only = on` (`adapters/postgres/client.go:271-280`), and for the agent
  `accessOf` refuses write and DDL modes outright with "read-only connection"
  (`internal/dbmcp/permissions.go:217`). So on such a connection the agent never reaches a write
  prompt: every prompt that carries the flag (`dbmcp/approval.go:241`, `approval_item.go:235`) is a
  read.
- Read-only session is not a setting. It names how an agent read is enforced, by engine kind
  (`permissions.go:170-180` `enforcementOf`, set on read items only by `tools.go:697-703`
  `enforcementFor`): every agent read runs on a separate read lane, a second connection opened with
  the read-only switch on (`adapters/lane.go:16-27`, `adapterhost/readlane.go:128-150`), so for
  Postgres, MySQL, MariaDB, SQLite and ClickHouse the engine itself refuses a write. MongoDB and Redis
  get Kira's own check (`app`). Kafka, SQS, S3 and Kibana get `none`; they have no write path at all
  (`permissions.go:160-168`).
- Both show only on reads, and both mean "this cannot change data". For the five SQL engines the
  session one already holds whatever the connection setting says, so the connection badge adds
  nothing to the decision. Showing both is redundant.
- Chosen: one merged fact on read items, wording by enforcement: green "Read-only · enforced by
  database" (session), neutral "Read-only · checked by Kira" (app), nothing for `none` (no write
  path; "not enforced" would alarm for no reason). The connection setting moves into the fact's
  tooltip ("The connection is also set read-only") and into Details (row "Connection"). Images 1, 3,
  12, 13.

### Data review: default state (images 7, 8)

Today `PendingResponse.vue:127-128` shows the first 3 rows (`PLAIN_ROWS = 3`, `open = false`). The
"+N more rows" link (`:266-275`) opens all rows, virtualized, scrolling at `max-h-72`; once open it
cannot collapse again. `before/7` is the default, `before/8` is after the click. Proposed default:
all rows open (virtualized, same `max-h-72` scroll box), no "+N more rows" link. The person is
deciding whether to send these rows; hiding all but 3 hides what is approved. Images
`proposal3/7` and `9a`.

### Data review labels ("Result", "not sent yet")

Today the verdict word is "Result" (`kinds.ts` `db.response`/`api.response` `operation` =
`common.field.result.label`); round 1 added a "Not sent yet" fact. The table and the Send to AI /
Withhold buttons already say both. Chosen: one badge that says what produced the rows, the only
thing not obvious from context: green "Read result", or amber "Write result · already ran" (from
`payload.mode`/`alreadyRan`, API from `payload.class`), tooltip "The statement already ran. Withhold
only keeps the result from the agent." The separate "Already ran" and "Request already sent" risks
go. Images 7 and 10.

### Explain asked by the agent (image 12)

`run_query` with `explain: true` raises a read approval with the agent's SQL and `Explain: true`,
no plan and no Review result offer (`tools.go:767-778`). The plan does not exist yet: EXPLAIN runs
only after Approve (`tools.go:860-897`). Today the card says "Explain" in muted text, nothing more.
Proposal: one kind badge "Explain" in its own hue. No extra fact: the word says it.

### Auto-explain (images 13, 14, 14b)

With the connection's auto-explain on and a statement classified read, Kira runs one EXPLAIN before
anything else (`tools.go:684-704` `planForCall`), and the plan feeds the row limit and the card
(`explain.go:22-51` `approvalPlanFrom`: warn issues first, at most 10).

- Passes (under the limit, no warn issue): today the card shows nothing about it
  (`kinds.ts` `planRisks` prints rows only when over the threshold). Proposal: still nothing. A
  clean pass carries no decision input.
- Over the row limit: the `expensive_query` limit refuses before any approval
  (`limits_gate.go` `checkLimits`, `expensive.go:16-29`). The agent retries with an exemption and a
  reason, and the person sees a `db.exemption` card ("Lift limit"). Today the reason sits in the
  details rows and the hit reads "~1,240,000 rows". Proposal: warnings list leads with "Agent's
  reason: ..." then "Estimated 1,240,000 rows, over the 100,000 row limit (explain ran before
  asking)", then plan issues.
- Plain read over the threshold (image 1): the warnings line reads "Estimated ~1,240,000 rows,
  over the 100,000 row limit".
- Warn issue under the limit (image 14b): a neutral line "Estimated ~48,000 rows, under the 100,000
  row limit" frames the issue lines (today the tag reads "warn"); info-severity issues render
  neutral, not amber.
- EXPLAIN fails: there is no prompt. The limit fails closed and the call is refused before any card
  (`expensive.go:18-21`, `tools.go:695`). On a call already exempted from the limit a failure
  degrades to no plan (`tools.go:699-701`): the exemption card then simply has no plan line. Nothing
  to design for it beyond that.
- API has no explain: `api_request` takes no explain argument (`api_tools.go:60-76`) and no row
  limit applies.

### Chains and scripts (images 15, 16)

- One approval per operation. `api_request` is one HTTP request per tool call
  (`api_tools.go:132-193`); `run_query` is one statement. There is no multi-operation request and no
  pre-request / post-response / test script triple.
- Scripts are part of that one operation: at most a prepare and a transform
  (`api_script.go:36-48`). Prepare runs before the card (`api_tools.go:147-152`, before the
  approval at `:160-162`) and may return method, url, headers, query, body, contentType or form
  (`api_script.go:72`); the card shows the request it built and lists the changed fields. Transform
  runs after the response (`api_tools.go:184-186`) on the masked response; the agent gets what it
  returns. This is the "JS parse step". A DB query script is a result transform only and cannot
  change the statement (`query_script.go:15-19`). "The text the user approves is the text that
  runs" (`api_script.go:42-43`).
- A chain across operations works through kept variables: a transform `kept.set`s a value, a later
  request or query reads it (`kept.get`, `{{name}}`, or a bound param). Reads are fixed when the
  card is planned, writes are staged until the response is final (`kept_script.go:24-25`). Each
  later step is its own approval; its payload carries the kept values it reads with their source
  (the request that kept them, `packages/shared/domain/kept.ts:5-13`).
- What the card shows today: the script sources in full (prepare, transform, script input, changed
  fields) and the kept values with their source, but as a long flat stack with no flag that code
  will execute, and nothing that frames the earlier step.
- Proposal: an amber fact "Runs 2 scripts" / "Runs a script" in the verdict row (tooltip says
  what each does and which fields prepare set). A compact chain list at the top of the box: one
  line per earlier step known from the kept sources ("Earlier GET .../users kept ids (by script)"),
  then "This step POST .../echo" with `prepare` and `transform` chips. Script sources stay visible
  in the box: they run, so they must be read before Approve. Later steps cannot be shown: they do
  not exist until the agent sends them. The "Built by script" and "Agent gets script result" tags
  fold into the fact.

## Ranking (what decides Approve or Deny)

1. Effect class: read, write, schema change, delete.
2. Bound on the effect: read-only enforcement; for API, credential sent; scripts that run.
3. Target: connection or environment name, colour, engine, location.
4. Statement or request, with API headers and variables (they are what is sent).
5. Warnings: rows estimate and limit, plan issues, agent's reason, kept values, truncation.
6. Secondary: options, declared vs detected mode, script input, response statement.
7. Who asked.

## Design

One layout for every kind; DB and API differ only in what the kind function returns.

1. Verdict row. A large kind badge first, icon plus word, each kind in its own hue (image 17):
   - Explain: blue, `graph` icon. Read: green, `eye`. Write: amber, `edit`. Schema change: purple,
     `symbol-structure`. Delete: red, `trash`.
   - DB `read` "Read" (masked "Masked read"), explain "Explain", `write` "Write", `ddl` "Schema
     change", unknown amber "Unclassified", exemption amber "Lift limit".
   - API by method: GET/HEAD/OPTIONS "Read", DELETE "Delete", others "Write".
   - Results: "Read result" (read hue) or "Write result · already ran" (write hue).
   Hues come from the existing status palette (`--kira-status-blue|green|amber|purple|red`,
   `tokens.css:174-187`): `bg-status-X/15 text-status-X border border-status-X/50` on the `chip`
   badge variant. The app ships one dark theme (`tokens.css` has only `:root`), so readability was
   checked on it alone. Selection tokens stay grey; `check-conventions` passes N1-N18 with the
   prototype applied. A new `ApprovalVerdict.hue` field carries the kind; `tone` still drives the
   Approve tint.
   Then fact badges, same height, only those that carry information: the one read-only fact
   (above); "Runs a script" / "Runs 2 scripts" (amber); API "Sends <credential names>" (amber on a
   write, neutral on a read; tooltip names hosts).
   Then the connection chip: a bordered chip holding the engine icon (DB kinds: `EngineIcon.vue`,
   the same component and 16 px mark the connections tree uses, `studio/project/TreeRow.vue:193`),
   target name, then location (host, database / schema) muted. No engine name: the icon says it;
   text only for a kind the app does not know. The connection colour paints the chip's left edge,
   4 px (variant A, image 18; replaces the band and the dot). Countdown right.
2. Focus box (`rounded-kira-sm border border-border p-3`), not indented:
   - DB: chain list when the query reads kept values, kept panel, Monaco statement with the toggle
     renamed Formatted | Raw (reuse `common.raw.label`; drop `studio.dbMcp.approval.asSent.option`,
     both callers `ApprovalStatement.vue:51-56` and `PendingResponse.vue:118`), params, script.
   - API: chain list, inputs and kept panels, one request line `METHOD scheme://host/path?query`
     (method coloured by `methodTextClass`, origin muted, kept ranges marked), then Headers and
     Variables as name/value rows, always visible (moved out of Details): secret header values show
     their template plus "Secret", secret variables show `••••` plus "Secret" (values arrive masked;
     nothing new is revealed). `ApprovalPairs` keeps its 3-row cap with "+N more". Then body and
     script sources.
   Headers and variables are visible by default rather than behind a "N headers, M variables"
   summary: they are the part of the request that carries credentials and tenant ids, the case
   the user named, and the cap keeps them compact (image 5).
3. Warnings list under the box: one line each, icon plus full text. Read-only, credential, script
   and "already ran" signals move into facts; exemption leads with the agent's reason.
4. Details, collapsed by default (shadcn `Collapsible`, `link-meta` trigger with chevron), per item:
   - DB query (new `DbQueryDetails.vue`): Declared mode, Looks like (only when it differs), Read-only

   - API: Options (redirects, timeout), Set by script, Script input.
   - Exemption: Reason (also in warnings). Result: Statement, sizes.
   - Every kind: "Asked by" (client, folder, task) as the last row.
5. Footer, one row. Left: "Deny all (N)" as `link-meta` only when N > 1. Right, in order: the kind's
   footer action (Review result checkbox), Deny on `dialog-deny` (N17 requires it), Approve tinted

   kbd hints on both). Kind labels stay (Send / Don't send, Send to AI / Withhold, Lift for this
   query / Keep the limit).
6. Header: title plus "N of M" badge when queued; drop the lone count badge.

Data review (`PendingResponse.vue`, used by `DbResponseBody.vue`; `ResultReview.vue` hosts it with
the scripted views):

7. All rows open by default (above).
8. Expand on click (images 7-hover, 9a): a click anywhere on a row toggles it expanded in place.
   An expanded row wraps every cell (`whitespace-pre-wrap break-words`) and shows each value in
   full, no cropping. A leading chevron column shows `chevron-right` on row hover and stays as
   `chevron-down` while expanded; its tooltip reads "Click the row to show every value in full.
   Drag its bottom edge to set a height." The row is `aria-expanded`; Enter or Space on a focused
   row toggles it too. Its natural height is measured once rendered (`nextTick`, then VueUse
   `useResizeObserver` in the implementation) and passed to `useVirtualRows({ rowHeights })`, which
   needs known heights. A click on the row again collapses it and drops any dragged height.
   Clicks on the expand button and the drag handle do not toggle.
9. Row resize (image 9b): each row keeps a drag handle along its bottom edge, the existing `ResizeHandle`
   (`packages/theme/src/components/ui/resizable/ResizeHandle.vue`, `usePaneResize` axis `y`: pointer
   drag via VueUse `useDraggable`, ArrowUp/Down, Home/End, ARIA separator). No grid in the repo has
   row resize today. Min = single row height (`useRowHeight`), max 480 px, double-click resets.
   Heights live per held result in component state (`Record<row, px>`) and feed
   `useVirtualRows({ rowHeights })` (`packages/workbench/src/behaviour/virtualRows.ts:31`). A taller
   row wraps its cells (`whitespace-pre-wrap break-words`, clipped to the row height). One handle
   per cell, all bound to the row (a positioned `<tr>` does not anchor an absolute child in WebKit);
   only the first cell's handle is in the tab order.
10. Full value (image 8), for one very long value: hover shows an expand button at the cell's top right; click, double-click or Enter
   on the focused cell opens one shared shadcn `Popover` anchored on that cell (`PopoverAnchor
   :reference`, the `KeyValueEditPopover.vue` pattern): header "column · row N", character count,
   Copy (VueUse `useClipboard`), value in the data font, JSON objects and arrays pretty-printed,
   scrolling at `max-h-80`. NULL cells get no button. `TruncatedText`'s tooltip on these cells goes
   (it covered the button). Double-click no longer opens it: two clicks would toggle the row twice.

Declined: Studio data grid (`SlickGridHost`) inside the dialog. It needs a data tab's page cache,
tab id and selection stores; the held result is a plain JSON blob of a few hundred rows at most.

## Open questions (for the user)

0. Connection colour (image 18): variant A, a 4 px coloured left edge on the connection chip, is
   recommended. It reads at a glance for every palette colour, matches the tab rail elsewhere, and
   leaves fill colour to the kind badge. Variant B, a tinted chip background, is quieter: a red
   production tint sits close to the red Delete badge and the tint is faint for dark colours.

1. API read-only: no such flag exists for an API environment. Want one (backend-enforced, shown as
   the same read-only fact)? Backend plus flow test plus UI spec; proposed as its own phase.
2. Approve tint by verdict (green read, amber write and write result, red delete and schema
   change) vs one neutral primary. Proposal tints; "Send to AI" on a write result is amber (image 10).
3. Row heights per review only (proposal), or remembered per column across reviews?
4. Words: "Schema change" for DDL and "Delete" for HTTP DELETE, or keep "DDL" and the method?
5. Chain list: earlier steps come only from kept-value sources. Enough, or should the backend
   record a real chain id across calls (backend work, own phase)?
6. Data review all rows open by default (proposal) vs keep the 3-row preview.
