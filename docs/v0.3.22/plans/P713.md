# P713: real `claude` `TestAdeReviewStep`: resumed implementer lacks `review.reply`

Spec row: `SPEC.md` P713. Found in P708: `TestAdeReviewStep` fails about half of runs, also at base
`605a98ec3`. Watch `TestAdeBranchRequest` (one 3 min headless timeout in a full run).

## Root cause (confirmed by planner, CLI 2.1.330, haiku)

Product bug: Kira's `state` tool schema changes between grants, and the CLI keeps the first schema a
conversation saw. Grant composition is correct; the round's grant does carry `review.reply`.

Evidence:

1. Server side is right. `startRound` passes `review: &agentmcp.ReviewGrant{...}`
   (`apps/kira-space/internal/ade/reviewstep.go:759`). `superviseAgent` puts it on the grant; the
   round has `Space` false (`apps/kira-space/internal/ade/runs.go` `superviseAgent`). `toolSetOf`
   sets `review`; `stateActionsOf` enables `review.reply` only for `ts.review`
   (`internal/agentmcp/state.go:66`). `--allowedTools` gets `mcp__kira-space__state` via
   `roundTools` (`runs.go:1203`; `agentmcp.ReviewReply = State`, `internal/agentmcp/tools.go:26`).
2. Implement run is a Space grant. Its `state` enum has no `review.reply`
   (`spaceOnly` actions plus `step.finish`). Its prompt carries the Claude load hint
   (`LoadHint`, `internal/harness/claude/mcp.go:92`, via `filesVars`,
   `apps/kira-space/internal/ade/detailsprompt.go:35`), so haiku runs
   `ToolSearch select:mcp__kira-space__state`.
3. CLI writes a `deferred_tools_record` attachment into the transcript at that first load: name,
   description, `input_schema`. Observed record of the implement run: enum
   `repo.declare … operation.cancel, step.finish`, no `review.reply`, description without its line.
4. The implementer round resumes that conversation (`applyReviewSend`, `reviewstep.go:584`,
   `launch.ResumeID`). In the round transcript the CLI records only the new `finish_step`; a second
   `ToolSearch` naming `state` adds no new record for it.
5. Planner probe (stdio MCP server, tool description carries a version code, enum grows per run):
   run 1 loads `act` with code N111, enum `alpha`. `--resume` with the server now at N222 /
   `alpha,beta`: model quotes `N111 | alpha`. `--resume` again with an explicit `ToolSearch` first,
   server at N333 / `alpha,beta,gamma`: still `N111 | alpha`. A call with `gamma` still succeeds
   (server answers, no client-side enum check). So the resumed model sees the stale schema, while
   the server accepts the new action.
6. Hence the coin flip: haiku either follows the prompt ("Per comment, call state review.reply
   once", `ade.review.comments`) and the call succeeds, or trusts the stale enum and reports no
   `review.reply`. Observation run here passed (44 s, 0.021 USD); the transcript still showed the
   stale record.

Not the test prompt: the prompt names the action correctly. Not a missing grant. Not a
config/settings difference: the MCP config file is fresh per launch and the server answers per
token (`Register`, `startLocked`, `internal/agentmcp/mcp.go`).

Who else can hit it: any conversation resumed under a grant whose `state` (or other deferred tool)
schema has an action or field the first grant lacked. Today only the implementer review round does:
round grant = `review.reply` plus the same step's sandbox actions; the implement run already had the
sandbox actions when sandboxed (same step `def`). Resumes Space to Space (send-back, restart resume)
keep the same action set. Dedicated review sessions start fresh with the review schema.

## Fix

Invariant: a tool's schema must never gain an action across resumes of one conversation. Make the
Space tool set's `state` a superset of every round tool set that can resume it.

1. `internal/agentmcp/state.go`: enable `review.reply` for `ts.review || ts.space` (new helper, e.g.
   `reviewOrSpace`). Comment the why in one line: the CLI keeps the first schema a conversation
   loads, and a review round resumes the implementer's Space conversation.
2. `reviewState` (`state.go:583`) already refuses a call without a review grant. Change the text to
   say why: `review.reply works only in a review round: no comments were sent to you.` Keep
   `StatusInvalid`.
3. Leave the sandbox actions as is: a round on the implementer session uses the same step's
   sandbox, so the sets match. Do not widen them (a Space run without a sandbox must not list
   `branch.push`).
4. `internal/agentmcp/tools.go:25` comment: add that a Space `state` lists `review.reply` too, and
   why.
5. No prompt change. No change to the round prompt, `roundTools` or the grant.

Rejected:

- Separate `review_reply` tool (fresh name gets a fresh record): reverses the deliberate merge of
  reply into `state` (`tools.go:25`), and leaves the general trap for the next action.
- Prompt line "state now has review.reply": still model-dependent; the stale enum stays.
- `--fork-session`: changes product behaviour (implementer conversation would not hold the review)
  and the record is likely copied with the history.
- Schema without enum and with a grant-free description: large prompt redesign, details bench
  baseline churn, out of scope.
