## What the gate measures (read from the harness)

- `TestDetailsBench` (`apps/kira-space/tests/claude/details_bench_test.go:328`) runs each flow on two
  arms in one round, sonnet, rep-major order (rep 1 of every flow and arm, then rep 2, ...).
  - Arm T: frozen v0.3.13 tool list `testdata/details-bench/tools-baseline.json` over spike stubs
    (`benchSetupT`). Prompt gets the handover and notes inline (`spikeRun.inline`,
    `details_spike1b_test.go:148`), no files fragment (`folderLine` returns "" for T,
    `details_spike_test.go:123`).
  - Arm R: real `agentmcp.Server` with a Space grant (`benchSetupR`) over a task folder seeded from
    `states-r/`; prompt gets `headless.space.files` with the Claude load hint (`folderLine`,
    `details_spike_test.go:123-139`).
- Ratio = median(R) / median(T) of the same round: `cost` is `total_cost_usd`, `context` is
  `CtxFinal` (fresh + cache read + cache write tokens of the last model call,
  `details_spike_metrics_test.go:46`). Gate (`benchReport`, `details_bench_test.go:461`): cost <= 1.2,
  context <= `benchCtxBound` (1.05 on F1 to F4, 1.0 on F5 and F6, `:483`), pass count not lower,
  failed edit-path calls plus retries not higher. `inconclusive` (`:500`): gap between medians smaller
  than the larger run-to-run range; then the verdict reads "fail, inconclusive: Opus review of the raw
  runs", which needs `KIRA_SPIKE_DUMP` transcripts.
- Budget guard (`:387-398`): before each run, stop if `spent + max(cost seen)` exceeds
  `KIRA_BENCH_BUDGET` (default 1.5, `:366`). Row command plans 4 flows x 2 arms x 3 reps = 24 runs at
  0.05 to 0.10 USD each, about 1.6 USD plus reserve, so the default budget always stops near 18 runs:
  2 reps of F5, F6, F1 and 3 of F4. That is why P713 had 2 reps per gated cell.

Correction to the row text: F5 context passes (0.97, 0.98 at bound 1.0). F5 fails on cost only; F6 on
cost and context (1.06); F1 cost is the inconclusive one.

## Harness fidelity defect (found by planner, free)

Arm R's prompt and its stub disagree on the draft, and neither matches Kira:

- Kira (`apps/kira-space/internal/ade/detailsprompt.go:30-32`) names the draft in the fragment
  (`Draft`) exactly when the route continues; the board refuses an ok draft-less `step.finish` under
  the same condition (`apps/kira-space/internal/ade/detailsmcp.go:97`).
- Bench: `folderLine` builds `llmprompts.FilesVars{Folder: r.taskDir}` with no `Draft`
  (`details_spike_test.go:125`), so the R prompt never says "Write your handover to ...". The stub
  `benchSpaceR.SubmitForFinish` (`details_bench_test.go:104-110`) refuses every ok finish without a
  draft. The fixture task sits at implement, position 3 of 4 (`states-r/*.yaml`): a continuing route,
  so Kira would name the draft.
- Effect, expected: every R run of F1, F4, F5, F6 that finishes ok gets one refusal, then writes the
  draft, then finishes again: 1 or 2 extra turns plus a counted failed edit-path call that a real
  Kira run would not pay. Present since P643 Part 5 (fragment had `{{if .Draft}}` at v0.3.14 too).
- Second asymmetry, by design not by bug: the F5 and F6 T prompts carry no finish instruction and
  their oracles do not need a finish (`details_spike_test.go` F5 and F6 oracles), while R's fragment
  always says "When the step is done, call state with step.finish". F1 asks both arms to finish.

## Hypotheses, ranked

1. Benchmark artifact (most likely, main share of the gap). The draft refusal round above, plus T
   never finishing on F5 and F6. Explains why F5 and F6 (the two flows whose T arm stops at one tool
   answer) fail hardest, and why F4 passes (T needs three read tools there).
2. Real, structural product cost, not a regression: the files design's step ceremony (ToolSearch for
   deferred `state`, draft write, `step.finish`) that the T flows skip. P643 diagnosis. Part of it
   remains even with a faithful harness.
3. Prompt-induced waste in the product: the fragment's "read state.yaml fileErrors after each edit"
   (a read after the draft write), an unneeded README read, or F5 polling `state.yaml` with
   `sleep` instead of one `state branch.request`. Fixable in product if transcripts show it.
4. Sample noise at 2 reps: weak. Gate already rules F5 and F6 conclusive (gap above the run range);
   P643 measured spread under 0.01 USD per cell against gaps of 0.02 to 0.03 USD. Only F1 is near the
   line. Still, 2 reps give no outlier protection; a verdict needs 3.
5. Regression in the details tool or prompt path since v0.3.14: contradicted by the numbers (ratios
   fell). P713 itself added about 20 tokens; base and post-fix rounds match.
6. Stale thresholds or baseline: the bounds are P643 design targets, never calibrated and never met;
   T is frozen and unchanged, so nothing drifted. Not a cause, but a recalibration is a user decision
   only (see Open questions).
