# P518 Cancel ops via MCP and status bar running-ops widget

Ask (SPEC row): "Agent can stop a running query via MCP, and any request listed in the ops panel. Status bar widget
lists running ops with a stop action per op."

Base: `chapter/v0.2.35` after wave B lands (P517 in flight at plan time, HEAD `9455311d0`). Wave C stream, beside P519.
No migration. Discovery: `codegraph_explore` over `Host.RunOp`/`CancelOp`, `Router.Cancel`, `OpsService.Cancel`,
`dbmcp.buildMCPServer`, `createOpLogStore.cancelOp`, both apps' `OperationsPanel.vue` and `StatusBar.vue`,
`RunsStatusItem.vue`, `useAutomationOps`, `scriptruns.Service.Stop`.

## 1. Facts this plan builds on

- Every Studio Operations panel row except automation runs comes from `adapterhost.Host.RunOp` (`execute`, tree ops,
  `connect`, `preconnect`, `http`, `grpc`, `kubernetes`). `Host.running` already holds each one's cancel func.
  `Host.CancelOp` is what the panel's Stop calls (`OpsService.Cancel` then `Router.Cancel`).
- `Host.CancelOp` on an unknown id remembers it as an early cancel (`earlyCancels`) so a Stop that beats its Run works.
  An agent cancel must not do that: a guessed or stale id would poison a later op with that id.
- `Host.Cancellable` registers gRPC stream work with no panel row. Not "listed in the ops panel"; out.
- A throttled op waits in `Host.running` before `op:start`; it has no panel row yet. Out until it starts.
- Automation runs show in both panels as `run:<id>` rows projected from `script_runs` (ARCHITECTURE "Script runs
  show in both apps' Operations panel"). Stop is `scriptruns.Service.Stop` (waiting skips, running stops).
- dbmcp tools run under `adapterhost.WithOpSource(ctx, OpSourceMCP)` (`withPanicRecovery`), so their ops carry
  `source: "mcp"`.
- `run_query` blocks until done. A client stops it either by MCP request cancel (go-sdk cancels ctx; already works)
  or by a second call, from a parallel tool call or another session. The new tool covers the second path. P520 makes
  tools async; `cancel_operation` is then the main stop path, unchanged.

## 2. Scope decisions (orchestrator: confirm the two marked ones with the user)

- MCP side is Studio only, on the `kira-db` server. "Running query" names Studio's DB MCP. **[confirm]** Kira Space's
  agent MCP (`internal/agentmcp`) gets no cancel tool: Space ops are git and CLI spawns, not queries, and agentmcp is
  P517's file this wave.
- Status bar widget ships in both apps. The bar, op-log store and panel are shared (`packages/workbench`), so one
  component serves both; each app's `StatusBar.vue` feeds it its own rows.
- Widget lists every running panel row: op-log ops plus live automation runs (the panel's own `runningCount` set).
  Space excludes `background` rows (sub-second tracker reads the panel itself hides by default) and disables Stop on
  rows with `cancellable: false`.
- **[confirm]** `RunsStatusItem` (count of running automation runs, click opens Runs) stays as is. A running
  automation run then counts in both items. Removing it is a feature removal nobody asked for.
- Agent visibility rule: an op on a connection not exposed to MCP is neither listed nor cancellable; the refusal reads
  exactly like an unknown id, so its existence never leaks. Connectionless ops (`http`, `grpc`, `kubernetes`, `test`,
  dialog `preconnect`) are listed by kind and time only, never command text (a URL or manifest can carry secrets).
  Automation runs are listed with script name and state.
- No approval prompt on cancel. A cancel stops work; it never changes data. A cancelled write rolls back like a user
  Stop. The row in the panel shows `cancelled` either way.

## 3. Backend

### 3.1 `adapterhost` (Studio)

`apps/kira-studio/internal/adapterhost/host.go`:

- `runningOp` gains `kind`, `source`, `startedAt string` and `listed bool`. `RunOp` sets `kind`/`source` at
  registration, then sets `startedAt` and `listed = true` under `h.mu` right before it emits `op:start` (after the
  throttle gate). `Cancellable` leaves `listed` false.
- New exported `RunningOp{OpID, Kind, Source, StartedAt string; ConnectionID *string}` and
  `func (h *Host) RunningOps() []RunningOp`: snapshot of listed ops under `h.mu`, sorted by `StartedAt` then `OpID`.
- New `func (h *Host) CancelRunning(ctx context.Context, opID string) (bool, error)`: cancels only a listed, present
  op; no `earlyCancels` entry on a miss. Extract the shared tail of `CancelOp` (local `cancel()`, then adapter
  `Cancel` under `disconnectTimeout`) into one unexported helper both call.

`apps/kira-studio/internal/adapterhost/router.go`: passthroughs `RunningOps()` and `CancelRunning` next to `Cancel`.

Test (`apps/kira-studio/internal/adapterhost/router_test.go`, one case, guards the early-cancel interaction):
`CancelRunning` on an unknown id returns false and a later `RunOp` with that id runs; a listed op is cancelled and ends
`cancelled`; a `Cancellable` id is not in `RunningOps` and `CancelRunning` refuses it.

### 3.2 Script runs (shared `internal/scriptruns`)

`internal/scriptruns/repo.go`: `func (r *Repo) Live() ([]Run, error)`: rows with state `running` or `waiting`, newest
first. `Repo.List(limit)` is not enough: a long run falls past the limit behind newer finished runs.

### 3.3 dbmcp tools

New file `apps/kira-studio/internal/dbmcp/ops_tools.go`:

- Consumer interfaces:
  - `OpsControl { RunningOps() []adapterhost.RunningOp; CancelRunning(ctx context.Context, opID string) (bool, error) }`
    (`*adapterhost.Router` satisfies it).
  - `ScriptRunControl { Live() ([]LiveRun, error); Stop(id string) error }` with
    `LiveRun{ID, ScriptName, State string; StartedAt *int64}`, declared here so dbmcp imports no `scriptruns`.
- `list_operations`, no args. Result `{"operations": [...]}`, oldest first. Entry fields: `opId`, `type` (`op` or
  `scriptRun`), `kind` (op kind, or `script`), `source` (`user`/`mcp`; `user` for script runs), `startedAt`,
  `elapsedMs`. Ops on a connection add `connectionId` and `connectionName`. Script runs add `name` and `state`. Gate
  per op: `connectionID != nil` keeps it only when `s.resolveEnabled(id)` succeeds (one call per distinct id per
  listing). Script runs use `opId` `run:<id>`, the panel's own row id.
- `cancel_operation {opId}` (required, `RequireNonEmpty`):
  - `run:` prefix: find in `Runs.Live()`, then `Runs.Stop(id)`. Result `{"opId", "type": "scriptRun", "stopped": true}`.
  - Otherwise find in `Ops.RunningOps()`, apply the same exposure gate, then `CancelRunning`. Result
    `{"opId", "type": "op", "kind", "cancelled": true}`.
  - Miss, hidden connection, or `CancelRunning` false: `errResult("no running operation with id %q; it may have
    finished. Call list_operations for current ids.")`. One message for all three.
  - A nil `Runs` makes `run:` ids miss and lists no script runs.
- `addOpsTools(srv, src)` registers both with `withPanicRecovery`, same shape as `addProofTools`.

`apps/kira-studio/internal/dbmcp/server.go`:

- `Config.Ops OpsControl` (nil leaves both tools unregistered, like `Kube`) and `Config.Runs ScriptRunControl`.
- `buildMCPServer`: `if s.cfg.Ops != nil { s.addOpsTools(srv, src) }`. Fix the stale "five-tool" comments in passing.

## 5. Tests (paired at the IPC boundary)

Backend: `apps/kira-studio/internal/flows/dbmcpflow/ops_test.go`, on `newFixture`.

- `TestDbMcpCancelOperation`:
  1. Session A runs a long query via `callAsync`: `WITH RECURSIVE c(x) AS (SELECT 1 UNION ALL SELECT x+1 FROM c)
     SELECT count(*) FROM (SELECT x FROM c LIMIT 2000000000)`. Bounded so a broken cancel fails on the test timeout,
     never hangs. Confirm the SQLite adapter's execute honors ctx; pick another long statement if not.
  2. Session B polls `list_operations` until an `op` entry has kind `execute`, source `mcp` and `f.connID`.
  3. While it runs, `Ops.Recent` holds that id as `running`: record contract `ops-running` (mask `id`, `startedAt`,
     `durationMs`, `connectionId`).
  4. `cancel_operation` returns `cancelled: true`. Session A's call ends `IsError` with a cancel message. The
     `Ops.Recent` row reads `cancelled`. A second `cancel_operation` with that id gets the no-running-operation error.
  5. Hidden connection: a second SQLite connection with `McpEnabled: false` runs the long query through the user path
     (`Router.Execute`, no MCP source). `list_operations` omits it; `cancel_operation` with its id gets the same
     error. `W.Ops.Cancel` (the widget's backend path) then ends it `cancelled`.
- `TestDbMcpCancelScriptRun`: create a script `sleep 60`, start it as termflow `TestScriptRunStopAndClose` does
  (local minimal helper, no import of termflow internals). `list_operations` shows `run:<id>`, type `scriptRun`, state
  `running`. `cancel_operation` stops it; the run ends `cancelled`, reason "stopped by you".
