# P521 Scripts MCP

Ask (SPEC row): "Agents run a script and fetch its logs via MCP. Log fetch capped at a max line count; simple filter
(planner picks, e.g. tail/head and substring). Per-script MCP access is explicit opt-in. Per-script choice to show an
approval prompt or not. Scripts get descriptions, as connections have. Tools are async per P520."

User decisions given at plan time (override the row): tools are **synchronous** (P520 dropped async). Logs are never
in a run result; only a separate log tool returns them. P521 runs **in parallel with P520**: its approval prompt plugs
into today's `dbmcp.ApprovalBroker` and `DbMcpApprovalDialog` so it works now, and its item shape is the one P520's
single app-wide dialog renders with no rework (section 5).

Base: `chapter/v0.2.35` at `23639d3dd`. Discovery: `codegraph_explore` over `ApprovalBroker`/`ApprovalRequest`/
`awaitApproval`/`kubeRun`, `scriptruns.Service` (`Begin`, `Start`, `Stop`, `startHeadless`, `runHeadless`, `finish`,
`plan`), `Repo.Live`/`ReadLog`/`AppendLogs`, `scripts.CustomScript`/`File`/`projection.Record`, `configfs.Form`,
`dbmcp` `buildMCPServer`/`addOpsTools`/`withPanicRecovery`/`resolveEnabled`, `DbMcpApprovalDialog.vue`,
`KubeApprovalTarget.vue`, `MCPInstaller`. go-sdk v1.8.0 `ServerRequest.ClientInfo` read in module source.

## 1. Facts this plan builds on

- Studio normal scripts run in a terminal tab (`Start` returns a launch token; `Begin` records the run). Output then
  lives only in the terminal; `script_run_logs` stays empty. Scheduled normal runs use `startHeadless`: login shell,
  no stdin, `Setsid`, timeout, output through `logSink` into `script_run_logs`, secrets masked by `p.mask`, 5000
  lines kept per run (`maxLogLines`), 2 KiB per line. An MCP run reuses `startHeadless`; nothing new spawns processes.
- `startHeadless` runs under `context.Background()`, not a request ctx: a client that drops the call never kills the
  run. Stop is `Service.Stop` (P518 `cancel_operation run:<id>` already reaches it).
- `Service.Start` holds `startMu`, refuses a second running run of one script (`Runs.Running`), and `checkStart`
  refuses a stale preview hash (`changedSincePreview`). MCP reuses both.
- `script_runs.trigger_kind` has a CHECK `IN ('terminal','manual','ade','scheduled')` (Studio 0037). A new trigger
  needs a table rebuild.
- `custom_scripts.config_json` is the last good file value (projection). Reading new keys from it needs no new column.
- dbmcp gate precedent: a hidden connection reads exactly like an unknown id (`resolveEnabled`). Kube approvals ride
  `ApprovalRequest.Cluster`, a per-kind payload pointer with its own dialog branch. Scripts follow both.
- `kira-db` is stateless HTTP with one shared bearer token: no caller identity, no session id. go-sdk v1.8.0
  `req.ClientInfo()` returns the client's `Implementation` (name, version) from the per-request
  `io.modelcontextprotocol/clientInfo` `_meta` (modern protocol) or the session's initialize params; it can be nil.
- `runoutcome.Outcome` carries `LastError` and `OutputTail` (output text). An MCP run result must drop both: logs only
  through the log tool.

## 2. Scope decisions

Decided here (non-MCP or forced by the ask):

- One YAML key set plus one form, same decode path (`configfs.Form` with the scripts `DecodeFunc`; P514 rule).
- Description lives at `mcp.description`, mirroring connections (`mcp.description`) and clusters.
- `mcp.run`: `prompt` (default) or `allow`. Opt-in is `mcp.enabled` (default false). Missing block = hidden.
- MCP runs are headless with their own timeout `mcp.timeout` (default `scripts.DefaultScheduleTimeout`, 30m; same
  1m to 24h bounds; shares `validScheduleTimeout` logic through one helper).
- New trigger `mcp` (Runs panel shows "Agent"). Studio migration rebuilds `script_runs` for the CHECK.
- Secret params: an agent never supplies one. Secret values come only from saved values (`fillSaved`); a passed
  secret name is refused; a required secret with no saved value is refused naming the param. Approval payload and
  `list_scripts` show secret params as masked, never their value.
- No extra cap on concurrent MCP runs: one running run per script (existing rule) and opt-in already bound it.
- Log filter: `from` `tail` (default) or `head`, `lines` default 100, max 500, optional `contains` (plain substring,
  case-sensitive, SQL `instr`), applied before the line cap. Total text capped at 64 KiB per answer
  (`truncatedBytes: true` when hit).
- Wait: `run_script` and `get_script_run` take `waitSeconds` 0 to 50, default 25. 50 stays under Claude's 60 s
  default MCP cut in user sessions that lack P520's per-server `timeout`. The run outlives the call either way.
- Run result fields: `runId`, `opId` (`run:<id>`), `state`, `exitCode`, `reason`, `durationMs`, `logLines` (count),
  `next` text "Call get_script_logs for output." Never `lastError`, `outputTail` or any output.

**User decisions (MCP-related; orchestrator asks; defaults ship if unanswered):**

1. **Studio only.** Tools live on Studio's `kira-db`. Kira Space has no general MCP server for user sessions
   (agentmcp is per-run grants; memory MCP is unrelated). The shared run file accepts `mcp` keys in both apps, but
   Space's form hides the tab and nothing in Space reads them. Default: Studio only.
2. **Normal scripts only.** Smart scripts (headless Claude, budget spend) refuse `mcp.enabled: true` at validation
   ("A smart run cannot be exposed to MCP"). Default: refuse, same stance as P513.
3. **P518 visibility of script runs.** Today `list_operations`/`cancel_operation` show and stop every live script run,
   opt-in or not. Default: P521 narrows both to runs of MCP-enabled scripts (unknown-id text for the rest), matching
   the connection gate. Alternative: leave P518 as is.
4. **Run visibility for get tools.** Default: `get_script_run`/`get_script_logs` read any run (any trigger, including
   the user's own) of a script that is MCP-enabled now; a run of a hidden script reads as unknown. Alternative: only
   runs the agent started (`trigger mcp`).
5. **Origin in the approval header** is the MCP client name and version (`claude-code 2.1.318`), "Unknown client"
   when absent. No session or agent id exists on stateless `kira-db`; showing one needs stateful sessions, a P520
   topic. Default: client name and version only.
6. **Wait bound** 50 s max (above). If P520's per-server `timeout` lands and is always installed, a larger max could
   cut polling. Default: 50.

### 3.4 dbmcp tools (Studio)

New file `apps/kira-studio/internal/dbmcp/script_tools.go`. Consumer interface declared here, no `scriptruns` import:

```go
type ScriptControl interface {
	Exposed() ([]ExposedScript, error)               // MCP-enabled normal scripts, panel order
	Plan(scriptID string, params map[string][]string) (ScriptPlan, error)
	Start(scriptID string, params map[string][]string, hash string) (runID string, err error)
	Run(runID string) (ScriptRun, bool, error)        // false: no such run

```

`ExposedScript{ID, Name, Description, Run string; Params []ScriptParamInfo}`, `ScriptParamInfo{Name, Type string;
Options, Default []string; Required, Secret, Saved bool}`, `ScriptPlan{Hash, Command, Cwd, Blocker string; Missing

*int; StartedAt, FinishedAt *int64; Headless bool}`.

Tools (all through `withPanicRecovery`, registered by `addScriptTools` when `Config.Scripts != nil`):

- `list_scripts`, no args: `{"scripts":[{scriptId, name, description, approval: "prompt"|"allow", params:[...]}]}`.
  Secret params listed with `secret: true, saved: bool`, never a value.
- `run_script {scriptId, params?: {name: string|string[]}, waitSeconds?}`:
  1. Gate: `scriptId` in `Exposed()`, else `errResult("no script %q exposed to MCP")` (unknown, hidden, smart alike).
  2. `Plan`; plan errors (secret passed, missing, blocker) become `errResult` texts naming the fix.
  3. `run == prompt`: `Approvals.Request(ctx, ApprovalRequest{Subject: "script", ConnectionName: name, Kind: "script",
     Class: "", Statement: plan.Command, Reason: permission, Origin: originOf(req), Script: &ApprovalScript{...}})`.
     Non-approved maps through `approvalOutcomeError(outcome, fmt.Sprintf("run of script %q", name))`. After approve:
     re-check exposure and `run` (a revoked script wins: "script %q is no longer exposed to MCP"), then `Start` with the
     approved `plan.Hash`; a changed script fails with the `changedSincePreview` text.
  4. `run == allow`: `Start` at once.
  5. `Wait` under `context.WithTimeout(ctx, waitSeconds)`; answer the run result (section 2). `state` `running` means
     the wait ended first.
- `get_script_run {runId, waitSeconds?}`: gate (decision 4), optional `Wait`, same result shape.
- `get_script_logs {runId, from?: tail|head, lines?: 1..500, contains?}`: gate; a terminal run (`!Headless`) answers
  `{lines: [], note: "This run ran in a terminal tab; its output is not stored."}`. Else `{runId, state, lines:
  [{seq, stream, text}], matched, returned, truncated, truncatedBytes}`. Text is what `logSink` stored (masked).
- Schemas via `llmprompts.InputSchema` plus `RequireNonEmpty` (`scriptId`, `runId`); `waitSeconds` min 0 max 50,
  `lines` min 1 max 500, `from` enum.

## 5. Approval item contract with P520

The item every kind shares (Go `ApprovalRequest`, wire `DbMcpApproval`):

- Header (generic, all kinds): `requestId`, `subject` (kind key), `title` (= `connectionName`: connection name,
  cluster context, script name), `operation` label (kind-defined: statement class, kube group, `run script`),
  `origin` (`{client, version}` or null), `expiresAtMs`, `stage`.
- Payload (per kind, one nullable field each): `target`/`statement`/`plan`/`response` (query), `cluster` (kube),
  `script` (script: `scriptId, name, description, command, cwd, params[], env[]`, each value
  `{name, value, secret, saved, fromVar}`, secret value always empty).
- Answer: per item by `requestId` (`ApproveQuery`/`DenyQuery`, or P520's successor); each call returns on its own
  answer.

P520 must expose (whichever lands second adapts; no behaviour change for P521):

1. `Subject` on `ApprovalRequest` and `subject` on the wire, defaulted for legacy call sites. If P520 lands first
   with `Subject`, P521 reuses it and adds only `"script"`; if P521 lands first, P520 keeps P521's field and default.
2. A frontend kind registry mapping `subject` to `{ header: Component, body: Component, title(item): string }`,
   each component taking exactly `{ item: DbMcpApproval }`. P521's two components already match it.
3. Per-item countdown and Approve/Deny in its generic row chrome; the kind components render no buttons.
4. A per-kind prompt-router title hook (or keep `openPrompt`'s switch); P521's key `backend.prompt.dbMcpScript.title`.
5. `origin` rendered in the generic header when non-null. P521 owns `dbmcp/origin.go`; P520 fills `Origin` for query
   and kube with `originOf(req)` when it lands after P521 (one line per call site), or adds `origin.go` itself if it
   lands first, and P521 then drops its copy.

P521 adds: `Subject "script"`, `ApprovalScript`/`ApprovalValue`, `ApprovalOrigin` plus `originOf`, wire types,
`ScriptApprovalHeader.vue`, `ScriptApprovalBody.vue`, one registration line in P520's registry (if P520 landed) or
the `v-if` branch in today's dialog (if not), i18n, prompt title key.

Implementer: run `git log --oneline -20` first. If P520's commits are present, register the script kind in P520's
registry instead of editing the old dialog, and use P520's answer methods.
