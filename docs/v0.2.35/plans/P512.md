# P512 Tracked-item update indicators with per-concept settings

Stream A of wave A (parallel with P513, P514). Base: `chapter/v0.2.35` at `63c0cad4e`.

## Ask

User's words: "easily see that smth I'm tracking has been updated. E.g. a PR has new comments or was
merged. Same for Jira or a branch etc. Not noise like assignee or checks succeeded; but checks failed
yes, or new comments. All configurable from Settings: for every trackable concept I can say it is or
isn't a meaningful change. Granular: checks passed and checks failed are 2 independent options."

SPEC row defaults: comments, merge/close, checks failed, status change on; assignee, checks passed off.

## Discovery (codegraph)

What a task tracks today, and where each fact comes from:

- **Change request per branch.** `TaskBoard.ChangeRequests` (`ade/board.go:643`) calls
  `resolveRepoHost` per repo, which calls `RepoEntry.ResolveBranchChangeRequest` per created branch.
  That reads the persisted index (`git_host_change_requests`, migration 0047) filled by
  `gitsession/crsync.go`, with per-branch host lookups as fallback. Fields held: number, title,
  state (open/draft/merged/closed), draft, head sha, base, review decision, checks state, updated at.
  No comment count, no assignees. GitHub sync fields: `githost/github/sync.go` `syncPRFields`, shared
  by `syncPageQuery` (Page) and `syncChecksQuery` (Checks). Azure: `githost/azure/map.go` `mapPR`;
  `az repos pr list` carries no comment count and Azure has no assignees.
- **Issue (Jira) per task.** `Task.Jira` (key, url). `issuetracker.IssueDetails.IssueDetail(ref,
  fresh)` returns status, status category, assignee, priority, title, `CommentsTotal`,
  `CommentsOmitted`, Development summary (`Summary.Known/Count`), `FetchedAt`. Jira saved copy:
  fresh 30 s, kept 10 min (`jira/detail.go`). `TaskBoardDeps.Trackers` already holds the registry.
- **Branch facts per task branch.** `TaskBoard.Board` -> `repoFacts` -> `adewire.Branch`: `Tip`,
  `Behind`, `UpstreamBehind`, `MergedIntoMain`, `ConflictsIfRebased` + `ConflictCheck`,
  `Deployments`. Recomputed on every board read; fetch runs on autofetch and `TaskBoard.Refresh`.
- **Not tracked kinds (out of scope, stated):** run outcomes and needs-input already notify through
  agent notifications (P238) and the Blocked overlay; task status is set by Kira itself (noise by
  definition); `Task.HostURL` always comes with an attached branch, so its change request is the
  branch's. Mobile web (`frontend/mobile`) gets no indicator this phase; its Board wire is untouched.
- **Settings pattern.** Kira Space `settings` table of JSON leaves. `model/settings.go` (`Settings`,
  `SettingsPatch`, `Validate`, `Default*`), `repos/settings.go` (`GetAll` reads leaves over defaults,
  `Set` upserts patched leaves; `memory.models` is a whole-map leaf precedent), TS mirror
  `frontend/src/state/settingsDomain.ts` (zod with defaults), sections list
  `frontend/src/state/settings.ts`, panes in `frontend/src/workbench/settings/*.vue` composed by
  `frontend/src/workbench/SettingsDialog.vue` over `SettingsShell` (`isAtDefault`/`resetLeaf` per
  `section.key` leaf). Settings reach the renderer through the Pinia settings store
  (`onSettingsChanged` keeps every window live).
- **Push and query pattern.** ADE channels in `bridge/adewire/channels.go`
  (`kira:adetask:<suffix>`); desktop-only subscriptions in `frontend/src/ade/queries.ts`
  (`control.onAdeTaskReview` precedent); TanStack queries in `frontend/src/ade/v2/queries.ts`
  (`useTaskIssue` precedent, `control.*` from `frontend/src/bridge/index.ts`).
- **Name clash.** `ade.Tracker` is the agent session tracker. New code says "updates" and
  "tracked items", never "tracker".
- **Next migration:** 0070 (last is `0069_p511_manual_step_sandbox.sql`).

## Design

### Model: seen vs current snapshot per tracked item

Backend detection against a stored "seen" marker. Per tracked item the server stores two snapshots:
`seen` (what the user last acknowledged) and `current` (latest observation). A change is
`Diff(kind, seen, current)`: a list of concepts. Consequences, all intended:

- First observation of an item stores `seen = current`: tracking something new raises nothing.
- Diff compares states, not history. Checks failed then passed before the user looked reads
  `checksPassed` only. Comments 3 -> 5 reads `commentAdded` with count 2.
- Toggling a concept in Settings changes the indicator at once, with no lost data: filtering is a
  read-time view over stored snapshots.
- Mark seen copies `current` to `seen`.
- An unknown value on either side (`nil` comment count, Azure, lookup not ok) never fires.
- Snapshot JSON carries `v`; a version mismatch on decode resets `seen = current` (no false fire).

Item keys: `cr:<branchId>`, `branch:<branchId>`, `issue` (one per task).

### Concept catalog (single Go source, mirrored in TS)

New leaf package `apps/kira-space/internal/updates` (no deps beyond stdlib): catalog, snapshot
types, `Diff`. Concept ids and defaults:

| kind | concept | default | fires when (seen -> current) |
|---|---|---|---|
| changeRequest | opened | on | no CR -> CR (branch row first observed without one) |
| changeRequest | commentAdded | on | comment count grows (count = delta) |
| changeRequest | merged | on | state -> merged |
| changeRequest | closed | on | state -> closed |
| changeRequest | reopened | on | merged/closed -> open/draft |
| changeRequest | readyForReview | on | draft -> open |
| changeRequest | checksFailed | on | not FAILURE/ERROR -> FAILURE/ERROR |
| changeRequest | checksPassed | off | not SUCCESS -> SUCCESS |
| changeRequest | approved | on | review decision -> APPROVED |
| changeRequest | changesRequested | on | review decision -> CHANGES_REQUESTED |
| changeRequest | newCommits | off | head sha differs |
| changeRequest | titleChanged | off | title differs |
| changeRequest | assigneeChanged | off | sorted assignee logins differ |
| issue | statusChanged | on | status differs |
| issue | commentAdded | on | `CommentsTotal` grows, neither side omitted |
| issue | assigneeChanged | off | assignee id differs |
| issue | priorityChanged | off | priority differs |
| issue | titleChanged | off | title differs |
| issue | linkedChangeRequests | off | Development count differs, both known |
| branch | remoteCommits | on | `UpstreamBehind` grows (someone pushed) |
| branch | merged | on | `MergedIntoMain` false -> true |
| branch | conflicts | on | conflict set empty -> non-empty, check `done` both sides |
| branch | deploymentChanged | on | any environment's deploy status differs |
| branch | baseMoved | off | `Behind` grows |
| branch | localCommits | off | tip differs |

The table above lives in Go only as `updates.Catalog` (ordered slice per kind). This plan doc is
the one place it is spelled in prose. The TS mirror is
`frontend/src/state/trackingConcepts.ts`; the settings contract fixture (Tests) keeps the two equal.

### Change request facts: extend the persisted index

- `githost.ChangeRequest` gains `CommentCount *int` and `Assignees []string` (nil = unknown).
  `github.PR` gains the same; `toChangeRequests` copies them.
- `syncPRFields` adds `comments{totalCount} reviews{totalCount} assignees(first:10){nodes{login}}`.
  Comment count = issue comments + reviews. GitHub files every review-thread reply under a review, so
  replies count; a reply inside an already-pending review counts once the review submits.
  Cost: nested `first:10` over a 100-node page adds about 1 point per page.
- Azure leaves both nil. Real limitation: Azure PRs never fire `commentAdded` or `assigneeChanged`.
  Record it in `docs/ARCHITECTURE.md` "Known open items" and in the pane's description.
- Migration 0070 adds `comment_count INTEGER` (NULL = unknown) and `assignees TEXT` (NULL = unknown,
  else a JSON array) to `git_host_change_requests`. `repos/githostchangerequests.go` reads and
  writes them.
- Bump `model.GitHostSchemaVersion` 1 -> 2 so existing rows drop and backfill with the new fields
  (the existing invalidation path). Until backfill completes the per-branch fallback answers.
- `gitrpc.ChangeRequestRecord` mirrors `githost.ChangeRequest` field for field: add
  `commentCount *int` and `assignees []string`, both `omitempty`.
- `fakehost.Forge`: `AddComments(number, n)` and `SetAssignees(number, logins...)`. Both bump `rev`
  and `UpdatedAt`, like a real host listing change. `PostChangeRequestComment` and `Comment` also
  bump the count. `withSyncFields` fills `CommentCount` and `Assignees`.

### Storage

`0070_p512_tracked_updates.sql`:

```sql
CREATE TABLE ade_tracked_items (
    task_id      TEXT    NOT NULL,
    item_key     TEXT    NOT NULL,
    kind         TEXT    NOT NULL,
    seen_json    TEXT    NOT NULL,
    current_json TEXT    NOT NULL,
    seen_at      INTEGER NOT NULL,
    observed_at  INTEGER NOT NULL,
    changed_at   INTEGER NOT NULL DEFAULT 0,
    PRIMARY KEY (task_id, item_key)
);
ALTER TABLE git_host_change_requests ADD COLUMN comment_count INTEGER;
ALTER TABLE git_host_change_requests ADD COLUMN assignees TEXT;
```

`changed_at`: time `current` last diverged from `seen` (0 while equal). No SQL FK, like the other
ADE tables. `repos.AdeTrackedItemsRepo` (new file, registered in the `repos.New` aggregate):
`List() ([]model.AdeTrackedItem, error)`, `Apply(upserts, deleteKeys)` in one transaction,
`MarkSeen(taskID string, itemKeys []string, now int64) (changed bool, err error)` (empty keys = every
item of the task).

### Backend watcher (`ade/updates.go`)

`updateWatcher` owned by `TaskBoard`. One `observe(ctx, fresh bool)` pass, serialized by a mutex,
coalesced with `singleflight`:

1. Load live tasks and live branches (`deps.Tasks`).
2. Branch facts: `b.Board(ctx)` branches by id -> `updates.BranchSnap`. A `checking` conflict state
   keeps the previous conflict value.
3. Change requests: per repo, `resolveRepoHost` (same call `ChangeRequests` makes). A lookup kind
   other than `ok` keeps the previous snapshot for that repo's branches. A created branch with no CR
   records `CRSnap{Present:false}`, so a later CR fires `opened`.
4. Issues: per task with `Jira`, resolve the ref the way `TaskIssue` does, then
   `IssueDetails.IssueDetail(ctx, ref, fresh)`. Not fresh: skip a task observed under
   `JiraInterval` ago; read fresh when the saved copy's `FetchedAt` is older than `JiraInterval`.
   Concurrency 2, each read bounded by the provider. A tracker error keeps the previous snapshot.
5. Diff against stored rows: insert new items with `seen = current`; update `current`,
   `observed_at`, `changed_at`; delete rows whose task is not live or whose item key no longer exists
   (archive, detach, Jira cleared). One `Apply` transaction.
6. If any row's `current` changed, or rows were added or removed, call `deps.OnUpdates()`.

Triggers (`TaskBoardDeps.Updates UpdatesConfig{Disabled bool; MinGap, Interval, JiraInterval
time.Duration}`, zero fields take defaults 30 s, 5 min, 10 min):

- End of `TaskBoard.Refresh` (explicit user action): `observe(ctx, true)`, awaited, so a flow test
  and the user both get a settled result.
- Board change: the `scheduleBoard`/`notifyBoard` debounce schedules a pass, gated by `MinGap`.
- Timer every `Interval`.
- `Disabled` turns the last two off, like `CRSyncConfig.Disabled`. Flowharness defaults to
  `Disabled` with `WithTrackedUpdates(cfg)` to override, mirroring `WithChangeRequestSync`.
- `Start` arms the timer; `Close` stops it and waits through `b.wg` (`goTracked`).

Engine methods: `TrackedUpdates(ctx) (adewire.TrackedUpdatesResult, error)` returns every item whose
raw diff is non-empty, unfiltered. `MarkTrackedSeen(ctx, args) error` calls `MarkSeen` and, when
anything changed, `OnUpdates`.

### Wire and bridge

`adewire`:

```go
type TrackedUpdate struct {
    TaskID    string         `json:"taskId"`
    ItemKey   string         `json:"itemKey"`
    Kind      string         `json:"kind"`     // changeRequest | issue | branch
    BranchID  string         `json:"branchId"` // '' for issue
    Label     string         `json:"label"`    // "#12", "KIRA-12", branch name
    Concepts  []string       `json:"concepts"`
    Counts    map[string]int `json:"counts"`   // commentAdded -> new comments
    ChangedAt int64          `json:"changedAt"`
}
type TrackedUpdatesResult struct{ Updates []TrackedUpdate `json:"updates"` }
type MarkTrackedSeenArgs struct {
    TaskID   string   `json:"taskId"`
    ItemKeys []string `json:"itemKeys"` // empty = every item of the task
}
```

`ChannelUpdates = "kira:adetask:updates"` (payload-free). `bridge.AdeTaskService` adds
`TrackedUpdates` and `MarkTrackedSeen` (validate task id with `validateAdeTaskID`, at most 64 item
keys, each matching `^(issue|cr:[A-Za-z0-9_-]{1,64}|branch:[A-Za-z0-9_-]{1,64})$`), plus
`AdeTaskUpdatesChanged(ev)` broadcasting the channel. `appwire.wireAdeTask` sets `OnUpdates`.
The server does not filter by settings. The renderer filters with the live settings store, so a
toggle re-renders with no IPC. Raw concepts stay testable in Go; the filter stays testable in the UI.

## Risks

- Schema version bump re-backfills every repo's change request index: a burst of GraphQL pages on
  first launch (bounded by PageCap 10 per run and the low-budget stop).
- Kira's own actions raise indicators: a comment posted from the PR view, an agent push
  (`localCommits`/`newCommits` default off for that reason). Comment self-echo stays; acceptable,
  one Mark seen.
- Azure never fires `commentAdded`/`assigneeChanged` (no data); documented as a known open item.
- Jira polling costs one `acli` view per linked task per 10 min while the app runs.
- The extra `Board` + `resolveRepoHost` read per watcher pass adds git work on board churn; gated by
  the 30 s MinGap and the existing fact caches.
- Shared i18n/test-support files with P513/P514 may need hand rebase; edits are additive blocks.
