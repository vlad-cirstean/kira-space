## 1. Facts (today)

- One tool, `run_query`, takes any statement. `resolveVerdict` asks the live adapter's `ClassifyStatement`
  (`tools.go:396`) and maps the class to the connection's read, write or ddl mode (`verdictFor`). Unknown takes the
  strictest. **The classifier decides which permission applies.** That is the security boundary today.
- `executeAndRender` (`tools.go:236`) sets `ExecuteRequestWire.ReadOnly` only when `class == read && write != "allow"`.
  So with writes allowed, a statement classified read (`SELECT write_fn()`) runs with no read-only wrap at all.
- `ReadOnly` per request reaches `ConsoleRequest.ReadOnly`. Honoured by **postgres** (`BEGIN READ ONLY`, plus
  session `default_transaction_read_only` when the connection is read-only) and **mysqlfamily** (`START TRANSACTION
  READ ONLY`, re-verified per statement). **Ignored** by sqlite (`Execute` passes no flag; `mode=ro`/`_query_only=1`
  only when the whole connection is read-only), clickhouse (`readonly=2` URL param only from `Handle.ReadOnly`),
  mongo and redis (use connection `readOnly` only; enforcement is Kira code: `isWriteStatement`,
  COMMAND-table flags in `isReadOnlyCommand`).
- `explain_query` and auto-explain (`planFor`, `explain.go:171`) call `Execute` with no `ReadOnly`; safety rests on
  `assertComposedStatementsAreReads` (classifier again).
- Kafka, S3, SQS: `Execute` returns `NoQueryConsole`. Kibana: `Execute` is one Discover search (read by construction).
  No Elasticsearch adapter exists.
- One live adapter per connection id (`adapters.SetLiveAdapter`), created by `Router.Connect` from a
  `ResolvedConnectionConfig` that `connections.resolve` builds (secrets from the connection file via
  `resolveSecret`). The human console and MCP share that adapter and its connections.
- Cancel: `Host.stopOp` cancels the op ctx, then calls `GetLiveAdapter(connID).Cancel(opID)`. Each adapter's tracker
  knows only its own queries, so an op on any other adapter instance cannot be server-cancelled today.
- Op ids minted in dbmcp with `uuid.NewString()` (`tools.go:229`, `explain.go:172`); approval ids in `approval.go:216`.
  P523 converts these.
- Permission modes: per connection file `mcp.read|write|ddl` = deny/allow/prompt (defaults allow/prompt/deny).
  Stored in `connections` columns. `read_only: true` connections are already read-only at session level.
- ARCHITECTURE Known open item (P329) documents residual side effects of the read-only wrap.

## 2. Design

### 2.1 Headline

Two dedicated tools replace `run_query`: **`run_read`** and **`run_write`**. The tool, not the statement text,
selects the permission and the connection:

- `run_read` always executes on the connection's **read lane**: a second adapter instance for the same connection,
  opened with the connection's existing read-only mode forced on (`ReadOnly: true`), optionally under a separate
  least-privilege read user. The read-only mode each adapter already has for `read_only: true` connections is the
  strongest enforcement Kira owns; the lane reuses it instead of writing a new path.
- `run_write` executes on the primary adapter, only after the write gate passes.
- The classifier stays, demoted: it labels the approval item (operation type and tone) and may only **tighten**
  (short-circuit a `run_read` call that classifies as write or DDL with a hint error). It never relaxes a gate and
  never picks the connection.

### 2.2 Per-adapter capability matrix

| Kind | Read lane mechanism (engine) | With read user | Residual limits on lane | Lane cost |
|---|---|---|---|---|
| postgres | Session `default_transaction_read_only = on` at dial plus `BEGIN READ ONLY` per batch, `AssertNoTransactionEscalation` (existing read-only connection path) | Role with `pg_read_all_data` (14+) or SELECT grants | Read-only tx still allows `pg_terminate_backend`/`pg_cancel_backend` on same-role backends, `dblink_exec`, advisory locks. A separate read role confines terminate/cancel to the lane's own backends | One extra backend per (connection, database) in the LRU `ConnSet` |
| mysql, mariadb | `SET SESSION TRANSACTION READ ONLY` at dial plus `START TRANSACTION READ ONLY` per batch, `verifyReadOnlyWrap` (existing) | User with `SELECT` (and `SHOW VIEW`) only | `GET_LOCK`, temporary-table writes, `KILL` of same-user threads. Read user closes `KILL` reach | One extra session per database in `ConnSet` |
| sqlite | Second `sql.DB` with `mode=ro&_query_only=1` (existing `buildDSN(path, true)`) | n/a (file) | `ATTACH` of another file: implementer verifies on the lane that `ATTACH` cannot create or write a file under `_query_only=1`; if it can, set `SQLITE_LIMIT_ATTACHED` to 0 on the lane conn when modernc exposes `sqlite3_limit`, else record a Known open item | One extra file handle, `MaxOpenConns(1)` |
| clickhouse | `readonly=2` URL setting on every lane request (existing `Handle.ReadOnly`) | User with `readonly = 1` profile or SELECT grants | `readonly=2` allows setting changes (console sends caps as settings). External table functions (`url()`, `s3()`) still read out. | None (stateless HTTP) |
| mongodb | **No engine read-only session.** Lane `ReadOnly: true` keeps today's Kira-side method check (`isWriteStatement`, aggregate `$out`/`$merge`) | User with `read` role: server refuses writes (code 13 Unauthorized). **Only DB-level option** | Without read user: app-level enforcement only (labelled `app`, section 2.6) | Driver pool; lane sets `maxPoolSize=2` |
| redis | **No engine read-only session** (`READONLY` is a cluster-replica flag, not a write block). Lane `ReadOnly: true` keeps COMMAND-table flag check; `EVAL_RO`/`FCALL_RO` server-enforced | ACL user `-@all +@read +@connection` (or `-@write -@dangerous`): server refuses (NOPERM). **Only DB-level option** | Without read user: app-level only (labelled `app`) | go-redis pool; lane sets `PoolSize=2` |
| kibana | No lane: `Execute` has no write path | n/a | `run_write` refused ("no write console") | none |
| kafka, s3, sqs | No console: both tools refused as today (`NoQueryConsole`) | n/a | metadata tools unchanged | none |

Enforcement label per connection (computed, never configured): `session` (engine read-only session or file mode),
`user` (read credentials set; strongest), `app` (mongo/redis with no read user), `none` (kibana: read by
construction, kafka/s3/sqs: no console).

### 2.3 Read lane (`adapterhost`)

New file `apps/kira-studio/internal/adapterhost/readlane.go`, owned by `Router`:

- `Router` keeps the last resolved config per connection (`cfgs map[string]model.ResolvedConnectionConfig`, under
  `teardown` lock), set in `Connect` after success, cleared in `Disconnect`. Same secret already sits in adapter
  memory; never serialised.
- `Router.ExecuteRead(ctx, req ExecuteRequestWire) (ExecuteResponse, error)`: requires a live primary (else
  `CodeEngineDown`, same as today), gets or opens the lane, runs `adapter.Execute` through `Host.RunOp` with
  `OpSpec{ConnectionID: &id, Kind: "execute", Adapter: lane}` and `ConsoleRequest.ReadOnly = true`.
  `Router.Execute` (primary) stays for the console and `run_write`.
- Lane open: `adapters.CreateAdapter(kind)` then `Connect` inside `RunOp` kind `connect` on the same connection id,
  with `laneConfig(cfg)`: copy, `ReadOnly = true`, read credentials substituted when set (2.5), pool caps for mongo
  and redis via `Options`. Deduplicated per connection (singleflight-style under the keyed mutex): concurrent first
  calls open one lane.
- **Fail closed.** A lane that cannot open returns its connect error to the agent. Never falls back to the primary.
- Lane teardown, every path: `Router.Connect` (reconnect) and `Router.Disconnect` tear the lane down first
  (cancel lane ops, `Disconnect` bounded by `disconnectTimeout`); `Router.CloseReadLane(id)` for exposure off;
  `Router.CloseReadLanes()` on DB MCP server stop and app quit; idle close after 10 minutes without a lane op
  (decision 5). A compare-and-delete like `DeleteLiveAdapterIf` guards the lane map against reconnect races.
- Pre-connect script and sidecar tunnel: the lane reuses the primary's resolved host/port, opens only while the
  primary is connected, and never runs the pre-connect script. Primary reconnect recreates the lane lazily.
- Throttle: lane ops share the connection's limiter (same `ConnectionID` in `RunOp`).
- Kinds without a lane (2.2) route `ExecuteRead` to the primary; kafka/s3/sqs return `NoQueryConsole` as today.
- `Router.ReadLaneState(id) (open bool, enforcement string)` feeds `list_connections` and the approval item.

Cancel with two connections (P518):

- `OpSpec` gains `Adapter adapters.Adapter`; `runningOp` stores it. `Host.stopOp` calls `op.adapter.Cancel` when
  set, else `GetLiveAdapter` as today. A lane query then server-cancels on the lane's own connection (postgres
  `pg_cancel_backend` from the lane role on its own backend, mysql `KILL QUERY` on its own thread, clickhouse
  `KILL QUERY` by query id, mongo `killOp`).
- `CancelOpsForConnection` already matches by connection id, so reconnect and disconnect cancel lane ops too.
- `list_operations` and the status bar widget list lane ops under the same connection (same id, `source: mcp`).
  `cancel_operation` needs no change: it resolves the op by id through `CancelRunning`.
- No op-log schema change. The op command text is the statement, as today.

### 2.4 Tools (`dbmcp`)

`tools.go` splits: `run_query` handler goes; new `read_tools.go` (`runRead`) and `write_tools.go` (`runWrite`)
share a pipeline helper kept in `tools.go` (resolve, path check, maxRows clamp, connect, approval, execute, render,
review). Both reuse `executeAndRender` with a `lane` argument instead of the `ReadOnly` expression.

`run_read` (args identical to today's `run_query`: `connectionId`, `sql`, `path`, `maxRows`):

1. `resolveEnabled`, `needsDatabasePath`, read mode deny refuses before connecting.
2. `connectForQuery` (primary must be up; the lane follows it).
3. Classify (hint). Write or DDL class returns `"run_read runs on a read-only connection; this statement writes.
   Use run_write."` without prompting. Unknown or read proceed. A classifier error proceeds (the lane enforces).
4. `maybeExplain` on the lane (heavy check unchanged).
5. Read mode prompt or heavy raises one approval (`Tool: "read"`), re-check after approval as today.
6. `ExecuteRead`. A server read-only refusal (postgres 25006, mysql 1792/1290, sqlite 8, clickhouse 164, mongo 13,
   redis NOPERM, Kira's own read-only refusal on `app` lanes) returns `"the database refused a write on the read-only
   connection: <engine message>. Use run_write."`, masked when the connection has mask rules (existing
   `maskedToolError`).
7. Render and result review unchanged.

`run_write` (same args):

1. `resolveEnabled`, `needsDatabasePath`. Refuse when the connection is `read_only: true`
   (`"connection %q is read-only"`) and for kinds with no write console (kibana, kafka, s3, sqs).
2. Write gate (decision 2, default): verdict = `strictestOf(write, ddl)` via a new `writeVerdict(modes)` in
   `permissions.go`. Deny refuses before connecting.
3. Connect, classify (hint only: labels the approval item; a read class adds the hint "this looks like a read; run_read
   needs no write permission" to the approval lede, never to the gate).
4. Prompt raises one approval (`Tool: "write"`). After approval, re-resolve and re-check `writeVerdict` (today's
   tightened-mode posture).
5. `Router.Execute` on the primary, `ReadOnly: false`. No auto-explain (EXPLAIN of a write is not run today either).
6. Render and result review unchanged.

`explain_query` executes its composed EXPLAIN through `ExecuteRead`; `assertComposedStatementsAreReads` stays as
defence in depth. `planFor` (auto-explain) does the same.

Schemas and descriptions (registry, `internal/llmprompts/registry.go`, ids `dbmcp.tool.run_read` and
`dbmcp.tool.run_write`, args copied from `run_query`'s four `arg` lines):

- `run_read`: "Run one read statement per call on a read-only connection to the database. Connects the connection if
  not connected. The database itself refuses writes here, including writes hidden in functions; a refused write
  returns an error naming run_write. Reading stops at maxRows: rowCount is rows fetched, a lower bound when truncated
  is true. The connection's read permission applies: deny refuses, prompt waits for user approval. With auto-explain
  on, an expensive plan pauses for approval. On kibana, `sql` is one Discover request as JSON."
- `run_write`: "Run one statement that changes data or schema, on the connection's normal session. Needs the
  connection's write permission; the stricter of its write and DDL permissions applies to every call. Refused on
  read-only connections and on kibana, kafka, s3 and sqs. Use run_read for reads: it needs no write permission."
- `dbmcp.instructions`: replace the `run_query` sentences with the two-tool rule and the `enforcement` field.
- `list_connections` view gains `enforcement` (`user`, `session`, `app`, `none`) and keeps `permissions`; its
  description names the field.

Registration in `buildMCPServer`: two `mcp.AddTool` calls replace `run_query`'s, same `RequireNonEmpty` and `LimitVars`.
`withPanicRecovery` names `run_read`/`run_write`.

### 2.5 Read credentials (optional, per connection)

Connection file keys under `mcp` (`connfiles.MCP`, `ConnectionFileMcp`, JSON schema):

- `read_username` (fields mode) and `read_password: ${secret:name}` (secret kind `password`, P516 reveal field).
- `read_uri: ${secret:name}` (uri mode, secret kind `uri`).

Resolution: `connections.resolve` reads them from `rec.File.MCP` (no SQL column, no migration) with the existing
`resolveSecret`; `ResolvedConnectionConfig` gains `ReadCredentials *ReadCredentials {Username, Password, URI
*string}` (never on the wire, same rule as `Password`). Unset keys mean the lane uses the primary credentials with
the session-level mechanism. A missing secret fails the lane open with the existing secret-missing text.

Write credentials are not added (decision 3).

### 2.6 Permission mode mapping

| Connection setting | `run_read` | `run_write` |
|---|---|---|
| read deny | refused | n/a |
| read allow / prompt | runs / approval, on lane | n/a |
| write and ddl both allow | n/a | runs |
| either prompt, neither deny | n/a | approval |
| either deny | n/a | refused (decision 2) |
| `read_only: true` | lane (primary also read-only) | refused |
| `review_results` | applies | applies |
| `auto_explain` | applies (on lane) | not applied |

`list_children`, `describe_table`, `describe_schema` stay on the primary: Kira-authored catalog reads, no agent SQL,
gated on read deny as today. Kube tools unchanged.

UI (`ConnectionMcpTab.vue`): the three segmented controls stay. Write and DDL notes gain one line: "MCP write calls
use the stricter of Write and DDL." A new "Read connection" block: enforcement badge (computed by kind and whether
read credentials are set), Read username field and `SecretInput` password (or Read URI in uri mode). Tailwind,
shadcn-vue, P525 outline rules. Form and YAML edit the same file (P514 `useConnectionFormDraft`).

## 7. Security checklist (implementer proves each by a test or a grep)

1. No code path executes `run_read` SQL on the primary adapter for a kind that has a lane (grep: `runRead` reaches only
   `ExecuteRead`; flow `TestDbMcpReadLanePostgres`).
2. Lane open failure never falls back to the primary (test: wrong read password returns the connect error).
3. Classification never relaxes a gate: `run_read` gate reads only the read mode; `run_write` gate reads only
   `writeVerdict`; grep that no verdict is computed from `OpClass` outside the hint.
4. `run_write` refuses `read_only: true` connections before connecting.
5. Re-check after approval on both tools (mode tightened or exposure revoked while waiting).
6. Read credentials never reach the renderer, logs or op command text; `ResolvedConnectionConfig` stays off the wire.
7. Lane closes on disconnect, reconnect, exposure off, server stop, app quit and idle; no orphan sessions (container
   process list in the lifecycle scenario).
8. Lane cancel hits the lane adapter (scenario `LaneCancel`).

## 10. User decisions (plan defaults shown)

1. **Tool names and `run_query`.** Default: `run_read` and `run_write`, `run_query` removed (breaking). Alternative:
   keep `run_query` one chapter as a router (read class to the lane, anything else to the write gate). Safe either way
   because the lane enforces, but it keeps text guessing in the agent's path.
2. **Write gate.** Default: `run_write` uses the stricter of the write and DDL modes, so classification never picks
   a gate. Cost: write allow + DDL prompt now prompts every write; write allow + DDL deny refuses every write.
   Alternative: classifier picks write vs DDL mode inside `run_write` (read/write stays database-enforced; DML vs DDL
   becomes text-guessed again). Third option: collapse the UI to Read and Write modes and retire `ddl`.
3. **Credentials.** Default: optional read credentials only. No write credentials, so DDL is never database-enforced.
   Say if a separate least-privilege write user (DML grants only) is wanted.
4. **Mongo and Redis without a read user.** Default: `run_read` still works with app-level enforcement, labelled `app`
   in `list_connections` and the approval item. Alternative: require read credentials before `run_read` is offered on
   those kinds.
5. **Lane idle close.** Default 10 minutes. Alternative: keep the lane open while the primary is connected (one extra
   server session per exposed connection while connected).
6. **Prompt overrides.** Default: a saved override of the `run_query` description is ignored, not migrated.
7. **Tighten-only hint.** Default: `run_read` refuses a statement the classifier calls write or DDL without prompting
   (saves a doomed approval). Alternative: always send it to the lane and let the database refuse.
