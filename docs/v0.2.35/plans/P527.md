# P527 DB MCP declared query mode enforced by the database

Ask (user, verbatim): "The db mcp tool should use dedicated read and write methods that actually enforce the
permissions on db level or by using 2 connections one for read and one for write depending on the db."

User decisions (after two drafts, binding):

- One tool, `run_query`, keeps its name. It gains a **required** `mode` argument: `read`, `write` or `ddl`.
- The declared mode picks the connection and the permission gate. `read` runs on a read lane: a second connection,
  same credentials, the engine's session-level read-only mode. `write` and `ddl` run on the main connection under the

- `list_connections` reports each connection's MCP permissions: allowed modes and whether each needs approval. An
  error for a mode the connection does not allow names the connection and its allowed modes.
- No second credentials anywhere.

## 1. Facts (today)

- `run_query` takes any statement. `resolveVerdict` asks the live adapter's `ClassifyStatement` (`tools.go:396`) and
  maps the class to the read, write or ddl mode (`verdictFor`); unknown takes the strictest. **The classifier decides
  which permission applies.** That is the security boundary today.
- `executeAndRender` (`tools.go:236`) sets `ExecuteRequestWire.ReadOnly` only when `class == read && write !=
  "allow"`. With writes allowed, a statement classified read (`SELECT write_fn()`) runs with no read-only wrap.
- `ReadOnly` per request reaches `ConsoleRequest.ReadOnly`. Honoured by **postgres** (`BEGIN READ ONLY`; session
  `default_transaction_read_only` when the connection is read-only) and **mysqlfamily** (`START TRANSACTION READ
  ONLY`, re-verified per statement). **Ignored** by sqlite (`mode=ro`/`_query_only=1` only for a read-only
  connection), clickhouse (`readonly=2` only from `Handle.ReadOnly`), mongo and redis (connection `readOnly` only;
  enforcement is Kira code: `isWriteStatement`, COMMAND-table flags in `isReadOnlyCommand`).
- `explain_query` and auto-explain (`planFor`, `explain.go:171`) call `Execute` with no `ReadOnly`; safety rests on
  `assertComposedStatementsAreReads` (classifier again).
- Kafka, S3, SQS: `Execute` returns `NoQueryConsole`. Kibana: `Execute` is one Discover search (read by construction).
  No Elasticsearch adapter exists.
- One live adapter per connection id (`adapters.SetLiveAdapter`), created by `Router.Connect` from a
  `ResolvedConnectionConfig` that `connections.resolve` builds. The human console and MCP share that adapter.
- Cancel: `Host.stopOp` cancels the op ctx, then calls `GetLiveAdapter(connID).Cancel(opID)`. Each adapter's tracker
  knows only its own queries.
- Op ids minted in dbmcp with `uuid.NewString()` (`tools.go:229`, `explain.go:172`); approval ids in `approval.go:216`.
  P523 converts these.
- Permission modes: connection file `mcp.read|write|ddl` = deny/allow/prompt (defaults allow/prompt/deny), stored in
  `connections` columns. `list_connections` already returns `permissions: {read, write, ddl}` raw.
- ARCHITECTURE Known open item (P329) documents residual side effects of the read-only wrap.

## 2. Design

### 2.1 Headline

`run_query(connectionId, sql, path, maxRows, mode)`. `mode` is required and is the security input:

| Declared mode | Connection | Gate | Classifier role |
|---|---|---|---|
| `read` | read lane (second adapter, same credentials, `ReadOnly: true`) | read permission | rejects write, DDL or unknown class |
| `write` | main | write permission | rejects DDL or unknown class |
| `ddl` | main | DDL permission | none (DDL is the most powerful mode) |

The classifier can only refuse; it never picks the connection and never relaxes a gate. The engine enforces `read` on
the lane where it can (2.2). `write` vs `ddl` is gated by permission and the classifier's tighten-only check; no
engine separates DML from DDL on one session with the same credentials, so a DDL statement the classifier
misreads as a write runs under the write permission. That residual is named in 2.2 and the Known open items.

Unknown class: under `read` it is rejected (the lane would enforce anyway on `session` kinds, but on `app` kinds Kira's
check is all there is, and today unknown already takes the strictest rule). Under `write` it is rejected too, with
the hint to declare `ddl`. A classifier error is treated as unknown.

### 2.2 Per-adapter capability matrix (read lane)

| Kind | Read lane mechanism | Enforcement | Residual limits | Lane cost |
|---|---|---|---|---|
| postgres | Session `default_transaction_read_only = on` at dial plus `BEGIN READ ONLY` per batch, `AssertNoTransactionEscalation` (existing read-only connection path) | `session` | Read-only tx still allows `pg_terminate_backend`/`pg_cancel_backend` on same-role backends, `dblink_exec`, advisory locks | One extra backend per (connection, database) in the LRU `ConnSet` |
| mysql, mariadb | `SET SESSION TRANSACTION READ ONLY` at dial plus `START TRANSACTION READ ONLY` per batch, `verifyReadOnlyWrap` (existing) | `session` | `GET_LOCK`, temporary-table writes, `KILL` of same-user threads | One extra session per database in `ConnSet` |
| sqlite | Second `sql.DB` with `mode=ro&_query_only=1` (existing `buildDSN(path, true)`) | `session` (file opened read-only) | `ATTACH`: implementer verifies on the lane that `ATTACH` cannot create or write a file under `_query_only=1`; if it can, set `SQLITE_LIMIT_ATTACHED` to 0 on the lane conn when modernc exposes `sqlite3_limit`, else record a Known open item | One extra file handle, `MaxOpenConns(1)` |
| clickhouse | `readonly=2` URL setting on every lane request (existing `Handle.ReadOnly`) | `session` (server setting per request) | `readonly=2` allows setting changes (caps go as settings). External table functions (`url()`, `s3()`) still read out | None (stateless HTTP) |
| mongodb | No engine read-only session. Lane `ReadOnly: true` keeps Kira's structural method check (`isWriteStatement`, aggregate `$out`/`$merge`) | `app` | **Known limit:** not database-enforced | Driver pool; lane sets `maxPoolSize=2` |
| redis | No engine read-only session (`READONLY` is a cluster-replica flag, not a write block). Lane `ReadOnly: true` keeps Kira's check against the server's COMMAND flags; `EVAL_RO`/`FCALL_RO` are server-enforced | `app` | **Known limit:** not database-enforced | go-redis pool; lane sets `PoolSize=2` |
| kibana | No lane: `Execute` has no write path | `none` | `write`/`ddl` refused: no write console | none |
| kafka, s3, sqs | No console: every mode refused as today (`NoQueryConsole`) | `none` | metadata tools unchanged | none |

Enforcement label (computed from kind, never configured): `session`, `app`, `none`.

**Known limit, stated plainly:** on Mongo and Redis `mode=read` is not database-enforced. A second connection with
the same credentials has the same server rights, and neither engine has a session read-only switch. Only a separate
least-privilege user could close it, and the user ruled out second credentials. The `app` label tells the agent and
the approver; ARCHITECTURE Known open items records it, with the write-vs-DDL residual of 2.1.

### 2.3 Read lane (`adapterhost`)

New file `apps/kira-studio/internal/adapterhost/readlane.go`, owned by `Router`:

- `Router` keeps the last resolved config per connection (`cfgs map[string]model.ResolvedConnectionConfig`, under
  the `teardown` lock), set in `Connect` after success, cleared in `Disconnect`. The secret already sits in adapter
  memory; never serialised.
- `Router.ExecuteRead(ctx, req ExecuteRequestWire) (ExecuteResponse, error)`: requires a live primary (else
  `CodeEngineDown`, as today), gets or opens the lane, runs `adapter.Execute` through `Host.RunOp` with
  `OpSpec{ConnectionID: &id, Kind: "execute", Adapter: lane}` and `ConsoleRequest.ReadOnly = true`.
  `Router.Execute` (main) stays for the console and `write`/`ddl`.
- Lane open: `adapters.CreateAdapter(kind)` then `Connect` inside `RunOp` kind `connect` on the same connection id,
  with `laneConfig(cfg)`: copy, `ReadOnly = true`, same credentials, pool caps for mongo and redis via `Options`.
  Deduplicated per connection under the keyed mutex: concurrent first calls open one lane.
- **Fail closed.** A lane that cannot open returns its connect error. Never falls back to the main connection.
- Lane teardown, every path: `Router.Connect` (reconnect) and `Router.Disconnect` tear the lane down first (cancel
  lane ops, `Disconnect` bounded by `disconnectTimeout`); `Router.CloseReadLane(id)` for exposure off;
  `Router.CloseReadLanes()` on DB MCP server stop and app quit; idle close after 10 minutes without a lane op
  (decision 2). A compare-and-delete like `DeleteLiveAdapterIf` guards the lane map against reconnect races.
- Pre-connect script and sidecar tunnel: the lane reuses the main connection's resolved host/port, opens only while
  the main connection is up, and never runs the pre-connect script. A main reconnect recreates the lane lazily.
- Throttle: lane ops share the connection's limiter (same `ConnectionID` in `RunOp`).
- Kinds without a lane (2.2) route `ExecuteRead` to the main adapter; kafka/s3/sqs return `NoQueryConsole` as today.
- `Router.ReadLaneOpen(id) bool` for tests and lifecycle checks.

Cancel with two connections (P518):

- `OpSpec` gains `Adapter adapters.Adapter`; `runningOp` stores it. `Host.stopOp` calls `op.adapter.Cancel` when set,
  else `GetLiveAdapter` as today. A lane query then server-cancels on the lane's own connection (postgres
  `pg_cancel_backend`, mysql `KILL QUERY`, clickhouse `KILL QUERY` by query id, mongo `killOp`).
- `CancelOpsForConnection` matches by connection id, so reconnect and disconnect cancel lane ops too.
- `list_operations` and the status bar widget list lane ops under the same connection (`source: mcp`).
  `cancel_operation` needs no change: it resolves the op by id through `CancelRunning`.
- No op-log schema change. The op command text is the statement, as today.

### 2.4 `run_query` (`dbmcp`)

Args: `connectionId`, `sql`, `path`, `maxRows` as today, plus `mode` (`string`, enum `read`, `write`, `ddl`,
required in the schema via `RequireNonEmpty(..., "connectionId", "sql", "mode")` and an `enum` on the property).

Pipeline (`resolveVerdict` rewritten; `queryResolution` gains `mode`):

1. `resolveEnabled`, `needsDatabasePath`.
2. **Mode check.** Missing or invalid `mode`: `"run_query needs mode: read, write or ddl. Connection %q allows: %s"`.
   go-sdk schema validation may reject a missing required field before the handler; the handler check stays for an
   empty string and for clients that skip validation, and the implementer confirms which text reaches the client
   (flow test asserts it names the allowed modes; if go-sdk's own text wins, set the property `description` so its
   message still lists the modes).
3. **Permission gate on the declared mode.** `modeVerdict(summary, mode)` in `permissions.go`: the connection's own
   read/write/ddl mode; `write` and `ddl` are deny on `read_only: true` connections and on kinds with no write
   console. Deny: `"connection %q does not allow %s over MCP. Allowed: %s"` (allowed list as in 2.5, e.g. `read,
   write (approval)`; `none` when nothing). Refused before connecting.
4. maxRows clamp, threshold, `connectForQuery`.
5. **Tighten-only classifier check.** `class := ClassifyStatement`; `rank(read)=0 < write=1 < ddl=2`, unknown ranks
   above `write` (rejected under `read` and `write`, passes under `ddl`). If `rank(class) > rank(mode)`:
   `"this statement looks like %s; run it with mode=%s. Connection %q allows: %s"` (for unknown: `"could not tell
   what this statement does; declare mode=ddl if it changes schema"`). Never runs it. A lower class than declared
   (a SELECT under `mode=write`) runs under the declared mode's gate and connection: the agent asked for more
   permission than needed, and the approval shows it (2.6).
6. `maybeExplain` only for `mode=read`, on the lane (heavy check unchanged).
7. Approval when the declared mode's verdict is `prompt`, or heavy. After approval re-resolve and re-check
   `modeVerdict` (today's tightened-mode posture).
8. Execute: `read` through `Router.ExecuteRead` (lane); `write` and `ddl` through `Router.Execute` (main),
   `ReadOnly: false`. The old `ReadOnly: class == read && write != allow` expression goes.
9. A database read-only refusal on the lane (postgres 25006, mysql 1792/1290, sqlite 8, clickhouse 164, Kira's own
   refusal on `app` lanes) returns `"the database refused a write on the read-only connection: <engine message>. Use
   mode=write or mode=ddl. Connection %q allows: %s"`, masked on masked connections (`maskedToolError`).
10. Render and result review unchanged.

`explain_query` executes its composed EXPLAIN through `ExecuteRead`; `assertComposedStatementsAreReads` stays as
defence in depth. It keeps its own read-mode gate and takes no `mode` argument. `planFor` (auto-explain) also uses the
lane.

### 2.5 Permissions in `list_connections`

`connectionView` keeps `permissions` (raw modes) and gains `access`, computed by one helper `accessOf(summary)` in
`permissions.go`. Gates and errors call the same helper, so report and enforcement never disagree.

```json
"access": {
  "read":  {"allowed": true,  "approval": false},
  "write": {"allowed": true,  "approval": true},
  "ddl":   {"allowed": false, "approval": false, "reason": "ddl permission"},
  "summary": "read, write (approval)"
},
"enforcement": "session"
```

- `reason` when not allowed: `permission denied`, `read-only connection`, `no write console`.
- `summary` lists allowed modes in order, `(approval)` after a prompt mode, `none` when empty. Error texts reuse it.
- `enforcement`: `session`, `app` or `none` (2.2), describing what backs `mode=read`.

### 2.6 Approval flow

- `ApprovalRequest.Enforcement string` (`session`/`app`/`none`) on read items, wire `enforcement`.

`Class` stays as a "detected" chip. When the detected class is lower than the declared mode (SELECT declared `write`),
the lede adds "Declared write, looks like a read; mode=read would run it read-only". i18n keys in
`packages/theme/src/i18n/en.json`; zod in the P520 approvals item schema (re-read its name).

Known-limit notes (user ask), in the same tab, next to the mode controls and the Agent access line. Plain one- or

| Note | Shown when | Text |
|---|---|---|

### 2.7 Descriptions and registry

`internal/llmprompts/registry.go`:

- `dbmcp.tool.run_query`: "Run one statement per call, not a script. Declare `mode`: read runs on a separate
  read-only connection (on engines where list_connections reports enforcement session, the database itself refuses
  writes, including writes hidden in functions); write and ddl run on the normal connection. The connection's
  permission for the declared mode applies: a denied mode is refused, an approval mode waits for the user.
  list_connections' `access` shows which modes each connection allows and which need approval. A statement that looks
  more powerful than its mode is refused with the mode to use. Reading stops at maxRows: rowCount is rows fetched, a
  lower bound when truncated is true. With auto-explain on, an expensive read pauses for approval. On kibana, `sql` is
  one Discover request as JSON; only mode read."

## 7. Security checklist (implementer proves each by a test or a grep)

1. `mode=read` never executes on the main adapter for a kind with a lane (grep: the read branch reaches only
   `ExecuteRead`; flow `TestDbMcpReadLanePostgres`).
2. Lane open failure never falls back to the main connection (test: stop the sqlite file's access or break the lane
   config, assert the connect error).
3. The gate reads only the declared mode's permission (`modeVerdict`); grep that no verdict comes from `OpClass`.
4. The classifier only refuses: no code path lowers the declared mode or switches connection from the class.
5. Missing or invalid `mode` never runs anything.
6. `write` and `ddl` refuse `read_only: true` connections and no-write-console kinds before connecting.
7. Re-check after approval (mode tightened or exposure revoked while waiting).
8. `access` and every refusal text come from `accessOf`; the flow test compares them for each mode combination.
9. Lane closes on disconnect, reconnect, exposure off, server stop, app quit and idle; no orphan sessions (engine
   process list in the lifecycle scenario).
10. Lane cancel hits the lane adapter (scenario `LaneCancel`).
11. Engine refusal text passes `maskedToolError` on masked connections.
12. Enforcement label is computed from kind, never read from config; `app` for mongo and redis.
13. Residuals (2.1 write vs DDL, 2.2 per kind) documented in ARCHITECTURE Known open items.
14. New op and approval ids use P523's id helper; its lint guard passes.
