## 1. Interpretation

"Stops" is a typo for "Steps". The code confirms the reading: there is no "stop" entity, and the Workflows page lists
workflows plus a Statuses row. Plainly:

- A **step** becomes a standalone, reusable definition with its own file, edited on its own. Today every step lives
  only inside one workflow file (`<home>/workflows/<id>.yaml`, `steps:` list), so the same step is copied per workflow.
- A **workflow** composes steps by reference and may **add on top**: per-workflow overrides of a step's fields, extra
  prompt text appended to the step's prompt, its own routes between steps, and workflow-only inline steps ("mostly"
  standalone: inline steps stay valid).
- The **Workflows page** gets three tabs, in this order: Statuses, Steps, Workflows.

## 2. Today (facts that drive the design)

1. Workflows are YAML files in `<home>/workflows`, read through `configfs.Folder[adewire.Workflow]` (`reader.go`).
   `Folder.List`/`Get` read and decode the files on every call (no in-memory cache), keeping a last valid value in
   `ade_workflow_last_valid` through the `Store` projection.
2. `adewire.Workflow{ID, Name, Steps []WorkflowStep}` is the resolved form every consumer reads: the run engine
   (`workflowSteps` builds `stepDef`), the graph editor draft, the phone (`mobileweb.Reader.Workflows`), task status
   (`AdeStepStatus`, status defaults per kind).
3. A started task stores a JSON snapshot of the workflow (`ade_tasks.workflow_json`, `snapshotWorkflow`). A not
   started task follows the live file. `WorkflowOutdated` compares the sha256 of the snapshot JSON with the live
   workflow's JSON (`liveWorkflows`, `decorateTask`). So any change to the resolved JSON shape flags every started task
   as outdated; section 3.4 avoids that.
4. Step ids are run keys (`ade_runs.step_id`, `ade_tasks.entry_step_id`, route targets `results[].next`,
   `review.implementer`). They must not change for an existing workflow.
5. Statuses live in SQLite (`ade_task_statuses`, `SaveStatuses`), are self-saving and are shown today as a special row
   at the top of the workflow list (`ade-wf-statuses-row`, `wfUi.pane = 'statuses'`).
6. Agent MCP surface: `task_info` returns the workflow and current step **names** only (`spaceInfo`). No MCP tool
   lists, edits or creates workflows or steps. LLM prompts (`internal/llmprompts/registry.go`) mention the workflow
   and step only as `task_info` text. Both read the resolved workflow, so **no MCP or prompt change** is needed.
7. Config folder conventions (P452/P514): YAML files for AI, forms for humans, both edit the same file; each folder
   gets a generated `AGENTS.md` (`WriteDocs`, `DocModel`); `config_last_valid (folder, file)` is the generic last-valid
   table for a folder with no module table (`configfs.TableProjection`).

## 3. Data model

### 3.1 Library step file: `<home>/steps/<id>.yaml`

One step per file; file stem equals `id` (same rule and pattern as workflows). Keys are today's step keys minus the
workflow-coupled ones:

- Allowed: `id`, `name`, `kind`, `status`, `session`, `outside_repo`, `runs_on`, `before`, `results`, `max_returns`,
  `timeout`, `prompt`, `command`, `smart_script`, `params`, `allowed_tools`, `review` (`send_to` only), `sandbox`,
  `agent`, `settings`.
- Refused in a library step (clear error naming the workflow-side key): `skip`, `review.implementer`, and a
  `results[].next` naming a step id. A library result's `next` is `next`, `end` or `stop` only (default `next`).
- Validation reuses `validator.step` with a `library` mode flag; no new validator.
- Last valid value: `configfs.TableProjection{DB, Folder: "steps"}` over the existing `config_last_valid` table.

### 3.2 Workflow item that references a library step

```yaml
steps:
  - step: implement            # library step id (required for a reference)
    id: implement              # workflow-local step id; default = the `step` value
    prompt_extra: |            # appended to the library prompt (agent prompt, manual session message)
      Also update CHANGELOG.md.
    timeout: 2h                # any overridable library key replaces the library value
    routes: { fail: implement-fix }   # result id -> next | end | stop | step id of this workflow
    skip: false                # workflow-only
  - id: notify                 # an inline step (no `step:` key) stays valid: workflow-only
    name: Notify
    kind: script
    command: ./notify.sh
```

Rules (one reference item):

- `step` names an existing library step; a missing or invalid library step is a workflow error
  (`step 2: library step "implement" does not exist`), so the last valid workflow stays in use.
- `id` is the run key; unique in the workflow; defaults to `step`. The editor mints `step-<8 hex>` ids for new items as
  today (`nextId`), so a library rename never moves runs.
- Overridable: every library key except `id` and `kind`. Scalars and lists replace; `params` and `settings` merge by
  key (override wins); `sandbox` replaces whole.
- Workflow-only keys: `skip`, `routes`, `prompt_extra`, `review.implementer`.
- `results` override replaces the library result list whole (routes inside it); `routes` only re-points the next of
  library results. Both on one item is an error.
- `prompt_extra` is allowed on agent and manual items only; refused on an inline step (no base to append to).
- Resolution builds one merged YAML mapping (library node with override keys applied) and runs the existing
  `validator.step` on it, then `resolveRoutes` over the whole workflow as today. Error lines point at the workflow
  file for override keys and are prefixed `library step "<id>": ` for keys from the library file.

### 3.3 Wire

Additive. Go in a new file `adewire/steps.go` plus two small hunks in `adewire/wire.go`; TS mirror in `wire.ts` in
the same commit.

- `WorkflowStep.Use string \`json:"use,omitempty"\`` (library id; "" = inline) and
  `WorkflowStep.PromptExtra string \`json:"promptExtra,omitempty"\``. TS: `use?: string; promptExtra?: string`.
  `omitempty` keeps the JSON of every existing snapshot and inline step byte-identical (section 2.3).
- `WorkflowsResult.Steps []StepEntry`, `WorkflowsResult.StepsDir string`. One query and one channel
  (`CHANNEL.adeTaskWorkflows`) carry both; a step edit changes resolved workflows anyway.
- `adewire/steps.go`: `LibraryStep` (= `WorkflowStep` value with library-mode fields), `StepEntry{FileName, Path,
  Step *WorkflowStep, Error *WorkflowError, UsedBy []string /* workflow ids */, Hash}`, `StepYaml`,
  `SaveStepArgs{FileName, Step WorkflowStep, BaseHash}`, `SaveStepYamlArgs{FileName, Yaml, BaseHash}`,
  `NewStepArgs{Name string; Kind StepKind; From *WorkflowStep}` (`From` set = save an inline step to the library),
  `DeleteStepArgs{FileName}`, `ValidateStepYamlArgs{Yaml}`.
- In the resolved `WorkflowStep` of a reference, every field holds the effective value (library plus overrides);
  `Prompt` is the effective base prompt and `PromptExtra` the workflow's addition. The editor diffs against the
  library entry to show what is overridden (section 6.4); no override list travels on the wire.

### 3.4 Engine and snapshot

- `workflowSteps` (`ade/steps.go`): `prompt = s.Prompt` plus `"\n\n" + s.PromptExtra` when the extra is non-empty.
  The run engine needs nothing else: it reads only the resolved workflow.
- `ade/taskwf.go`: one helper `snapshotJSON(wf)` marshals a copy with every `Use` cleared. `snapshotWorkflow`,
  `liveWorkflows` and the `decorateTask` re-hash all use it. A migrated workflow whose content is unchanged keeps the
  same hash, so no started task turns outdated by the migration. A later library edit changes the resolved content and
  flags started tasks outdated, which is correct.
- Library step edits apply to new work only, like workflow edits today: started tasks keep their snapshot; a not
  started task follows the live, resolved workflow.

### 3.5 SQL migration

None. Last-valid steps use `config_last_valid` (exists since 0063); snapshots keep their shape. Next free Space number
would be 0076 (highest is `0075_p517_worktree_dir.sql`; 0071 to 0074 unused). If the implementer finds a real need,

## 5. Migration of existing user data (one time)

`adeflow.MigrateInlineSteps(workflowsDir, stepsDir)` runs in `Start` when `<home>/workflows/.p526-backup/` does not
exist. That folder is the marker; `Folder` never lists dot entries.

1. Copy every workflow file to `.p526-backup/` first (plain copy, original names).
2. For each valid workflow, in file name order, each inline step in order:
   - Library content = the step's library-allowed fields (3.1); results lose step-id targets.
   - Library id = the step's id. Same id already in the library with identical content: reuse it. Different content:
     `<id>-2`, `<id>-3`, ... (first free).
   - Rewrite the item as a reference: `step: <library id>`, `id: <old id>` when they differ, plus the workflow-only
     keys it had (`skip`, `routes` for step-id targets, `review.implementer`).
3. A broken workflow file (parse error) is left untouched and logged; its last valid version keeps running.
4. Write library files first, then workflow files, each with `configfs.WriteAtomic`. The backup folder (step 1) is
   the marker, so a re-run never re-extracts: with the marker present the migration is a no-op. A crash after step 1
   leaves the originals in `.p526-backup/` and any not yet rewritten workflow still inline and valid, so nothing
   breaks. `docs/ARCHITECTURE.md` notes the backup path for manual recovery.
5. Invariant checked by the unit test and the flow test: for each migrated workflow, `snapshotJSON(resolved after)`
   equals `snapshotJSON(resolved before)`. No step id, route or task position changes; no task becomes outdated.
