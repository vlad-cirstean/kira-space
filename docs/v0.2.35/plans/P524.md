## 2. Design decisions

- **Order is app state in the DB, not in the files.** Same as connections (P475), runs (`custom_script_collections`)
  and kube clusters (P485). An order key in each file would rewrite every file on one drag and fight hand edits.
  Consequence (documented): a new machine with the same files starts from file-load order.
- **No migration.** Both columns exist. Existing DBs hold dense by-name order, which becomes the initial manual order.
  Studio's highest migration is `0057_p485_kube_cluster_order.sql` (the 0070/0075 numbers are Kira Space's dir). If
  the implementer finds a real need, the next Studio number is `0058_p524_...`; none is expected.
- **Projection keeps order** (replaces `reorder()` by name):
  - Insert of a new collection or environment row: `sort_order = COALESCE(MAX(sort_order) + 1, 0)` of its table,
    in the insert statement's transaction. New rows append. First load of a folder appends in `configfs` file-list
    order.
  - Record of an existing row (stem match): never touches `sort_order`. A rename in the file or via `Rename` keeps
    the stem, so keeps the place.
  - Forget: delete, then `sqlitex.ReindexSortOrder` over `ORDER BY sort_order, name, stem` to keep the set dense.
    Set `ch.Tree` / `ch.Environments` as today.
  - A file renamed on disk (new stem) is a forget plus a record: it moves to the end. Documented, not fixed.
  - Delete `reorder()` and its two callers' by-name behaviour. `DuplicateEnvironment` and `CreateCollection` /
    `CreateEnvironment` / `ImportCollection` / `ImportEnvironment` append (no "after source" placement; not asked).
- **Writer stays `apifiles.Store`** (ARCHITECTURE: it owns every write to `api_*`). New file
  `apps/kira-studio/internal/apifiles/order.go`:
  - `func (s *Store) ReorderCollections(ids []string) error` and `ReorderEnvironments(ids []string) error`.
  - Each: `s.mu.Lock()`, `s.pend = &Changes{}`, `s.tx(...)` running `sqlitex.ReorderSortOrder(tx,
    "SELECT id FROM api_collections ORDER BY sort_order, name, stem", "UPDATE api_collections SET sort_order = ? WHERE
    id = ?", ids)`, setting `ch.Tree = true` (environments: `ch.Environments = true`), unlock, `s.emit(ch)`. Same
    lock/pend/emit shape as `createFile`, so the store's `OnChange` (`bridge.EmitApiChanges`) broadcasts to every
    window. No file is written; no `config_last_valid` change.
  - Empty `ids`: `ErrInvalidOrder`. An unknown or repeated id (`ReorderSortOrder` error): wrap as
    `fmt.Errorf("%w: %v", ErrInvalidOrder, err)`. Ids left out keep their relative order after the listed ones
    (helper semantics; a stale window never collides with a row created since).
  - `var ErrInvalidOrder = errors.New("apifiles: the order is not valid")` in `order.go`.
- **Bridge** (restored names, so the pre-P473 IPC keys come back unchanged):
  - `CollectionsService.ReorderCollections(args CollectionsReorderCollectionsArgs) error`,
    `CollectionsReorderCollectionsArgs{IDs []string `json:"ids"`}` in `bridge/collections.go`.
  - `VariablesService.ReorderEnvironments(args VariablesReorderEnvironmentsArgs) error`,
    `VariablesReorderEnvironmentsArgs{IDs []string `json:"ids"`}` in `bridge/variables.go`. Update the
    `VariablesService` doc comment ("Names, order and plain values are edited in the files" loses "order").
  - Both: `len(ids)==0` gives `ipcerr.Required("ids")`; other errors through `apiFilesErr`, with a new case
    `errors.Is(err, apifiles.ErrInvalidOrder)` giving `ipcerr.T(ipcerr.CodeBadRequest,
    "backend.studio.collection.invalidOrder.body", nil)`. No explicit emit in the bridge: the store emits.
  - A setting write, not an op: no op-log row (kube precedent).
- **Items within collections: no new backend.** P514 restored it as file order. P524 adds nothing there except the
  coverage in the paired tests (section 5) proving drag of items still works beside collection drag, and the
  `onStart` split below. If the implementer finds an item-order gap while wiring, fix it in commit 3 and say so.
- **Collection drag in the tree** (restore pre-P473 design on the current `useTreePointerDrag`):
  - `onStart`: a selection of only collection rows starts a collections drag (`dragKind = 'collections'`, ids in
    visible order); a mix of collection and item rows refuses; items keep today's path. Refuse a collections drag
    while searching (a filtered list hides siblings; same rule as `zoneFor`).
  - `resolve` for collections: `resolveCollectionDrop(row, fraction)`: header top half gives `before` that
    collection, anything else inside a collection block (bottom half of header, any item row) gives `after` it,
    drawn at that block's last visible row (`lastRowKeyOf`). Order from `collectionOrderFor(order, moved, targetId,
    edge)`; `null` (target is moved, or no change) gives no drop.
  - `RowDrop` becomes a discriminated union `{kind:'items', key, zone, placement} | {kind:'collections', key, zone,
    order}`. `onDrop` calls `moveRows` or `reorderCollections`. The existing drop indicator renders `before`/`after`
    for both kinds unchanged.
  - Multi-select of collections drags as one block, keeping relative order.
- **Collection Move up / Move down and keyboard**: `menu.ts` collection-row menu gains `...moveItems(row, actions)`
  (same ids `move-up`/`move-down`, shortcuts `list.moveUp`/`list.moveDown`). `canMoveStep`/`moveStep` in
  `state/collections.ts` handle `row.kind === 'collection'` via `collectionStepOrder(ids, id, step)` (restore into
  `state/collectionOrder.ts` beside `itemStepBefore`). `moveViaMenu` in `CollectionsTree.vue` already dispatches the
  chords, so keyboard works with no tree change. Update the stale `canMoveStep` comment.
- **Store** (`state/collections.ts`, Pinia + TanStack Query): `reorderCollectionsMutation` (`mutationKey
  ['apiCollectionsTree','reorderCollections']`, `mutationFn: control.collectionsReorderCollections`, `onSuccess`:
  the store's existing tree refresh used by `moveRows`'s mutation); `reorderCollections(ids): Promise<boolean>`
  sets/clears `state.error` like `moveRows`. Optional optimistic `setQueryData` on `apiCollectionsTreeKey` only if
  the drop visibly flickers; then roll back on error.
- **Environments** (`EnvironmentsView.vue`, `state/variables.ts`):
  - Grip span (`data-testid="environment-grip"`, `CodiconIcon gripper`, `cursor-grab`, Tailwind) leading each row.
    Filtered: grip shows a shadcn `Tooltip` "Clear the filter to reorder" and the drag is disabled.
  - `useSortableReorder(listEl, () => displayEnvironments ids, onMove, {draggable:
    '[data-testid="environment-row"]', handle: '[data-testid="environment-grip"]', direction: 'vertical', disabled:
    () => isFiltered.value, keyboard: true, keyboardHandle: '[data-testid="environment-grip"]'})`. The handle is
    needed: rows hold a `RadioGroupItem` and buttons. `keyboardHandle` keeps Alt+Arrow off the radio (the radio
    group owns arrow keys). Make the grip focusable (`tabindex="0"`, `aria-label` "Drag to reorder" via the new key)
    so the keyboard path is reachable.
  - `onMove(from, to)`: `variablesStore.reorderEnvironments(moveId(ids, from, to))`. No local order mirror
    (the old `order`/`reconcileOrder` drafts are gone with P473's inline editing); `useSortableReorder` already
    reverts its DOM move and lets the refetched list re-render.
  - Store: `reorderEnvironmentsMutation` (`control.variablesReorderEnvironments`, `onSuccess` invalidates
    `apiEnvironmentsKey` the way `createEnvironmentMutation` does); `reorderEnvironments(ids): Promise<boolean>`.
  - The environment picker (request tab toolbar, `selectEnvironmentForTab`) already renders
    `variablesStore.environments` in list order; verify it follows the new order, no change expected.
- **Library choice**: no new dependency. Tree: `useTreePointerDrag` (the virtualized tree cannot use Sortable; it
  only renders the visible window). Environments list: `useSortableReorder` over `vue-draggable-plus` (already in
  the repo, P137). Both are the repo's existing DnD seams. All components stay `<script setup lang="ts">`.
