# P520 Aggregated MCP approvals: one dialog, minimise to toast, long approval timeouts

Base: `chapter/v0.2.35` at `23639d3dd` (P525 done). Branch `chapter/v0.2.35`. One sequential Sonnet implementer.

## 0. Scope (user decisions)

- **Async dropped entirely.** No handles, no `await_results`, no MCP Tasks, no stdin injection, no inline window, no
  output-schema change. Tools stay synchronous; the agent waits on its call.
- **No hold-until-last.** Each call returns as soon as its own item is answered, timed out or abandoned.
- **One approvals surface per app.** One dialog holds every pending agent approval in that app: Studio DB MCP
  statements, result previews, Kubernetes reads, proof edit reviews; Space branch requests and renames. P521 scripts
  and P522 API requests plug in later as new item kinds.
- Close (X) or Escape **minimises** to a toast at top right; it never denies.
- Item presentation redesigned: target, operation, origin first, then payload.
- Studio `ApprovalTimeout` 120 s to 10 min. Per-server MCP `timeout` written for users' own sessions and Kira's
  per-run configs, so Claude's 60 s default cut no longer applies.
- Space: concurrent `request_branches`/`rename_branch` calls for one task merge into one open request.
- `plans/P520-async-research.md` stays as the record of "async deferred"; `docs/ARCHITECTURE.md` gets a short note
  (2.9).

## 1. Facts (from discovery and the research file)

- Claude CLI 2.1.318 cuts an MCP call at 60 s on HTTP unless the server entry has `"timeout"` (ms, ≥1000) or
  `MCP_TOOL_TIMEOUT` is set. Verified: `"timeout": 600000` lets a 75 s call finish.
- Idle timeout `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` defaults to 300 s on HTTP. A per-server `timeout` raises it too.
- The Claude TUI auto-backgrounds an MCP call still running after 120 s. Its result then arrives as a task
  notification turn. That is fine for a held approval: the call still completes. Plain `-p` does not auto-background
  unless `CLAUDE_AUTO_BACKGROUND_TASKS=1`, so the call simply blocks.
- `internal/harness/claude/hooks/agenthooks.go`: `MCPToolTimeoutEnv = "MCP_TOOL_TIMEOUT=2100000"` (35 min), set
  only on Kira-launched Space agents.
- Space `defaultBranchRequestWait` is 30 min (`ade/branchrequest.go:23`).
- Studio `dbmcp.ApprovalTimeout = 120 * time.Second`. Error texts in `tools.go:317,491` say "2 minutes".
- A Studio call can pass two approvals in a row: the query stage (up to `ApprovalTimeout`), the run, then the response
  stage (up to `ApprovalTimeout`).
- `mcpinstall` registers through `claude mcp add-json` with `serverJSON{Type, URL, HeadersHelper}`. Studio's copy-paste
  text comes from `Installer.Command`.
- `agentmcp` renders its per-run config at `internal/agentmcp/mcp.go:449` through `harness.MCPHost.MCPConfig`
  (`claude.Provider.MCPConfig` writes `type/url/headers`).
- OpenCode's remote-server `timeout` key is a tool-list fetch timeout, not a call timeout. OpenCode is unchanged.
- Prompt router (`internal/prompts`):
  - Entries are metadata only, one per `<kind>:<ref>`.
  - OS notifications group per kind with a count (`countTitle`).
  - `RaiseOnOpen(kind)` raises the window (Studio: `KindDbMcp` with `DbMcp.FocusOnApproval`).
  - `PromptHost` renders only the oldest visible entry targeted at this window.
  - `usePromptVisibility` hides by entry id.
- Today Studio shows one `dbmcp` dialog per request. The dialog shows the head only, with "N more" queued; Escape
  denies.
- Today Space shows one `branch-request` prompt per request, from the Task tab row or `PromptHost`. A second call for
  a task with an open request is refused.
- Proof:
  - `proof_close_session` on an edit opens a `proof` prompt (`proofEdit` title); Accept or Reject happens in the proof
    window (`AcceptEdit`/`RejectEdit`).
  - A new session's prompt is a "ready" notice, not an approval.
- Studio DB MCP is stateless HTTP with one bearer token and no client identity. The only per-request origin signal is
  the `User-Agent` header (for example `claude-code/2.1.318`).
- Space `agentmcp` tokens are per run or session, so the task, step, source (session, run, automation) and session
  label are known.
- Connections have a palette colour and a read-only flag. There is no environment field.

## 2. Design

### 2.1 Shared backend: `internal/approvals` (new package)

One queue per app process. Owners keep their own blocking logic and answer semantics; the queue holds view items and
routes answers.

```go
type Item struct {
    ID        string    `json:"id"`        // "<kind>:<ref>", stable for the item's life
    Kind      string    `json:"kind"`      // db.query | db.response | kube.read | proof.review | branch.request
    CreatedAt int64     `json:"createdAt"` // ms
    ExpiresAt int64     `json:"expiresAt"` // ms; 0 = no expiry (proof.review)
    Origin    Origin    `json:"origin"`
    Target    Target    `json:"target"`
    Operation Operation `json:"operation"`
    Reason    string    `json:"reason"`    // permission | heavy | preview | review | request
    Payload   json.RawMessage `json:"payload"` // per-kind, zod-validated on the client
}
type Origin struct {
    Client string `json:"client"` // "Claude Code 2.1.318" from User-Agent; "" unknown
    Cwd    string `json:"cwd"`    // see 2.3; "" unknown
    Task   string `json:"task"`   // Space task title
    Step   string `json:"step"`   // Space step name
    Source string `json:"source"` // session | run | automation | ""
}
type Target struct {
    Name     string `json:"name"`     // connection, cluster, repo set, script, API request
    Kind     string `json:"kind"`     // postgres, kubernetes, git, http, ...
    Color    string `json:"color"`    // palette colour, "none"
    ReadOnly bool   `json:"readOnly"`
    Location string `json:"location"` // host / database path / context+namespace / base URL
}
type Operation struct {
    Class string `json:"class"` // read | write | ddl | unknown | create | rename | review | run | request
    Tone  string `json:"tone"`  // neutral | caution | danger
}
type Answer struct {
    Approve bool            `json:"approve"`
    Options json.RawMessage `json:"options,omitempty"` // per kind (branch.request: itemIds, remoteItemIds)
}
type Owner interface { Answer(ref string, a Answer) error } // ipcerr NotFound when already resolved
```

- `Queue`:
  - `Register(kindPrefix, Owner)` and `Put(Item)`: insert or replace by id.
  - `Remove(id)` and `List() []Item`: oldest first, ties by id.
  - `Answer(ids []string, a Answer) []Result` answers each item through its owner. A per-id error is reported, never
    aborting the rest.
- Changes publish through `notify.OrderedEmitter[[]Item]` on the channel `kira:approvals:changed`.
- Router: `Put` of a new id opens one prompt `approval:<id>` (`prompts.KindApproval`, `Ref` = item id, `Title` from
  the kind's title key). `Remove` closes it.
  - Router entries exist for routing (target window) and grouped OS notifications: "N things await your approval".
    The queue view itself never reads titles.
  - `prompts.KindDbMcp` and `KindBranchRequest` are deleted. `countTitle` gains the `approval` case.
  - Studio `RaiseOnOpen` keys on `KindApproval` with `DbMcp.FocusOnApproval` (setting unchanged). Space keeps false.
- Bridge (`internal/approvals/service.go`, bound by both apps' bridge registration):
  - `ApprovalsList() []Item`.
  - `ApprovalsAnswer({ids []string, approve bool, options map[string]json.RawMessage}) []{id, error}`.
  - `options` is keyed by id, so approve-all can carry each branch item's choices.
- Owners never publish secrets: statements and branch names only. P522 masks auth (2.8).

### 2.2 Studio owners

- `dbmcp.ApprovalBroker`:
  - Its snapshot emitter and `openPrompt`/`closePrompt` are replaced by `approvals.Queue` `Put`/`Remove`. FIFO,
    deadlines, `ctx` abandonment, `maxPendingApprovals` (50) and `AbandonAll` stay.
  - Every pending request is an item at once; the "presented head" concept goes.
  - `Request` still blocks its own caller only and returns on its own answer.
  - Kinds: `db.query` (stage query; reason `permission` or `heavy`, payload: statement, plan), `db.response` (stage
    response; payload: `{isError, bytes, alreadyRan}`, text still fetched by `PendingResponse(requestId)`),
    `kube.read` (payload: cluster `{context, namespace, operation, resource, name}`).
  - Operation tone: `read` neutral, `write` caution, `ddl` and `unknown` danger, kube neutral.
  - Target from `ApprovalTarget`: name, kind, colour, readOnly, location = host plus decoded path or database.
- `ApprovalTimeout = 10 * time.Minute`. `tools.go` texts derive from it (`"got no answer within %s"` with
  `approvalWindow()` rendering "10 minutes"), with no literal duration left. `mcp-approval` prompt text in
  `internal/llmprompts` (if it names 2 minutes) updated.
- Bridge `dbmcp.go`:
  - `PendingApprovals`, `ApproveQuery` and `DenyQuery` go; `approvals.Service` replaces them.
  - `PendingResponse` stays.
  - The broker's `Owner.Answer` maps approve or deny to `resolve`.
- Proof: `proof_close_session` on an edit puts `proof.review:<sessionId>`:
  - No expiry; the agent's call already returned.
  - Payload: `{name, revision, steps, reason}`. Operation: `review`, caution.
  - Answer approve calls `AcceptEdit`, deny calls `RejectEdit`.
  - The item row also offers "Open in proof window".
  - The `proof` prompt then serves new sessions only (`ProofReadyPrompt` keeps the "ready" notice).
  - `RaiseUnreviewed` re-puts pending edits after restart.

### 2.3 Origin for Studio (stateless HTTP)

- `dbmcp/http.go` wraps the handler, reads `User-Agent` and stores `Client` (product and version, max 64 chars,
  printable only) in the request ctx. Tools copy it into `Origin`.
- Cwd: the generated headersHelper script (`EnsureHeaderHelperScript`) additionally prints
  `X-Kira-Cwd: <percent-encoded $PWD>`. Only when Claude runs the helper in the session's cwd: the implementer
  verifies this with the real `claude` (DB MCP real row) before committing that part.
  - Not in the session cwd: drop the header and keep Client only. Record the outcome in the plan Result and in
    ARCHITECTURE.
  - Never a token in this header; the helper already prints only `Authorization`.
- Display: "Claude Code 2.1.318 · ~/src/app" or "Unknown client".

### 2.4 Long approval timeouts

- `harness.MCPCallTimeout = 35 * time.Minute`: one value, the longest wait any Kira tool holds (Space branch request
  30 min plus margin; Studio query plus run plus preview ≤ 2 × 10 min plus run).
- `hooks.MCPToolTimeoutEnv` becomes `"MCP_TOOL_TIMEOUT=" + strconv.FormatInt(MCPCallTimeout.Milliseconds(), 10)`
  (var, same 2100000).
- `harness.MCPServer` gains `Timeout time.Duration`. `claude.Provider.MCPConfig` writes `"timeout": ms` when > 0 for
  http and stdio entries. OpenCode ignores it (comment says why).
- `agentmcp/mcp.go:449` sets `Timeout: harness.MCPCallTimeout`.
- `mcpinstall`:
  - `serverJSON` gains `Timeout int64 \`json:"timeout,omitempty"\``.
  - `Install` and `Command` set it to `harness.MCPCallTimeout` in ms, so the copy-paste text matches the click.
  - `stdioServerJSON` unchanged (memory MCP has no approvals).
- Existing user registrations get the timeout on the next Install click. ARCHITECTURE notes it; no silent rewrite of
  the user's Claude config (see 5, decision 2).

### 2.5 Space owner: merged branch requests

- One open `branchRequest` per task stays the unit and is one approval item `branch.request:<requestId>`.
- A `request_branches` or `rename_branch` call that finds one open merges its items in:
  - The refusal text goes.
  - `ExpiresAt` resets to now plus `branchRequestWait()`.
  - The item is re-put so the countdown updates.
- Item ids are request-unique, `c<call>i<k>` (call counter per request). Each item carries its call's `Source`,
  `StepName` and session label. Request-level `Source`/`StepName` move to items (`adewire.BranchRequestItem`).
- `branchDecision.renameRemote bool` becomes `remoteItems map[string]bool`.
  `ApproveBranchRequestArgs.RenameRemote` becomes `RemoteItemIDs []string`.
- One answer resolves every merged call at once, each with its own decision slice. That is not hold-until-last: all
  merged calls belong to the one item the user answered.
- Two tasks' requests are separate items, answered and returned independently.
- Run note `noteBranchApproval` stays set while any call of that run waits.
- `Owner.Answer` decodes options `{itemIds, remoteItemIds}`. Approve with no options approves every item with the
  remote choice off.
- Task row: `task.branchRequestId` stays. The Review button opens the approvals surface focused on
  `branch.request:<id>`.
- Payload: `{taskId, taskTitle, items: [{id, kind, repo, branch, base, from, upstream, stacked, source, stepName,
  session}]}`. Item ids must not be renumbered on merge.

### 2.6 Frontend: shared surface (`packages/workbench/src/approvals/`)

- `approvalsQueries.ts`:
  - TanStack `useQuery(['approvals'])` over `ApprovalsControl.approvalsList()`, with push `setQueryData` on
    `kira:approvals:changed` and refetch on focus (same pattern as `usePrompts`).
  - `useAnswerApprovals` mutation.
  - `ApprovalsControl` is provided by each app's bridge (`createCoreControl.ts` pattern).
- `packages/shared/domain/approvals.ts`: zod `approvalItemSchema` (common fields) plus `payload` validated per kind
  by the registry (unknown kind: rendered with the generic header and a "not supported" body, deny only).
- `state/approvals.ts`: Pinia `useApprovalsStore`. One concern: the approvals view.
  - `minimised`, `focusId`, `answering: Set<id>`.
  - `options: Record<id, unknown>`: renderers write per-item choices here.
  - Actions: `minimise()`, `open(focusId?)`, `answer(ids, approve)`, `approveAll()`, `denyAll()`. Approve-all and
    deny-all act on the visible ids captured at click time; items joining mid-click stay pending.
  - Server data stays in TanStack, not in the store.
- `registry.ts`: `provideApprovalKinds(map)`, `useApprovalKind(kind)`.
  - Each kind defines `body: Component` (payload view), `title(item)`, `approveLabel`/`denyLabel` keys,
    `options?(item)` (initial choices) and `extraActions?: Component` (for example "Open in proof window").
  - Kinds per app (2.7).
- `ApprovalsSurface.vue`, mounted once in each app's `App.vue` beside `PromptHost`:
  - Visible items are those whose router entry `approval:<id>` targets this window (`usePrompts` data).
  - Shows `ApprovalsDialog` when there are items and not minimised, else `ApprovalsToast` when there are items.
  - New items while minimised keep it minimised and update the toast. When the queue empties, it resets
    `minimised = false`.
  - While `PromptHost` shows a prompt (quit, update, credential), the surface renders as the toast without changing
    `minimised`, so two modals never stack. `PromptHost`'s visible list moves into a shared composable
    `usePromptHead()` that both read. `PromptHost` skips `approval` entries.
  - Notification click: `onPromptsReveal` with an `approval:` id calls `open(id)`.
- `ApprovalsDialog.vue` (shadcn-vue `Dialog`, `DialogContent size="2xl" fixed-height`):
  - `DialogHeader`: title "Awaiting your approval" plus `Badge` count. No icon (P525 rule, guard U107). Close X and
    Escape call `minimise()`; `@update:open` never denies.
  - `DialogBody`: list of `ApprovalItemCard`, oldest first. `focusId` scrolls into view and expands.
  - `DialogFooter`: "Deny all (N)" (`variant="dialog-danger"`) and "Approve all (N)" (`variant="dialog-primary"`).
    No filled buttons (P525, guard U106).
  - Initial focus: the first item's Deny.
- `ApprovalItemCard.vue`: one item, structured; no tinted fill box.
  - Row 1:
    - 3px left rail in the target colour (`border-l-[3px]` with the palette var; no background mix).
    - Target name (`text-kira-lg font-medium`), kind label with `KIND_ACCENT_CLASS`, location in `font-data
      text-muted-foreground`.
    - Right side: operation `Badge` toned (neutral `default`, caution `warn`, danger `error`), read-only `Badge`
      when set, countdown (`usePendingDecision`, mm:ss; "Expired" at 0).
  - Row 2: origin line (2.3, 2.5): client and cwd, or task, step and source.
  - Row 3, when present: reason line (heavy plan estimate, "already ran: result review", "edit to review").
  - Body: `Collapsible`, expanded when it is the only item or focused. Renders the kind's `body`.
  - Actions: per-item Deny (`dialog-danger`) and Approve (`dialog-primary`), labels from the kind (Send/Withhold for
    `db.response`, Accept/Reject for `proof.review`), plus `extraActions`.
  - An answered item shows a pending spinner until the push removes it. A per-item error renders inline (`Alert`).
- `ApprovalsToast.vue`: fixed `top-[calc(var(--kira-titlebar-h)+8px)] right-4`, `floatingSurface` recipe (P525 rule
  8), `role="status"` with `aria-live="polite"`.
  - Text: "N things awaiting your approval" (i18n plural) and "Next expires in m:ss" from the soonest `expiresAt`
    (hidden when none expire).
  - Button "Review" (`dialog-primary`) calls `open()`.
  - A count increase replays a one-shot `animate-pulse` ring (Tailwind) for 1 s, via VueUse `useTimeoutFn`.
  - Library: no Sonner/vue-sonner. Requirement it cannot meet without wrapping all of it: a single pinned status
    surface bound to reactive queue state, never auto-dismissed or stacked, gone exactly when the queue empties. That
    is a fixed div with an existing recipe and `Button`.
- Countdown: the shared `usePendingDecision` (`behaviour/pendingDecision.ts`) per card and for the toast's soonest
  item. Expiry is decided by the backend; the push removes the item.

### 2.8 Item model hooks for P521 and P522

- P521 scripts: kind `script.run`.
  - Target: script name, kind `script`, repo as location.
  - Operation: `run` with tone from the script's own setting (default caution).
  - Payload: `{command, cwd, args, env: [{name, masked}]}`.
  - Owner: the scripts MCP broker, a generalised copy of the `dbmcp` broker pattern: blocking per call, item into the
    app queue.
  - The per-script "prompt or not" setting decides whether an item is put at all.
- P522 API requests: kind `api.request`.
  - Target: request name, kind `http`, colour of the active API environment, location = environment name.
  - Operation: `request`, tone by method (GET/HEAD neutral, others caution, DELETE danger).
  - Payload, defined now in the ARCHITECTURE "Approvals surface" section so P522 implements to it:
    - `method` and `url` (variables resolved).
    - `query: [{name, value}]`, `headers: [{name, value, masked}]`.
    - `auth: {scheme, display}`: display masked, for example `Bearer ••••3f2a`.
    - `body: {contentType, text, truncated}`.
    - `variables: [{name, value, source, secret}]`, secrets masked.
  - Renderer `ApiRequestBody.vue` (P522):
    - Method `Badge` plus URL in `font-data`.
    - Tables for query, headers and variables.
    - Body formatted by content type: JSON pretty-printed, form fields as a table, XML/text in a read-only Monaco with
      language by type.
  - The "prompt or not" per item feeds whether an item is put.
- The contract lives in `packages/shared/domain/approvals.ts` (common item plus the `payload` schemas of the P520
  kinds). P521 and P522 add their payload schemas and renderers only; no surface change.
