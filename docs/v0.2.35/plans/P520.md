# P520 Async MCP tools with aggregated approvals and result push

Ask (SPEC row): "Every MCP tool is async: call returns at once, result is pushed to the agent when done. Pending
approvals accumulate in one dialog (agent launches 3 requests: one dialog, accept or deny each). Results push only
after the last pending approval is answered. Same for endpoints with result preview enabled."

Base: `chapter/v0.2.35` at `cc66a3868` (P512 to P519 and P524 landed). Runs alone (SPEC wave plan). No migration.
Discovery: `codegraph_explore` over every `mcp.AddTool` site (`agentmcp` space/mcp/gittool/sandboxgit/review/
handover/outcomes, `dbmcp` server/kube/proof/ops tools, `memory/mcpserver`), `ApprovalBroker` and its callers
(`awaitApproval`, `reviewResponse`, `kubeRun`), `bridge/dbmcp.go`, `TaskBoard.RequestBranches`/`RenameBranch`/
`awaitBranchRequest`, `AdeBranchRequestDialog`, `DbMcpApprovalDialog`, `state/dbmcp.ts`, `mcpcall.Record`,
`mcpRecorder`, harness claude settings and hooks. Protocol facts checked in go-sdk v1.8.0 source and the installed
`claude` 2.1.318 binary.

## 1. MCP protocol facts (decide the design)

- Real push into the agent's conversation exists in Claude Code only as **channels**: server capability
  `experimental["claude/channel"]`, notification `notifications/claude/channel {content, meta}`. Verified in the
  2.1.318 binary. Not usable here, for five independent reasons:
  1. Gated by org policy `allow_channels` plus server flag `tengu_harbor`; Teams/Enterprise also need managed
     `channelsEnabled: true`. Not on Bedrock, Vertex or Foundry.
  2. Session must start with `--channels server:<name>`. A non-plugin `server:` entry also needs
     `--dangerously-load-development-channels`, which shows a confirmation dialog at startup. Headless `claude -p`
     cannot answer it; the user's own terminal sessions (Studio DB MCP) would need flags Kira does not control.
  3. Binary string: "this connection's protocol version has no channel delivery path"; channels are dropped for the
     `modern` protocol era. go-sdk v1.8.0 speaks protocol 2026-07-28 (`PropagateRequestCancellation` comment in
     `dbmcp/http.go`). Not confirmed on a live handshake.
  4. `agentmcp` and `dbmcp` serve Streamable HTTP with `Stateless: true`: no session id, no standalone GET stream,
     so no server-initiated message can reach a client outside a request.
  5. go-sdk v1.8.0 sends only methods in its `clientMethodInfos` table (`defaultSendingMethodHandler` returns
     `ErrNotHandled` for any other); `notifications/claude/channel` cannot be emitted without a fork or a hand-built
     HTTP transport.
- MCP Tasks (`tasks/get`, `tasks/result`, `notifications/tasks/status`, tool `execution.taskSupport`) exist in the
  bundled client SDK, but go-sdk v1.8.0 has no server support, and a task-augmented call still blocks the model's
  turn. No gain for "returns at once".
- Claude cuts an MCP call at 60 s unless `MCP_TOOL_TIMEOUT` is set (DEV_ENVIRONMENT "Real `claude` tests"). Kira sets
  it for its own launches (`hooks.MCPToolTimeoutEnv`, 35 min); the user's own sessions on Studio DB MCP do not.
- Progress (`notifications/progress`) and logging only flow during an open request. Memory MCP already uses
  progress inside `ingest_files`.
- OpenCode has none of the Claude extensions; whatever P520 builds must be plain MCP.

Consequence: "pushed when done" is implemented as a **held long-poll**: a slow or approval-gated call returns a
pending handle; a new tool `await_results` holds its request open and answers the moment any awaited job finishes
(server push over the agent's own open request). This is the only delivery path that works for every client, both
transports and both providers. User decision 1 (section 9): accepted, push alternatives deferred.

Scope (user decision 2): not literal. A call that finishes within the inline window (1 s) answers inline with its
real result; only slower calls and approval-gated calls return a handle.

## 2. Design

### 2.1 Shared package `internal/mcpasync` (new)

One job registry per MCP server instance. Generic over a tool's In/Out, so every server and P521/P522 register
through the same seam.

- `mcpasync.AddTool[In, Out any](srv *mcp.Server, r *Registry, t *mcp.Tool, h mcp.ToolHandlerFor[In, Out])`
  replaces `mcp.AddTool` at every site. It registers the tool with go-sdk output type `any`, so no `outputSchema` is
  declared: one call can now answer with either the tool's real Out or a `Pending`, and Claude validates structured
  output against a declared schema. Structured content still rides both answers. Input schema validation still runs
  in go-sdk before the handler: a bad argument fails at once, never as a job.
- Call path: mint handle (`mj_` + `internal/shortid.New(12)`, P523 convention), start the job goroutine, then wait
  for the first of three events:
  1. Job done within `Registry.InlineWindow` (default 1 s): answer inline with the real result. The job is dropped
     from the registry (never listed by `await_results`), and its op row finishes normally.
  2. Job calls `mcpasync.SetState(ctx, awaiting_approval)`: answer `Pending` at once, without waiting out the
     window. An approval-gated call always returns a handle.
  3. Window ends: answer `Pending`.
  `Pending{handle, tool, state, next}` carries text "Started <tool> as mj_x. Call await_results." The job runs `h`
  under `context.WithoutCancel(reqCtx)` (keeps token info, op source, origin) joined with the owner's lifetime ctx
  (2.2), not the request ctx, so a client that drops the request during the window does not stop it. The job
  recovers panics (log stack, result "internal error handling this tool call"), and normalises a nil result from
  `out` exactly as go-sdk does (read `mcp/tool.go`/`server.go` toolForErr and the typed-handler wrapper; JSON text
  plus structured content), and a Go error to an `IsError` text result. Both paths return the same normalised
  result, so an inline answer is byte-identical to what `await_results` would have delivered.
- `InlineWindow` is a `Registry` field so flow tests can set it (0 forces a handle, a large value forces inline)
  without sleeping on real timing.
- States: `running`, `awaiting_approval` (set by approval sites through `mcpasync.SetState(ctx, ...)`), `done`.
  A finished job keeps `Result{IsError, Content, Structured}`.
- `Registry.Owner(req) string` scopes jobs. Owner-wide bounds: at most 32 unfinished jobs (beyond: immediate
  `IsError` "too many calls are still pending; call await_results first"), finished results kept 15 min, at most 64
  finished per owner (oldest delivered evicted first, then oldest undelivered).
- `mcpasync.AddAwaitTool(srv, r, desc, schema)` registers `await_results`, the one synchronous tool:
  - Args: `handles []string` (optional where the owner is a single client, required on `dbmcp`, see 2.4),
    `waitSeconds int` 0 to 50, default 30. 50 stays under Claude's 60 s default cut.
  - Answers at once with every finished awaited job; else waits until one finishes, the wait ends, or the request
    ctx ends. Without handles it awaits the owner's undelivered jobs.
  - Output (typed): `results[] {handle, tool, isError, text, structured}`, `pending[] {handle, tool, state}`,
    `unknown[]` (expired or foreign handles). Text content renders one block per result:
    `[mj_x run_query] <text>`. A result counts as delivered once returned; an explicit handle returns it again until
    eviction.
- `Registry.Drain(owner, d)` waits up to `d` for the owner's `running` jobs (not `awaiting_approval`), then cancels
  every remaining job of that owner. `Registry.Close()` cancels all and waits up to 5 s.
- Op log: `mcpcall.Record` gains a deferral seam. Record puts a slot in ctx. On an inline answer `mcpasync` leaves
  the slot alone and Record finishes the row as today. On a handle answer `mcpasync` takes the slot before returning,
  calls the finish func with the job's real verdict at job end, and hands the job's cancel to it; Record skips its
  own finish. Effect: an op row spans the job, not the dispatch, and P518's running-ops widget can stop a slow job
  (2.3). The take must happen under the same lock that decides inline vs handle, so a job finishing at the window's
  edge never finishes its row twice or never.
- Unit tests `internal/mcpasync/jobs_test.go` (concurrency qualifies under CLAUDE.md): inline answer within the
  window and no registry entry left; `SetState(awaiting_approval)` returns a handle before the window ends; a job
  finishing at the window edge gives exactly one answer and one op finish; long-poll wakes on the first finish, not
  the last; delivered-once without handles; owner bound and eviction order; Drain waits only for running jobs and
  cancels the rest; job panic becomes an error result on both paths; request ctx cancel ends the await but not the
  jobs.

### 2.2 Owners and lifetimes per server

| Server | Owner key | Job lifetime ctx | Handles in `await_results` |
|---|---|---|---|
| `agentmcp` (Space ADE, smart scripts) | registration id (`g<id>`) | `registration.ctx` | optional |
| `dbmcp` (Studio `kira-db`) | one owner (stateless HTTP, one shared bearer token: no caller identity) | server ctx, new, ended in `Close` | required, non-empty |
| `memory/mcpserver` (stdio, one process per client) | one owner | `RunStdio` ctx | optional |

`dbmcp` handles are unguessable capabilities: without caller identity, a handle-less await would hand one agent
another agent's rows.

Per-server specifics:

- `agentmcp`: `callCtx` is no longer needed by tool handlers (the job ctx already ends with the registration);
  keep it only where a handler still blocks on the request. `finish_step` and `handover` normally answer inline (an
  in-memory store plus the artifact list), so the agent sees the ack (P409) as today. `release` (from `Register`)
  calls `Registry.Drain(owner, 5s)` before `forget`. `ade/runs.go` calls `release()` before `endAgentRun` reads
  `takeFinish` (verified, `runs.go:930`), so a slow `finish_step` or `handover` still lands before the exit is applied.
  Same for `scriptruns/smart_run.go` (`releaseGrant`). `ade/opsrecord.go` `mcpRecorder`: take the job cancel from
  the deferral and `op.SetCancel` it, so the widget's Stop ends the job.
- `dbmcp`: `withPanicRecovery` keeps wrapping the sync part; `bindRequestCancellation` moves to `await_results`
  only (a cancelled await stops waiting; a cancelled dispatch has nothing left to stop). `adapterhost.WithOpSource`
  stays on the job ctx. `StopFn` order: `AbandonAll`, then `srv.Close()` which calls `Registry.Close()` before
  `closeHTTP`. `cancel_operation` is unchanged: a job's DB work is a `Host.RunOp` op, cancellable as in P518.
- `memory/mcpserver`: `recovering` keeps wrapping the sync part; `mcpcall.Record` deferral as in agentmcp.
  `ingest_files` sends progress only while the dispatch request is open (the inline window); after a handle answer
  it sends none (`req.Session` progress needs the open request). `ingest_status` stays the way to watch an import.

### 2.4 Aggregated approvals, Studio (`dbmcp.ApprovalBroker`)

- Batch rule: **a batch is the period during which the broker's queue is non-empty.** Every request that enqueues
  while any is unanswered joins the open batch; the batch ends when the queue empties. One queue serves every
  client (no caller identity on stateless HTTP; the one human answers all of them in one dialog).
- Every pending request is presented at once (today only the head is). Each item resolves on its own answer,
  timeout (`ApprovalTimeout` 120 s from its own enqueue, unchanged) or abandonment.
- Held results: new `ApprovalBroker.WaitIdle(ctx)` returns when the queue is empty. `runQuery`, `explainQuery`,
  `kubeRun` and `reviewResponse` call it after their own item resolved and their work finished, before returning.
  An approved statement runs on its own approval (no reason to delay the database work); only its result waits.
  A denied item's error result waits too: "results push only after the last pending approval is answered".
  Starvation bound: `maxPendingApprovals` (50) and per-item timeouts.
- Result preview: response-stage items (`ApprovalStageResponse`) join the same batch. Three reads with preview on give
  one dialog with three previews; all three results release when the last is sent or withheld.
- `mcpasync.SetState(ctx, awaiting_approval)` around each `Request`, back to `running` after.
- Item model generalised for P521/P522: `ApprovalRequest` gains `Subject string` (`query`, `kube`; P521/P522 add
  `script`, `api`) beside the existing per-kind fields. No script/API fields now.
- Snapshot: `ApprovalSnapshot{BatchID string, Items []ApprovalRequest}` replaces `{Pending, Queued}`. `BatchID` is
  minted (`ab_` + shortid) when the queue goes non-empty.
- Prompt router: one `dbmcp` prompt per batch (`Ref` = batch id, opened on the first enqueue, closed when the queue
  empties), not one per request. New titles `backend.prompt.dbMcpBatch.title` ("Database requests wait for you") and
  `backend.prompt.dbMcpBatchNamed.title` (one connection name when every item shares it). Drop the four per-request
  title keys. `RaiseOnOpen` then raises once per batch.
- Bridge: `PendingApprovals` returns the new snapshot; `ApproveQuery`/`DenyQuery` become `ApproveQueries`/
  `DenyQueries {requestIds []string}` so "Approve all" acts only on the items the user saw (items joining mid-click
  stay pending). `PendingResponse(requestId)` unchanged.

### 2.5 Aggregated approvals, Space (`ade` branch requests)

- One open `branchRequest` per task stays the unit. A `request_branches` or `rename_branch` call that finds one open
  **merges** its items into it instead of failing ("A branch request for this task already waits..." is removed).
  `ExpiresAt` resets to now plus `branchRequestWait()` on merge so a late item gets its full window.
- Item ids become request-unique (`c<call>i<k>`; today `i<k>` per call would collide). Each item carries its call's
  `Source` and `StepName`; request-level `Source`/`StepName` move to items (dialog labels per item).
- Each call keeps its own slots and gets its own decision slice when the user answers. The answer is one atomic
  action, so "after the last answer" holds by construction.
- Per-item remote rename: `ApproveBranchRequestArgs.RenameRemote bool` becomes `RemoteItemIDs []string`;
  `branchDecision.renameRemote` becomes a set. Two merged renames each get their own remote choice.
- Run note `noteBranchApproval`: set while any call of that run waits; restored when the last one returns.
- `mcpasync.SetState(ctx, awaiting_approval)` inside `awaitBranchRequest`.
- Other Space prompts (`handover`, `schedule`) are not tool approvals; unchanged.

## 9. User decisions

1. **Push mechanism: decided, long-poll.** True unsolicited push is not achievable today (section 1); P520 delivers
   through `await_results`. Deferred, each its own later phase if ever wanted: channel push for Kira-launched
   interactive sessions, or hooks feeding finished results back as `additionalContext`.
2. **Scope: decided, not literal.** 1 s inline window (2.1); only slower or approval-gated calls return a handle.
3. **`finish_step` and `handover`: follows from 2.** They answer inline when fast, as today; `release` drains a slow
   one up to 5 s so the finish lands before the exit is applied.
4. **Open: one Studio batch for every client.** Stateless `kira-db` cannot tell clients apart, so agent A's results
   also wait for agent B's pending approvals. Option: per-client batches, which needs stateful sessions on
   `kira-db`. The plan ships the single batch unless the user says otherwise.
