## Design

### Scope decision: normal scripts only (orchestrator: confirm with user)

Repo hooks are shell contracts: prepare = exit code, deployed sha = a stdout line. They reference a
Run-module **normal** script (`kind: script`), resolved exactly as `planSmartStep` resolves a
workflow's smart script (same lookup, secrets, params, built-in vars, dir rule), and executed on the
runner the hook already uses. A smart script is refused with a clear message. Reason: the workflow's
smart path needs an ADE run row, a headless session and `finish_step`; setup and env checks have
neither, and a smart run claiming a worktree that setup is still preparing deadlocks on
`launchGate`. Running smart scripts from repo hooks would be a new agent supervisor, which the ask
rules out ("no new runner"). If the user wants smart scripts as prepare hooks, that is its own phase.

### YAML syntax

A sibling object key beside each inline key, mirroring the workflow pair `smart_script` + `params`:

```yaml
worktree:
  prepare_run:
    script: Install deps        # Run-module script name
    params:
      mode: ci                  # text or list of text, like workflow params
  prepare_timeout: 15m
environments:
  - name: staging
    deployed_sha_run:
      script: Staging sha
  - name: prod
    deployed_sha_script: curl -fsS https://prod.example.com/version
```

Rules:

- `worktree`: `prepare_script` and `prepare_run` are exclusive (both keys present = problem on
  `/worktree/prepare_run`). `prepare_timeout` applies to either.
- `environments[i]`: exactly one of `deployed_sha_script` (not blank) or `deployed_sha_run`.
  Schema `required` drops `deployed_sha_script`; the existing blank rule becomes the exactly-one rule.
- `script`: required, trimmed, not blank, one line, at most 200 runes (`model.MaxScriptRefName`).
- `params` names match `^[a-z][a-z0-9_]{0,31}$` (rule, not schema `propertyNames`, for a clear
  message); values text or a list of text.
- Kind, existence, uniqueness, secret params and param values are checked at run time, as workflows
  do. A file carrying a value for a secret param fails at run time with the workflow's wording, file
  word swapped to "repo file".

### Runtime: one resolver, two callers

New `apps/kira-space/internal/ade/scriptref.go`, extracted verbatim from `planSmartStep` steps 1 to 5:

```go
// scriptUse says who references a Run script: the kind it must be and the file it is named in.
type scriptUse struct{ kind, file string } // {scripts.KindSmart, "workflow file"} | {scripts.KindScript, "repo file"}

type resolvedScript struct {
	script   scripts.CustomScript
	env      []string          // KIRA_<builtin> then KIRA_PARAM_<name>
	rendered map[string]string // builtins + non-secret params (Compose input)
	secrets  []string          // values for the log mask
	dir      string
}

// resolveScriptRef finds the one script of use.kind named name and resolves its params, env and
// folder as a workflow step does. adeDir is where a UseAdeDir script runs.
func (b *TaskBoard) resolveScriptRef(use scriptUse, name string, given map[string][]string, vars map[string]string, adeDir string) (*resolvedScript, error)
```

- Lookup: same `CustomScripts.List()` scan. 0 of the wanted kind but ≥1 of the other kind gives a
  precise error ("is a smart script: a repo file runs a normal script" / the reverse for workflows);
  otherwise "not found" / "%d scripts have that name" unchanged.
- `secretParams` gains the `file` word parameter; workflow wording stays byte-identical.
- `planSmartStep` becomes: `resolveScriptRef(scriptUse{KindSmart, "workflow file"}, def.SmartScript,
  def.Params, b.adeVars(tc, sb, path), path)`, then its own timeout and prompt compose. Error prefix
  `smart script %q: ` unchanged. Behavior identical; existing workflow flow tests prove it.
- Repo callers wrap errors as `Run script %q: <reason>`.

Prepare (`ade/setup.go`):

- `startSetup`: "no prepare script configured" when both `WorktreePrepareScript == ""` and
  `WorktreePrepareRun == nil`.
- With a ref: resolve before claiming. Vars = `b.adeVars(tc, sb, path)` with `tc` from
  `b.loadTaskCtx(sb.TaskID)`; adeDir = worktree `path`. Resolve failure records a failed setup the
  way the script path records one (log `event` line with the reason, `UpsertSetup` failed with
  `Note`, `setPendingNote(noteSetupFailed)`, `notifyBoard`) and returns nil, so `RetrySetup` after a
  fix works. Factor the "record failed setup with note" lines already in `runSetup`'s `fail` path into
  one helper rather than duplicating.
- `runSetup` takes a small `setupScript{command, dir string; env []string; mask *secrets.Masker;
  label string}` instead of the raw script string. Inline: command = text, dir = path, env none,
  label = text. Ref: command = `script.Command`, dir = resolved dir, env = resolved env, mask =
  `secrets.NewMasker(resolved.secrets...)` via `sink.setMask`, label = `script.Command`. Env is
  `gitprepare.BuildEnv(...)` then the resolved env appended. First log line for a ref:
  `event` `running Run script "<name>"`. Timeout = `worktree.prepare_timeout` for both forms. Op log
  `startSessionOp(..., label)`.
- Sandbox: none, as today's inline prepare script and a workflow script step's default.

Deployed sha (`ade/deploy.go`):

- `runEnvScript(ctx, root, env model.AdeRepoEnv, vars)`: inline path unchanged; ref path resolves
  with `scriptUse{KindScript, "repo file"}`, vars `{repo: nickname, worktree: root, base: main short
  name, others ""}`, adeDir = repo root; runs `script.Command` in the resolved dir with
  `BuildEnv` + resolved env, same timeout and sha parse. A resolve error becomes `AdeEnvState.Error`
  (`Run script "x": not found`), shown as the existing "unknown" deployment row.
- `RunEnvScripts` lists scripts once per call, not once per environment (pass a lazily loaded list
  into the resolver, or resolve all refs first). `RepoConfigChanged` swaps `slices.Equal` for
  `slices.EqualFunc` with an `AdeRepoEnv` equality that compares the ref with `ScriptRef.Equal`
  (pointer fields make `slices.Equal` compare addresses, so every reload would rerun scripts).

A Run script renamed or deleted breaks the reference at the next run with "not found", as a workflow
step does. No reverse index.

## Risks

- Scope: smart scripts refused (see decision). User may want them; needs explicit confirmation.
- Dir rule surprise: a referenced script without "run in ADE worktree" runs in its own folder, not
  the worktree. Same as workflows; schema description, template comment and intro say it; env
  `KIRA_WORKTREE_PATH` / `KIRA_WORKTREE` still point at the worktree.
- Secret values in plain-text repo files: refused at run time only (repocfg rules have no scripts
  access). Same position as a workflow file at run time; workflow Save-time refusal has no repo-file
  equivalent without wiring scripts into `repocfg.Service`. Documented in the schema description.
- `scripts.List()` per env per refresh: bounded by one list per `RunEnvScripts` call.
- Behavior drift in the extraction: workflow error strings must stay byte-identical; existing flow
  tests and contracts catch drift.
- `configfs.DocFromSchema` rendering of `type: [string, array]`: verify generated `AGENTS.md` reads
  well; fall back to a plain description if the renderer chokes.
- UI spec timing against P514's editor change: spec asserts read-only text only; rerun after wave A
  lands.
