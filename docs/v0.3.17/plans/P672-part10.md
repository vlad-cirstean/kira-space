# P672 Part 10: second pass over Parts 2..9 (master plan)

Spec row: `P672 Part 10` in `docs/v0.3.17/SPEC.md`. Base commit `6c098b5f5`. UI only: no Go, no
bridge, no new unit tests.

This file is the loop. Each iteration gets its own plan, `plans/P672-part<k>-iter2.md`. Row names get
no new numbers; Part 10 runs as one loop and is not cut into new rows.

## Method

- Eight iterations, in Part order: Part 2, 3, 4, 5, 6, 7, 8, 9. One at a time.
- Per iteration: one Opus planner writes `P672-part<k>-iter2.md` and commits it. Then one Sonnet
  implementer lands it on `chapter/v0.3.17`. The next planner starts only after that landing.
- Each planner plans against the tree as the previous iteration left it, never the first-pass state
  and never its own memory of an earlier iteration.
- Default: one sequential implementer per iteration. Streams only when the iteration plan proves
  independence per working agreement "Streams" (file-ownership table, no ordering dependency).
  `scripts/check-ui-primitives.sh` and theme pieces are shared by nearly every group, so expect none.

## Fresh scan

Every planner scans from scratch. Never read a first-pass Result as evidence that something is done.
First-pass plans (`P672-part<k>.md`) and SPEC Results only give the subject's scope and its named
exceptions.

- `mcp__codegraph__codegraph_explore` for every component, composable and caller question: who
  renders a piece, which hosts hand-roll it, blast radius before a change. Several real calls per
  iteration; the orchestrator greps the log.
- Class-token and template scans over every non-`components/ui/` `.vue` file in the six guard DIRS
  (`apps/kira-space/frontend/src`, `apps/kira-space/frontend/mobile`, `packages/workbench/src`,
  `packages/git-ui/src`, `packages/docker-ui/src`, `packages/theme/src`). Multi-line aware: a tag
  often spans lines, so scan whole files (`grep -Pzo`, or a small script in the scratchpad), not
  line greps.
- Compare against ARCHITECTURE "UI uniformity rules (P672)" (rules RD..RTa) and
  `plans/P672-inventory.md`.
- Record queries and counts in the plan's "Current state" section, so a reviewer can rerun them.

## What counts as a finding

Any element of the iteration's subject that still differs from the canonical rule, or from its
siblings doing the same job. That includes:

- elements the first pass skipped as exempt, special-cased or outside its file lists;
- variants a guard regex misses (attribute order, extra attrs, bound class, `:class` object, a
  wrapper component that hides the primitive);
- hand-rolled equivalents of a shared piece (a hand grid where KeyValueList fits, a hand title bar
  where DetailHeader fits);
- exemptions whose reason no longer holds, or never named a real requirement.

Not a finding: a difference a named rule allows, a deliberate first-pass exception (below), or a
taste call without a rule behind it. An iteration that finds nothing real says so plainly in its plan
with the queries and counts, commits that plan, and ends with no implementer. Never manufacture work.

## Guards

- No TEMPORARY mechanism exists any more (removed in Part 9). Never reintroduce one, never add a
  baseline.
- A new guard lands with zero offenders, in the same commit as or after the fixes that clear it.
- A regex that misses variants gets extended in place (same id), not shadowed by a second guard.
- A built-in exempt name or PERMANENT line needs a named requirement (what breaks without it). A
  stale PERMANENT line or a built-in exempt name that exempts nothing fails the run: delete it in the
  commit that makes it stale.
- Update the guard header comment (`# Guards ...: docs/v0.3.17/plans/P672-part<k>-iter2.md.`) and
  ARCHITECTURE (guard range, PERMANENT count, the rule line) in the iteration's ARCHITECTURE commit.

`P672-part2-iter2.md` "Handoff" lists observations from the Part 2 scan for later iterations. Each
later planner re-verifies them; they are leads, not findings.

## Done condition

across all subjects finds nothing real. Then SPEC row Part 10 gets Done and a Result.

## Test lessons (sandbox)

- Implementer runs only specs naming changed testids or touched surfaces, once, near the end of the
  iteration. Visual baselines re-record in PR CI; never record them locally.
- Monaco menu items need a hover before the click.
- reka radio and toggle arrow presses need `delay: 40`, through `tests/ui/support/radioKeys.ts`.
- New spec helpers go in shared support files (N8 duplicate helper check).
- N17 conventions marker: keep it on files that carry one.
- N10: `.vue` files cap at 600 lines; a conversion that grows a file over the cap splits it.
- U91 exemptions go stale when a tooltip conversion removes the pattern; delete the PERMANENT line.
- A timeout under load gets one lone rerun first, before any fix.
- Run `bun run build:mobile` before mobile specs.
- PERMANENT exemptions need a named requirement.
