## Decisions

### D1 Which edits count

User edits made from the task panel (bridge calls under `adeUserCtx`), on a live task:

| Item key | Edit | Engine method |
|---|---|---|
| `note:<id>` | add, edit, delete a user note | `AddNote`, `UpdateHandover` (state `note`) |
| `handover:<id>` | edit or delete a handover body (draft or handed) | `UpdateHandover` |
| `link:<artifactId>` | add, rename, re-file, recategorise, remove a stored link | `AddLink`, `EditLink`, `RemoveArtifact` |
| `link:jira`, `link:host` | set, change, clear the Jira or host slot | `AddLink`, `EditLink`, `UpdateTask` (`jira`, `clearJira`, `hostUrl`) |
| `proof:<proofId>` | attach, detach a proof session | `LinkProof`, `UnlinkProof` |
| `field:title` | rename the task | `UpdateTask` (`title`) |

Not counted, and why (scope note for the orchestrator; the SPEC row says "others in the panel" and lets the plan decide):
- Status and step moves: a move changes which agents run (`closeStageSessionsLocked`) and has its own handover path.
- Estimate, colour, parked: planning metadata; no agent prompt carries them.
- Branches, workflow, sessions: own launch and stage flows; not panel content an agent reads.
- `DismissHandover`: hides a card, changes no content.
- Agent-made changes (`attach_proof`, handover drafts via MCP, `report_artifact`): not user edits. P545 event rows and
  P547 audit rows are read-only; no forward on them.

Recording sits in the engine, where the before value is known under the task mutex. `UpdateTask` is also called by
`clearSlotLocked` and branch rename: it records only when `oplog` origin trigger is user (what `adeUserCtx` sets;
implementer confirms the accessor), and reads the previous task row only when `title`, `jira`, `clearJira` or `hostUrl`
is in the patch. `EditLink` slot moves record once, under the final key, from the engine method, not from
`clearSlotLocked`.

### D2 Targets: agents running in the step

`forwardTargets(tc)` in `ade/panelforward.go`, same rule shape as `stageSessions` (and its TS mirror):
- step = `currentStepID(tc)`; none when "" or `done`.
- a session row qualifies when `task_id` matches, `state = running`, and either `step_id = step` (purpose not review),
  or purpose `review` while step is `review`. Branch sessions (no step) never qualify.
- reachable = mode `tui` and `Tracker.TerminalOf(id)` is bound. Unreachable = mode `headless` (or a TUI row with no bound
  terminal, which Reconcile is about to stop).

Headless runs are not reached (scope note for the orchestrator): no provider's headless mode reads input after the
prompt. Considered and declined: piggybacking the diff on the run's next `agentmcp` tool result (via the
`mcpcall.Record` wrapper). Delivery would not be guaranteed before the run ends (an agent may call no Kira tool before
`finish_step`), so the UI could not say "sent" truthfully. Instead the offer names headless runs as unreachable and
points to Take over (existing `TakeOver` turns the run into an interactive session in the same step; the pending
changes then forward to it).

### D3 Offer UX: one pending set per task, one bar

Per-save accumulation, not a prompt per edit: the review window's forward bar is the precedent, a prompt per save is
noise during a burst of edits, and coalescing gives the agent the net change.

- Every counted edit, when at least one session (reachable or not) runs in the step, adds to the task's pending set.
  With none running, nothing records: no offer.
- New `panel/AdePanelForwardBar.vue` (`<script setup lang="ts">`, Tailwind only), rendered by `AdeTaskPanel.vue`
  under the action-error alert, above the tabs, so title edits (header) and Details edits (links, chain) share one
  offer visible from every tab. Hidden for review and archived tasks and when `pending` is empty.
- Content: `Alert variant="info" strip` with codicon `send` and "{count} panel changes not sent to agents in {step}";
  `Button variant="dialog" size="kira"` "Forward to {n} agent(s)" (testid `ade-panel-forward`); a shadcn-vue
  `Collapsible` "Show message" revealing a `<pre>` of the exact text that will be pasted (testid
  `ade-panel-forward-preview`); `TooltipIconButton` `close` "Discard pending changes" (testid
  `ade-panel-forward-dismiss`). Each pending item shows as a small chip line (label from D5) under the text.
- Reachable count 0 with headless running: Forward disabled (`TooltipDisabledTrigger`) with tooltip "Background runs
  take no messages. Take over a run to send." (`AdeTip`, as the review bar does).
- After a forward: bar hides (pending cleared server-side); partial failure shows an error alert naming the failed
  sessions by badge; total failure keeps pending and shows the error.
- Server state, so TanStack Query, no Pinia store: `usePanelForward(taskId)` query, `useForwardPanelEdits`,
  `useDismissPanelEdits` mutations in `queries.ts`.

### D4 "Diff only": exact meaning

- An item's forward text is the change from its value when it first entered the pending set (before the first edit
  since the last forward or dismiss) to its value now. Repeated edits to one item coalesce; an item whose net change is
  empty (edit then undo) drops out.
- Text items (notes, handovers): unified hunks, 2 context lines, file headers (`---`/`+++`) stripped, `@@` headers
  kept. Unchanged text more than 2 lines from a change never appears. A new note is all `+` lines; a deleted one all
  `-` lines.
- Links, proof, title: one line per side, `- <old>` / `+ <new>`: link `<kind> <title> <url-or-ref>`, proof
  `<name>: <summary>` (no steps, no data), title the text. Add has only `+`, remove only `-`.
- Nothing else goes in: no task context, no other notes, no links that did not change, no proof data.
- Bounds: 200 diff lines per item and 32 KiB per message; over either, the item's diff is cut and ends with
  `[cut: N more lines; full text in the task panel]`. Pending set capped at 32 items per task; the 33rd evicts the
  oldest item and the bar says "oldest change dropped" (count kept in the result).
- Diff library: `github.com/aymanbagabas/go-udiff` (port of the Go tools' internal diff; implementer confirms the
  package licence is fully open, BSD-3 or MIT, and pins the latest tag). A line diff with hunk grouping is non-trivial
  infrastructure (library rule). Fallback if the licence check fails: `github.com/sergi/go-diff` (MIT, already in
  `go.sum`) in line mode with hunk grouping done in `panelforward.go`; the implementer names the reason in the commit.

### D5 Message

New `llmprompts` entry `ade.panel.forward.message` (`AdePanelForwardMessage`, `KindMessage`, `Apps: spaceApp`,
`Applies: NextCall`, title/purpose/usedBy catalog keys under `llmPrompts.entry.adePanelForwardMessage.*`), with an
example in the registry and a `budget.tsv` line. Default:

```
The user changed the task panel. Only the changes follow, as a diff; nothing else changed.
{{range .Items}}--- {{.Label}}
{{.Diff}}
{{end}}Take these changes into account in your current work.
```

Labels: `note ({stage}, {time})`, `handover ({from} to {to})` or `handover draft ({stage})`, `link`, `Jira link`,
`host link`, `proof`, `task title`. Times in local `15:04`. The composed text is what `PanelForward` returns as
`preview`, byte for byte, so the UI shows exactly what is sent.

### D6 Backend shape

`ade/panelforward.go` (new):
- `type panelEdits struct{ mu sync.Mutex; byTask map[string]*pendingSet }`, field on `TaskBoard`, created in
  `NewTaskBoard`. `pendingSet{ stepID string; items map[string]*pendingItem; order []string; dropped int }`,
  `pendingItem{ key, kind, label string; before, after string; at int64 }`. In memory only: a restart ends every
  interactive session anyway (TUI terminals close on quit), so nothing pending could still reach its target. No
  migration (P547 owns `storage/migrations` in B6).
- `recordPanelEdit(tc, key, kind, label, before, after)`: no-op when the task is archived, has no step, or
  `forwardTargets` is empty; drops a set whose `stepID` differs from the current step before adding.
- `PanelForward(ctx, taskID) (adewire.PanelForward, error)`: drops the set when the step changed or no session runs in
  it any more; returns items, targets, unreachable and `preview`.
- `ForwardPanelEdits(ctx, taskID) (adewire.PanelForwardResult, error)`, under the task mutex: recompute targets;
  none running refuses `backend.space.ade.panelForward.noAgent.body` and drops the set; none reachable refuses
  `backend.space.ade.panelForward.unreachable.body` and keeps it. `Tracker.Send` to each reachable target;
  `ErrSessionNotRunning` counts as ended, not failed. At least one delivered: clear the set (the agents in the step
  share it; a second forward would paste it twice, as `ForwardReviewComments` reasons). None delivered: keep it,
  return the joined error. Emits board change so every window's bar refreshes.
- `DismissPanelEdits(ctx, taskID)`: clears the set; board change.
- Hooks in `AddNote`, `UpdateHandover`, `AddLink`, `EditLink`, `RemoveArtifact`, `UpdateTask` (D1 guard), `LinkProof`,
  `UnlinkProof`: capture before (row or slot value, read before the write), write, then `recordPanelEdit` after a
  successful write only.

Wire (`adewire/wire.go`, `wire.ts`): `PanelForwardItem{ key, kind: 'note'|'handover'|'link'|'proof'|'field', label,
at }`, `ForwardTarget{ sessionId, badge, headless }`, `PanelForward{ stepId, stepName, items, targets, unreachable,
dropped, preview }`, `PanelForwardResult{ sent: string[], ended: string[], failed: { sessionId, error }[] }`. Args:
existing `TaskArgs`. Bridge: `AdeTaskService.PanelForward`, `ForwardPanelEdits`, `DismissPanelEdits`, each validating
`taskId` and mapping through `adeTaskError`. Regenerate bindings; add channels to `tests/ui/support/ipcChannels.ts`
and mock entries to `tests/ui/support/mockRuntime.ts`.

Frontend refresh: `panelForwardKey = (taskId) => ['adetask', 'panelForward', taskId]` in `readQueries.ts`;
`installAdeReadSignals` invalidates the `['adetask', 'panelForward']` prefix on board and sessions pushes (every
recording edit already calls `notifyBoard`; a session start or stop pushes sessions). Mobile shares the signal file and
gains no UI.

### D7 Failure and offline agents

- Agent exits between offer and click: `ended`, not an error; if every target ended, `noAgent` refusal, set dropped,
  bar hides on the next refetch.
- PTY write error: `failed` entry with the error text; pending kept only when nothing was delivered.
- Step moves while pending: set dropped at the next read or record (the move closed those sessions).
- Archived task, review task: no recording, no bar.
- Concurrent edits from two windows: one set per task under `panelEdits.mu`; the task mutex serialises a forward with
  edits.
