## Today

- Kira DB calls from a `db_mcp` step session reach `kira-db-session` (P548). Each tool handler runs under
  `withPanicRecovery`, which tags the ctx `adapterhost.OpSourceMCP`; adapter work goes through `Host.RunOp`, whose
  `op:start`/`op:end` events become `op_log` rows (`category='db'`, `source='mcp'`) through `oplog.DbSource`. Those
  rows carry no task or session (`opStartPayload` has none), and their command can carry bound params
  (`adapters.SetCommand` appends `-- params: [...]` when `LogParams`).
- One tool call can fan out to several adapter ops (connect, children, read lane open); a refused call (permission,
  allow list, limit) runs no op at all and leaves no row. Approvals (`ApprovalBroker`) leave no row either.
- `op_log` prunes db rows by `advanced.opLogRetentionDays` plus a 20 000 row global cap, and other rows by 30 days /
  5000. A long-lived task would lose its trail while the task still exists.
- `agentmcp` already records each of its own tool calls as an `mcp` op through `mcpcall.Record` (`ade.mcpRecorder`):
  the pattern this phase follows for the call hook.

## Decisions

### D1 Data source: one audit row per tool call and per approval, not op log rows

- Considered: tag `op_log` db rows with task and session (new `opStartPayload` fields from ctx) and read them per
  task. Rejected, with reasons:
  1. Granularity: `op_log` rows are adapter ops, not agent actions. A refused call has no op; a `run_query` is
     connect plus read; approvals are not ops at all. The SPEC row asks for each action and each prompt.
  2. Retention: `op_log` pruning (above) would delete a live task's trail. An audit trail lives as long as its task.
  3. Redaction: db op commands may carry bound params and unmasked literals; the Operations panel shows them on
     purpose. The audit needs a stricter, separate policy (D4) without weakening the Operations panel.
- Chosen: table `ade_db_audit` in `kira.db`, written by code at two capture points (D2), keyed by task.
  `op_log` is untouched. The Operations panel and the audit trail answer different questions; neither reads the
  other.

### D2 Capture points (recorded by code, never by the agent)

- Tool calls: the session server's `buildMCPServer` ends with `mcpcall.Record(srv, s.auditHook)` when
  `s.cfg.Audit != nil`. Only the session pool's config sets `Audit` (`bridge.NewDbMcpSessions`); the external
  instance (port 8766) never audits (its calls carry no task). The hook:
  - reads `SessionFrom(ctx)`; no identity or empty `TaskID` records nothing (defence in depth; the session verifier
    always sets it);
  - inserts a `running` call row (tool, connection, redacted statement or summary, start time), stamps the call id
    into the request origin (`ApprovalOrigin.CallID`, new field, via the existing `originContextKey`), and returns
    the done func;
  - done func: duration from a monotonic clock, status from `(isError, err)` (D3), redacted error (D4); updates the
    row. It never stores the result text of a successful call.
- Approvals: `ApprovalBroker.SetObserver(ApprovalObserver)` (atomic pointer, set once at wiring). Interface in
  `dbmcp`: `ApprovalRaised(req ApprovalRequest)` and `ApprovalResolved(req ApprovalRequest, outcome ApprovalOutcome)`.
  Called from `RequestChoice` only, the single funnel every approval passes:
  - after enqueue: `ApprovalRaised` (row `pending`);
  - on each return path (answer, timeout, ctx abandon, `abandonWhere`/`AbandonAll` via the entry result):
    `ApprovalResolved` with the final outcome, called once, after the select returns, from `RequestChoice` itself
    (so every resolution path is covered without touching `resolve`);
  - early returns `ApprovalQueueFull`, `ApprovalTooLarge`, `ApprovalHeldFull`: one `ApprovalResolved` with no
    prior raise (row inserted already resolved; no human saw it, and the trail says so).
  - Called outside `b.mu` (observer does SQLite I/O). Observer records only `req.Origin.SessionID != ""`; the
    external client's approvals stay out of every task trail.
- Exemption prompts (P528): `req.Reason == ApprovalReasonExemption`, `req.Exemption` gives the agent's reason and
  the limits to lift. Recorded as subject `db.exemption` with limit names and the reason (D4 caps).
- Link: approval rows carry `call_id` from `req.Origin.CallID`. Every approval raised on the session server happens
  inside a tool call, so `call_id` is always set there; an empty one is dropped with a `slog.Warn` (programming
  error, not data).
- Package: new `internal/dbaudit` (`Recorder`): implements `dbmcp.Auditor` (call start/finish, consumer-declared
  in `dbmcp`) and `dbmcp.ApprovalObserver`; owns redaction (D4), writes through `repos.DbAuditRepo`, emits the push
  event (D6). Writes are synchronous at start and finish (one small insert/update each, sub-millisecond on the
  WAL DB; no queue, so nothing is ever dropped). A write error logs `slog.Warn` and never fails the tool call.
- Startup: `DbAuditRepo.ReconcileRunning("app exited")` turns `running` calls to `error` and `pending` approvals to
  `abandoned` (same posture as `OpLogRepo.ReconcileInterrupted`), before the session pool can start.

### D3 Status vocabulary

- Call `status`: `running`, `ok`, `error` (adapter or internal failure), `refused` (dbmcp declined: permission,
  read-only, allow list, limit, approval not given), `cancelled` (ctx cancelled: client gone, session token revoked).
- Mapping in the done func: `err != nil` -> `error`; ctx `Canceled` -> `cancelled`; `isError` with an adapter or
  ipcerr code prefix (D4) -> `error`; any other `isError` -> `refused`; else `ok`.
- Approval `outcome`: `pending`, `approved`, `denied`, `timedOut`, `abandoned`, `queueFull`, `tooLarge`,
  `heldFull` (one string per `ApprovalOutcome`; a `String()` method on `ApprovalOutcome` is the one mapping).
  UI groups them: accepted (`approved`), denied (`denied`), not answered (rest).

### D4 Redaction: no row data, no bound values, no secrets

- Allow list, not deny list. A call row stores only:
  - `tool`, `connection_id`, `connection_name` (from `cfg.Conns` summary), `mode` (run_query `mode`), `target`
    (`path` or cluster/namespace/name or script id, whichever the tool takes; identifiers, not data);
  - `statement`: the statement field of `run_query` and `explain_query` (`sql`) through `redactStatement` below;
  - `summary`: for every other tool, `oplog.RedactJSON` of the args after keeping only allow-listed keys
    (`connectionId`, `path`, `mode`, `cluster`, `namespace`, `kind`, `name`, `scriptId`, `method`, `url`, `limit`,
    `refresh`); request bodies, headers, documents, values and params never pass. `url` goes through
    `oplog.RedactText` (userinfo) and drops its query string. Cap 1 KiB.
- `redactStatement(connectionID, statement)`:
  - New optional interface `adapters.StatementRedactor { RedactStatement(statement string) string }`, resolved
    by new `Router.RedactStatement(connectionID, statement) (string, bool)` through the connection's read lane
    adapter, else its live adapter (same lookup shape as `Router.ClassifyStatement`); `false` when neither exists
    or the adapter has no redactor. No hard-coded kind list in `dbmcp` or `dbaudit`.
  - SQL adapters (postgres, mysqlfamily, sqlite, clickhouse): `adapters.MaskSQLLiterals(statement, dialect)`, new,
    built on the same quote-aware scanner as `lexSQLComments` (`errors.go`): every string literal (single quote,
    `E'...'`, dollar-quoted, MySQL double-quoted string where the dialect treats `"` as a string) becomes `'…'`;
    comments are removed; quoted identifiers, keywords and numbers stay. A `SQLQuotingHazard` (scanner unsure of
    a literal's extent) withholds the whole statement rather than risk a partial mask.
  - Mongo: `db.<collection>.<method>(…)` from its existing `parseTarget` (arguments are documents, so data).
  - Redis: the command name only, uppercased, then ` …` (keys and values can be data).
  - Other kinds: no redactor; the row stores `statement_withheld = 1` and the statement's length.
  - Then `oplog.RedactText` (URL credentials) and a 4 KiB cap (`truncateRunes`, `statement_truncated`).
  - Bound params: `run_query` takes no params today; `adapters.SetCommand`'s `-- params:` suffix belongs to op
    commands, which the audit never reads. Rule for later tools: params are never an allow-listed key.
- Errors: adapter and ipcerr failures store only the code and a fixed text, the `maskedToolError` posture applied
  to every connection, masked or not (driver messages echo the failing value, e.g. a unique-key violation names
  the key). Factor the code extraction shared by `toolError` and `maskedToolError` into one unexported
  `errorCode(err) (string, bool)` in `render.go`, and expose `dbmcp.AuditErrorText(code string) string` for the
  fixed wording "E_X: failed (message not recorded)". At the hook, text from `isError` results that starts with a
  known code prefix is reduced the same way; other `isError` text (dbmcp's own refusal wording, which names
  connections, modes and limits, never values) goes through `redactStatement`'s literal mask too (refusals can
  quote the statement), then `RedactText`, cap 1 KiB. Go `err` (internal fault): fixed "internal error".
- Approvals store: subject, reason, stage, outcome, raised and resolved times, `call_id`. Exemption: limit names
  and their configured thresholds (settings, not data) as JSON, and the agent's reason through `RedactText`,
  capped 280 runes. Never: the held response (`ApprovalResponse.Text`), the plan evidence, the statement again
  (the call row has it).
- Existing masking reused: `oplog.RedactJSON`/`RedactText` (secret-keyed fields, URL credentials), the
  `maskedToolError` code-only rule, the dialect scanner behind `StripSQLComments`. PII mask rules (`MaskRules`)
  apply to result values; results are never stored, so they need no new hook. `secrets.Masker` needs plaintext
  secret values, which neither `dbmcp` nor `dbaudit` holds; literal masking covers secrets typed into statements
  (`... PASSWORD '…'`).

### D5 Storage and retention

- Migration `storage/migrations/0081_p547_db_audit.sql` (P547 owns the dir in B6; renumber at rebase only if the
  tip moved past 0080):

  ```sql
  CREATE TABLE ade_db_audit (
    id TEXT PRIMARY KEY,
    task_id TEXT NOT NULL REFERENCES ade_tasks(id) ON DELETE CASCADE,
    call_id TEXT REFERENCES ade_db_audit(id) ON DELETE CASCADE, -- approvals only
    kind TEXT NOT NULL CHECK (kind IN ('call', 'approval')),
    session_id TEXT NOT NULL, step_id TEXT NOT NULL, run_id TEXT NOT NULL,
    started_ms INTEGER NOT NULL, ended_ms INTEGER,
    status TEXT NOT NULL,          -- call: D3 status; approval: D3 outcome
    tool TEXT NOT NULL DEFAULT '', connection_id TEXT, connection_name TEXT NOT NULL DEFAULT '',
    mode TEXT NOT NULL DEFAULT '', target TEXT NOT NULL DEFAULT '',
    statement TEXT, statement_len INTEGER NOT NULL DEFAULT 0,
    statement_withheld INTEGER NOT NULL DEFAULT 0, statement_truncated INTEGER NOT NULL DEFAULT 0,
    summary TEXT, error TEXT,
    subject TEXT NOT NULL DEFAULT '', reason TEXT NOT NULL DEFAULT '', stage TEXT NOT NULL DEFAULT '',
    exemption_json TEXT
  );
  CREATE INDEX ade_db_audit_task ON ade_db_audit (task_id, started_ms);
  ```

  `connection_id` gets no FK: a deleted connection keeps its name in the trail. `embed.go` names entry 81.
- Retention: the trail lives and dies with its task (cascade); archived tasks keep it. Per-task cap 2000 call
  rows: the call insert deletes that task's oldest calls past 2000 in the same transaction (approvals follow by
  `call_id` cascade). No age limit. 2000 bounds one runaway agent; a normal run is tens of calls.
