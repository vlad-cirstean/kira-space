## Decisions

### D1 Step schema field

- YAML key `db_mcp`, boolean, default `false`. Wire field `dbMcp` on `adewire.WorkflowStep` (Go `DbMcp bool
  json:"dbMcp"`) and `WorkflowStep` in `frontend/src/ade/v2/wire.ts`.
- Kinds: `withSession` (agent, review, manual). Rules, in `parse.go`:
  - agent: refused with `smart_script` ("db_mcp is not allowed with smart_script"; a smart script picks its own MCP
    servers, same rule as `allowed_tools`).
  - manual: only with `session: true` (same wording as `agent`/`settings`: "db_mcp needs session: true").
  - review: allowed (review rounds run the step's agent through `superviseAgent`).
- Options table row (`options.go`, after `allowed_tools`): `{Path: "steps[].db_mcp", Type: "boolean", Kinds:
  withSession, Default: "false", Doc: "Give the step's agent sessions the Kira DB tools (MCP server
  `kira-db-session`), for that session only. Works with the Database MCP server off in Settings. Not with
  `smart_script`. Manual steps: only with `session: true`."}`. Parser, writer and generated AGENTS.md all derive from
  the table.
- Writer (`applyStep`): `setScalar(m, "db_mcp", kBool, "true", s.DbMcp, stepOrder)`, else `dropKeys(m, "db_mcp")`;
  manual branch writes it only when `s.Session`; agent branch drops it on the smart-script path.
- Library references: `db_mcp` is overridable. Add to the Go override key set in `refs.go` (`overrides` /
  `applyRoutes` neighbours; follow how `allowed_tools` is handled) and `'dbMcp'` to `OVERRIDABLE` in
  `board/stepLibrary.ts` (after `allowedTools`).
- `ade.stepDef` gains `DbMcp bool`; `workflowSteps` copies it and zeroes it for script and manual-without-session
  (parser already guarantees it; the copy keeps snapshots safe).
- Legacy top-level `kira_space_mcp` (P408) stays legacy and unrelated (it was the Kira Space task server).

### D2 Session server: a second, session-only dbmcp instance

- Shape: `bridge.DbMcpService` keeps the external instance (port 8766, global token, Settings switch) exactly as
  today. New `dbmcp.SessionPool` (file `internal/dbmcp/sessions.go`) owns a second `*dbmcp.Server` that:
  - binds `127.0.0.1:0` only (Config.Port `EphemeralPort`; `New` refuses `Sessions` with any other port, so the
    external port is never touched);
  - authenticates only live session tokens, never the global token (no token file read or written);
  - starts on the first grant and closes when the last grant is released (start and stop under the pool mutex;
    a grant racing a close waits, then starts a fresh server).
- Why a second instance, not a mode switch on the one server: the external instance's lifecycle, port, token and
  Regenerate/Install surface stay untouched; turning the switch on or off never moves a running session's URL; the
  session listener can never be mistaken for the registered 8766 endpoint. Why not reuse `agentmcp`: the tool set,
  access gates, mask rules, approvals and limits live in `dbmcp.Server`; duplicating them would fork the gates.
- Both instances share the one `ApprovalBroker` (one prompt queue, one UI) and the same backends. Build both
  configs from one unexported `(*DbMcpService).serverConfig(port int) dbmcp.Config` (today's literal in
  `NewDbMcpService` StartFn); StartFn adds `Token`, the pool adds `Sessions`. Each instance keeps its own
  exemption store (an exemption is minted and used on the same server).
- `dbmcp.Config` gains `Sessions *SessionTokens`. Exactly one of `Token` and `Sessions` is set (`New` refuses
  both or neither). With `Sessions`: no `cfg.Token()` call, `tokenVerifier` verifies against the table.
- Pool constructor: `bridge.NewDbMcpSessions(s *DbMcpService) *dbmcp.SessionPool`, a package func, never a method
  on the bound service (Wails binds every exported method; a bound Grant would hand a token to the renderer).

### D3 Session credential lifecycle (app-managed, never shown)

- `dbmcp.SessionIdentity{SessionID, TaskID, StepID, RunID, Cwd string}`.
- `SessionPool.Grant(id SessionIdentity) (harness.MCPServer, func(), error)`: mints with `tokenauth.Mint` (hash
  and salt in memory only), registers in `SessionTokens`, ensures the server runs, returns
  `harness.MCPServer{Name: dbmcp.SessionServerName, URL: srv.URL(), Headers: {"Authorization": "Bearer " + plain},
  Timeout: harness.MCPCallTimeout}` (same call timeout as the `kira-db` registration) and an idempotent release.
- Release: removes the token (next request with it gets 401 at once), abandons that session's parked approvals
  (`ApprovalBroker.AbandonSession(id)`), closes the server when no grant is left.
- Where it rides: the plaintext goes only into the launch's existing `agentmcp` config file (0600, in the agent
  dir, deleted on release). `agentmcp.Grant` gains `Extra []harness.MCPServer`; `Register` appends them to the
  `MCPConfig` call next to `kira-ade` (refuse an empty name, a duplicate name or `ServerName`). One file, one
  release, both providers (Claude `--mcp-config`, OpenCode `OPENCODE_CONFIG` merge) with no harness change.
- Never shown: no wire type, binding, i18n string, log line, op command or contract carries the token. Op command
  shows only the config path (today's behaviour). Status, Install, Regenerate stay about the external instance.
- Lifetime equals the process: headless grant released after `RunHeadless` returns (same point as the agentmcp
  release); TUI grant joins the `bindTUI` release chain (record stop or launch expiry). A resume re-grants.
- App quit: `SessionPool.Close()` (abandon all session approvals, close server) in the Studio teardown next to
  `bridge.StopDbMcp` (`appwire/studio_build.go:181`).

### D4 Global switch off: per-session access, never external

- The pool never reads `settings.DbMcp.ServerEnabled`. Switch off: external instance stopped, 8766 unbound; step
  sessions with `db_mcp` still work through the pool. Switch on: same, the session still uses the pool, never the
  global token.
- External clients cannot reach the pool: its port is ephemeral and unregistered, every token is per launch,
  in-memory hash only, 32 random bytes, revoked on release; the global token (file) is rejected on the session
  listener; a session token is rejected on 8766 (separate verifiers). Same exposure model as `agentmcp` grants.
- Approvals: shared broker, so session calls in prompt mode show in the normal approval UI. Scope abandonment:
  `AbandonAll` splits into `AbandonExternal()` (origin `SessionID == ""`, external StopFn), `AbandonSession(id)`
  (release) and `AbandonSessions()` (pool close); app quit calls both broad ones. Toggling the switch off never
  drops a session's pending approval.

### D5 Identity in dbmcp (for P547)

- Session verifier returns `auth.TokenInfo{UserID: "session:" + id, Expiration: far future}`; table lookup gives
  the identity. `withRequestContext` reads `auth.TokenInfoFromContext` (set by `RequireBearerToken` before it) and
  stores the identity; exported `dbmcp.SessionFrom(ctx) (SessionIdentity, bool)`.
- `ApprovalOrigin` gains `SessionID`, `TaskID`; `Cwd` is filled from the identity for session calls (the launch
  cwd Kira knows). External calls keep client-only origin. The approval body already renders `Cwd` when set; no
  new UI. P547 reads `SessionFrom` and `ApprovalOrigin.SessionID/TaskID` for attribution.

### D6 Launch wiring in `internal/ade`

- `TaskBoard` gets `SetDbMcp(DbMcpSessions)` with an `atomic.Pointer` holder, the `SetProofs` pattern
  (`ade/proof.go`): the pool exists only after the Studio stage builds. Interface in `ade` (consumer-declared):
  `Grant(dbmcp.SessionIdentity) (harness.MCPServer, func(), error)`; `ade` may import `dbmcp` only if layering
  allows (check `layering_test.go`), else declare the identity struct in `ade` and adapt in appwire.
- `appwire.go` after `w.AdeBoard.SetProofs(w.ProofStore)`: `w.AdeBoard.SetDbMcp(w.DbMcpSessions)`; pool built in
  `wireStudioEmbedded` right after `NewDbMcpService`, stored on `studioEmbedded` and `Wired.DbMcpSessions`.
- Headless (`superviseAgent`): when `def.DbMcp`, grant before `b.agent.Register`, pass `Extra`, append
  `dbmcp.SessionAllowTool` (`"mcp__kira-db-session"`, server-level allow; OpenCode maps `mcp__<server>` via
  `port.go kiraEntry`) to `AllowedTools`; release with the agentmcp release. Rebase runs never (rebase def).
  No pool bound (nil holder) or a grant error fails the launch with the error ("Kira DB tools could not start:
  ..."), never a silent run without the tools.
- TUI (`prepareWithGrant`): look up the step def of `pa.StepID` (or `grantStep`) in `tc.wf`; when `DbMcp`, same
  grant, `Extra`, allow tool, release in the error paths and in the `bindTUI` chain. Ad hoc task sessions (no
  step) get none.
- Server name `dbmcp.SessionServerName = "kira-db-session"`. P537 naming kept: the external server stays `kira-db`
  with its registration, token files and helper. A distinct session name avoids a clash with a user-scope `kira-db`
  registration in non-hermetic launches (Claude Code's precedence between `--mcp-config` and user scope is not
  verified here; a clash with the switch off would 401). The MCP `Implementation.Name` stays `kira-db`.
