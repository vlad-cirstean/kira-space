# P583 Agent worktree: work on an already existing branch

Stream A of batch P583-P585 (`plans/batch-P583-P585.md`). Worktree `/home/user/kira-wt-p583`, branch `stream/p583`.

Ask, decision, UI: `SPEC.md` row P583. Agent checks out an existing branch in its own task worktree. When another
worktree holds it, the user approves detaching it there (adopt), then Kira checks it out. Rows show the branch name,
never `HEAD`; two tasks on one branch show it; a detached worktree shows a detached glyph whose hover names the task and
worktree holding the branch now.

All paths below are under `apps/kira-space/` unless they start with `internal/` at repo root (`internal/agentmcp`,
`internal/llmprompts`, `internal/kiraschema`) or `packages/`, `docs/`.

## 1. Findings (current code)

### How an agent gets a worktree and branch

- MCP `request_branches` (`internal/agentmcp/space.go:366`, args `BranchSpec{repo, branch, base}` at `:197`) calls
  `TaskBoard.RequestBranches` (`internal/ade/branchrequest.go:437`).
- Phase 1 `planBranchRequest` (`branchrequest.go:493`) runs `planItem` (`:567`) per spec under the task lock.
  - Task already has a row with that name: `planNamed` (`:594`). Non-`mine` row fails "not yours to create" (`:596`).
    `worktreeOf` (`internal/ade/setup.go:269`) returns the path where the branch is checked out *anywhere*; non-empty
    gives outcome `existing` with that path (`:611`), even when the path is another task's worktree or the main
    checkout. Empty gives item kind `worktree`.
  - No row: `planNew` (`:638`). **A branch that exists in git fails here**: `branchExists` then `outsideTaskText`
    "Branch %s exists outside this task. Pick another name or ask the user to attach it." (`:563`, `:657-659`). This is
    the user's reported block. The agent has no path to an existing branch.
- Phase 3 `finishBranchRequest` (`:749`) then `createApproved` (`:809`) then `createFor`/`createBranch`
  (`internal/ade/agenttools.go:304`, refuses non-`mine`) then `ensureWorktree` (`setup.go:117`).
- `ensureWorktree` for a named row (`setup.go:132-151`): branch checked out anywhere (repo root included) returns that
  path as is (`:133-134`); else `worktreeDirFor` (`internal/ade/worktreedir.go:23`) and `worktreeAdd existingBranch`
  (remote-only: `newBranch` off the tracking ref, `:141-146`).

### Where git refuses a branch held elsewhere

- `git worktree add <path> <branch>` refuses a branch checked out in another worktree. Kira paths that can hit it:
  - `addWorktree` (`setup.go:253-266`): wraps git's message as `invalid("worktree for %s: %s")`. Reached only when the
    inventory shows no holder, so in practice only on a race.
  - `gitsession` `WorktreeAddPreflight` (`internal/gitsession/worktree.go:139`) and `gitpreflight.ClassifyWorktreeAdd`
    (`internal/gitpreflight/worktree.go:83`): blocker `branchCheckedOutElsewhere` with route `detachHere`. That route
    (Git UI `packages/git-ui/src/components/dialogs/WorktreeDialog.vue:170-190`) detaches the *new* worktree, the
    opposite of adopt. Not on the agent path.
- Agent path never reaches git with a held branch: `planNew` refuses first, and `ensureWorktree` silently reuses the
  holder. Second is a hazard once branches are shared (see below).

### Row-to-worktree identity is by branch name

- `worktreeOf` (`setup.go:269`) = inventory `WorktreePath` of the branch. Used by `linkedBranchOf`
  (`internal/ade/archive.go:47`), hence `ArchiveTask` (`:136`, removes `linked` worktrees `:177-181`), `detachRow`
  (`taskbranches.go:76`), `TaskBranchRisk`, `branchSandboxed` (`branchrename.go:206`), `task_info`, launches.
- Board facts: `computeBranch` sets `wb.Worktree = row.WorktreePath` (`internal/ade/board_facts.go:299`), dirty and
  rebase state from it (`:322-331`). `boardCtx.byName` (`board_facts.go:58`, filled `:216`; `base.go:45`) keys rows by
  name for base resolution.
- Rebase: `planRebase` reads `localBranch(...).WorktreePath` (`internal/ade/rebase.go:219`, `:320`); script runs
  `ClaimWorktree` path via `worktreeDirFor` (`internal/ade/automation.go:121`).
- Consequence once a branch moves to task B's worktree: task A's row would report B's worktree, A's launch would run in
  B's worktree (`setup.go:133`), and **archiving A would remove B's worktree** (`archive.go:51` then `:178`). Ownership
  must become explicit.
- Own worktree is derivable: `ade_task_branches.worktree_dir` (`model.AdeTaskBranch.WorktreeDir`,
  `internal/storage/model/adetask.go:119`) gives `<home>/kira-space-wts/<pathSegment(repo)>/<wt_id>`
  (`worktreedir.go:18-24`). Reserved on first worktree, never changes.

## 2. Decisions

D1. MCP surface: extend `request_branches`, no new tool. Add optional `existing: bool` per entry. Reasons: same
approvals item, call merging, wait, timeout and abandon machinery; agents already call it for every worktree; one tool
description to budget. Explicit flag, not inference: a name collision while creating stays a failure instead of
silently adopting someone's branch. `existing` with `base` fails that entry ("base only applies to a new branch").

D2. Item kinds: add `checkout` (existing branch checked out nowhere, or remote-only) and `adopt` (held by another
worktree; detach there first). `worktree` stays for a named row with no worktree and a free branch.

D3. Holder classes (new `classifyHolder`, see §3): `none`, `own` (this row's own worktree path), `task` (another live
row's own worktree), `main` (repo root), `other` (any other registered worktree), `missing` (registered path gone).

D4. Plan rules per entry:
- Named row on this task (`planNamed`): `own` gives `existing`. `none` gives `worktree` item. `task` gives `adopt` item.
  `main`/`other` keep today's `existing` with that path (user attached it there; unchanged behavior). `existing` flag
  ignored here.
- No row, `existing: false`, branch exists: fail with new text "Branch %s exists outside this task. Pick another name,
  or pass existing: true to work on it."
- No row, `existing: true`: branch not found locally or on a remote fails "Branch %s not found. Omit existing to create
  it." `none` (or remote-only) gives `checkout`. `task`/`main`/`other` give `adopt`. `missing` fails "Branch %s is
  registered to a missing worktree at %s. Ask the user to run git worktree prune."
- Refused before any prompt (failed outcome, no item) for `checkout` and `adopt`: reserved name (`reservedBranchText`);
  task kind `review` ("A review task cannot take a work branch."); for `adopt` also donor busy (D6) and a git operation
  in progress in the holder path.
- Protected branch status does not refuse a local checkout. Pushing stays gated by `push_branch`/push preflight.

D5. Row for `checkout`/`adopt` with no row yet: kind `mine` (`parked` on a parked task; never review: the agent works
on it and step runs only take `mine` rows). Origin `agent`. When another live row (any task) has the same repo and
name, the new row sets `adopted = 1` (D7). Reuse the task's waiting draft row in that repo when present (as
`createApproved` does), else `AddBranch`.

D6. Donor busy (block, before prompt and again at apply). Applies when holder is `task` (checks run on that row):
active step run, running rebase, script claim, running prepare script, live sandbox bound to the ref or worktree, live
agent TUI session on the row. Lock-free reads only: never take the donor task mutex while holding the requester's
(deadlock risk). Holder `main`/`other`: only the in-progress git operation check. Warn, not block: holder dirty
(uncommitted changes stay in that worktree, they do not move; count shown) and holder `main` ("your main checkout is
left on a detached commit").

D7. Shared branches: migration `0094_p583_adopted.sql` adds `ade_task_branches.adopted INTEGER NOT NULL DEFAULT 0
CHECK (adopted IN (0, 1))`, drops `ade_task_branches_live_name`, recreates it unique with `AND adopted = 0`. So exactly
one non-adopted live row per name stays enforced by the DB; every existing insert/rename/set-name path keeps its
unique-violation mapping unchanged. Only the adopt apply inserts `adopted = 1`. No promotion on owner archive: name-keyed
lookups prefer the non-adopted row, else the oldest adopted one. User Attach existing, `checkFreshName`, restore keep
refusing a name live on another task (out of scope).

D8. Row worktree ownership (one helper, `rowWorktree`, used everywhere a row's worktree is needed):
- `own` = row's own path (from `WorktreeDir`), `holder` = inventory path, `owners` = live rows' own paths.
- Attached path: `holder` when `holder == own`, or when `holder` is non-empty and no *other* live row owns it (legacy:
  main checkout or unknown worktree, as today). Otherwise "".
- Detached: own path exists on disk and attached path is "" and `own != holder`. Holder then named by class.
- `worktreeOf` returns the attached path. `linkedBranchOf` returns the own path when it exists (attached or detached),
  else the legacy attached path; it never returns a path another live row owns. Archive or remove of the donor deletes
  only its own detached folder.

D9. Launches on a detached row (`ensureWorktree`):
- Holder owned by another live row: refuse `invalid("branch %s is checked out in the worktree of another task (%s).
  An agent can take it back with request_branches existing: true.")`. Surfaces through existing setup-failure and
  launch-gate paths (`recordSetupFailure`, `prepareWorktrees` `runs.go:420`).
- Branch free and own path is a registered worktree: reattach with `git switch --no-guess <branch>` in the own path
  (no redraw, no orphan folder, `Fresh=false`, no prepare rerun). git refusing (local changes would be overwritten)
  is returned as is.
- `rebaseBlockers` (`rebase.go:335`) adds block `attachedElsewhere` for a row whose holder another live row owns;
  `rebase.go:219`/`:320` and `automation.go:121` use `rowWorktree`.
- `rename_branch` refuses while another live row shares the name ("Branch %s is also on task %q; it cannot be renamed
  while shared."), added to `renameRefusal` (`branchrename.go:143`).
- `branchInfo` (`agenttools.go:338`): worktree "" gives Next "No worktree. Call request_branches with existing: true to
  check it out." instead of "Ready. Work in ."

D10. Apply (phase 3, `createApproved` branch for `checkout`/`adopt`), under requester task lock then repo mutex:
1. Recompute holder. Holder now differs from the item's (path changed and not `none`): fail "Branch %s moved to %s
   while waiting. Call request_branches again." Holder now `none`: treat as `checkout`.
2. Re-run D4 refusals and D6 busy. Busy: fail with the busy text.
3. Row: reuse named/draft row or add one (D5). Row insert error fails the entry, git untouched.
4. `adopt`: `entry.DetachWorktree(ctx, holder)` = `git switch --detach` in that path (same commit, never touches files,
   works dirty).
5. `ensureWorktree` (now finds the branch free). Failure after step 4: best-effort `SwitchWorktree(holder, branch)` to
   restore the donor, log, delete the just-added row (new `repos.DeleteFreshBranch(id)`: hard delete of a row with no
   runs; refuses otherwise), fail with git's text.
6. `startSetup` on a fresh worktree, as `createBranch`. Outcome new constant `BranchCheckedOut = "checkedOut"`
   (`internal/agentmcp/space.go:73`), Next as `branchInfo`, prefixed for adopt with "Detached it in %s first. ".
7. `notifyBoard` (already in `finishBranchRequest` `:788`) refreshes both tasks. No other event needed: board facts
   recompute attach state on read.
