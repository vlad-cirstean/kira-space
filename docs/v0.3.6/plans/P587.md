Problem: every `run_script` call blocks up to `waitSeconds` (default 25), and the reply to a still-running
run says "call get_script_run to wait". A process meant to run for hours (dev server, watcher, tail) makes the
agent burn 25-50 s per call waiting for an end that never comes, gets no output while it runs unless it
passes a filter, and is killed at the 30m default timeout.

## Decisions

1. Setting: `mcp.mode` in the run file, enum `short` (default) or `long`. Not a free wait limit: the wait cap
   stays a server bound (50 s per call keeps an MCP request under client timeouts); what differs per script
   is whether the agent should wait at all. File form:

   ```yaml
   mcp:
     enabled: true
     run: allow
     mode: long
     timeout: 8h
   ```

   `short` keeps today's behavior exactly. `mode` is written only when `long` (like `run: prompt`), so
   existing files and shared copies stay byte-identical.

2. Long-mode behavior:
   - `run_script`: `waitSeconds` default 0 for a long script (stays 25 for short, bound 0..50 for both).
     Returns at once after start with `runId`, `opId`, `state: running`, `mode: long`, current output tail
     (usually empty) and `next` = new `scriptNextLong`: "Long-running script, still running: call
     get_script_run to read output; stop it with operations cancel and this opId." An agent may still pass
     `waitSeconds` (e.g. 10 to catch a fast startup failure).
   - `get_script_run` on a run of a long script: `waitSeconds` default 0; with no `from`/`lines`/`contains` it
     returns the last 50 lines at any state (short scripts keep "lines only once ended or filtered").
   - Exit state: once the process ends, `state`, `exitCode`, `reason`, duration and lines read exactly as
     today. Stop: existing `operations` cancel (`run:<id>`), no new tool.
   - Mode is read from the script's current config at each call (no column; `config_json` is the authority,
     same as exposure). A mode edit during a run changes only defaults of later calls.
3. Timeout: bounds stay 1m..24h. Empty `mcp.timeout` means 30m for short, 24h for long
   (`LongMCPTimeout = "24h"` in `scripts`). A long run still ends at its timeout or app quit (headless runs
   fail on restart; restore never offers `mcp` runs, unchanged).
4. Agent sees the mode before running: `list_scripts` adds `mode` per script; run results add `mode`.
5. Validation: `validMCPAccess` normalizes `""` to `short`; anything other than `short`/`long` is
   `invalid("/mcp/mode", "backend.core.runs.mcpMode.body")`. `isZero` treats `""`/`short` as default. Smart
   scripts: no extra rule (`mcp.enabled` is already refused; mode is inert).
6. Config sync (`runs`): no code change. The key travels inside the file under the existing whole-file
   modes; `runsCommands` badge unchanged; omitting `mode: short` means no churn on existing shared files.
   Adding a `Validate["runs"]` gate is out of scope (pre-existing, not caused by this phase).
7. UI: a second RadioGroup in `RunMcpTab.vue` and a "Long running" Badge in `ScriptsMcpSection.vue`. No new
   store, query or composable: the tab already edits the run file through the form pipeline
   (`runFileQueries`/`configForm`); server state stays where it is. Primitives: shadcn-vue `RadioGroup`,
   `Label`, `Field*`, `Badge`; Tailwind utilities only; `<script setup lang="ts">`.
8. Approval card unchanged (the user approves a start; mode does not change what runs).
