## 1. Decisions (no user question; defaults below are final unless overturned at chapter end)

1. Strips. Multi-select is on when the host sets the new `TabStripHost.selectionScope`. Set by the
   main workbench host (`'workbench'`: Studio data and API, Runs, Git and every other module; the
   ade review and opened-files windows inject the same host) and the Kubernetes resource strip
   (`'kubernetes'`). Proof window host: unset (no close, no move), strip unchanged.
2. Selection model. A set of tab ids plus an anchor, per scope, in one Pinia store. Separate from
   the active tab. Pinned tabs never join.
   - Cmd-click (macOS) / Ctrl-click (others) (`isPrimaryModifier`): toggles the tab. The first
     toggle while the set is empty seeds it with the active tab too (browser behaviour: the active
     tab is part of the highlight). Anchor = toggled tab. Active tab unchanged.
   - Shift-click: set = strip-order range from anchor (else active tab) to the clicked tab,
     replacing the set. Anchor unchanged. Active tab unchanged.
   - Plain click: clears the set, anchor = clicked tab, activates it (today's click).
   - Esc with focus inside the strip, not during a drag: clears. Raw `Escape` check like
     `sortableReorder`'s drag cancel; no `SHORTCUTS` id (a dismiss key, nothing to display, N19).
   - Cleared on workspace change (strip shows another tab list). Pruned when tabs leave (close,
     move). Right-click or drag start on a tab outside the set clears it (browser behaviour).
   - macOS Ctrl-click is a right-click there and stays the context menu: `isPrimaryModifier` reads
     `metaKey` on macOS.
3. "Multi" means: the tab acted on is in the set and the set holds 2 or more ids. Otherwise every
   path behaves as today, single tab.
4. Look. New `selected` variant on `tabChipVariants`: not active: `bg-select text-fg`; active and
   selected: active look plus `ring-1 ring-inset ring-select-edge` (grey selection edge token,
   already used as `ring-select-edge`; N18: never blue). `data-selected` on the chip for tests;
   an `sr-only` "Selected" inside the chip's button for screen readers.
5. Multi menu (right-click or Shift+F10 on a selected tab, set ≥ 2), replacing the single menu:
   - "Close {count} tabs" (`close-selected`), shown when the host has `closeTabs`. Shortcut chip
     `tab.close` only when the active tab is in the set (⌘W then closes the set, item 6).
   - Separator, then "Move {count} tabs to new window" (`move-selected-to-new-window`) and submenu
     "Move {count} tabs to window" (`move-selected-to-window`) ▸ "Window N"
     (`move-selected-to-window-<n>`), when `windowMove` exists. `{count}` = movable tabs in the set.
     No movable tab: both omitted. Some not movable: those stay put, the rest move.
   - Single-tab items (Close others, Close to the right, Close all, Duplicate, Copy name, kind
     extras) are not shown in the multi menu. Plain right-click on an unselected tab still opens
     today's single menu.
6. ⌘W (`tab.close`): closes the set when the active tab is in it and the set has ≥ 2 ids; else the
   active tab as today. Registry chord reused, no new id. Native menu "Close Tab" calls the same
   `appCommands.closeTab`, so both paths agree.
7. Close many. Dirty tabs: same as Close others (`confirmCloses`): kinds with their own question
   (API requests) ask one by one in strip order, the rest share one discard confirm. Any decline
   closes nothing. Then one removal pass and one save.
8. Drag. Sortable has no MultiDrag here: `vue-draggable-plus` 0.6.1 bundles Sortable with only
   AutoScroll, Revert and OnSpill mounted and exports no Sortable class; a second `sortablejs` copy
   has its own plugin registry, and MultiDrag owns selection itself (its own click and modifier
   handling), which would fight the store's Shift-range and seeding rules. So Sortable keeps
   dragging the grabbed chip (library mechanism, no hand-rolled drag) and the strip applies the set
   on drop:
   - Grabbed tab in a multi set: other selected chips dim (`SORTABLE_GHOST_CLASS`) while dragging.
   - Drop outside the viewport: moves every movable selected tab, strip order. Grabbed tab not
     movable: no tear-off (P722 rule). Hint pill reads "Release to move {count} tabs to another
     window." when count ≥ 2, P722's text otherwise.
   - Drop inside the strip: the set moves as one block (strip order kept) to the drop slot:
     `moveId` rule, so a drop onto a later tab lands after it, onto an earlier one before it. Drop
     onto a tab of the set: no-op.
   - Grabbed tab outside the set: set cleared, single drag as today.
9. Move many. One bound call carries the list; Go moves all or nothing (any refusal, storage
   fault or ownership clash rolls back the transaction and deletes a window it created).
   - Incognito: per entry, as P722 (no row written).
   - Kinds that cannot move (P722 `IsMovableTab`): filtered out in the frontend; Go refuses the
     whole call if one slips through.
   - Dirty: one `confirmRelease(ids)` for the set (item 7 rules). Decline moves nothing.
   - Live Runs terminals: hold all (parallel), one `Move`, Go re-owns each, the target adopts each.
     A refused hold or failed move releases every hold taken. Snapshot budget per terminal =
     min(4 MiB, 16 MiB / terminal count); Go refuses a call whose snapshots total over 16 MiB.
   - Cap: 100 tabs per call (E_CONTRACT past it); a strip never gets near.
   - Source after success: tabs removed in one pass (`dropTabs`), active falls to the nearest
     remaining neighbour (existing `closeTabInternal` rule, applied per id), one save, set
     cleared. Zero tabs left: `tabsCloseEmptyWindow` as P722.
   - Target: entries appended in source strip order. Exactly one entry per call has `focus`: the
     one whose record was active in the source, else the first. Pull activates the focused entry
     of the last call it processed and switches mode by that entry. Others join inactive.
10. One move at a time per strip: a second move while one is in flight is ignored (a `moving`
    flag in `tabWindowMove`), so a double drop cannot hold a terminal twice.

### 2.2 `apps/kira-space/internal/storage/repos/tabs.go`

`(*TabsRepo).Move(src, dst string, moves []appstorage.TabMove[model.TabRecord]) error`, one
transaction:

1. Empty: nil. Each `Rec.Validate()`; a repeated id: `ErrInvalidTab` "duplicate tab id".
2. `SELECT id, window_key FROM tabs WHERE id IN (...)` (`sb.In`). Any owner not `src`:
   `ErrTabOwnedElsewhere` naming that id.
3. `DELETE FROM tabs WHERE window_key = src AND id IN (...)`.
4. Persisted moves: `order := NextSortOrder(dst)`, insert each in list order with `order+i`,
   `active = false`, same column list as today.
5. Commit. Any error returns before commit (deferred rollback).

Built with `r.Dialect` and `sqlb` (N16). No schema change.

### 2.3 `apps/kira-space/internal/bridge/tabs.go`

```go
// TabsMoveArgs moves tabs out of window WindowKey. Exactly one of Target, NewWindow, Drop.
type TabsMoveArgs struct {
	WindowKey string       `json:"windowKey"`
	Tabs      []TabInbound `json:"tabs"` // source strip order
	Target    string       `json:"target"`
	NewWindow bool         `json:"newWindow"`
	Drop      *TabDrop     `json:"drop"`
}

type TabInbound struct {
	Tab       model.TabRecord `json:"tab"`
	Incognito bool            `json:"incognito"`
	Terminal  *TabTerminal    `json:"terminal,omitempty"`
	// Focus marks the one entry of a move the target activates.
	Focus bool `json:"focus"`
}

const (
	maxMoveTabs          = 100
	maxMoveSnapshotBytes = 16 << 20
)
```

`validateMove`: `windowKey` required; exactly one destination; target ≠ source; `len(Tabs)` in
`1..maxMoveTabs`; per entry: `Tab.Validate()`, `IsMovableTab`, terminal payload only on `terminal`,
`terminal` kind needs `Terminals.Reown`; no repeated id; sum of `len(Terminal.Snapshot)` ≤
`maxMoveSnapshotBytes`; shell present. Messages name the offending id. All `ipcerr.Contract`.

`Move` flow (P722 steps, now over the list):

1. Validate, geometry, source real, `destination`, `createWindow` on a new window (unchanged).
2. `moves[i] = TabMove{Rec: e.Tab, Persist: !e.Incognito && !IsSessionTabKind(e.Tab.Kind)}`;
   `appstorage.MoveWindowTabs(...)`. Error: delete the created window row, return it.
3. Every `terminal` entry: `Terminals.Reown(id, src, dst)` (false is fine, as P722).
4. `focusIndex`: first entry with `Tab.Active`, else 0. Push entries in order, `Focus` set on that
   one only, cleared on the rest (the frontend value is ignored).
5. Open the created window, or nudge plus focus `dst`: once per call.

`Inbound`, `Targets`, `Capabilities`, `CloseEmptyWindow`, `ForgetTabWindow`: unchanged.

Regenerate bindings (`wails3 task common:generate:bindings`, gitignored).
