## Practice applied (judgment calls marked J)

- Definitions are paid every session and every ToolSearch load (Anthropic "Writing effective tools for
  agents", "Advanced tool use"; Claude Code defers MCP schemas, `tests/claude/kube_test.go:77`): fewer, more
  capable tools; one rule stated once (instructions), never per tool.
- Consolidate near-duplicates behind a verb field when they share target, gate and result family (kube reads,
  listings). J: a flat union schema documents per-op args less tightly; per-op errors cover it.
- Front-load what the tool is for, then call order; drop anything only an error needs.
- Details on demand: engine-specific syntax rides the `list` entry of a connection that has that engine
  (only for engines present). No `help` tool (J): it costs a definition, models rarely call it unprompted,
  and errors already carry the fix.
- Response shaping: compact JSON text, no `outputSchema`/`structuredContent` (J: an output schema adds
  definition tokens every session; Claude Code reads text content). Smaller defaults, omit empty fields,
  a `hint` on every truncation saying the next move. Claude Code caps a tool result at 25k tokens
  (`MAX_MCP_OUTPUT_TOKENS`); defaults stay far below.
- Keep offset paging on browse_table (works, already keyset-safe with `pagingNote`); no new cursors.

## 4. Always sent vs on demand

Always: 8 definitions + instructions (~3.4k). On demand: engine syntax and Kibana shape (in `list` only for
present kinds), review/exemption/limit procedure (in the error), saved names (`list` or a result's `saved`).
Tradeoff: an agent that never calls `list` misses `paramSyntax`; the `params` arg names where to look, and a
bad placeholder errors from the engine. Instructions are also always sent: rules live there once instead of
per tool, which is cheaper only because several tools share them.
