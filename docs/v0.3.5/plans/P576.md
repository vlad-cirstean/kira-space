## Findings (from code)

### Where the title bar renders

- Main window: `apps/kira-space/frontend/src/App.vue:220-242` renders
  `packages/workbench/src/components/WorkbenchTitleBar.vue` (its only caller). It wraps the shared
  chrome `packages/workbench/src/components/TitleBar.vue` (`TitleBarBase`).
- `TitleBar.vue:24-28`: root `relative flex items-center shrink-0 wails-drag h-titlebar
  min-h-titlebar pl-titlebar-inset pr-1.5 bg-chrome`, default slot inside. `pl-titlebar-inset` is
  `--kira-titlebar-inset-left: 78px` (`packages/theme/src/tokens.css:72`,
  `tailwind-core.css:107`): clears the traffic-light cluster.
- `WorkbenchTitleBar.vue:41-89` slot content today:
  - `ModeSwitcher` (`:43`): `absolute top-1/2 left-1/2 -translate-x-1/2 -translate-y-1/2`
    (`ModeSwitcher.vue:21-23`), so it takes no flex space. Its comment `ModeSwitcher.vue:18-20`
    says "No app title (HideTitle already drops AppKit's own)": goes stale with this phase.
  - Action row (`:48`): `flex items-center gap-0.5 ml-auto wails-no-drag`.
  - So the first in-flow element after the inset is empty space today. A title placed as the slot's
    first child sits directly at the inset, i.e. right after the traffic lights.
- Secondary windows already show their own title at that same spot, same classes
  (`min-w-0 truncate text-kira-md font-medium`): `OpenedFilesWindow.vue:11-13`,
  `ConfigSyncReviewWindow.vue:91-93`, `ProofHeader.vue:13-15`, `HostViewFrame.vue:29-31`,
  `AdeReviewHeader.vue:51-53`. Main window title follows that pattern.

### Platform handling

- `internal/shell/window.go:65-103` `Options`: only `Mac.TitleBar` is set (`AppearsTransparent`,
  `HideTitle`, `FullSizeContent`); AppKit draws the traffic lights at the left over the web content,
  hides its own title. `Title: cfg.WindowTitle` (`apps/kira-space/main.go:177`, "Kira Space") still
  feeds Mission Control and the Window menu.
- No Windows/Linux window options: native frame there, OS draws title and controls. ARCHITECTURE
  `:30` "targeting macOS 26+ on arm64 only"; `:447` Linux is dev/CI only. The 78 px inset is already
  unconditional.
- Decision: render the title unconditionally, no platform sniff. Reasons: shipping target is macOS
  only; inset already ignores platform; UI specs run in Linux Chromium and must see it. A Linux dev
  build shows the title twice (native frame plus bar): dev only, acceptable, noted in Result.

### Drag region

- `wails-drag` on the bar root sets `--wails-draggable: drag` (`tailwind-core.css:156-161`); drag.ts
  reads the target's computed style. Interactive children opt out with `wails-no-drag`.
- Title is plain text, not interactive: it stays inside the drag region (no `wails-no-drag`), so
  dragging or double-clicking the title moves or zooms the window, like a native title. `body` is
  already `select-none` (`packages/theme/src/base.css:37`): no text selection on drag.

### Width

- Window floor 1024 px (`window.go:24`). At 1024: inset 78 + title ~70 px ends near 150 px; 8 mode
  tabs (`apps/kira-space/frontend/src/workbench/modes.ts:23-32`) centred, start near 380 px; action
  row (3 icons, keep-awake, labelled New window) starts near 800 px. No overlap.
- Title gets `shrink-0 whitespace-nowrap`: two words, never truncated. No `truncate`: an ellipsis
  "Kira Sp…" is worse than the fixed floor guarantees. UI spec pins the no-overlap fact at 1024.

### Copy

- Catalog already holds `common.product.kiraSpace.label` = "Kira Space"
  (`packages/theme/src/i18n/en.json:3694`), used by `AboutPane.vue:23`, `StudioStart.vue:111`,
  `PairScreen.vue:58`. Reuse it; no new key, so `PROPER_NOUNS` and catalog lint need nothing new.
- Shared workbench components take the app name as a prop (`BootFailure.vue:13` `appName`,
  `AppMetricsItem.vue:12` `appName`). Same here: `WorkbenchTitleBar` gets `appTitle: string`; App.vue
  passes `t('common.product.kiraSpace.label')`.

### Library rules

- No primitive needed: a `<span>`. Tailwind utilities only. No shadcn-vue, VueUse, Pinia or TanStack
  surface involved (static text, no state, no DOM wiring).
