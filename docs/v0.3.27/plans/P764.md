# P764: Task colours as a faint background (design for review)

Owner request: "Redesign task colours using a fainted background. This implies the task details, and
review window use the same fainted color and design."

Decided:

- Header-only band; neutral card body; no colour line under the details header or the review/files
  title bars.
- 10 colours: Pure-B. Pure inks plus an OKLCH band at L 0.235 C 0.035 (rest) and L 0.250 C 0.045
  (hover/selected), precomputed hex per slot.
- Neutral selection ring inside the card edge, 1.5px (round 8). Focus ring unchanged.
- Ripple: neutral dashed 1.5px edge in `--kira-select-edge` (round 8).
- Slot change via the `color % 10` migration; temporary shared colours accepted.

Defaults applied unless the owner objects (round 8):

- List rows (shelf, needs, sessions) keep the small colour mark, drawn in the new 10 inks.
- Phone plan card dot takes the new palette through `taskColor`; no extra design work.
- Light theme stays out of scope (P138).

Status: design final pending owner objections. No product code. Mockup:
[`P764-mockup.html`](P764-mockup.html) (open locally; Today vs Pure-B, ring widths, ripple state; dark
and light toggle top right).

## 2. Design

### Principle

Hue lives in the header band only. Card body, text, borders and controls stay neutral tokens. No
colour lines under headers. The band tells tasks apart through hue spacing at equal lightness, not
loudness.

### Inks and band (Pure-B)

- Inks: 10 named hues 36 deg apart in OKLCH, starting at red 20 deg. Lightness 0.68 (amber 0.76, so
  it reads amber, not ochre). Chroma 0.13, gamut-clamped (teal 0.115).
- A search over hue offsets and per-slot nudges returned the equal 36 deg grid as the optimum. At equal
  chroma, OKLab already corrects the green/cyan compression of HSL hue.
- Band: OKLCH at fixed lightness with explicit chroma, gamut-clamped per hue (cyan-teal tops out near
  0.041 at L 0.235). Rest L 0.235 C 0.035; hover/selected L 0.250 C 0.045. Fixed lightness gives every
  slot the same text contrast.
- Slot order is farthest-first on the rest band, so the first live tasks and consecutive slots are
  maximally apart.
- Why not `color-mix`: an 8% sRGB mix over the dark chrome keeps only 0.012-0.023 chroma. Its
  separation then depends on loud inks.

### Selected card: 1.5px neutral ring

Ring: `--kira-fg` outline inside the card edge (`outline-offset` minus the width). An outline does not
reflow and paints above the head band and row grounds. The selected head takes the hover/selected band.

| Width | fg on chrome rows | fg on selected band (min) | vs neighbour rest border `#323237` | Notes |
|---|---|---|---|---|
| 2px (today's width, reference) | 12.56 | 10.68 | 8.63 | heaviest; reads as a frame |
| 1.5px (chosen) | 12.56 | 10.68 | 8.63 | 3 device px on Retina; WebKit snaps to 1px or 2px on a 1x display |
| 1px | 12.56 | 10.68 | 8.63 | same weight as every card's rest border; at a glance it reads as a brighter border, not a selection |

- Contrast does not change with width; visibility does. 1.5px keeps a clear step above the 1px rest
  border of neighbouring cards (the border is only 1.46:1 on chrome). The ring is 8.63x brighter than
  that border. It stays slimmer than today's 2px colour outline, which the owner found heavy.
- Grey `select` is no longer used on card heads, so the 3.70:1 subtle failure goes away.
- Selected branch row in a card: `field` ground (subtle 4.58) plus a 1px inset `--kira-fg` ring. The row
  sits inside the card's 1.5px ring, so 1px keeps the nesting legible.
- Span rows in the day band (`AdeDayBand.vue`) use the same `TASK_EDGE_SELECTED`, so they get the same
  1.5px ring.
- Focus ring unchanged: the card head's own `:focus-visible` outline in `--kira-focus`. The selection
  ring sits on the card element and points inward, so the two never share an element or cover each
  other (`ade-v2-plan.spec.ts:513` keeps passing).

### Ripple: neutral dashed edge

`TASK_EDGE_RIPPLE` (`plan/taskGrid.ts:22`) marks cards whose branches must rebase when the selected task
merges (`rippleOf`, `board/timeline.ts:404`). `AdeTaskCard.vue:131` applies it only when the card is not
selected. Today it is `border-dashed` on the 1px task-colour border.

New look: `outline-[1.5px] outline-dashed -outline-offset-[1.5px] outline-(--kira-select-edge)`.

| Edge | Style | Colour | On chrome | On band rest (min) | On band hover (min) |
|---|---|---|---|---|---|
| Rest | 1px solid border | `--kira-border` `#323237` | 1.46 | 1.32 max | n/a |
| Ripple | 1.5px dashed outline | `--kira-select-edge` `#71717a` | 3.84 | 3.41 | 3.27 |
| Selected | 1.5px solid outline | `--kira-fg` `#d4d4d8` | 12.56 | 11.16 | 10.68 |

- Each step is distinct. Ripple is 2.64x the rest border and passes the 3:1 non-text minimum on every
  ground. The selected ring is 3.27x the ripple, and the solid line separates it from the dashes too.
- Same width as the ring, drawn as an outline over the rest border, so no reflow when the selection
  changes.
- Composition:
  - Hover changes only the head band (rest to hover ground). The ripple dashes stay as they are.
  - Selected wins over ripple, as today, because the selected task is the ripple source.
  - A ripple card keeps its rest band.
  - Keyboard focus on a ripple card's head shows the focus ring on the head; the dashes stay on the card.

### CSS: precomputed hex

- The webview supports `oklch()`: release notes require macOS 14 or later
  (`.github/workflows/release.yml:213`); `apps/kira-space/build/darwin/Info.plist:530` sets 26.0.0.
- Still precompute hex per slot (`TASK_BAND`, `TASK_BAND_HOVER` in `palette.ts`, inline
  `--task-band` / `--task-band-hover`). Three reasons:
  - each slot needs its own gamut-clamped chroma;
  - WebKit and Chromium gamut-map out-of-range `oklch` differently, and UI specs compare computed
    colours;
  - the repo keeps perceptual palettes as hex with the OKLCH recipe in a comment (`tokens.css:161`,
    `:177`).
- Recipe tokens `--kira-task-band-l: 0.235`, `--kira-task-band-c: 0.035`, `--kira-task-band-l-hover:
  0.250`, `--kira-task-band-c-hover: 0.045` document the values and drive the unit guard; no CSS reads
  them.

### Slot model: 20 to 10

Stored `AdeTask.Color` is an int 0-19 (`internal/storage/model/adetask.go:56`). `pickColorSlot`
(`internal/storage/repos/adetask.go:388`) assigns the first slot no live task uses, else the least
used. `patchLeaves` (`:594-599`) rejects values outside `0..maxColorSlots-1`.

1. Migration `0112_p764_color_slots_10.sql`: `UPDATE ade_tasks SET color = color % 10 WHERE color >= 10;`.
2. `maxColorSlots = 10`; `pickColorSlot` and `patchLeaves` keep their logic.
3. `palette.ts`: 10 inks plus 10 rest and 10 hover band hex, indexed directly.

Effect: slots 0-9 keep their number and take the new colour; 10-19 become slot minus 10. Two live tasks
can share a colour (old 3 and old 13) until one is archived; new tasks avoid both. Accepted.

### Shared design: `AdeTaskBand`

- `apps/kira-space/frontend/src/ade/v2/AdeTaskBand.vue` (`<script setup lang="ts">`): prop
  `slot: number`; root `bg-(--task-band)` with inline `--task-band` / `--task-band-hover` from
  `taskBand(slot)`; default slot. No `ColorLine`. `data-testid="ade-task-band"`.
- Users: `AdePanelFrame` head (task, branch, archived panels), `AdeReviewHeader`,
  `AdeTaskFilesWindow`. Card heads and span rows use the same variables through `taskGrid.ts`.
