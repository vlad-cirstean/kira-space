# P766: One colour module, two palettes

Owner request: unify colour components so a later colour change is one edit. One module owns palette,
band, mark and selection ring; every coloured surface consumes it.

Owner decisions (`SPEC.md` P766, audit `colour-audit.md` §5, mockup `colour-rollout-mockup.html`),
binding:

- One identity palette app-wide: the task Pure-B inks and bands (`P764.md` §2) serve tasks,
  connections, environments, repos, scripts and terminals.
- Task statuses do NOT share it (owner reversal of the first answer): they get their own stronger,
  purer, more saturated palette, clearly different from the task colours (§2 "Status palette").
- Legacy names: add `lime` and `sky` as stored names; stored `olive`, `cyan`, `indigo` display as
  `lime`, `sky`, `blue`.
- Engine and connection icons stay as they are (P767 must not neutralise them; P766 keeps engine kind
  colours at today's values).
- Band only, no dots in heads; tabs and list rows take the band; repo chips: band ground, neutral text.
  These are P767's rollout. P766 builds the pieces they need and changes no treatment.

Scope of P766: one source per colour fact, frontend and Go, with two palettes in one module, one
editing point each. Visible change: identity marks repaint in Pure-B inks; task status text, dots and
chips repaint in the new status palette (solid chips). Rails, bars, dots, lines, chips keep their
shape.

## 2. Design

### Two palettes, one editing point each

| Palette | Serves | Editing point | Shape |
|---|---|---|---|
| Identity (task/band) | task slots, repos, connections, environments, scripts, terminals | hue block in `tokens.css` (`--kira-hue-*`) | 10 hues + grey; ink, rest band, hover band |
| Status | task statuses only | status block in `tokens.css` (`--kira-task-status-*`) | 8 hues + grey; one ink each |

`colour.ts` reads both through `var()` and literal class maps; neither holds hex. Specs and the unit
guard read hex from `tokens.css`. Changing a colour = edit its block (hex plus recipe comment), unit
guard green. Categorical (`--kira-cat-*`, methods, lanes) and semantic tones (`--kira-status-*`,
`--kira-ok` etc) are separate families, never edited by a palette change.

### Tokens: status block (new)

Design goals (owner): stronger, purer, more saturated than the task inks, clearly apart from them.
Means: chroma target 0.21 (task inks 0.13), clamped per hue to sRGB at a per-hue lightness near each
hue's chroma peak, hues on pure anchors; drawn as solid chips, not tints, so status never reads like a
task band.

Count: 9 (grey plus 8 hues), down from 16. Sixteen pastel hues at 15-30 deg spacing cannot all be
saturated and still apart; 8 hues at 30-65 deg spacing can (min pairwise OKLab distance 0.111). The
set holds 1-20 statuses (`model.AdeStatusMax = 20`); colours may repeat, as today.

Semantic roles: Kira reads no meaning into a status colour (`wire.ts:738`, ARCHITECTURE "A status is
a label"). The seed set keeps its colours and roles: `todo` grey (`new` default), `in-progress` amber
(`step`), `in-review` blue (`review`), `done` green (`finished`) (`model/adetask.go:462-483`). Red reads
as stopped/blocked for a user status; the board's derived blocked tag stays a tone.
