# P662 Query module UI freeze

Stream C of batch 2 (`plans/batches.md`). Worktree `/home/user/kira-space-b2-c`, branch
`stream/v0.3.16-b2-c`, base `2ffa59ed`. Siblings: A = P660 (keep tab state), B = P661 (agents
memory).

Discovery: `codegraph_explore` (projectPath worktree) over bridge port, Wails stream runtime, frame
decode, console run path, result page store, console result grid (document, key/value, tabular),
SlickGrid wrapper, column width measurement, document row store, MainView keep-alive, run-state
ticker, data grid, documents, key/value, stream, logs, HTTP response body. Worktree files read to
confirm line numbers below. Worktree has no `node_modules` and no Playwright browsers, so no live
repro ran during planning; step 1 of the implementation is the repro.

## Symptom, restated as facts

- Freeze shows after Run, before rows paint. User cannot tell whether data arrived.
- Native menu bar still works. Menu "New request" runs `studioControl.onNewRequest`
  (`frontend/src/App.vue:170-173`): `modeStore.setMode('api')` plus `openApiRequestTab()`. Native
  menu events reach JS through Wails `ExecJS`, so the JS main thread is not blocked forever: it
  yields between tasks or frames.
- Leaving Studio clears the freeze. Returning brings it back without a new query.

## Mount path that explains unfreeze and re-freeze

- `packages/workbench/src/components/MainView.vue:56`: a tab kind without `keepMounted` renders
  through `v-if` on the active tab, keyed by `tab.id`. Only `RepoGraphView`'s kind sets
  `keepMounted` (`frontend/src/state/tabKinds.ts:121`). Console is not kept.
- Mode switch to API makes the API tab active. `ConsoleView`, `ConsoleResultGrid` and
  `ConsoleSlickGrid` unmount: their computeds, watchers, SlickGrid instance, `ResizeObserver` and
  rAF chase die. Whatever main-thread work they drove stops. That is the unfreeze.
- Result pages live in `console/resultPages.ts` (module-scope page store) and console runtime lives
  in `useConsoleViewStore`; neither is tied to the component. Returning remounts the grid onto the
  same cached page, which re-runs every mount-time pass over that page. That is the re-freeze.
- So the cause sits in work the result view does over a large page, proportional to page size or to
  cell size, on mount and on later re-renders. Transport and backend run once per query and cannot
  re-freeze on return.

## Ranked hypotheses

### H1 (root cause, document results): full-page parse in `ConsoleResultGrid`

`frontend/src/studio/views/console/ConsoleResultGrid.vue`:

- `:84-92` `documentRows` builds a `DocumentRowView` for every row in `rowIndices` (`:74-78`, the
  whole page). `documentRowsStore.rowView` (`views/shared/document/rows.ts:140`) calls `parseRow`
  (`:120-137`), which calls `documentRow` (decode id and full body text, `resultPages.ts:61-73`)
  and `parseDocument(doc.body)` (`JSON.parse` plus DocNode tree build, `ejson.ts:327`).
- `:94-108` `documentRowHeights` maps every view again.
- `:186-197` the virtualizer watch prunes exactly those caches to the visible window:
  `setVisibleWindow` drops decode and view caches outside it (`shared/page/store.ts:162-174`);
  `pruneRows` drops `parseCache` outside it (`rows.ts:224-234`).
- Result: every recompute of `documentRows` re-decodes and re-parses every row outside the window.
  It recomputes on every `pageVersion` bump. `pageVersion` is one counter for the whole console
  store (`store.ts:83`), bumped by any console tab's `setPage`, `drop`, `dropForPrefix` or
  `setActiveResult` (`console/state.ts:473`). A multi-statement run bumps once per result page.
- Mount pays the same full pass. With `DefaultConsoleCap` (10,000 rows, 56 MiB,
  `internal/adapters/consolecap.go`) a Mongo result can carry up to 56 MiB of JSON bodies, parsed
  into DocNode trees inside one synchronous Vue flush, before the first result paint.
- Contrast: `views/documents/DocumentView.vue:141` `rowAt` builds views for visible rows only. The
  console copy predates that discipline.
- Extra O(page) readers of `documentRows`: `expandAll` (`:204-212`), `expandedIds` for the scroll
  state report (`:243-246`, runs on every scroll report), copy-all (`:387`).

### H1b (root cause, tabular results): full cell text in the grid DOM

- `frontend/src/studio/views/console/ConsoleSlickGrid.vue:156-169` `cellFormatter` returns the full
  `view.text`. A cell holds up to `MaxCellBytes` = 64 KiB (`internal/page/chunk.go`).
- `kiraSlickGrid.ts` budgets renders by cell count (`MAX_NEW_CELLS_PER_RENDER`), never by text
  size. One render can put hundreds of 64 KiB text nodes in the DOM, twice with `frozenColumn: 0`.
  WebKit (WKWebView, WebKitGTK: what the app embeds) shapes the whole text run of a `nowrap` cell
  even when clipped. Each render, each chase frame (`scheduleChase`, rAF re-arm while a deficit
  stays), each `ResizeObserver` callback (`:752`, `grid.resizeCanvas()`) and each search-layer
  refresh repeats the layout. Frames take seconds; events still slip in between, which matches the
  working menu bar.
- Remount repeats it: the grid rebuilds and renders the same huge cells.
- Same formatter pattern in the data grid: `views/grid/SlickGridHost.vue` `cellFormatter` (`:194`
  onwards) returns full `view.text` for non-insert cells.
- Same pattern outside SlickGrid, inside virtual rows:
  `views/shared/keyvalue/KeyValueRowsTable.vue:227,234` (`TruncatedText` with full field and value:
  Redis, console key/value results), `views/stream/StreamRowsTable.vue:396` (full message body:
  Kafka, SQS).

### H1c (contributor, tabular): `measureText` over 64 KiB cells

- `views/shared/page/columns.ts:134-153` `measuredWidths` decodes and measures the header plus 50
  sampled rows per column via `cellText` at full length, then clamps to `MAX_WIDTH` = 480 px. With
  huge cells that is up to 50 x 64 KiB canvas text measurement per column. Cached per page object
  (`WeakMap`, `:128`), so it costs once per page, not once per remount. Still a multi-hundred-ms
  block in the "before data shows" window.

### H2 (rejected as cause): transport

- `bridge/port.ts:104-110` handles one frame per message: Wails `stream.ts` reads
  `resp.arrayBuffer()`, `decodeFrames` slices a copy, `decodeFrame` builds zero-copy chunk views,
  `decodeExecuteResponse` copies buffers only for multi-page responses, `data.ts` runs
  `assertPageStructure` (O(chunks) offset checks). Linear memcpy plus offset checks over at most
  ~64 MiB: tens of ms, once per query. Cannot re-freeze on return. The repro measures it anyway
  (H2 probe below) so Result can name its share.

### H3 (rejected as cause): stuck dismissable layer

- Reka `DismissableLayer` sets `pointer-events: none` on `body` for modal popovers. Input inside the
  webview would die while the native menu still works, so it fits the first half. It does not fit
  re-freeze: a remount does not reopen a closed popover. The repro checks
  `getComputedStyle(document.body).pointerEvents` during the freeze to close this out.

### H4 (rejected as cause): run-state ticker and spinner

- `state/runState.ts`: one 200 ms `useIntervalFn` while any op runs; each `useRunState` computed
  re-runs. Cost per tick is a handful of computeds. Stops when no op runs, so it cannot hold a
  freeze after data arrived. No change.

### H5 (rejected as cause): backend

- `internal/bridge/studio_stream.go` dispatches each data frame through
  `router.HandleDataFrameAsync` (concurrent, bounded per session); data ops have no client timeout
  and cancel through `control.opsCancel` and `Router.Cancel(opID)`. Console caps bound rows and
  bytes. The flow test below pins those guarantees: it protects the boundary the UI fixture
  mirrors.

## Reproduction

New Playwright support file `apps/kira-space/tests/ui/support/freezeProbe.ts`:

- `installFreezeProbe(page)`: `page.addInitScript` that installs `window.__kiraFreeze` with
  `reset()` and `read()`. A rAF loop records the largest gap between frames and the sum of gaps over
  50 ms (`maxGapMs`, `blockedMs`). If `PerformanceObserver.supportedEntryTypes` includes
  `longtask`, it also records long tasks (Chromium only; WebKit has no `longtask`, so rAF gap is the
  assertion and long tasks are diagnostics). `read()` also returns
  `getComputedStyle(document.body).pointerEvents` (H3 check).
- `expectResponsive(page, label, budgetMs)`: reads the probe and fails with label, `maxGapMs`,
  `blockedMs` and long-task count when `maxGapMs > budgetMs`.
- `measureClickLatency(page, locator)`: time from a click dispatch to the next frame where the
  clicked control changed state. Proves input, not only paint.

Fixture in `apps/kira-space/tests/ui/studio/support/mockStream.ts` (additive): builder helpers
`largeDocumentPage(rows, bodyBytes)` and `largeTabularPage(rows, cols, cellBytes)` on the existing
`createDocumentPageBuilder` and `createTabularPageBuilder`. Sizes mirror the backend cap the flow
test asserts:

- documents: 10,000 rows, 2 KiB nested JSON bodies (about 20 MiB, under the 56 MiB cap);
- tabular: 800 rows x 4 columns x 16 KiB text cells (about 50 MiB), plus a 200-row page of 64 KiB
  truncated cells (truncated flag set, the `MaxCellBytes` edge).

Reproduce first, on the unfixed tree, and record the numbers in the plan's Result: expected
`maxGapMs` in seconds for documents and tabular, sub-budget after the fix. A spec that passes on the
unfixed tree is wrong: raise the fixture size until it fails, never lower the budget.

## Fixes

Rule for every module: on mount and on every re-render, main-thread work is bounded by the visible
window, never by page row count or by cell byte size. Whole-page passes only on explicit user action
(copy all, expand all, export).

### F1. Console document results: window-only row views

`views/console/ConsoleResultGrid.vue`:

- Delete `documentRows` (`:84-92`). Virtualizer `docVirtual` counts `rowIndices.value.length`.
- Add `visibleDocViews = computed(() => { void pageVersion.n; void documentRowsStore.rowsVersion.n;
  return new Map(docVirtual.virtualItems.value.map((vi) => [vi.index,
  documentRowsStore.rowView(props.pageKey, rowIndices.value[vi.index]!)])); })`. Template
  (`:486-521`) reads `visibleDocViews.get(vi.index)` instead of `documentRows[vi.index]`.
- `documentRowHeights` (`:94-108`): read `consoleViewStore.resultDocExpandedIds(tabId, pageKey)`.
  Empty: return `undefined` so `useVirtualRows` uses the uniform `rowHeight` (no per-row work).
  Otherwise map `rowIndices` with `documentId(pageKey, row)` (id only) and call
  `documentRowsStore.rowHeight` with the expanded flag. Collapsed rows stay O(1); only expanded rows
  parse, and `lineCounts` survive `pruneRows`.
- `watch(docVirtual.virtualItems)` (`:184-197`): map positions through `rowIndices`, not
  `documentRows`.
- `expandAll` (`:204-212`): ids from `rowIndices.value.map((r) => documentId(pageKey, r))` (user
  action, O(page) id decode only, no body parse).
- `expandedIds` (`:243-246`): `() => consoleViewStore.resultDocExpandedIds(props.tabId,
  props.pageKey)`.
- Copy-all (`:387`): iterate `rowIndices` with `documentRow(...).body` (user action, unchanged
  cost, no parse).
- Remaining `documentRows` reads (`:118`, `:134`, `:171`) switch to `rowIndices`.

`views/console/resultPages.ts`: add `documentId(key, row): string | null`, decoding only
`page.ids` through `store.cached(key, row, 'id', ...)`. `documentRow` reuses the same `'id'` cache
entry.

`views/console/state.ts`: add `resultDocExpandedIds(tabId, resultKey): string[]` (scan
`expandedDocIds` by `${resultKey}:` prefix; set size equals expanded count). Export it next to
`isResultDocExpanded` (`:713`).

### F2. Display text cap for cells in the DOM

New `views/shared/page/display.ts`: `CELL_DISPLAY_CHARS = 2_000` (wider than any column a user can
drag at the smallest font) and `displayText(text: string): string` returning the prefix plus `…`
when longer. Comment: display only; editor, copy, search and export keep full text.

- `ConsoleSlickGrid.vue:156-169` `cellFormatter`: `displayText(view.text)` in both returns.
  Cell editor path (`:464`) keeps `view.text`.
- `grid/SlickGridHost.vue` `cellFormatter` (non-insert returns after `:227`): same.
- `shared/keyvalue/KeyValueRowsTable.vue:227,234`: `:text="displayText(rowAt(entry.i)?.field ??
  '')"` and the same for `value`.
- `stream/StreamRowsTable.vue:396`: `{{ displayText(rowAt(rowIndices[vi.index])?.body ?? '') }}`.
- `ConsoleResultGrid.vue` key/value row cells: same wrap where they print `field` or `value`.
- Search highlight layers address matches by row and column, not by character offset in the DOM
  text; a match past the cap stays found and selectable, and the cell editor shows it. Implementer
  confirms by reading `refreshSearchLayer` before the edit; if any layer slices the DOM text by
  offset, clamp that offset to the cap.

### F3. Width measurement on a bounded prefix

- `packages/shared/protocol/page.ts`: add `cellPrefixText(chunk, row, decoder, maxBytes)` decoding
  at most `maxBytes` of the cell's byte range (non-fatal decoder; a split code point at the end
  becomes U+FFFD, harmless for measurement).
- `views/shared/page/columns.ts:149`: measure `cellPrefixText(chunk, r, decoder, MEASURE_BYTES)`
  with `MEASURE_BYTES = 512` (480 px clamp needs fewer than 512 chars at the smallest data font).
  Width results stay identical for any cell that fits under the clamp.

## Overlap with P660 and P661

- P660 (keep tab state) owns module keep-alive and view-state restore. P662's cause sits in the
  result views' own render work (H1, H1b), not in keep-alive. Unmount on module switch is only why
  the freeze lifts and comes back; it is not the cause.
- Semantic interplay, no ordering dependency: if P660 makes Studio tabs stay mounted, leaving Studio
  no longer clears the freeze on the unfixed tree. P662's fixes bound the work for any mount
  strategy, so either landing order yields a correct tree. P662's case 3 asserts the round trip
  under both strategies with no change.
- Shared files: possibly the five view files and `console/state.ts` and `mockStream.ts` listed
  above, only if P660 edits their scroll and view-state code. P662's hunks there are a formatter
  body, binding expressions, window-only computeds and one arrow body, all disjoint from scroll and
  restore code.
- Verdict: small overlap. Split stands. At landing, a conflict outside the listed hunks means the
  boundary was wrong: stop, per Streams rule.
- P661 (agents memory): no shared file. Independent.
