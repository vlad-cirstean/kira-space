### Can an interactive session be sandboxed

Yes on macOS, with the same Seatbelt wrapper headless runs use. Findings:

- The command is shell text run as `$SHELL -l -i -c <command>`. Prefixing the agent binary with `/usr/bin/env -u SSH_AUTH_SOCK K=V … /usr/bin/sandbox-exec -f <profile>` works the way headless `Script` does (`claude/headless.go:93` `sandboxWords`). `Compose` appends `--settings` and the prompt at the end, so the prefix survives.
- The profile already allows writes to `/dev/tty`, `/dev/ttys[0-9]+`, `/dev/fd/` (`agentsandbox/profile.go:81`). A PTY needs nothing new.
- Hooks: shim and `hooks.json` live in the app temp dir (`/var/folders/…`), outside the `/Users` read deny; the shim talks to a unix socket, which network-off still allows (`profile.go:113`). The merged-settings case writes into the app settings file, which needs a read allow (below).
- Denial watch needs the root pid. Compose runs before the spawn; the PTY pid exists only after `Registry.Open`. A new start callback carries it (§3).
- Linux: not enforced, as for agents: env overrides and agent flags only.

Honest limits, stated in docs and Result:

- The login shell itself (rc files) runs unconfined before `exec` of the wrapper, same as headless runs.
- A sandboxed TUI cannot fetch or push: the sandbox git tools need a run (`agentmcp.Register` refuses `Sandbox` without `RunID`), and the profile keeps the common git dir read-only. The user pushes from Kira's branch actions.
- `~/.claude` config writes and keychain writes stay denied (profile `protectWrites`, P341): `/config` changes, plugin installs and a sign-in that writes the keychain fail inside a sandboxed session. The inspector hint says so.
- Out of scope, unchanged: Take over of a headless run, the review agent TUI, StartBranch/StartAdHoc sessions. None has a manual step's sandbox setting.

## 2. Decisions

- **Manual default `off`.** `DefaultSandboxFor(KindManual)` returns the canonical off value `{off, [], [], true}`, like scripts. Every existing manual step keeps today's unconfined session. TS `defaultSandbox('manual')` matches.
- **Where `sandbox` is allowed:** agent, script, review, and manual only with `session: true` (same rule as `agent`/`settings`/`outside_repo`). Manual without a session: refused, "sandbox is not allowed on manual steps without a session".
- **`off` means no sandbox at all for a manual session:** no `ResolvePolicy`, no `Enforcer.Prepare`, no wrapper words, no env overrides, no `--add-dir`/`--disallowedTools` additions, no prompt note, no session sandbox row, no watch. Same contract as scripts (no row), stricter than agents (badge row). The inspector shows Off as a selectable access option for manual sessions with its own hint.
- **Policy for a manual session (read or write):**
  - Repo aware: `Worktrees` = the writable branch worktrees from `launchDirs` (`repoLine.Worktree`), `Read` += read-only repo roots (`repoLine.ReadOnlyRoot`), `Branch[worktree] = branch name`, `RunDir` = cwd.
  - Outside repo or task with no repo: `Worktrees = [taskDir]`, `RunDir = taskDir`, no `Branch` (`ProbeGit` returns not-a-repo cleanly, P510 relies on it).
  - `Scratch = <AgentDir>/sandbox/<recordID>`, `Cache` shared, `Ports = [agentmcp port]`, `RunID = recordID` (proxy registration and `Release` key).
  - Runtime `DiscoverRuntime(ctx, agent, AgentBin)`; profile needs the agent's config dirs like headless.
  - Launch files: the profile's `ConfigDir` regex is keyed `<RunID>-…` and never matches `task-<taskID>-<n>.mcp.json` or the `tui-<id>` app files. Add `Input.ReadFiles []string` → `Policy.ReadFiles` rendered as literal `file-read-data` allows (no `--add-dir`). Manual sessions pass the MCP config path, every `App.Files` value and, when hermetic, the isolation dir goes to `Allow` (the provider writes its config home there). `ContextDir` from the context file.
- **Resume / Take over of a manual session** re-prepares from the step's current snapshot sandbox (same record id, new scratch). A stopped record's sandbox row is replaced.
- **Storage:** new table `ade_session_sandbox` keyed by session id (`ade_run_sandbox` has an FK to `ade_runs`; a TUI has no run). Same columns.
- **Visibility:** `adewire.Session.Sandbox *RunSandboxBadge` (nil when off or none). The TUI pane header shows the existing badge; its popover loads detail through new `AdeTaskService.SessionSandbox`. No run log exists for a TUI, so denials surface only in the badge and its popover.
- **Not-enforced notice:** the badge carries `enforced: false` and the reason; the prompt note says not enforced (existing `SandboxNoteVars.Enforced`).
- **Prompt note:** append `llmprompts.HeadlessSandboxNote` to the first message of a new sandboxed session (not on resume, not when off). If its default text says "headless" or names the run log, add a sibling fragment `ade.manual.sandboxNote` instead of rewording the headless one; `checkprompts` must pass.
- **Libraries:** none new. shadcn primitives and theme components already used by `AdeStepSandbox.vue`; TanStack Query for the new detail query (`useSessionSandbox`, mirror of `useRunSandbox`).
