# P760 plan: drop Kibana as a connection kind, keep the chart module

Goal: `kibana` stops being a connection kind everywhere (adapter, Discover UI, saved Discover queries,
form, kind lists, MCP, docs, tests, CI images). Charts and time series stay and keep working for every
other source. Stored kibana connections are removed by migration `0110`.

## Migration `0110_p760_drop_kibana.sql`

Number: latest on disk is `0108_p751_drop_issue_tracker.sql`. P757 (earlier row) adds one migration
(`plans/audit-merged.md` fix 2: `merged_tip`), which takes `0109`. P760 takes `0110`, version 110, name
`p760_drop_kibana`. At implementation start, check `ls internal/storage/migrations/`: if `0109_p757_*`
exists, use `0110`; if P757 landed no migration, use `0109` (no gap). Never reuse a taken number.

Connection storage facts (CodeGraph `configfs.Folder.List`, `connfiles.projection`):

- Connections are files `<home>/config/connections/<stem>.yaml`; `connfiles.Loader` projects them into
  `connections`. The row's `config_json` is the file's last good value (`projection.Snapshot`).
- `Folder.entryFor`: an invalid file keeps serving its last good value from that snapshot. So
  removing `kibana` from `connectionKinds` alone leaves the old kibana row alive with an unknown kind.
- Deleting the row removes the last good value. The file then loads with a Problem at `/kind`
  ("kind must be one of ..."), `Value` nil, no `Record`, so no row comes back. Forget runs only for
  files gone from disk, so it does not fire.

SQL (plain step; foreign keys stay on, so the deletes cascade):

```sql
-- P760: Kibana is no longer a connection kind. Its rows go; foreign keys cascade to tabs, saved
-- queries, mask rules, reviewed columns, filter history and metadata cache, and null op_log.connection_id.
-- The connection file stays on disk and loads as invalid, with no last good value to serve.
DELETE FROM connections WHERE kind = 'kibana';

-- Saved Discover queries existed only on kibana connections. Rebuild without the kind.
DROP INDEX connection_saved_queries_discover_name;
CREATE TABLE connection_saved_queries_new ( ...same columns..., kind TEXT NOT NULL CHECK (kind IN ('filter', 'console')), ... ) STRICT;
INSERT INTO connection_saved_queries_new (...) SELECT ... FROM connection_saved_queries WHERE kind <> 'discover';
DROP TABLE connection_saved_queries;
ALTER TABLE connection_saved_queries_new RENAME TO connection_saved_queries;
CREATE INDEX connection_saved_queries_path ON connection_saved_queries (connection_id, path, kind, pinned DESC, used_at DESC, name);
```

Copy the column list from `testdata/schema.sql:453-463` exactly. `connection_saved_queries` is a child
(nothing references it), so no `-- kira:foreign-keys off` marker; same shape as `0108`.

Secrets: leave `secret_values` alone. The file still on disk references its `${secret:<name>}`, and
names are one module-wide namespace another file may share (`connfiles/secrets.go:17`). Deleting the
file through the UI follows the normal path.

Verify migration runs before `connfiles.Loader.Start` (storage open in appwire precedes `wireAdapters`);
quote the call order in the commit body.
