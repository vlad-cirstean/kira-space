## 1. Facts (today)

- Rules live in the connection file (`masks:` list, `connfiles.Mask{Table, Column, Kind, KeepHint, Correlate}`),
  projected into `connection_mask_rules`. `maskrules.Service.MaskSetFor` folds every rule by
  `strings.ToLower(ColumnName)`; the rule's table is ignored; two rules on one name keep the stricter
  (`mask.Stricter`). Cached per connection, invalidated on file change.
- `run_query` render (`render.go`): `columnRules` maps each result column to a rule by `mk.RuleFor(c.Name)`
  (case-insensitive). Matching is by result column name only. No source table or source column is known.
- Guards on a masked connection (rules non-empty), all statement-text heuristics:
  `refuseRiskyStatementSyntax` (quoting hazards, `U&"`, `AS a(...)`, ClickHouse `APPLY`/`COLUMNS`),
  `riskyResultTypeClasses` (JSON or `other` result column), `maskedColumnRenamedOrHidden` (rule name behind an
  alias/expression or set-op reorder: refuse; rule name in the statement but absent from the result: refuse).
  Document and stream pages are refused; key-value pages mask by field only when `FieldsAreColumns`.
- Driver errors on a masked connection go through `maskedToolError` (value-free); same in `explain_query`,
  `limitFailure`, `checkStatementTables`.
- P536-style held results (`reviewResponse`) re-read `MaskSetFor` after approval and refuse when it changed.
- Known leaks (the en.json `mcp.enforceMasking.body` already admits 1 to 3):
  1. Name-only: a PII column whose name no rule names is returned in clear. The rule's table is ignored.
  2. Alias scan is best effort; a view that renames a masked column (`CREATE VIEW v AS SELECT email AS e`) returns
     `e` unmasked.
  3. A WHERE/ORDER BY on a masked column that is also in the result passes: rows chosen by value reveal it.
  4. A column added after the rules were written has no rule, so it is returned in clear. **This is the gap P534
     closes.**
  5. `run_script` results are not masked (user-authored script, like P532's exclusion).
- No per-connection record of which columns the user looked at exists anywhere.
- Live columns: `tree.Service.SchemaColumns(ctx, id, containerPath, refresh)` returns every relation of one
  container with its columns (`[]model.RelationColumns`), metadata-cached (L1, freshness floor = connect time),
  backed by `Router.SchemaColumns`, op kind `schemaColumns` (throttled by P531's per-connection gate). Containers:
  postgres `database/schema`; mysql, mariadb, clickhouse, sqlite `database`. `Caps.SchemaColumns` is true only for
  those five kinds (relational caps plus clickhouse). Mongo, redis, kafka, s3, sqs, kibana: false.
- Connect: `connections.Service.attemptConnect` emits state `connected` then `metadataInvalidated.Emit(id)`.
  Refresh: `TreeService.Invalidate` (bridge) drops L1 for a node or the connection; no push of its own.
- Notification mechanism: `internal/prompts` router. An owner calls `Sink.Open(Prompt{ID, Kind, Ref, Title})`; the
  router targets one window, `PromptHost.vue` shows that kind's dialog, and one OS notification per kind is posted
  (desknotify, darwin, gated by `advanced.notifyPrompts`); clicking it reveals the popup. Studio kinds today:
  `schedule`, `update`, `quit`, `proof`, `approval`. `proof` (`proof.Service.openPrompt` +
  `ProofReadyPrompt.vue`, Later/Open) is the exact shape this phase needs.
- The connection dialog section is local state in `ConnectionFileDialog.vue` (`section` ref, reset to `general`
  when `dialogStore.file` changes); `useConnectionDialogStore.openFile(name)` takes no section.

## 2. Decisions

### 2.1 Storage: file key, projection table, migration 0062

Follow P532 (`mcp.tables`): the connection file is the source; DB rows are a projection.

```yaml
masks:
  - column: email
    kind: email
mask_review:            # absent = column review off
  columns:              # every column the user confirmed as reviewed
    - shop.public.customers.email
    - shop.public.customers.id
```

- Top-level `mask_review`, beside `masks` (masking config, not MCP permissions). Absent = off, the gate does
  nothing. Present = on; `columns: []` is valid (on, nothing reviewed yet).
- Entry = P532's `tableref` entry plus one column segment, same quoting (`"` around a segment holding `.`, `"` or
  edge space; `""` escape): postgres `db.schema.table.column`; mysql, mariadb, clickhouse `db.table.column`;
  sqlite `table.column`. New `tableref.ColumnRef{Ref; Column string}`, `FormatColumn`, `ParseColumn`,

### 2.2 What counts as covered

A live column `c` (table `T`, column `C`) is **covered** when either:
- **explicitly masked**: some mask rule has `lower(rule.column) == lower(C)` and `rule.table` is `*` or
  `lower(rule.table) == lower(T.name)` (table name part only, as rules store it today), or
- **explicitly marked clear**: `ColumnKey(c)` is in the reviewed set.

Uncovered = **pending**. A rule with table `*` covers the name in every table, so a new `email` column under a
`*.email` rule is masked already and never pending. Confirming review records every listed column, masked or not;
a later rule removal does not un-review it (the user removed the rule on purpose).

Go: `maskreview.Covered(kind, col, rules, reviewed)`; TS mirror `columnCovered` in
`packages/shared/domain/maskReview.ts`. One function each side, used by the diff and the UI.

### 2.3 Diff on connect and refresh

`maskreview.Service.Check(ctx, connID, why)`:
- Skip (state off, no ops) when: kind not applicable, `MaskReviewOn` false, MCP disabled, or not connected.
- Containers: walk `tree.Children` from the root through `database`/`schema` nodes (P532 `ListTables` walk and
  `containerDepth`), cached L1 listing. With a P532 allow list, keep only containers holding a listed table.
- Per container: `tree.SchemaColumns(ctx, id, path, refresh)`; each is one throttled `schemaColumns` op, visible in
  the op log. `refresh` true on TTL and post-DDL checks, false right after connect (L1 is already stale by floor).
- Live set = every `(relation, column)`; relation kinds `table`, `view`, `matview` (views count: a new view column
  `v.x` is a new column).
- Pending = live columns not covered (2.2), restricted to tables the P532 list allows (all when absent).
- Removed columns: ignored. Their reviewed entries stay in the file until the next confirm, which rewrites the list.
- Renamed: seen as removed plus new. The new name is pending. No rename detection: no engine reports column history.
- Triggers: `OnMetadataInvalidated` (fires right after every connect) runs `Check` in a goroutine with a 2 min
  timeout; `TreeService.Invalidate` with a nil path or a container path calls `Check` async after dropping L1; the
  MCP gate (2.4) runs it inline when the last check is older than 30 s; a successful MCP `write` or `ddl` call
  marks the state stale; a file change (rules or reviewed list edited) recomputes pending from the cached live set
  with no ops.
- Caps: 50 containers, 50000 columns. Over either → state `incomplete`. Fail closed (2.4).
- Cache: per connection `{live []LiveColumn, pending []ColumnRef, withheld map[string]bool, incomplete bool,
  checkedAt time, gen uint64}`; generation guard like `MaskSetFor` (a check started before an invalidation does not
  store its result). Dropped on disconnect, file change (recompute), connection removal.

### 2.4 Enforcement in the MCP result path: drop, refuse only where a drop cannot be trusted

**Withheld names** = lowercased column names of pending columns. Result columns carry no source table, so the gate
works by result column name, like masking.

- **Plain projection** (`SELECT *`, `SELECT id, note FROM t`): the result column named like a withheld name is
  **dropped** from `columns` and every row. The result gains
  `withheldColumns: ["note"]` and
  `withheldNote: "1 column was withheld: it is new on this connection and the user has not reviewed its masking yet. The user has been notified. Do not try to read it another way."`
  Names only, never values. Why drop over refuse: the ask says the column "is not returned"; the rest of the result
  is reviewed data, and `SELECT *` keeps working.
- **Refuse** whenever a drop could miss the value, using the existing guards with withheld names treated as rule
  names:
  - alias, expression, set-op reorder of a withheld name (`maskColumnRenamedViaAlias`, `setOpMovesColumn`) →
    `connection "shop" has a column the user has not reviewed for masking: note. It cannot be renamed, transformed or reordered until the user reviews it in the connection's Privacy tab.`
  - withheld name in the statement but absent from the result (WHERE, JOIN, ORDER BY, GROUP BY) → same prefix,
    `It cannot be filtered or sorted on until ...` (row choice by value reveals it).
  - `refuseRiskyStatementSyntax` and `riskyResultTypeClasses` run when rules **or** withheld names exist (a JSON or
    row-typed result can carry the new column inside it).
- **Incomplete** (over cap) or a **check failure** (op error, not connected mid-check) → refuse before execute:
  `connection "shop" has column review on, and Kira could not check its columns (<reason>). Ask the user to narrow the table allow list or turn column review off.`
  `<reason>` is `over 50000 columns`, `over 50 schemas` or the masked error class, never a driver message.
- Gate position: last step of `resolveVerdict`, after P532's tables gate (`checkColumnReview`): refuses
  incomplete or failed checks before any exemption claim, EXPLAIN or approval. `executeAndRender` re-reads the
  state (inline TTL check, usually a cache hit) right before Execute, so a column that appeared during a 10 min
  approval wait is still caught. `reviewResponse` compares the state used at render with the state after approval
  (`maskState.Equal`), like the rules today.
- Driver-error scoping: a connection with withheld names counts as masked (`maskedToolError`), in `run_query`,
  `explain_query`, `limitFailure`, `checkStatementTables`.
- Document, key-value and stream pages: only produced by kinds where review does not apply (2.9); no change.
- Not gated: `run_script`, ops, kube, proof, api tools (same as P532 and masking). `describe_table`,
  `describe_schema`, `list_children` keep listing new column names: names are schema, not values; the agent learns
  they are withheld from `list_connections` and from results.
- **Not exemptable.** A P528 exemption approves one statement past a limit; it does not review masking. The refusal
  never names `exemption` and mints no id. The one-click fix is the Privacy tab.

### 2.5 `select *`, aliases and expressions

- `SELECT *` and `t.*`: expands to real names; withheld ones are dropped. Works.
- `SELECT note AS n`, `lower(note)`, `note || ''`, `CAST(note AS text)`: refused (2.4), named.
- `SELECT count(*) AS n FROM t`: no withheld name in the statement; passes, `n` returned.
- `SELECT id FROM t WHERE note LIKE 'a%'`: refused (filter).
- A view created after the snapshot that renames a new column: its columns are live columns too, so `v.n` is
  pending and `n` is withheld. A view reviewed earlier, defined with `*` over a table that later gained a column:
  postgres and mysql fix a view's column list at creation, so the view does not expose it.
- Residual (ARCHITECTURE): a reviewed column in table A that shares a name with a pending column in table B is
  withheld too (false withhold, safe direction) until B's column is reviewed. Statement scan limits of masking
  apply unchanged (leak 2 for a rename hidden from the token scan).

### 2.6 Interaction with P532 and P528

- P532: only allowed tables matter. Pending, withheld names, the notification count and `list_connections` all
  drop columns of tables the list does not allow. Allowing a table later makes its unreviewed columns pending at the
  next check (fail closed). Containers without a listed table are not fetched.
- P528: not an exemptable limit (2.4). Gate runs before `claimExemption`, so a refused call spends no id.
- P529/P531: checks are ordinary ops under the connection's throttle; the statement timeout does not apply to them
  (metadata ops, not MCP statements).

### 2.7 Notification: prompt kind `masking`

- New `prompts.KindMasking = "masking"`; Ref = connection id; ID `masking:<connID>`. Owner `maskreview.Service`.
  Title `backend.prompt.masking.title`: `New columns on {name} need a masking review`.
- Opened after any check that leaves pending > 0 (on, MCP enabled); closed when pending reaches 0, review is

### 2.9 Engines without columns

Applies to postgres, mysql, mariadb, clickhouse, sqlite (`maskreview.Applies(kind)`, mirror
`MASK_REVIEW_KINDS` in `packages/shared/domain/maskReview.ts`). Skipped, with a note in the Privacy tab: mongodb
(documents, no fixed columns; masking already refuses document results), redis, kafka, s3, sqs (no columns),
kibana (no `SchemaColumns`; data view fields are not listed by the adapter). The file key on those kinds is a
validation error.

### 2.10 Performance

- Steady state: zero extra ops per `run_query` while the last check is under 30 s old (map lookup).
- Stale: one `schemaColumns` op per in-scope container (usually 1), throttled, op-logged.
- Connect: one background check per MCP-enabled, review-on connection; it never blocks connect.
- Withheld lookup is a `map[string]bool` per result column, once per call, like `columnRules`.
- Memory: cached live set capped at 50000 columns per connection.

### 2.11 Existing connections and new connections

No `mask_review` key = off: nothing withheld, no prompt, no check ops. Stated in the tab. New connections also
start off: a new connection has no columns known until first connect, and turning review on is the user's
statement that the current masking is right. (User decision, section 10.)

## 11. Decisions for the user

- **Recheck window 30 s.** A column another client adds can reach the agent until the next check (connect,
  Refresh, MCP write/ddl, or 30 s). Closing it fully needs result-column provenance from each driver (postgres
  table OID/attnum, MySQL org_table/org_name): a separate phase. Shorter TTL costs one throttled op per container
  per window while the agent queries.
- **New connections default off**, like existing ones. Alternative: on for new connections with `columns: []`, so
  every column is withheld until the first review.
- **Prompt popup vs quieter surface.** The prompt router shows a popup in the target window plus an OS notification
  (the existing mechanism). A status-bar item would be quieter but is not an existing notification path.
