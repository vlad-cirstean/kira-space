has a mechanism, like the P527 read lane sets read-only. Value set in the connection MCP tab. On timeout the call

labelled `app` (P527 labels). Every MCP mode (read, write, ddl). Default decided here.

## 1. Facts (today)

- No statement timeout anywhere on the MCP path. Postgres forces the opposite: `buildConfig` sets startup param
  `statement_timeout=0` on every connection (`postgres/client.go:95`) so Stop stays the only stopper.
- P528 seams exist and are called: `executeAndRender` runs every `ExecLimit.Apply` (exempt flag per limit) before
  `Execute`/`ExecuteRead`, and on error asks each non-exempt `ExecLimit.Hit(c, err, elapsed)` before the read-only and
  masked branches (`tools.go:260-283`). `elapsed` there wraps the whole router call, so it includes throttle queue
  wait and lane open.
- `ExecuteRequestWire` already carries Go-only fields with `json:"-"` (`Cap`, `ReadOnly`); `executeOn` copies them into
  `model.ConsoleRequest`. One op = one `Host.RunOp`: register, throttle `admit` (P531 slot then token, up to 30 s),
  `op:start`, `safeRun(fn)`, release slot, `op:end`.
- P518 cancel path: `Host.stopOp` = `op.cancel()` then `adapter.Cancel(opID)` bounded by `disconnectTimeout`; the
  adapter kills server-side (postgres `pg_cancel_backend`, mysql `KILL QUERY`, clickhouse `KILL QUERY` by query id,
  mongo `killOp` by comment, sqlite `sqlite3_interrupt` via the op's driver ctx). Lane ops carry `OpSpec.Adapter`, so
  stop reaches the lane.
- Connections per engine:
  - postgres and mysqlfamily: one pinned connection per database, held under the entry lock for the whole op
    (`ConnSet.Acquire`). The read lane is a second adapter (`LaneConfig`, `ReadOnly` true), MCP-only (`ExecuteRead`
    callers are `dbmcp` only), batch wrapped in `BEGIN READ ONLY` / `START TRANSACTION READ ONLY`. Write and ddl run on
    the user's main adapter, same pinned connection as the console.
  - mysqlfamily: `MultiStatements=false` (one statement per Execute).
  - clickhouse: hand-rolled HTTP client, no session id, every setting a URL query param per request (`buildURL`);
    lane requests carry `readonly=2` (settings stay changeable). Error 159 `TIMEOUT_EXCEEDED` maps to `E_TIMEOUT`.
  - sqlite: `modernc.org/sqlite` v1.61.1, per-op `*sql.Conn`, ctx cancel becomes `sqlite3_interrupt`.
  - mongo (driver v2.9.2), redis (go-redis v9.23.0), kibana (HTTP): no engine timeout wired.
- Drivers: pgx v5.12.0, go-sql-driver/mysql v1.10.1.
- Connection MCP settings: YAML `mcp:` block (`connfiles.MCP`), projected to first-class `connections` columns (0045

## 2. Decisions

### 2.1 Setting

- YAML: `mcp.statement_timeout_sec`, integer seconds. Absent: default. `0`: off. `1`–`3600`: the limit.
- Default **10 s**. Reasons:
  - Below P531's 30 s throttle wait with margin (10 s + 2 s grace): on a throttled connection one timed-out MCP
    statement cannot by itself push a queued user op past its busy timeout.
  - Long enough for normal agent probes (schema reads, filtered selects, small aggregates); anything longer is the
    exception the exemption dialog exists for.
  - Applies to existing connections without the key. That is the ask (MCP calls run under a timeout), not a silent
    change of user behaviour: the console is untouched, and the MCP tab shows the value.
- Seconds, not ms: every engine knob below takes whole seconds or ms; sub-second limits buy nothing for agent calls.
- Bounds 3600: an hour is past any interactive use; beyond it the user wants "off" and can set 0.
- Model: `ConnectionFields.McpStatementTimeoutSec int` (`json:"mcpStatementTimeoutSec"`). File field
  `StatementTimeoutSec *int` (`json:"statement_timeout_sec,omitempty"`): nil means default, so 0 survives omission.

### 2.2 Where the timeout acts (one design for all engines)

Two layers, both armed per op, both after throttle admission:

1. **Engine layer** (label `session`): the adapter applies the engine's own timeout to this one request, scoped so it
   cannot outlive the request (section 4).
2. **App backstop** (always, label `app` where it is the only layer): `Host.RunOp` arms a timer after `op:start`.
   It fires at `limit` when no engine layer applies, at `limit + 2 s` grace when one does. Firing calls `stopOp`
   (P518 path: ctx cancel plus `adapter.Cancel`, server-side kill) and the op returns a typed timeout error.

The backstop also covers an agent statement that tries to lift its own engine limit (`SET statement_timeout = 0`
inside the call): the timer does not read engine state.

Queue wait never counts: the timer starts after `admit`, so a statement queued 25 s behind a user op still gets its
full limit. Lane open (exempt `connect` op) never counts.

### 2.3 Exemption: no timeout

An exempted call (`c.Exempt`) runs with **no** Kira timeout: `Apply` leaves `StatementTimeout` zero. Reasons:

- The user sees measured vs limit and the statement, and approves that one run. A guessed longer ceiling would often
  trip again and cost a second dialog round.
- Stop stays available (Operations panel, P518; agent `cancel_operation`).
- Leak-proof by construction: an exempt call issues no `SET` at all. It runs at the connection's baseline, which the
  restore rules in section 4 guarantee (postgres baseline `0` from `buildConfig`; mysql/mariadb server default).
- A server-wide limit a DBA set (MySQL global `max_execution_time`, a ClickHouse profile) still applies: an exemption
  lifts Kira's limit only. Docs say so.

The dialog adds one line for a timeout hit: approving runs the statement with no time limit; stop it from the
Operations panel.

### 2.4 Scope of calls

- `run_query` (all modes): the `ExecLimit`, exemptable.
- `explain_query` and `run_query`'s auto-explain (`planFor`): same timeout fields, no exemption path (plan-only
  EXPLAIN). A timeout there surfaces as the plain typed error (`E_TIMEOUT: ...`) in `explain_query` and as "no plan"
  in auto-explain (current degrade). P530 rebuilds auto-explain into a PreLimit and keeps this.
- `list_children`, `describe_*`: metadata through `tree.Service`, not statements. Out of scope.

## 3. Per engine

Label column is what `list_connections` and the MCP tab report per mode (read / write / ddl). `session` = the engine
stops it; `app` = backstop plus P518 cancel path; `none` = kind has no console, `run_query` runs nothing.

| Kind | Mechanism | Scope that cannot leak | read / write / ddl | Timeout error (calibrate) |
|---|---|---|---|---|
| postgres | `statement_timeout` (ms) | read: `SET LOCAL` inside the lane's `BEGIN READ ONLY`, reverts at its `COMMIT`/`ROLLBACK`. write/ddl: save, `set_config(..., false)`, restore under the entry lock (4.1) | session / session / session | SQLSTATE `57014` "canceling statement due to statement timeout" |
| mysql (server MySQL) | `max_execution_time` (ms), SELECT only | read lane only: save, `SET SESSION`, restore (4.2) | session / app / app | `3024` ER_QUERY_TIMEOUT "maximum statement execution time exceeded". A query that is only `SLEEP()` returns 1 with no error; calibrate with `WHERE SLEEP(n)` over 2 rows |
| mariadb (server MariaDB) | `max_statement_time` (s) | both lanes: save, `SET SESSION`, restore (4.2) | session / session / app | `1969` ER_STATEMENT_TIMEOUT "max_statement_time exceeded". Not applied to some admin statements, hence ddl `app` |
| clickhouse | `max_execution_time` (s) + `timeout_overflow_mode=throw`, URL params | per HTTP request; no session id exists | session / app / app | `159` TIMEOUT_EXCEEDED "Timeout exceeded: elapsed … maximum …". Mutations are async, DDL not covered, hence write/ddl `app` |
| sqlite | none in the engine | n/a | app / app / app | backstop: `stopOp` cancels the op's driver ctx, modernc `interruptOnDone` calls `sqlite3_interrupt` ("interrupted (9)"); statement rolled back |
| mongodb | none wired (maxTimeMS needs CSOT; not adopted) | n/a | app / app / app | backstop: `Cancel` runs `killOp` on the op's comment (server-side kill) |
| redis | none (single-threaded, no per-command limit) | n/a | app / app / app | backstop: ctx cancel abandons the reply; the server still finishes a running command. Docs state it |
| kibana | none usable (search `timeout` returns partial hits, no failure) | n/a | app / – / – | backstop: HTTP request aborted |
| kafka, s3, sqs | no console | n/a | none | n/a |

Kind vs server flavour: mysqlfamily picks the variable by the server it detects at connect (`mariadbVersionRE` on
`VERSION()`, stored in adapter state), not by kind. Labels go by kind (the UI has no server before connecting). A
`mysql` connection to a MariaDB server is enforced more than labelled. A `mariadb` connection to a MySQL server gets
no engine timeout on writes: the backstop fires at limit + grace. Docs note the 2 s.

Engine timeout vs user Stop share postgres SQLSTATE `57014` and message text is localised (`lc_messages`). The adapter
tells them apart by ctx: Stop cancels the op ctx first (`stopOp`), a statement timeout leaves it live. Rule in every
adapter: engine timeout code **and** `req.StatementTimeout > 0` **and** `ctx.Err() == nil` → typed timeout error.

## 4. Scoped engine settings (no leak)

Shared rule: set and restore run inside the adapter's `Execute`, under the per-connection entry lock, before
`release()`. No other op can run on that connection in between. Restore uses a detached ctx
(`context.WithoutCancel` plus 5 s, as `BeginReadOnlyConsole` cleanup) and waits for in-flight abort-race goroutines
first (`waitInFlight`). If restore fails, the connection is closed, so the pool drops it (postgres `Acquire` F5
`IsClosed` drop; mysqlfamily: implementer confirms the same drop path in `ConnSet.Acquire`, adds it if missing). A
failed restore never leaves a live connection carrying the setting.

Assumption stated in docs: one pgx/mysql connection is one server session (direct or session pooling). Transaction
pooling proxies already break the P527 lane (`SET default_transaction_read_only`) and pid cancel; not supported.

### 4.1 postgres (`postgres/console.go` `execute`)

- New param `timeout time.Duration` (from `req.StatementTimeout`).
- Read-only wrap present (`readOnly`): right after `BEGIN READ ONLY` succeeds, `SET LOCAL statement_timeout = <ms>`
  (integer literal from `timeout.Milliseconds()`, no user text). Reverts at the wrap's `COMMIT`, which already runs on
  every exit including cancel. Nothing to restore.
- No wrap (write, ddl on main): before the batch, `SELECT current_setting('statement_timeout')` → saved; `SELECT
  set_config('statement_timeout', $1, false)` with `<ms>ms`. Deferred restore `SELECT set_config('statement_timeout',
  $1, false)` with saved.
  - Inside a user transaction (`TxStatus` `T`): both calls run in it. Commit keeps saved; rollback reverts both.
  - Statement failed inside a user transaction (`TxStatus` `E`): restore fails, but the earlier `set_config` reverts at
    the rollback the user must issue anyway; do not close (closing would destroy the user's transaction). Every other
    restore failure closes the connection.
- Error mapping in `execute` (not `mapError`, which lacks the request): `57014` with the timeout rule of section 3 →
  `adapters.StatementTimeout(timeout, 0, err)`.

### 4.2 mysqlfamily (`mysqlfamily/console.go` `execute`)

- New params `timeout time.Duration`, `mariadb bool` (adapter state, set in `Connect`).
- MySQL server: only when `readOnly` (lane). MariaDB server: always.
- Save `SELECT @@SESSION.max_execution_time` (MySQL) or `SELECT @@SESSION.max_statement_time` (MariaDB); set `SET
  SESSION max_execution_time = <ms>` or `SET SESSION max_statement_time = <s>` (integer literals); deferred restore to
  the saved value. Session variables are not transactional: restore always applies, inside a user transaction too.
  Order on the lane: set before `START TRANSACTION READ ONLY`, restore after its `COMMIT`.
- Error mapping: `3024` (MySQL) or `1969` (MariaDB) with the section 3 rule → typed timeout.

### 4.3 clickhouse

- `execute` gets `timeout`; when > 0, both `runRowReturning` and `RunCommand` send settings `max_execution_time=<s>`,
  `timeout_overflow_mode=throw` (merged with `cancelOnCloseSettings`; `RunCommand` gains a settings param).
- Error `159` with the section 3 rule → typed timeout (mapping in `execute`, where `timeout` is known; `mapCode` stays).
- Settings refused (least-privilege profile with `readonly=1`: code `164` naming the setting, or `452`
  SETTING_CONSTRAINT_VIOLATION): settings are validated before execution, so nothing ran. Retry that statement once
  without the two settings, set `Handle.noEngineTimeout` (atomic) so later requests skip them, log once at warn. The
  backstop still enforces (fires at limit + grace; docs note it). Calibration case below.

### 4.4 sqlite, mongodb, redis, kibana

No adapter change. Backstop only.

## 6. Interaction with P531 throttle

- Order inside `RunOp`: register, `admit` (≤ 30 s queue), `op:start`, timer armed, run. The limit is run time only.
- A running MCP statement holds the slot up to limit (+ grace). Default 10 (+2) s stays under the 30 s queue bound.
- MCP tab: when `throttle_per_sec > 0` and the timeout is 0 or ≥ 28 s (≥ 30 minus grace), a note warns that a long
  agent statement can make the user's own ops wait past 30 s.
- An exempt run holds the slot until it ends or is stopped; the dialog line says how to stop it.
- Throttle queue timeouts (`E_TIMEOUT` busy/rate keys) are not statement timeouts: they carry no `TimeoutDetail`, so
  `Hit` ignores them and they surface as today.
