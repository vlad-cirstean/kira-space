## 1. Facts (today)

Result review already exists (P382, P520). P536 widens it; it does not build a second mechanism.

- `runQuery` (`tools.go:233`): resolve, claim exemption, plan, pre-limits, `awaitExemption` or `awaitApproval`,
  `executeAndRender`, then `reviewResponse` when `executed && s.reviewResults(summary)`.
- `reviewResults` (`permissions.go:14`): one value per connection, `McpReviewResults` `inherit|review|send`;
  inherit reads `cfg.PreviewResponses()` (app setting `dbMcp.previewResponses`, default off) fresh per call.
- `reviewResponse` (`tools.go:355`): copies the result's TextContent into `ApprovalResponse{Text, IsError, Bytes}`,
  raises a `db.response` item (`ApprovalStageResponse`), blocks up to `ApprovalTimeout` (10 min). Approve re-checks
  exposure and the mask set (`mask.Set.Equal`), then returns the held result untouched. Every other outcome returns
  app-authored text with no row data.
- Every exit after Execute is held (success, empty, adapter error, masked error, masking refusal); limit refusals and
  exits before Execute are not.
- Held text lives in the broker entry (`approvalEntry.req.Response`) and in the handler goroutine (`res`). No cap on
  its size: `run_query` caps rows (`maxRows` up to 2000, `ResultCap.Rows` only, no `Bytes`), cells are shortened by
  the adapter (`truncatedCells`), so wide rows can still reach several MB.
- Queue snapshots (`kira:approvals:changed`) carry only `{connectionId, statement, isError, bytes, alreadyRan}`.
  `DbMcpService.PendingResponse(requestId)` serves the text while queued. `PendingResponse.vue` fetches with
  `gcTime: 0`, parses it into a virtualized table (lock icon on masked columns, row/truncation summary) and shows the
  verbatim bytes on an As sent tab.
- Router prompts (`prompts.Prompt`) and OS notifications carry the title only (`Review this result · {name}`), never
  the statement or data. `ApprovalsToast` shows a count.
- Op log: `Host.RunOp` emits `op:end` with status, duration, row count, command (the statement), error. No result
  payload. The op ends and `releaseSlot()` runs before `executeAndRender` returns, so before any review.
- P529 exec limits derive `ctx` inside `executeAndRender` and `defer done()` there; the `RunOp` backstop timer stops
  at op end. Neither covers the review wait.
- Approval answers carry per-item `options` (`approvals.Answer.Options`): a body emits `options`,
  `useApprovalsStore.setOption` keeps it, `useApprovalActions.answer` sends it for each answered id, Approve all
  included. `brokerOwner.Answer` ignores options today.
- `ApprovalKindDef.individualOnly` (P528): Approve all skips the kind. `db.exemption` sets it; `db.response` does not.
- `harness.MCPCallTimeout` 35 min covers two 10 min waits plus the run.
- `list_operations` lists started ops only; a held result has no op (op ended).

## 2. Decisions

### 2.1 Per-mode setting: tri-state per mode, same vocabulary as P382

Each mode gets `inherit | review | send` (UI: App setting (on/off) / Always / Never), the values P382 already uses for
the whole connection.

- Why not a plain boolean per mode: `inherit` today follows the app switch. A boolean defaulting off would silently
  drop review for every connection on inherit while the app switch is on. `send` today opts a connection out of a
  global on; a boolean cannot express it. Tri-state keeps every existing connection's effective behaviour.
- Existing connections: `review_results: X` reads as X for all three modes; absent reads inherit for all three. No
  change in what gets reviewed. New connections: inherit for every mode (app switch default off, so off).
- The app switch (`dbMcp.previewResponses`) stays one switch for all modes. Its description gains "per mode".

### 2.2 Which mode's setting applies: declared mode and detected class, any one holds

`tightenByClass` refuses a statement that looks more powerful than its declared mode, but accepts a weaker one. With
read on Always and write on Never, an agent could declare `write` for a SELECT and skip review. So:

- Hold when the declared mode's setting resolves to review **or** the detected class's setting does.
- Detected class `unknown`: hold when any mode resolves to review (unknown already resolves to the strictest mode).
- `inherit` resolves to `cfg.PreviewResponses()`, read once per call; a read failure is already fail-closed (review).

```go
// reviewFor reports whether a call's result is held: the declared mode's setting or the detected class's.
func (s *Server) reviewFor(c model.ConnectionSummary, mode string, class adapters.OpClass) bool
```

Replaces `reviewResults`. P535's browse tool calls it with mode `masked` (section 9).

### 2.3 Review on request: checkbox on the pre-run item, then a second result item

The `db.query` and `db.exemption` items of a `run_query` call show a checkbox "Review the result before the AI gets
it". Approve with it ticked sends `options: {"reviewResult": true}`; the call then holds its result exactly as a
toggle would.

- Two items, not one dialog that waits through execution:
  - the result does not exist when the user approves the run; a single item would have to stay open through a run of
    up to the statement timeout (or none, when exempted);
  - one item, one decision is the P520 contract (`Request` blocks on one answer); stretching one item over two
    decisions would need a second answer channel and a stage change in place;
  - Deny on the first item still means nothing runs, and the second item appears in the same dialog list, so it
    reads as one flow.
- A checkbox, not a third button: it rides the existing `options` seam (no change to the shared card's two buttons or
  to Approve all), and the button words stay Approve/Deny (or Lift/Keep for exemptions).
- When the call is already reviewed by setting (`reviewFor` true at prompt time), the checkbox renders checked and
  disabled with a note naming the mode. Payload field `reviewResult` carries that.
- Only on prompt-mode calls and exemptions: an `allow` call raises no pre-run item. The toggle covers those.
- Approve all sends each item's own options, so a ticked box survives Approve all.
- Options on any other item (`explain_query`'s `db.query`, `kube.read`, ...) or an unknown option field is a contract
  error; the item stays pending. `ApprovalRequest.OfferReview` marks the items that offer it.

### 2.4 Result items are approved one by one

`db.response` gets `individualOnly: true`. Inspecting the data is the point; Approve all would send unseen results
in bulk. Deny all still covers them (withholding is the safe direction). Same rule as `db.exemption`. This changes
P382's behaviour for Approve all; nothing is sent that was not, so no migration note beyond ARCHITECTURE.

### 2.5 Held results: memory only, capped, discarded on every exit

- Where: only in the broker entry and the handler goroutine, as today. No DB row, no file, no slog line, no op log
  field, no queue snapshot, no prompt title, no OS notification. Nothing new stores it.
- Caps, enforced in `ApprovalBroker.Request` under `b.mu` (one place, no race with other enqueues):
  - per result: `maxHeldResultBytes = 8 << 20` (8 MiB of TextContent). Over it: outcome `ApprovalTooLarge`, no item;
    the agent gets a refusal naming the size and the cap. Never delivered unseen.
  - all pending results: `maxHeldTotalBytes = 64 << 20`. Over it: outcome `ApprovalHeldFull`, no item; refusal like
    queue full.
  - Counter `heldBytes` grows on enqueue, shrinks in `resolve` and `AbandonAll`.
  - Why these numbers: 8 MiB is far above a 2000-row result of normal width and still parses in the webview without a
    stall; 64 MiB bounds the worst case of the 50-item queue cap far below 50 × 8 MiB.
- Cleanup (each path ends the handler, so both copies become garbage):
  - Deliver: result returned, broker entry removed.
  - Withhold, timeout (10 min): app text returned, entry removed.
  - Agent cancel or client disconnect (session end): ctx done, `ApprovalAbandoned`. Clients on protocol 2026-07-28 or
    newer cancel through `PropagateRequestCancellation`; older ones through the HTTP request context
    (`withRequestContext`).
  - Server toggle off, app quit: `StopFn` calls `AbandonAll`.
  - Frontend: `PendingResponse.vue` keeps `gcTime: 0`; the item leaves on answer, so the query and its text drop.
- Logging audit (implementer): grep `s.log`, `slog` in `dbmcp` and `bridge/dbmcp.go`, and any generic IPC call
  logger on the Wails side (`main.go` dev mode); confirm no path logs `ApprovalResponse.Text` or a
  `PendingResponse` result. A panic in a handler logs tool name and stack only (`withPanicRecovery`).

### 2.6 Cancel while a result waits (P518 path)

The query's op has ended and released its throttle slot, so there is no op for `cancel_operation` or the Operations
panel to stop. A held result is not listed in `list_operations`, same rule as throttled-but-queued work (not a
database operation). Ways out of a held result: Withhold (user), agent request cancel or disconnect (abandon), timeout,
server stop, quit. While the query itself runs, the P518 path cancels it as today; a cancelled query returns its
cancel error, and that error is held like any post-Execute exit only when review applies. Decision for the user if
they want `review:<id>` entries in `list_operations` (section 11).

### 2.7 Interplay

- **P528 exemption**: the `db.exemption` item offers the checkbox too. Exemption plus review is one exemption item
  then one result item. A limit refusal after Execute is app text, never held (unchanged).
- **P529 timeout**: covers the query only. Exec-limit ctx and the backstop timer end before review; the review wait is
  bounded by `ApprovalTimeout` alone. Flow test pins it.
- **P531 throttle**: `releaseSlot()` runs before `op:end`, so the slot is free during review; other ops on the
  connection proceed. Flow test pins it.
- **P532 table gate**: refuses before any run; a refused call holds nothing.
- **P534 masking review**: unreviewed columns are dropped (or the call refused) before render, so the held bytes are
  already filtered and carry `withheldColumns`/`withheldNote`. P534 extends `reviewResponse`'s approve-time re-check
  with its column state (`maskState.Equal`); keep it at rebase.
- **Masking**: applied once in `render.go`; the body shows those bytes and never re-masks.
- **Writes and DDL**: the result is what `run_query` would return: RETURNING/OUTPUT rows as a table, else an empty
  result with the affected-row count where the adapter reports one, or the error text. The statement already ran;
  Withhold hides the result and the count, it does not undo the change (`alreadyRan` warning, unchanged).
- **Timeouts**: worst case per call is still two 10 min waits (exemption or query item, then result item) plus the
  run; `MCPCallTimeout` 35 min unchanged.

### 2.8 Agent-facing texts (English, app-authored, never data)

In `reviewResponse` (replace current strings):

- withheld: `the user withheld the result of this query on "<conn>"; it ran, but you get no rows. Do not rerun it to get the result another way.`
  Write/ddl class appends ` Its changes stay.`
- too large: `the result of this query on "<conn>" is <n> MB, over the 8 MB review limit, so it was withheld unseen. Ask for fewer rows or columns.`
  (`<n>` one decimal.)
- held full: `too many results are waiting for the user's review; retry after the user answers them`.
- timeout, abandon, mask change, exposure loss, queue full: current texts, unchanged.

### 4.1 `permissions.go`

### 4.2 `approval.go`

```go
// ApprovalChoice is what an approver ticked on the item. Zero for every kind but run_query's pre-run items.
type ApprovalChoice struct {
	ReviewResult bool `json:"reviewResult"`
}

const (
	...
	ApprovalTooLarge // the held result is over maxHeldResultBytes; no human saw it
	ApprovalHeldFull // held results already total maxHeldTotalBytes
)

const (
	maxHeldResultBytes = 8 << 20
	maxHeldTotalBytes  = 64 << 20
)
```

- `ApprovalRequest` gains `OfferReview bool` (the item shows the checkbox) and `ReviewOn bool` (already reviewed by
  setting; checkbox checked and disabled).
- `approvalEntry.result` becomes `chan approvalResolution` (`{outcome ApprovalOutcome; choice ApprovalChoice}`),
  buffered 1, one send as today.
- `RequestChoice(ctx, req) (ApprovalOutcome, ApprovalChoice)`: today's `Request` body. Under `b.mu`, before the queue
  check result: when `req.Response != nil`, `Bytes > maxHeldResultBytes` returns `ApprovalTooLarge`;
  `b.heldBytes + Bytes > maxHeldTotalBytes` returns `ApprovalHeldFull`; else `b.heldBytes += Bytes`.
- `Request(ctx, req) ApprovalOutcome` wraps `RequestChoice` (every other caller unchanged).
- `resolve(id, outcome, choice)`: subtracts the entry's `Response.Bytes` from `heldBytes` under `b.mu`; sends the
  resolution. `Approve`/`Deny`/timeout/abandon pass a zero choice. `AbandonAll` zeroes `heldBytes`.
- Cap fields are package constants; tests reach them through an unexported `newApprovalBrokerCaps(now, q, per,
  total)` used by `NewApprovalBroker` with the constants. Flow tests get them through
  `flowharness.WithApprovalHeldCaps(per, total int)` (sets the broker's fields before the server starts).
- `brokerOwner.Answer(ref, a)`: approve with non-empty `a.Options` decodes strictly (`json.Decoder`,
  `DisallowUnknownFields`) into `ApprovalChoice`; a decode error or a non-zero choice on an entry without
  `OfferReview` returns `ipcerr.Contract("reviewResult is not offered for this approval")` and leaves the entry
  pending. Deny ignores options. Implement as `b.answer(ref, outcome, choice) (ApprovalActionResult, error)` so the
  `OfferReview` check runs under `b.mu` with the entry lookup.
