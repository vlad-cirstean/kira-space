# P528 DB MCP limit exemptions: agent asks, user always approves

Ask (SPEC row P528): shared mechanism for P529 (statement timeout) and P530 (EXPLAIN threshold). A limit rejects a
call with a clear reason; the agent may ask for an exemption in its next call. Exemption is a new approval kind on the
P520 surface (Go owner plus registered frontend body). It always shows a dialog, even when the connection allows the
mode without approval. Dialog shows which limit hit, measured value, limit, statement. One statement only, never the
session. Agent passes request plus short reason on `run_query`; never a way to skip the dialog. Denied returns a clear
refusal.

## 2. Decision: field on `run_query`, not a separate tool

`exemption` is an optional object field on `run_query`. Reasons:

- The exempted call is the same call. It must pass the same resolve, mode gate, tighten check, read lane, masking,
  result review and op log. A separate tool duplicates that pipeline or forwards to it; either way two entry points
  to keep identical.
- One tool keeps the tool list and prompt budget small. P535 later demotes `run_query` to fallback; a sibling tool
  would need the same treatment.
- The rejection text tells the agent to repeat the exact call plus one field. Smallest correct retry.
- A tool named for lifting limits invites calling it pre-emptively. A field bound to an id from a refusal does not.

## 3. Exemption model

- A limit refusal mints an **exemption id** (`exm_<12>`, new prefix) and stores a record:
  `{connectionId, mode, path, sql, hits []LimitHit, expiresAt}`. Server-local, in memory.
- The agent retries with `exemption: {id, reason}`. The server claims the record: **single use on first
  presentation**, whatever the outcome (mismatch, deny, approve). No replay, no probing.
- Match is exact: same `connectionId`, `mode`, `path`, byte-equal `sql`. Mismatch refuses; the id is spent.
- Record TTL `ApprovalTimeout` (10 min) from mint. Cap 256 records; on mint purge expired, then evict the oldest by
  `expiresAt`.
- A claimed record exempts exactly the limits in its `hits` for that one call. Nothing else is remembered: no
  session, connection or statement allow list.
- An exempted call always raises one `db.exemption` approval, before execution, regardless of the connection's mode
  verdict (`allow` or `prompt`), result-review setting or any other setting. No code path reads a setting to decide
  whether to raise it.
- Exemption never relaxes a gate. Deny, exposure off, missing path, tighten-by-class all refuse in `resolveVerdict`
  before the record is even claimed.
- One prompt per call: when the verdict is `prompt` or the plan is heavy, the exemption item replaces the
  `db.query` item. It carries mode, detected class, enforcement and plan, so the user sees everything the query item
  would show. Approving it approves the run.
- Result review (`reviewResponse`) still applies after an exempted run. Exemption covers the limit, not delivery.
- A call can hit a second limit after an exemption for the first. The new refusal mints a fresh id whose `hits` are
  the union: claimed record's hits plus the new ones. Next dialog lists all. The user decides on everything the
  statement needs at once.
- Store lives on `Server` (survives prompt-edit rebuilds via `server()`, cleared on server restart). Uses the
  broker's clock (`cfg.Approvals.now`) for testability.

## 4. Go API

### 4.1 `apps/kira-studio/internal/dbmcp/limits.go` (new)

```go
// Limit names. P529 and P530 implement them.
const (
	LimitStatementTimeout = "statement_timeout"
	LimitExpensiveQuery   = "expensive_query"
)

// Units of LimitHit.Measured and LimitHit.Max.
const (
	UnitMillis = "ms"
	UnitRows   = "rows"
)

// LimitHit is one limit a statement went over. Numbers only: never row data, never adapter text.
type LimitHit struct {
	Limit    string
	Measured float64
	Max      float64
	Unit     string
}

// LimitCall is what a limit sees of one run_query call. Exempt is true when the user approved lifting this
// limit for this call.
type LimitCall struct {
	Summary model.ConnectionSummary
	Mode    string
	Class   adapters.OpClass
	SQL     string
	Path    string
	Exempt  bool
}

// Limit is one enforced run_query limit. Implement PreLimit, ExecLimit or both.
type Limit interface{ Name() string }

// PreLimit checks before any approval or execution. The server never calls Check for an exempt limit.
// A nil hit passes. An error fails the call (toolError, masked on a masked connection).
type PreLimit interface {
	Limit
	Check(ctx context.Context, c LimitCall) (*LimitHit, error)
}

// ExecLimit acts at execution. Apply runs just before Execute/ExecuteRead, for exempt calls too (c.Exempt
// set), and may change req and derive ctx; done releases the derived ctx. Hit maps an Execute error to this
// limit; the server calls it only when the limit is not exempt.
type ExecLimit interface {
	Limit
	Apply(ctx context.Context, c LimitCall, req *adapterhost.ExecuteRequestWire) (context.Context, func())
	Hit(c LimitCall, err error, elapsed time.Duration) *LimitHit
}

// LimitError is a run_query call refused by limits. Error() is the agent-facing text.
type LimitError struct {
	ConnectionName string
	Hits           []LimitHit
	ExemptionID    string
}
```

- `LimitError.Error()` (one line per call, no statement echo, no values from data):
  `refused by limit statement_timeout on "notes db": measured 5200 ms, limit 5000 ms. Improve the statement, or ask the user to lift the limit for this statement only: repeat this exact call with exemption {"id":"exm_…","reason":"<one sentence why>"}. The id works once and expires in 10 minutes.`
  Several hits: `refused by limits a, b on "x": a: measured …; b: measured …. …`. Numbers via `strconv.FormatFloat(v,
  'f', -1, 64)`. Window via `approvalWindow()`. Field name `exemption` and both keys appear literally: this is how
  the agent learns the path exists (SPEC "rejection text names the field").
- Returned as `errResult(e.Error())` (IsError text), never a raw Go error.
- A limit refusal is app-authored text with no data, so it is **not** held for result review, even after Execute.

### 4.3 `tools.go` changes

- `runQueryArgs` gains the field below:

  ```go
  Exemption *exemptionArgs `json:"exemption,omitempty"`

  type exemptionArgs struct {
  	ID     string `json:"id"`
  	Reason string `json:"reason"`
  }
  ```
- New pipeline in `runQuery`:
  1. `resolveVerdict` (unchanged).
  2. `claimExemption(args, rv) (ex *exemptionRecord, res, out, err, done)`:
     - nil `args.Exemption` → nil, continue.
     - `!ids.Is(ids.Exemption, id)` → refuse `exemption.id is not an id from a limit refusal`.
     - reason: collapse whitespace runs to one space, trim; empty or over 300 runes → refuse `exemption.reason needs
       one sentence, at most 300 characters`.
     - `claim` miss → refuse `exemption <id> is unknown, used or expired. Run the statement without exemption; a
       limit refusal gives a new id.`
     - field mismatch → refuse `exemption <id> was issued for a different call. Repeat the refused call exactly: same
       connectionId, sql, path and mode.` (id already spent).
  3. `checkLimits(ctx, args, rv, ex)`: every `PreLimit` not in `ex.hits`; collect hits. Any hit → mint record with
     `hits = ex.hits ∪ new`, return `LimitError` refusal. Runs before any prompt: no approval spent on a refused call.
  4. `maybeExplain` (unchanged).
  5. `ex != nil` → `awaitExemption(ctx, args, rv, ex, reason, plan)`; else `awaitApproval` (unchanged).
  6. `executeAndRender(ctx, args, rv, plan, ex)`: for each `ExecLimit`, `Apply` with `Exempt` per limit (in order;
     defer each `done`); time Execute; on error, before the read-only and masked branches, ask each non-exempt
     `ExecLimit.Hit`; first hits → mint union record, return `LimitError` refusal with `executed=false` (skips
     review). Exempt limits' errors flow through the existing error branches.
  7. Review as today.
- `awaitExemption`: `s.cfg.Approvals.Request` with `Subject: approvals.KindDbExemption`, `Reason:
  ApprovalReasonExemption`, `Mode`, `Class`, `Enforcement: enforcementFor(...)`, `Statement`, `Target`, `Plan:
  approvalPlanFrom(plan, rv.threshold)`, `Exemption: &ApprovalExemption{Reason, Hits}`, `Origin`. Always called when
  `ex != nil`; never consults `rv.verdict`.
  - Approved → shared `recheckAfterApproval(args, rv)` (extract from `awaitApproval`: `resolveEnabled` plus
    `modeVerdict != deny`). Both functions call it.
  - Denied → `the user kept limit <names> for this statement on "<conn>"; it did not run. Improve the statement or
    stop.`
  - Timed out, abandoned, queue full → `approvalOutcomeError(outcome, fmt.Sprintf("exemption request for query
    against %q", name))` (same window and texts as P520).
- Update `runQuery`'s doc comment for the new order.

## 10. Hand-off for P529/P530

Both implement interfaces in `apps/kira-studio/internal/dbmcp/limits.go` and return `*dbmcp.LimitHit`. The server
owns refusal text, ids, exemption claim, the dialog and union. A limit never builds a refusal or an approval itself.

- **P530 (EXPLAIN threshold)**: a `PreLimit` named `LimitExpensiveQuery`, unit `UnitRows`, `Measured` = plan
  estimate, `Max` = `ExplainThreshold()`. It needs `s.planFor`, so it lives in package `dbmcp` as a built-in
  appended to `s.limits` in `New` ahead of `cfg.Limits`. `Check` returns `nil, nil` to skip (engine without an
  estimate, statement not explainable). P530 decides how `maybeExplain`'s heavy prompt and `McpAutoExplain` fold into
  it and must keep one EXPLAIN per call.
- **P529 (statement timeout)**: an `ExecLimit` named `LimitStatementTimeout`, unit `UnitMillis`. `Apply` reads the
  connection's timeout from `c.Summary`, sets it on `req` (new `ExecuteRequestWire` field, P529's design) or derives
  a ctx deadline for `app` enforcement; when `c.Exempt`, it runs with no timeout or the longer one P529 picks.
  `Hit` recognises the engine's timeout error (and the ctx deadline) and returns elapsed vs limit. Built in `dbmcp`
  or passed via `bridge.DbMcpService.Limits`; either way it ends up in `s.limits`.
- Labels: `LIMIT_LABEL` in `DbExemptionBody.vue` and the `limitName` i18n keys already cover both names.
- Tests: add the real limit's own flow cases beside P528's; reuse `WithDbMcpLimits` only for fakes.
- `ConnectionMcpTab.vue` and Settings explanations are theirs.
