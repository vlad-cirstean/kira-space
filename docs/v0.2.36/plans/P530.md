# P530 Expensive-query (EXPLAIN) threshold enforced for MCP, with explanation

Ask (SPEC row P530): `advanced.expensiveQueryRows` (used by `queryplan.FromPages` and the user-side auto-explain)
becomes enforceable for MCP like the timeout. Before running, the app runs EXPLAIN; an estimate past the threshold
rejects the query. The agent improves it or asks for a P528 exemption, which always raises a dialog. Plain
explanation next to the setting (i18n, Settings and connection MCP tab): estimated rows from the plan, not rows
returned; user side warns, MCP side rejects. Engines without a usable row estimate skip the check and say so.
Standing requirement: the connection dialog says tersely who enforces it, what happens on violation, known limits.

## 1. Facts (today)

- Threshold: `advanced.expensiveQueryRows`, app-wide (not per connection). Default 100,000, range 1,000 to
  1,000,000,000 (`model/settings.go:177`, `settingsDomain.ts:35`); no 0, no "off". Estimated rows read, never a cost
  unit (ARCHITECTURE:1144). MCP reads it fresh per call via `Config.ExplainThreshold` (`bridge/dbmcp.go:239`; a
  settings read failure falls back to the default).
- `queryplan.FromPages(kind, pages, threshold)`: `EstimatedRowsRead` = the widest single scan-node estimate (D14:
  `maxEstimatedRows` over scan nodes; root/`Limit` rows deliberately ignored), `OverThreshold` = estimate `>=`
  threshold (`isOverThreshold`). Per engine: postgres `Plan Rows` of scan node types (`pgScanNodeTypes`: Seq, Index,
  Index Only, Bitmap Heap, CTE, Function, Foreign Scan); mysql `rows_examined_per_scan`; mariadb `rows`; clickhouse
  `EXPLAIN ESTIMATE` rows; **sqlite none** (`EXPLAIN QUERY PLAN` has no estimate, `parseSqlitePlan` leaves it nil). A
  plan with no scan node (`SELECT 1`) has a nil estimate. A truncated page returns `ErrTruncated`.
- `queryplan.Supported`: postgres, mysql, mariadb, sqlite, clickhouse. `Explainable`: leading SELECT/WITH after
  comments, no embedded `;`. `StatementsFor` never composes ANALYZE.
- User side: console `auto_explain` (top-level connection key, default false) runs `autoExplainCheck` before a run and
  shows a warning strip on an over-threshold plan; an EXPLAIN failure never blocks the run (`console/state.ts:202`).
  The console Explain button parses with the same threshold.
- MCP side today: per-connection `mcp.auto_explain` (column `mcp_auto_explain`, migration 0022, default **true**).
  `runQuery` (`tools.go:207`) order: `resolveVerdict` → `claimExemption` → `checkLimits` (PreLimits; none built in
  yet) → `maybeExplain` (only `McpAutoExplain && mode == read`; any error degrades to "no plan") → `awaitExemption`
  or `awaitApproval` (`heavy` = `plan.OverThreshold` raises a `db.query` prompt with reason `heavy`, even on `allow`)
  → `executeAndRender` (result carries `plan` summary). So an over-threshold read today **prompts**, never refuses;
  a SELECT declared `write`/`ddl` is never planned.
- `planFor` (`explain.go:161`): returns `(nil, nil)` for an unsupported kind or non-explainable SQL; classify-asserts
  each composed statement as read; runs on the read lane (`ExecuteRead`) under `applyStatementTimeout(modeRead)`
  (P529); reads `ExplainThreshold()` a second time for `FromPages` (can differ from `rv.threshold`).
- `explain_query` (`tools.go:630`): refuses unsupported kinds and non-SELECT/WITH before connecting, refuses when read
  mode is deny, classify-asserts, own `prompt` approval on read `prompt`, read lane, P529 timeout, parses, masks the
  plan on a masked connection. Plan only; never the statement.
- P528 seam: `PreLimit.Check(ctx, LimitCall)` runs in `checkLimits` before any approval, skipped for a limit the
  claimed exemption covers. A hit refuses via `refuseByLimits` (mints `exm_`, `LimitError` text names `exemption`).
  A Check error goes to `limitFailure` (`toolError`, masked on a masked connection). `builtinLimits()` returns
  `statementTimeoutLimit{}`; a `Config.Limits` entry with a built-in's name replaces it (`fakeRowsLimit` in
  `exemption_test.go` is named `expensive_query`, so it keeps replacing the new built-in).
- Every EXPLAIN is its own op: `Router.ExecuteRead` → `Host.RunOp` → P531 `admit` (serial slot plus token) → P529
  backstop timer. It shows in the Operations panel and op log.
- `DbExemptionBody.vue` already labels `expensive_query` (`studio.dbMcp.approval.exemption.expensiveQuery.label`,
  "Estimated rows read") and renders `ApprovalPlanEvidence`.
- Nothing tests the `heavy` prompt path (grep: no Go test, flow or UI spec references it).

## 2. Decisions

### 2.1 Setting, threshold, default (no migration)

- **Threshold**: the existing app-wide `advanced.expensiveQueryRows`, unchanged: absent = 100,000, range 1,000 to
  1,000,000,000. No 0 and no per-connection threshold: the ask makes the existing setting enforceable, it does not add
  a second number. One number keeps the console warning and the MCP refusal in agreement.
- **Per-connection on/off**: the existing `mcp.auto_explain` (absent = true). Reasons: it already means "plan agent
  queries before running" and already gates the heavy dialog; MCP-only (the console keeps its own `auto_explain`);
  first-class column exists (0022), so **no migration, no file/schema/repo change**. YAML key and column keep their
  names; only UI wording changes. Off = no EXPLAIN and no check (as today).
- **Existing connections, no silent change**: switch on (default) today means an over-threshold read waits for a
  dialog; after P530 it is refused and the agent's exemption retry waits for a dialog. Either way a heavy read never
  runs without the user approving it in a dialog. Switch off stays unchecked. Nothing loosens. The only widening is
  2.3 (a read-class statement declared `write`/`ddl` is now checked), which closes an agent-chosen bypass; the
  enforcement model forbids leaving it. MCP tab, docs and `list_connections` state the behaviour.
- Comparison: estimate `>=` threshold (the parser's `OverThreshold`), same as the console warning. Text says "at or
  above".

### 2.2 Where it runs (one EXPLAIN per call)

New step `s.planForCall` replaces `maybeExplain`, placed **before** `checkLimits`:

```
resolveVerdict → claimExemption → planForCall → checkLimits (incl. expensive_query) → awaitExemption|awaitApproval → executeAndRender
```

- `planForCall` runs `planFor` once when the switch is on and the call is in scope (2.3); stores `rv.plan` and
  `rv.planErr`. The same plan feeds the limit, the approval evidence (prompt or exemption dialog) and the result's
  `plan` summary. Never a second EXPLAIN.
- `planFor` gains a `threshold int` parameter: `runQuery` passes `rv.threshold`, `explainQuery` its own single read.
  The limit and the plan's `OverThreshold` then use one number per call.
- The built-in `expensiveQueryLimit` (PreLimit, `dbmcp/expensive.go`) only compares; it never runs EXPLAIN itself.
  An exempt call skips `Check` (P528 rule) but still gets its plan as dialog evidence (today's behaviour).
- `LimitCall` gains `Plan *queryplan.Plan`, `PlanErr error`, `Threshold int`, doc: "filled once per call by the
  server; limits never run statements". `limitCall` fills them from `rv`.

### 2.3 Scope: tools and modes

- **`run_query` only.** `explain_query` executes nothing and stays unchecked. `describe_*`, `list_*`: metadata, no
  statement.
- **Every declared mode, when the classifier says `read`** (`rv.class == adapters.ClassRead`) and the statement is
  `Explainable`. Reasons:
  - Mode is the agent's declaration; class is the app's. A `SELECT` declared `write` on a `write: allow` connection
    would otherwise skip the check. Checking by class closes that.
  - Write/DDL/unknown classes are not checked: their EXPLAIN differs per engine, ClickHouse EXPLAIN can execute some
    non-SELECT forms (ARCHITECTURE "EXPLAIN (M3)"), mutations cost writes, not "rows read", and a data-modifying CTE
    (`WITH d AS (DELETE …) SELECT …`, class write) would fail the composed-EXPLAIN read assertion and block a legit
    write. Write and ddl default to `prompt`/`deny`; the timeout still applies. Docs and MCP tab say "SELECT and WITH
    only".
- EXPLAIN always on the read lane (`ExecuteRead`), whatever the declared mode: the engine refuses writes there. A
  write-mode SELECT therefore opens the read lane if closed; noted in ARCHITECTURE.

### 2.4 Engines

| Kind | EXPLAIN this app runs | Row estimate | Check |
|---|---|---|---|
| postgres | `EXPLAIN (FORMAT JSON, COSTS TRUE, …)`, no ANALYZE | widest scan node `Plan Rows` | `plan` |
| mysql | `EXPLAIN FORMAT=JSON` | `rows_examined_per_scan` | `plan` |
| mariadb | `EXPLAIN FORMAT=JSON` | `rows` | `plan` |
| clickhouse | `EXPLAIN PLAN json=1 …` + `EXPLAIN ESTIMATE` | estimate rows (MergeTree parts only) | `plan` |
| sqlite | `EXPLAIN QUERY PLAN` | none | `none` (plan still attached when switch on, as today) |
| mongodb, redis, kibana, kafka, s3, sqs, others | none | none | `none` |

- New `queryplan.HasRowEstimate(kind string) bool` (postgres, mysql, mariadb, clickhouse), beside `Supported`. TS
  mirror `ROW_ESTIMATE_KINDS` in `packages/shared/domain/connection.ts` beside `EXPLAIN_SUPPORTED_KINDS` (comment
  cross-references, like that set).
- Check state per connection (Go `expensiveCheckOf(c)`, TS `expensiveQueryCheckOf(kind, autoExplain)` in
  `packages/shared/domain/dbmcp.ts`): `none` when `!HasRowEstimate(kind)`, else `off` when `!McpAutoExplain`, else
  `plan`. Pinned by the flow contract (section 7).
- A supported engine can still yield a nil estimate: no scan node (`SELECT 1`, `SELECT now()`), ClickHouse table
  functions or non-MergeTree tables (`numbers()`, `system.*`). **Nil estimate passes**: nothing measurable is read
  from a table. Known limit; the statement timeout is the backstop.

### 2.5 EXPLAIN cost and safety

- EXPLAIN must not execute the statement. `StatementsFor` never composes ANALYZE (unchanged; ARCHITECTURE:1145
  measured plain EXPLAIN ~1000x cheaper). Residual execution during planning, all on the read lane (engine read-only)
  and under the P529 timeout:
  - postgres: the planner may evaluate immutable functions with constant arguments (constant folding). Writes are
    refused by `BEGIN READ ONLY`.
  - mysql/mariadb: the optimizer reads const tables (at most one row via a primary or unique key) and may evaluate
    constant subqueries while planning.
  - clickhouse: scalar subqueries are evaluated during analysis, so `EXPLAIN` runs them. A heavy scalar subquery
    costs its run time up to the timeout.
  - sqlite: `EXPLAIN QUERY PLAN` never executes.
- `EXPLAIN ANALYZE …` sent by the agent as its own `run_query` statement is not `Explainable`, so it is not checked
  and its inner statement runs (read lane, timeout). Same for other forms that read rows without a leading
  SELECT/WITH (postgres `TABLE t`, `VALUES`, a parenthesised SELECT). Known limit, stated in the MCP tab and docs.
- Throttle (P531): the EXPLAIN is one more op through `admit`; a checked call costs two slots/tokens. At 1 op/s each
  checked call waits about 1 s more. Already true today for auto-explained reads; now also for read-class statements
  in write/ddl mode.
- Timeout (P529): `planFor` keeps `applyStatementTimeout(&req, summary, modeRead)`. An exemption from
  `statement_timeout` lifts it for the statement only, never for the EXPLAIN.
- Cancellation: a ctx error during the EXPLAIN (client gone, `cancel_operation` on the EXPLAIN op) returns as the plain
  error; the statement never runs.

### 2.6 Fail behaviour when EXPLAIN fails: fail closed

The check passes only on a readable estimate under the threshold (or nil, 2.4). The enforcement model forbids a
limit that an agent passes by making EXPLAIN fail. `expensiveQueryLimit.Check` with `c.PlanErr != nil` returns an
error, and `checkLimits` fails the call before any approval or execution:

| EXPLAIN outcome | Result to the agent | Exemption id |
|---|---|---|
| engine error (syntax, missing table, permission) | `toolError` of the wrapped adapter error: `E_…: expensive_query check: EXPLAIN failed: <engine text>`; masked text on a masked connection (`limitFailure`) | no: the statement as written fails the same way |
| P529 timeout during EXPLAIN | same path, `E_TIMEOUT: …`; planning past the timeout is itself the red flag | no |
| composed EXPLAIN not classified read (`assertComposedStatementsAreReads`) | `planCheckError`, app text: `expensive_query check could not plan this statement on "<name>"; it did not run.` | no |
| `ErrTruncated` or parse failure | `planCheckError`: `expensive_query check could not read the query plan's row estimate on "<name>" (<plan too large to parse \| unreadable plan>); it did not run. Simplify the statement. The user can turn the check off in the connection's MCP tab.` | no |

- No exemption without a measured value: the dialog shows measured vs limit; an unknown estimate gives the user
  nothing to judge, and the P528 payload has no "unknown" (adding one would change its contract for a rare case).
  Truncation needs a plan above `page.MaxCellBytes`; a parse failure is an app bug to fix, and the per-connection
  switch is the user's escape.
- `planCheckError` (unexported, `expensive.go`): app-authored, no data. `limitFailure` renders it with `errResult`
  before the `toolError`/masked branch (safe on masked connections; no adapter text inside).
- An **exempt** call (expensive_query covered) whose EXPLAIN fails degrades to no plan evidence with one `slog.Warn`
  (the user is approving anyway). A call exempt only from `statement_timeout` keeps fail closed.

### 2.7 Heavy prompt removed

- `awaitApproval` loses the `heavy` parameter and `ApprovalReasonHeavy`: an over-threshold statement never reaches
  it. A `prompt` verdict still asks, with plan evidence when a plan exists (`approvalPlanFrom`).
- `DbQueryBody.vue`: drop the `reason === 'heavy'` lede branch. `en.json`: delete `studio.dbMcp.approval.heavy.body`
  (C10 unused key otherwise). Zod `reason` is `z.string()`: no schema change.
- Focus-on-approval wording "heavy-read prompts" (ARCHITECTURE) updated.

### 2.8 Refusal text

`LimitError.Error()` unchanged in shape. One added sentence when a hit is `expensive_query`, before `Improve the
statement`: ` expensive_query is the query plan's estimated rows read, not rows returned; explain_query shows which
scan. Filter on an indexed column or narrow the join.` Example:

```
refused by limit expensive_query on "pg": measured 5000 rows, limit 1000 rows. expensive_query is the query plan's estimated rows read, not rows returned; explain_query shows which scan. Filter on an indexed column or narrow the join. Improve the statement, or ask the user to lift the limit for this statement only: repeat this exact call with exemption {"id":"exm_…","reason":"<one sentence why>"}. The id works once and expires in 10 minutes.
```

`Measured` = `*plan.EstimatedRowsRead` (whole number by construction), `Max` = `c.Threshold`, `Unit` = `rows`.

### 2.9 Known limits (stated in MCP tab, docs)

- Estimates come from table statistics: stale statistics under- or over-estimate.
- Scan estimates ignore `LIMIT` (D14, parity with the console): `SELECT * FROM big LIMIT 10` is refused when `big`
  is estimated at or above the threshold. Agents sample with `describe_table` (row estimate) or a filtered query;
  the user can raise the threshold or turn the check off. Changing D14 would change the console warning too; out of
  scope.
- Only read-class SELECT/WITH statements are checked (2.3, 2.5); nil estimates pass (2.4).
- The EXPLAIN counts against the throttle (2.5).
