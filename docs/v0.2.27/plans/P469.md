# P469 Stage move: advance button with close-session prompt

Spec row: `docs/v0.2.27/SPEC.md` P469. App: Kira Space. User ask: after a stage change the Finish
button shows while the open session belongs to the previous stage. Replace it with a clear move-on
button. If a previous-stage session is open, ask whether to close it, then advance.

## 1. Current mechanism and the bug

- The step action is `taskCell` → `stepAction` → `manualAction` (`frontend/src/ade/v2/board/actions.ts:80`).
  On a manual step with `session: true` it offers `Start <step>` (kind `session`) unless a session is
  "talking"; otherwise it returns `doneAction` (`Done ›`, kind `done`, or `Finish`, kind `finish` on the
  last non-skipped step).
- `talking` (line 84) is any running TUI session of the task, except review-purpose ones off the
  review step. It ignores `Session.stepId`. So after a move from stage A to session stage B, A's
  still-open session counts as B's: B shows `Done ›`, or `Finish` when B is the last stage, before B's
  own session ever started. That is the reported bug.
- `useTaskAction.run` (`run/useTaskAction.ts:46`): kinds `done` and `finish` fall to the `else` branch,
  `stage.open({ taskId })`. Every stage move goes through the stage dialog
  (`state/adeStageDialog.ts`, `stage/AdeStageDialog.vue`): step mover, step block menu, task menu,
  Done/Finish action, Notes tab "Move on", routed `handover` prompt.
- The store's `move` sends `StepDone {taskId, notes?}` for a manual step's natural next stage, else
  `SetTaskStep {taskId, stepId, fromStepId, notes?}`.
- Backend `TaskBoard.StepDone` (`internal/ade/runs.go:1457`) and `TaskBoard.SetTaskStep` (line 1505)
  move the entry step and the handover in one `SetEntryStep` transaction. Neither touches sessions.
  `SetTaskStep` refuses while a run is live (`HasRunning`), so only interactive sessions can be open
  at a move. `StepDone` does not call `advanceLocked`; no change there.
- Session ownership: `ade_sessions.step_id` (`Session.stepId` on the wire). `LaunchStep` sets it to
  the step id (`launches.go:628`), also for a repo-less task folder session (P467). Branch sessions
  (`StartBranch`, `StartAdHoc`, `launches.go:744`) have `StepID ""`. The review agent
  (`review_agent.go:69`) has `StepID ""` and `Purpose "review"`. Take over keeps the record's
  `StepID` (`launches.go:181`).
- `CloseSession` (`launches.go:224`) closes one TUI under `taskMu` via `closeTUILocked`, which blocks
  until the process exits and keeps history (Take over resumes it).

## 2. Design

### Decisions

- Move-on button: kind `advance`, label "Next stage ›". Replaces kind `done` ("Done ›").
- Last stage: kind `finish` stays, label "Finish". Moving past the last stage finishes the workflow;
  "Next stage" would name a stage that does not exist. It gets the same close prompt. The bug goes
  away because `Finish` (and `Next stage ›`) now show only once the current stage's own session runs.
- `talking` counts only sessions of the current stage. A session whose `stepId` names another step
  never suppresses `Start <step>`. Branch sessions (`stepId ''`) keep counting, as today.
- The close question lives inside the stage dialog, not a second dialog: one RadioGroup "Close
  session(s)" / "Keep open". Default Close. Closing loses nothing: history stays, Take over resumes.
  Every opener (action button, step mover, menus, Notes tab, routed prompt) gets it for free.
- The close decision rides the move call: new field `closeSessions` on `StepDoneArgs` and
  `SetTaskStepArgs`. Why not separate `CloseSession` calls afterwards: one call under one task lock,
  no half-done state (moved but sessions open after a failed close), and the backend owns the rule so
  the flow test proves it. Bridge method signatures do not change; only the arg structs gain a field.
- Close set ("stage sessions" of a move from `from` to `to`): the task's running TUI sessions where
  `StepID != "" && StepID != to`, plus the review agent (`Purpose == "review"`) when
  `from == "review" && to != "review"`. Covers several sessions at once, including one kept open from
  an earlier stage. Never closes branch sessions or headless sessions.
- Order: close first, then move. A session that exits between list and close (`the session is not
  running`) is skipped. Any other close error aborts with the error and no move.
- Repo-less steps (P467): their session has `StepID` set and cwd the task folder. Same rule; nothing
  special.
- Mobile: `POST /api/ade/tasks/step` passes the args struct through, so `closeSessions` defaults to
  false: mobile moves keep sessions open, as today. No mobile UI change.

### Backend (`apps/kira-space/internal/`)

1. `bridge/adewire/wire.go`:
   - `StepDoneArgs` gains `CloseSessions bool \`json:"closeSessions,omitempty"\``. Comment: "closes
     the stage sessions of the move first".
   - `SetTaskStepArgs` gains the same field.
2. `ade/stagesessions.go` (new):
   - `func (b *TaskBoard) stageSessions(taskID, from, to string) ([]model.AdeSession, error)`: reads
     `b.deps.Sessions.ListRunningTUI()`, filters by the close-set rule. Use `reviewStepID`.
   - `func (b *TaskBoard) closeStageSessionsLocked(taskID, from, to string) error`: returns nil on an
     empty set without touching the tracker. Else `b.tracker()`, then `closeTUILocked(tr, &rec)` per
     row. Skip `errors.Is(err, ErrInvalidInput)` whose text is "the session is not running"; better,
     make `closeTUILocked`'s two "not running" returns a sentinel `errSessionGone`
     (`invalid("the session is not running")`, same text, so `CloseSession` behaviour and messages
     stay) and match it with `errors.Is`. Wrap other errors: `fmt.Errorf("ade: close stage session
     %s: %w", rec.ID, err)`. The task mutex is held by the caller.
3. `ade/runs.go`:
   - `StepDone(ctx, taskID string, notes *string, closeSessions bool)`. After `next` is known and
     before `SetEntryStep`: `if closeSessions { closeStageSessionsLocked(taskID, plan[cur].Def.ID, next) }`.
   - `SetTaskStep(ctx, taskID, stepID, fromStepID string, notes *string, closeSessions bool)`. After
     the `HasRunning` refusal and the target checks, before `snapshotWorkflow`: same call with
     `from` (`currentStepID`) and `stepID`. The early return for `stepID == from` closes nothing.
   - Update both doc comments.
4. `bridge/adetask.go`: `StepDone` and `SetTaskStep` pass `args.CloseSessions`. Fix every other
   caller of the engine methods the compiler finds (the dynamic-dispatch hop codegraph showed for
   `SetTaskStep`; mobile `MobileWriter.SetTaskStep` calls the bridge and needs no change).
5. Bindings: the arg structs changed, so regenerate per `docs/DEV_ENVIRONMENT.md`
   (`wails3 task common:generate:bindings`, gitignored) before typechecking. Say so in the Result.

    - `move`: `const close = closable.value.length > 0 && closeChoice.value === 'close'`; spread

    - Return `closable`, `closeChoice`. Update the header comment (one concern stays: the stage move).
