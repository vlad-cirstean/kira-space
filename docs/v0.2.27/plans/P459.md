### 1.3 Jira to code host PR search

How it works today:

- `jira/client.go:197-204` `fetch` calls `c.crs(ctx, key)` when Jira's Development summary has PRs
  or is unknown. `crs` is `jira.Options.ChangeRequests`, wired in `appwire/wire.go:109` to
  `ade.KeyChangeRequests(hosts, repositories.GitHostChangeRequests)`.
- `ade/issuetracker.go:148-266` `KeyChangeRequests`: `fromHosts` runs every host's
  `githost.ChangeRequestSearch.SearchChangeRequests(key, 50)`; `fromIndex` reads
  `GitHostChangeRequestsRepo.ByHeadContaining`. Results keep whole-token key matches.
- GitHub: `githost/github/search.go` runs `gh search prs "<KEY>" --match title` across all of
  github.com, no `--repo`/`--owner`. Root cause of the bug: any public repo with a PR title holding
  the same key (e.g. `ABC-123`, common Jira key shapes) shows. Azure (`githost/azure/search.go`) scans
  the default project's newest 200 PRs.
- Rows land in three places: task tab issue line (`AdeTaskIssueLine.vue:98-121`), artifacts list
  (`ade/issuetracker.go:77-91`, source `jira`, gaps `changeRequestsMissing` / `changeRequests<Reason>`),
  issue view sidebar (`hostview/IssueSidebar.vue` PR section; `jira/detail.go:92-97`).

Does the ticket expose PR links? No route without touching credentials:

- acli `workitem view --fields` returns the Development field summary only (count, state), not rows.
  `docs/ARCHITECTURE.md:2259,3593` record this (P417).
- PR rows live in Jira's dev-status REST API (`/rest/dev-status/latest/issue/detail`); acli has no
  command for it. Calling it needs Kira's own authenticated HTTP, which the credential rule forbids.
- Remote links (`/issue/{key}/remotelink`) are no issue field; acli has no remote-link command
  (`workitem link` covers work item to work item links only). GitHub for Jira writes development info,
  not remote links, anyway.

Decision: remove the search, all three surfaces' PR rows, and wiring nothing else uses. Keep Jira's own
Development summary (count from the ticket, `Summary`): it is ticket data, not a search. The task's
own PRs still show through its branches (artifacts source `host`, `board.go` `ChangeRequests`); that
path is untouched.
