# P460 plan: Jira issue view: fast open, readable render, images

Spec row: `docs/v0.2.27/SPEC.md` P460. User words: "Opening a jira ticket is very slow. I mean is slower
than in the browser. Also it looks ugly, hard to read, doesn't render images etc."

App: Kira Space (`apps/kira-space`). Plan is against the tree after P459 (commits `f1e1ee1`, `b63f83e`,
`809cdde` plus its test/doc commits): the code host PR search is gone from `jira/client.go` `fetch`.
Discovery ran through `codegraph_explore` (jira client/detail/adf/status, bridge `HostViewService`,
hostview frontend, `markdown.ts`, fakeacli, flow and UI specs).

## 1. Root cause of slowness

acli does not run in the sandbox (`docs/DEV_ENVIRONMENT.md` "acli fixtures"), so no live trace. Cost
below is derived from the code: count of acli spawns on the critical path. Each spawn is a process
start plus acli's own auth load and a fresh HTTPS round trip to Jira (no connection reuse), roughly
0.5-2 s each. The browser reuses one session and paints progressively.

Critical path today, click "View issue" to first paint:

1. `HostViewService.Open` (`bridge/hostview.go:174`) creates the window. No fetch starts here.
2. New webview boots the bundle, asks `WindowTarget`, mounts `IssueView.vue`, then calls
   `hostViewIssue` (`IssueView.vue:27`, `queries.ts:26-31`). acli starts only now: window boot and
   acli run in series.
3. `client.detail` (`jira/detail.go:39-54`): `c.ready` may probe status (`jira/status.go:60`, two
   serial spawns `--version` then `jira auth status`) when the 5 min cache lapsed. Then
   `c.forget(key)` (line 48) throws away the 60 s `Issue` cache: every open is a full re-read.
4. `readDetail` (`detail.go:56-97`) runs two spawns at once and waits for both (`wg.Wait`, line 67):
   `c.issue` (`client.go:141-197`, `workitem view summary,status,<devId>`, only for the Development
   summary; on the first read per site the field list is `*all,-comment,...`, a large payload, with an
   oversize retry run serially, `client.go:156-161`) and `detailView`.
5. `detailView` (`detail.go:121-138`): when output passes the 1 MiB cap it has already downloaded 1 MiB,
   then runs `view DetailFieldsNoComments` and `comment list` **in series**: 3 serial spawns.
6. Nothing renders until the whole detail lands: no cache in the new window (fresh `QueryClient`), no
   cached copy on the Go side (P428 "every load is a fresh read").
7. Render: `markdown-it` over the description and at most 100 comments, synchronous. Small next to
   acli (sub-millisecond per KB); not a cause. No virtualization needed.

Root causes, in weight order: (a) fetch starts only after window boot; (b) no cached copy at all, so
reopening pays full price; (c) a second acli spawn per read only for the Development summary; (d)
overflow path serial; (e) status probe on the path once per 5 min.

## 2. Fetch fix design

### 2.1 Prefetch on open (cause a)

- `bridge/hostview.go` `openIssue` (225-238): when `openTarget` returns `Opened`, start
  `go s.prefetchIssue(p, ref)`. It calls `IssueDetail(context.WithoutCancel(ctx), ref, true)` and drops
  the result; errors are not cached, so the window's own call reports them.
- Covers `Open` and `OpenHostViewIssue` (capture path), both go through `openIssue`.
- A focused existing window (`Opened` false) does not prefetch.

### 2.2 Detail cache with stale marker (cause b; "cached data first" is safe)

Safe because the view is read-only, the copy is labeled stale and revalidated at once, and a post drops
it.

- `issuetracker/detail.go` interface: `IssueDetail(ctx, ref Ref, fresh bool) (IssueDetail, error)`.
  Update the doc comment (no longer "no result cache"). Only caller: bridge `Issue` and the prefetch.
- `issuetracker.IssueDetail` gains `FetchedAt int64 json:"fetchedAt"` (unix ms, when acli answered)
  and `Stale bool json:"stale,omitempty"`.
- `jira/client.go`: `client` gains `details map[string]detailEntry` (`d`, `at`). Constants
  `detailFreshFor = 30 * time.Second`, `detailKeepFor = 10 * time.Minute`.
- `jira/detail.go` `detail(ctx, ref, fresh)`:
  - `ready` first (unchanged).
  - `!fresh` and entry age < `detailFreshFor`: return it.
  - `!fresh` and age < `detailKeepFor`: return it with `Stale = true`. No acli call.
  - Else read. Singleflight key `detail|<key>` as today, but run like `issue()` does: `sf.DoChan`, work
    on `context.WithTimeout(context.WithoutCancel(ctx), detailBound)`, caller `select`s on its own
    ctx. A caller that gives up leaves the read running for the next one (prefetch joins cleanly).
  - On success store the entry, and store an `Issue` cache entry built from the detail (Ref, Title,
    Status, StatusCategory, Summary) via `c.store` instead of `c.forget` (drop line 48). Errors are
    not stored in `details`.
- `jira/comment.go:51` `postComment`: also delete the `details` entry, so the post's refetch reads fresh.
- `bridge/hostview.go`: `HostViewIssueArgs` gains `Fresh bool json:"fresh"`; `Issue` (303-324) passes
  it. `prefetchIssue` passes `true`.

### 2.3 One acli call per read (cause c)

- `jira/detail.go`: replace the constants with `detailFields(devID string, comments bool) string`.
  Base list `summary,status,issuetype,priority,resolution,assignee,reporter,labels,components,created,updated,duedate,parent,description,attachment`,
  then `,comment` when `comments`, then `,<devID>` when known. Keep exported `DetailFields` and
  `DetailFieldsNoComments` as the base forms (with `attachment`, no dev id) for fakeacli and docs.
- `parseDetail(out, site, devID)`: when `devID != ""`, `d.Summary` from `parseDevSummary(fields[devID])`.
- `readDetail`: read `c.devInfo(st.Site)`.
  - `info.id != ""`: one spawn, `detailView` with the dev id. No `c.issue`.
  - `info.id == ""` and `noDevTo` passed (first read per site): run `c.issue` beside `detailView` as now
    (it discovers the field id); take `Summary` from it.
  - `noDevTo` active (site has no Development field): `detailView` only; `Summary` stays unknown.
  - After P459 `c.issue` serves only `Summary` here; title/status come from the detail.

### 2.4 Overflow path in parallel (cause d)

- `detailView`: after `ErrOutputTooLarge`, run `view` without comments and `commentList` concurrently
  (`errgroup` is not needed: two goroutines and a `sync.WaitGroup`, as `readDetail` does). Same
  result rules: view error fails the read; list error sets `omitted`.

### 2.5 Status probe (cause e): declined

Serving an expired OK status while re-probing in the background would hide a sign-out behind a less
precise view error and change `Status()` for every caller (settings, task tab). It costs at most once
per 5 min. With 2.1 it overlaps window boot. No change.

## 3. Readable render design

### 3.1 Markdown layer (`frontend/src/hostview/markdown.ts`, shared by PR and issue views)

- Add `markdown-it-github-alerts` (MIT, 1.0.1, peer `markdown-it >= 13`) to root `package.json` beside
  `markdown-it`. Library over a hand-rolled callout rule. Titles from i18n
  (`space.hostView.markdown.alert.{note,tip,important,warning,caution}.title`), passed via the plugin's
  `titles` option. GitHub PR bodies gain the same callouts.
- Core rule `kira-chips` (after `inline`): a `link_open` whose href starts `#kira-mention` or
  `#kira-status-<color>` becomes a `span` (its `link_close` too) with classes from
  `badgeVariants` (`@theme/components/ui/badge`): mention `default`; status color map green `ok`, blue
  `info`, red `error`, yellow `warn`, purple and neutral `default`. Drops `href`/`title`. A user link to
  such a fragment just renders a chip: harmless.
- Image rule (21-27): render a chip, not `[image: …]` text. `data-kira-image`, classes
  `badgeVariants({variant:'default'})` plus `kira-prose-media`. https src: `<a href title>`; any other
  src: `<span>`. Never `<img>`: CSP `img-src 'self' data:` (`frontend/index.html:7`) blocks remote
  loads anyway, and the no-remote-load stance (ARCHITECTURE "Pull request view") stays.
- `table_open`/`table_close`: wrap in `<div class="kira-prose-scroll">` so wide tables scroll, not
  the page.
- Update the header comment.

### 3.2 Prose styles (`packages/theme/src/base.css`, the one prose layer)

`MarkdownBody.vue` (`class="kira-prose kira-prose-host"`), so notes and repo file views do not shift:

## 4. Images and attachments: credential rule

- Route search: acli has `jira workitem attachment list` and `delete`; no download command
  (Atlassian reference pages; Atlassian suggestion JRACLOUD-97830, "Gathering interest"). The
  attachment `content` and `thumbnail` URLs need an authenticated HTTP call. Making it would mean
  Kira reading acli's token: forbidden ("CLI credentials: never touched", guard G5 under
  `issuetracker/`). Media UUIDs in ADF need the media API, same problem.
- Requirement no route meets: inline image bytes. Even with bytes, CSP allows only `self`/`data:`.
- Shown instead: metadata from `workitem view --fields attachment` (same call, no extra spawn):
  attachment tiles and inline chips at the image's place in the text, both opening the attachment
  `content` URL in the OS browser, where the user's Jira session shows it. External (public URL) images
  get the same chip linking out.
- Backend: `issuetracker.Attachment {ID, Filename, MimeType, Size int64, CreatedAt int64, Author
  *Person, URL}` with json tags matching 3.5. `IssueDetail.Attachments []Attachment json:"attachments"`,
  `AttachmentsTruncated bool json:"attachmentsTruncated,omitempty"`. `DetailMaxAttachments = 50`;
  `Normalize`: nil to `[]`, https-only URL, sort newest first, cap. `jira/detail.go` `parseAttachments`
  reads `fields.attachment` (`id`, `filename`, `mimeType`, `size`, `created`, `author`, `content`).
- Docs: "Known open items" gains: "**Jira images do not render inline (P460).** acli lists attachments
  but downloads none; the content URL needs credentials Kira never touches, and the CSP blocks remote
  images. The view shows tiles and chips that open in the browser. Delete once acli downloads an
  attachment."

The orchestrator must tell the user this part of the ask ("render images") is met only as links.
