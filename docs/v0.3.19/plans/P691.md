### Q2 Session keying

- `TaskBoard` owns its own `codeworkspace.Registry` field `files`, created in `NewTaskBoard`, keyed
  by branch row id (`model.AdeTaskBranch.ID`). Separate from `CodeWorkspaceService.Registry`, so a
  code_repos id never collides and `RemoveRepo` never touches a task session.
- Each call resolves the worktree server-side: `GetBranch` → `loadTaskCtx` → `openRepo` →
  `worktreeOf`. That is `reviewWorktree` minus the `reviewableBranch` gate. Factor a helper
  `taskWorktree(ctx, branchID) (*gitsession.RepoEntry, model.AdeTaskBranch, string, error)` in
  `internal/ade/taskfiles.go`; have `reviewWorktree` call it and then apply `reviewableBranch`. Empty
  path returns `ErrNoWorktree` (new sentinel in `ade` errors file; catalog key
  `backend.space.ade.files.noWorktree.body`, text "This branch has no worktree.").
- Session opened with `files.Open(sb.ID, path, entry.Repo.Runner(), entry.Repo.GitPath())`.
  `Registry.Open` already reuses on same root and gitPath and closes a stale one, so a moved or
  re-created worktree gets a fresh session.
- One search per branch worktree (`Session.BeginSearch` already enforces this).
- Lifetime: `removeWorktree` (archive.go, single removal point for `detachRow` and `ArchiveTask`)
  calls `b.files.Close(lb.sb.ID)` before removing. `TaskBoard.Close` calls `b.files.CloseAll()`.
  Frontend calls `TaskFilesClose` when the Files tab unmounts or the selected branch changes.
- Cost: one `for-each-ref` per call through `loadTaskCtx`, same as `ReviewWorkingDiff`. Accepted.

### Q4 Edit vs read-only

Read-only. Risk named: the agent writes the same worktree files. The hash compare-and-replace in
`codeworkspace.WriteFile` is not atomic against an external writer: a write can land between hash
check and rename. The agent's Edit tool holds its own in-memory view and overwrites a human edit (or
gets overwritten) without either side seeing a conflict. Uncommitted-review stamps go stale the same
way. Editing path is Open in VS Code, which the user opts into knowingly. `useFileEdit` editing stays
for repo roots only.

### Q5 Launch seam

- `AdeTaskService` gains two fields:
  - `Revealer interface{ RevealFile(path string) error }`: the existing `shell.fileOpener` satisfies
    it. Wire from `Options.FileOpener` (appwire.go:97-98).
  - `Editor EditorLauncher` with `type EditorLauncher interface{ Open(paths []string) error }` in
    `bridge/adetask_files.go`. Wire from new `Options.Editor`.
- New package `apps/kira-space/internal/editorlaunch`:
  - `Locate(goos, home string, getenv func(string) string) (string, error)`: VS Code discovery via
    `toolexec.Locate(exec.LookPath, os.Stat, name, candidates)`. Order: PATH first, then candidates.
    - darwin: `code` on PATH; `/Applications/Visual Studio Code.app/Contents/Resources/app/bin/code`;
      `~/Applications/Visual Studio Code.app/Contents/Resources/app/bin/code`;
      `/opt/homebrew/bin/code`; `/usr/local/bin/code`.
    - linux: `code` on PATH; `/usr/bin/code`; `/snap/bin/code`; `/usr/share/code/bin/code`.
    - windows: PATH hit on `code.cmd` maps to `..\Code.exe` beside its `bin` dir; then
      `%LOCALAPPDATA%\Programs\Microsoft VS Code\Code.exe`;
      `%ProgramFiles%\Microsoft VS Code\Code.exe`. Never launch a `.cmd` (avoids cmd.exe parsing).
      Windows does not build today (toolexec `Setpgid`); write the branch anyway, compile-checked by
      `GOOS=windows go vet ./internal/editorlaunch/` only if the package itself avoids toolexec's
      unix-only spawn (it does: `Locate` is portable).
  - Not found: `ErrNotFound`.
  - `VSCode{}` with `Open(paths []string) error`: `Locate` on each call (user may install while app
    runs), then `exec.Command(bin, paths...)`, `cmd.Env = loginshell.ScrubGitEnv(os.Environ())`,
    `cmd.Stdin/Stdout/Stderr = nil`, `Start()`, `go cmd.Wait()`. Detached: `start_unix.go`
    (`//go:build !windows`) sets `SysProcAttr{Setpgid: true}`; `start_windows.go` sets
    `CREATE_NEW_PROCESS_GROUP`. Never `toolexec.Run`: it waits and kills the group on cancel, which
    would kill VS Code.
  - Args: root target gives `[root]`; file target gives `[root, file]` (opens folder window and
    focuses the file). argv only, never a shell string.
  - Declined: `open -a "Visual Studio Code"` (bundle path candidate covers it, and it cannot report a
    missing install before launch); `vscode://` URL (cannot detect a missing install).
- Failure text:
  - Editor missing: `E_NOT_FOUND`, key `backend.space.ade.files.editorMissing.body`, text
    `VS Code was not found. Install it, or run "Shell Command: Install 'code' command in PATH" from VS Code.`
  - Target path missing: `E_NOT_FOUND`, key `backend.space.ade.files.targetMissing.body`, text
    "This file no longer exists in the worktree."
  - Containment refusal: `E_BAD_REQUEST`, key `backend.space.ade.files.badPath.body`, text "This path
    is outside the task worktree."
  - Launcher nil: `E_UNSUPPORTED`, key `backend.space.ade.files.launchUnsupported.body`, text "Not
    available in the browser build."
- `-tags server`: package-main pair `launch_native.go` (`//go:build !server`) returns
  `editorlaunch.VSCode{}`; `launch_server.go` (`//go:build server`) returns nil. Same pattern as
  `locator_server.go`. In server build `main.go` also passes nil as `Revealer` for tasks (Wails
  fileexplorer would open on the server host, not the viewer's machine). `TaskFilesLaunchers`
  reports `{reveal: 'none', editor: false}`; UI hides both buttons and menu items.
- Fake: `flowharness/shellfakes.go` gains `EditorLauncher{mu, opened [][]string, missing bool}` with
  `Open`, `Opened() [][]string`, `SetMissing(bool)` (Open returns `editorlaunch.ErrNotFound` when

  `harness.go` next to the existing `FileOpener: a.FileOpener` lines (:273/:331/:510).
- No credential touched: VS Code and file manager run as plain processes; nothing reads tokens.

## Security

- Client sends only `branchId` and a relative path. Worktree root comes from the branch row
  (`worktreeOf`), never from the caller, same as `review_working.go`.
- Every path passes `pathsafe.ValidateRelPath(root, rel)`: rejects absolute, `..`, dangling-symlink
  leaf, and any symlink resolving outside root (EvalSymlinks containment). Reveal and open use the
  resolved absolute path.
- Launch is argv only (`exec.Command(bin, paths...)`), never `sh -c`, never a `.cmd` on Windows.
  Paths beginning with `-` cannot occur: both are absolute.
- Child env `loginshell.ScrubGitEnv(os.Environ())`; no secret added, none logged.
- Search regex is RE2 (`codeworkspace.Search`), no catastrophic backtracking.
- Listing cap stays 200k (`EnumerateAll`), file read limits stay (`tooLarge`).
- Server build: reveal/open disabled (would act on the server host).
- No credential read or written; G5 guard paths untouched.
