# P745: Kube MCP: unambiguous transform script globals in the tool description

Spec: `docs/v0.3.24/SPEC.md` § P745. Base: `6616650ab`. One Sonnet implementer, no streams.

## Verdict on the claim

Real defect: the globals named are correct, but the text around them is ambiguous. Not a code bug.

Engine bindings (verified in code):

- `run_query` script: one global, `result` (`apps/kira-space/internal/dbmcp/query_script.go:80`).
- `api_request` transform: `response`, `request` (`api_script.go:275`); prepare: `request`, `input` (`:96`).
- `kube_read` transform: `result` (the op's JSON reply), `request` (`kube_script.go:311`); prepare:
  `request` (`:172`).
- The return value becomes `output` of the envelope the agent gets: `queryScriptEnvelope`
  (`query_script.go:110`), `kubeScriptEnvelope` (`kube_script.go:342`), API `{"output":…}`
  (`api_script.go:390`). `output` and `input` are never script globals.

Description text (`internal/llmprompts/registry.go`):

- `:843` run_query `script`: `Global result {…}; you get {output, input: {rowCount, truncated}}.`
- `:904` api_request `script.transform`: `Globals response {…} and request. You get {output}.`
- `:928` kube_read `script.transform`: `Runs on globals result (what op returns) and request; can set
  values for a later read. You get {output, input: {rowCount, truncated}}.`

Decisive ambiguity:

1. "You get {output, input}" follows the globals list and never says `output` is the script's return
   value. Read as "the script gets", it names two more globals: Haiku's `output` and `input` guesses.
2. kube "what op returns" is circular: with a script, op returns `{output, input}`, so
   `result.output` is a fair reading (Haiku's third guess). Nor does it give the list shape, so a
   transform on `op list` must guess `rows`/`cells` or first read the table, which breaks the kept
   chain. run_query already spells its `result` shape; kube does not.

The fixer's evidence matches: `4af0ed833` commit message, original prompt 8 of 10, guesses
`output`/`input`/`result.output`, one run returned the table.

## Fix

Edit only the three `arg(...)` defaults in `internal/llmprompts/registry.go`. Same phrase in each:
`You get output (its return value)`. No Go logic change, no schema change.

- `:843` `dbmcp.tool.run_query.arg.script`:
  `Runs on the result before you get it; it can set values for params. Global result {columns, rows of text cells or null, rowCount, truncated}. You get output (its return value) and input {rowCount, truncated}. SQL numbers are text: use Number() or BigInt().`
- `:904` `dbmcp.tool.api_request.arg.script.transform`:
  `Runs on the response. Globals response {status, headers [{name, value}], contentType, body (masked text), json, truncated, finalUrl} and request. You get output (its return value). Integers above 2^53 are BigInt; kira.parseJSON keeps exact numbers.`
- `:928` `dbmcp.tool.kube_read.arg.script.transform`:
  `Runs on globals request and result: op's reply without a script, list {columns, rows [{name, namespace, cells per column}], rowCount}. You get output (its return value) and input {rowCount, truncated}.`

Kube drops "can set values for a later read": `dbmcp.instructions.scripts` already says every script
writes `plain.name` for a later script. Prepare texts (`:902`, `:927`) stay: their globals and return
are already explicit. `run_script` has no JS script arg; untouched.
