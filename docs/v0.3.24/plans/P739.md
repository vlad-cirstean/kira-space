`(program)` (style and layout of the 500-row tree), then Vue patch of every row (`patchStyle`,
`setStyle`, `createMessageContext` from per-row `t()`); per mark at 3000 files about 17 ms of
`buildFileTree` (`compareNatural`, `insertFile`, `walk`): a mark replaces `files`, so the tree folds
again although no path changed.

Causes, measured:

1. **File tree not virtualized** (`FileTree.vue`). It renders up to 500 rows (`useCappedList`,
   `FILE_TREE_PAGE_SIZE`), about 9 elements each with a reka `Checkbox`. Every file open changes
   `selectedFile`, so all 500 rows re-render and re-lay-out. The A/B above isolates it: same 3000
   files, 60 rows instead of 500 cuts steady open time 1.5 s to 0.7 s, first open 3.8 s to 1.3 s,
   filter 1.1 s to 0.44 s. File size is not a lever (20k-line row above). Also breaks ARCHITECTURE
   "a list that can pass 200 rows must use useVirtualRows".
2. **Copy detection in `review.files`** (`porcelain.NameStatusArgs` `-C`): 201 of 209 ms of the
   warm call at 3011 files; `-M` alone is 9 ms. `-C` compares every added file against every
   modified file, so a PR adding many files pays more. `review.files` runs on boot, every window
   focus (`AdeReviewFiles` `api.refresh()`), every `refsChanged` and every mark failure.
3. **`review.markMany` writes one transaction per file** with a fresh `flate.NewWriter` each
   (`MarkFiles` loop into `markFileAt` into `Store.Put`): 1506 files 2.2-8.2 s. Folder checkbox.
4. **Tree refold on every mark** (`ReviewFilesState.files` replaced, `FileTree` `buildFileTree`
   reruns): about 17 ms per mark at 3000 files, Chromium. Small; one line once item 1 lands.

Measured and not a cause (no change): `review.fileDiff`, `file.read`, `review.comment.list`,
`resolveBase` (all under 20 ms at this size); Monaco diff of a 20k-line file (+150 ms at most);
boot to first row (about 2.3 s at 30 and 3000 files alike). `review.fileDiff` runs twice per open
(`ReviewFilesState.#loadDiff`, `committedReviewSource.loadDiff`); at 1-17 ms each it stays.

## Changes

### 1. Virtualize `FileTree` (Stream A only)

`packages/git-ui/src/components/FileTree.vue`:

- Replace `useCappedList` and `ShowMoreButton` with `useTreeVirtualRows`
  (`@workbench/behaviour/treeVirtualRows`, @tanstack/vue-virtual), the recipe of
  `apps/kira-space/frontend/src/studio/api/CollectionsTree.vue` (lines 44-55, 395-440): `treeEl` is
  the scroll element (`@scroll="onScroll"`), an inner `relative` spacer of `totalSize`, rows with
  `VIRTUAL_ROW_CLASS` and `translateY(item.start)`, `height` from `useRowHeight().single`
  (`@workbench/lib/rowHeight`; rows are `min-h-row` single line). Row keys come from `rowKey`.
  Rows need a `key` field for `useTreeVirtualRows`: map `FileTreeRow` to `{ ...row, key }` in the
  `rows` computed, or widen `FileTreeRow` in `fileTreeModel.ts` with `key` (implementer's pick).
  `StickyRowLike` needs `depth`, `hasChildren`, `expanded` (file rows: false, false). No sticky
  ancestor band (FileTree has none today); `band` stays unused. If `StickyRowLike` does
  not fit the row type, use `useVirtualRows` directly plus `scrollToIndex`; still no hand-rolled
  windowing.
- `useListNavigation`: pass `scrollToIndex: (_i, key) => revealKey(key)` and
  `rendered: () => virtualItems.value`, as `CollectionsTree` does, so arrow keys reach unmounted
  rows. Keep the focused row mounted (`useVirtualRows` `pinned`) only if focus drops while
  scrolling in the existing specs.
- Scroll keep: today `keptScrollIf` (only when a keep is injected). Keep that semantics: pass
  `keepScroll` to the virtualizer only when `inject(KEPT_VIEW_STATE_KEY, null)` is set, else null.
- Drop the cap announce watch (`git.fileTree.capped.announce`) and `watch(() => props.files,
  resetCap)`; delete the catalog key if now unused (`check-catalog --unused` tells).
- Per-row `t()` hoisted (ARCHITECTURE "never per cell" rule): the four toggle titles
  (`reviewToggleTitle` keys, folder titles) resolve once per render pass in a computed map keyed by
  attention state, rows read from it.
- One template for every mount; a bounded parent gives the scroll element its height. Every caller
  but one already is bounded: `DetailPane`, `StashDetailPane`, `WorkingDetailPane`,
  `ReviewFilesPane` (committed tree `flex-auto min-h-0`; working tree in a `max-h-[40%]` section).
- `ReviewCommitRow.vue` mounts `FileTree` inside an expanded commit row whose height is content
  (measured by `ReviewCommitList`). A virtualized tree there has no viewport. Add a prop
  `capped?: boolean` (default false) that keeps today's `useCappedList` plus `ShowMoreButton` path
  for that one mount; `ReviewCommitRow` passes `capped`. The row markup is one shared template
  either way: iterate `renderRows` (virtual items mapped to rows, or the capped slice), with the
  positioning class and style only in virtual mode. Not measured slow, out of this ask; its
  behaviour stays byte for byte.

`packages/git-ui/src/lib/useRevealSelectedFile.ts`: drop `visibleRows`/`showMore`/`treeEl`
querying; expand collapsed parents as today, then call a passed `reveal(key)` (the virtualizer's
`revealKey`, or in capped mode the old raise-cap-then-`revealElement`). Never moves focus, as now.

`packages/git-ui/src/lib/fileTreeModel.ts`: `FILE_TREE_PAGE_SIZE` stays (capped mode uses it).

### 2. No copy detection in `review.files`

`apps/kira-space/internal/gitclient/porcelain/difftree.go`: add

```go
// RangeNameStatusArgs is NameStatusArgs without copy detection (-C): a PR range lists a copy as
// added, as GitHub does, and -C cost grows with added x modified files (P739).
func RangeNameStatusArgs(from *string, to string) []string {
	args := []string{"diff-tree", "-r", "--no-commit-id", "--name-status", "-M", "-z"}
	return appendRevPair(args, from, to)
}
```

`apps/kira-space/internal/gitsession/incremental.go` `rangeFilesRecords` (line 559): use it. Only
this caller changes; commit detail, stash, working detail keep `-C`. Renames (`renameSource`
carry-over) are untouched.

### 3. `review.markMany` in batched transactions

- `apps/kira-space/internal/gitreview/snapshot.go`: `Compress` reuses writers from a
  `sync.Pool` of `*flate.Writer` (`Reset` onto the buffer), same `BestCompression` level, so
  stored bytes and `Decompress` stay compatible.
- `apps/kira-space/internal/gitreview/store.go`: `PutMany(ctx, repoID, branch, []PutItem)` with
  `PutItem{Rec FileRecord; Content []byte}`: one transaction, one `upsertSession`, prepared
  statements (`tx.PrepareContext`) for the upsert, the range delete and the range insert, reused
  across items. `Put` becomes `PutMany` of one item (one write path).
- `apps/kira-space/internal/gitsession/incremental.go`: split `markFileAt` into
  `prepareMark(ctx, tip, branch, path, reviewed, ranges) (PutItem, error)` (everything up to the
  record build, `captureCommitted` included, unchanged) and the write. `MarkFile` keeps lock,
  prepare, `Put`. `MarkFiles` works in chunks of at most 256 paths or 16 MiB of snapshot content,
  whichever first: take the chunk's path locks in sorted path order (no deadlock with single-path
  holders), prepare each, `PutMany` once, release. Content is held raw only per chunk (bounded
  memory). The first error stops the batch; earlier chunks stay written, as today, so the
  frontend's reload-on-failure (`reviewFiles.ts` `#runMarkMany`) stays right. Update the handler
  comment in `gitrpc/incremental.go:205` ("each file's record is independent") to say chunks.
- Lock order invariant goes in a comment on `MarkFiles`.

### 4. Keep the tree when only review states change

- `packages/git-ui/src/state/reviewFiles.ts`: add `readonly changes: ShallowRef<readonly
  FileChange[]>`, set in `#loadFiles` `onResult` only when the path/kind/originalPath sequence
  differs from the current one, cleared in `setTarget`. Marks leave it alone.
- `packages/git-ui/src/components/review/ReviewFilesPane.vue` line 91: `const files = computed(()
  => props.reviewFiles.changes.value);`. Review states keep flowing through `reviewStatesMap`.
