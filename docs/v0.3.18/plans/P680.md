# P680: DB MCP: JS scripting and kept variables for SQL

Planner: Opus. Implementers: two Parts, one sequential Sonnet subagent each, Part 1 then Part 2. No
streams: adapter param path, dbmcp gate order, payloads and card are one order-dependent chain, and
Part 2 builds on Part 1's payload and gate changes.

Spec row: same abilities as the API MCP for SQL. Agent prepares a query and may post-process its
result with a JS script before it returns to the AI (parse, pick, anonymise). Script shown next to
the statement in the approval card and op log. Results kept in named variables (P678 store, same
retention and visibility), used by later queries or scripts (ids from one query passed as a list
into the next). Kept values never return to the AI. P675 engine and P678 store reused, not forked.
Connection MCP settings hold: script never widens what a connection allows, runs after masking and
redaction, approval class comes from the statement. Review shows raw rows and transformed result as
in P677. Plan decides tool shape, safe variable binding (parameters, never splicing), per-adapter
limits.

## Decisions

### Tool shape: two optional arguments on `run_query`

No new tool. `run_query` keeps every gate, lane, limit, exemption, review and op-log path; a second
tool would duplicate them or drift.

- `params: string[]`: kept variable names bound to the statement's placeholders. 1 to 64 entries,
  at most 16 distinct names (P678 per-request cap). Kept variables only: no literal values (the agent
  writes literals in SQL as today; a literal channel would add an unmasked-data path to audit and
  card for no spec gain).
- `script: string` (Part 2): P675 function body that post-processes the result. Up to 64 KiB
  (engine source cap).
- No preparation script for SQL. The statement is literal agent text, so the user approves exactly
  what runs and the class is decided from that text. "Prepares a query" maps to the statement plus
  `params`. A script that generated SQL would run a statement the classifier, table allow list and
  user never saw.
- Refused at argument check (before connecting, agent text in quotes):
  - `script` with `explain: true`: "script post-processes query results; it does not apply to
    explain".
  - `params` on mongodb, redis, kibana: "connection \"x\" (redis) takes no params; kept variables
    bind into SQL statements only (postgres, mysql, mariadb, sqlite, clickhouse)". `script` is
    allowed on every kind `run_query` serves (it reads the rendered result).
  - `params` without `Config.Kept`: unknown-name text (P678's).
- `explain: true` with `params`: the EXPLAIN runs with the same binds.

### Binding: parameters, never splicing

The statement text runs byte for byte as approved. Values reach the server as bind parameters
(server-side bind or the engine's own typed parameter channel), never inserted into SQL text by Kira
and never by the driver's client-side interpolation.

New Go-only channel:

```go
// model (storage/model/console.go)
type BindParam struct {
	Label string          // "{{kept.ids}}": op log and errors only, never a value
	Name  string          // clickhouse placeholder name; "" for positional kinds
	Value json.RawMessage // compact JSON from the kept entry
}
// ConsoleRequest.Params []BindParam  (Go callers only, dbmcp)
// adapterhost.ExecuteRequestWire.Params []model.BindParam `json:"-"`
```

`adapters/sqlparams.go` (new) holds the shared, dialect-aware pieces:

- `ParamStyle` per kind: `Dollar` (postgres `$n`), `Question` (mysql, mariadb, sqlite `?`),
  `Braces` (clickhouse `{name:Type}`).
- `PlaceholderSites(statement string, d SQLDialect, s ParamStyle) (sites []PlaceholderSite, err
  error)`: walks the statement with the existing comment/quote lexer and returns each placeholder
  outside literals, quoted identifiers and comments (`From`, `To` byte offsets, `Index` 1-based for
  `$n`, `Name` and `Type` for braces). Errors (app text): quoting hazard (`lexSQLComments` hazard,
  dollar quote, backslash escape, executable comment), unterminated quote, sqlite `?NNN`, `:name`,
  `@name`, `$name` ("use plain ? placeholders"), `$0` or `$n` past 65535.
- `SecondStatement(statement string, d SQLDialect) bool`: a `;` outside literals and comments
  followed by anything but whitespace or comments.
- `DecodeParam(raw json.RawMessage) (ParamValue, error)`: one decoded value shape every adapter
  converts from: `Null`, `Bool`, `Int` (int64), `Number` (exact JSON text: decimals, exponents,
  integers outside int64), `String`, `List` (elements all one of Int, Number, String, Bool; `Int`
  and `Number` mixed promote to Number; null elements and nested arrays or objects refused).
  Object values are refused: "kept variable \"x\" is an object; only text, number, boolean or a
  list of one type binds as a parameter".
- `CommandWithParams(statement string, params []model.BindParam, linePrefix string) string`: the op
  log command, statement plus one trailing line `-- params: $1 = {{kept.ids}}, $2 = {{kept.n}}`
  (labels only; `#`/`--` per dialect via the existing prefix arguments of `JoinConsoleStatements`).
- `RefuseParams(req model.ConsoleRequest) error`: `CodeUnsupported` when `len(req.Params) > 0`;
  called first in mongo, redis and kibana `Execute` (defence in depth; dbmcp refuses earlier).

Per adapter, active only when `len(req.Params) > 0`; the unparameterised path is unchanged:

| Kind | Placeholder | Bind path | Scalar | List | One statement |
|---|---|---|---|---|---|
| postgres | `$1..$n`, `params[i]` is `$i+1`; every index 1..len used | `conn.Query(ctx, sql, pgx.QueryExecModeDescribeExec, pgx.QueryResultFormats{pgx.TextFormatCode}, args...)` from `runRaw` (server-side bind; text results keep cells as the server's text, same as today) | Int `int64`, Number `string`, String `string`, Bool `bool`, Null `nil`; pgx encodes to the described parameter type | Go slice of the element type (`[]int64`, `[]string`, `[]bool`; Number as `[]string`) bound to an array parameter: `WHERE id = ANY($1)` | extended protocol refuses several commands |
| mysql, mariadb | `?`, one per occurrence, `params[i]` is the i-th `?` | `conn.PrepareContext` then `stmt.QueryContext(args...)`: binary protocol, server-side bind; `InterpolateParams` is untouched (it applies to non-prepared calls only) | Int `int64`, Number and String `string`, Bool `int64` 0/1, Null `nil` | JSON text of the list as one `string` param: `WHERE id IN (SELECT j.v FROM JSON_TABLE(?, '$[*]' COLUMNS (v BIGINT PATH '$')) j)` | prepare refuses several statements |
| sqlite | `?`, as mysql | `conn.QueryContext(ctx, sql, args...)` (modernc `sqlite3_bind_*`) | Int `int64`, Number `string`, String `string`, Bool `int64`, Null `nil` | JSON text as one `string` param: `WHERE id IN (SELECT value FROM json_each(?))` | Kira refuses via `SecondStatement` |
| clickhouse | `{name:Type}`; names = the `params` set, every placeholder name listed and every listed name used | `doRequest` `extraParams` (`param_<name>`), ClickHouse parses each value as its declared type server-side; `RunCommand` gains a `params` argument | value in ClickHouse parameter text format: Int and Number as JSON text, String raw, Bool `true`/`false`, Null `\N` | `[1,2,3]`, strings `['a','b']` with `\\` and `\'` escaped (`clickhouse/params.go`): `WHERE id IN {ids:Array(UInt64)}` | one statement per HTTP request (server refuses more); Kira also checks `SecondStatement` |

- Order of values per kind is fixed by placeholder order, so `params` is positional for `?`/`$n`
  and a name set for clickhouse; the tool text says so per kind.
- Big integers stay exact: Int within int64 binds as an integer; anything else as exact decimal text
  the server casts. Floats never pass through float64 on the bind side.
- Read lane and read-only wrap apply unchanged (params ride the same `ExecuteRead`).
- Statement timeout, cancel, throttle, op log: unchanged paths. `op.SetCommand` gets
  `CommandWithParams(...)` when params are present.
- MySQL prepared statements return binary-protocol rows; cells go through `appendConsoleRows` as
  today. Implementer checks float, decimal, datetime and bit cells against the text path in the
  adapter scenario; a real difference becomes a Known open item (text below), not a workaround.

### Per-adapter limits

| Limit | Value | Why |
|---|---|---|
| Kept value size | 1 MiB (P678 store cap) | already bounded at `Put` |
| List elements | 100,000 | P678's "list of 100k ids fits"; bounds pgx array encode and JSON_TABLE work |
| `params` entries / distinct names | 64 / 16 | P678 per-request cap; 64 lets a name repeat in `?` dialects |
| clickhouse encoded params total | 256 KiB | params ride the URL (`http_max_uri_size` default 1 MiB, proxies less); refusal names the cap |
| postgres `$n` | ≤ 65535 | protocol limit |
| mysql, mariadb list | JSON text ≤ 1 MiB | under default `max_allowed_packet` (64 MiB) |

Refusal texts name the variable and the cap, never a value.

### Gate order with params (Part 1)

`runQuery` adds one step, `resolveParams`, after `resolveVerdict` and before `claimExemption`:

1. Kind supports params (table above) else refusal.
2. `PlaceholderSites` on `args.SQL`; `SecondStatement` refusal ("params need exactly one
   statement"); count or name mismatch refusal naming expected and given ("statement has 2
   placeholders ($1, $2) but params lists 1 name").
3. Each name: `keptvars.ValidName`; `Kept.Get(scope, name)` live (P678 text on unknown or expired);
   `DecodeParam` and the per-kind checks above (object, mixed list, nested, element cap,
   clickhouse total). Snapshot the entry `Meta` (IDs) into `rv.kept []agentapi.KeptUse` with sites.
4. Classification, table allow list, column review already ran on the same text in
   `resolveVerdict`: placeholders do not change them. The statement decides the class.

Then:

- `claimExemption`: exemption records bind `params` (names, order) and, in Part 2, the script hash,
  beside connectionId, mode, path and sql. A changed list or script spends the id as a mismatch.
- `planForCall`: EXPLAIN statements carry the same `Params` (values fetched as in step 5). An engine
  that cannot EXPLAIN with binds fails the `expensive_query` check closed, as any EXPLAIN error does.
- `awaitApproval` / `awaitExemption`: kept watch from P678 (below) wraps the wait.
- Execute (step 5): just before building `ExecuteRequestWire`, every snapshot ID must equal the ID
  `Kept.Get` returns now; the same call takes the value copy. Mismatch or absence refuses with
  P678's "changed" or reason text, nothing ran. An `allow` verdict (no card) uses its own snapshot.
- `recheckAfterApproval` unchanged. No forced card: kept use never changes the verdict, the same
  rule as P678 (allow, read auto-approve and review settings stay the user's trust settings).

Kept watch: P678 Part 1 puts the `OnRemove` cancel-on-removal logic inside `approveAPI`. Part 1
moves it into `dbmcp/kept_tools.go` `watchKept(ctx, kept []agentapi.KeptUse) (ctx2, stop,
gone func() error)` and calls it from `approveAPI`, `awaitApproval` and `awaitExemption`. Same
texts ("kept variable \"ids\" <reason> while waiting for approval; nothing ran. Produce it again,
then repeat the query."). Moving code inside `dbmcp` is not a fork of the store.

### Script (Part 2): where it runs and what it sees

- Validated with `jsengine.Check` in the argument step (before connecting): a syntax or source
  error refuses with the engine's positioned text and raises no item.
- Runs in `runQuery` after `executeAndRender` returned a success page result and before
  `reviewResponse`. Input is the agent-bound render output after masking, column-review withholding
  and plan summary: the exact JSON the agent would get today. Error exits (adapter error, masked
  error, masking refusal, limit refusal, empty result is a success) never reach the script; they
  return as today.
- So the script never widens access: it runs after every gate and after execute, has no database,
  network or filesystem binding, sees only masked rows, and cannot change the statement, mode,
  lane, class or verdict. Kept values a script writes come from masked input.
- Bindings: `result` (the render JSON: `kind`, `columns`, `rows` as text cells or null, `rowCount`,
  `truncated`, `truncatedCells`, `withheldColumns`, `plan`, `note`; documents, keyvalue and stream
  shapes as rendered) and `kept` (P678 Part 2 `keptRun.Bindings()`, `keptAfterResponse` stage:
  `get` and `set`). SQL numbers arrive as cell text: the tool text says to use `Number(...)` or
  `BigInt(...)`; big decimals stay text (answers P675's open "how SQL numeric arrives").
- Limits: `Timeout` 2 s, `MemoryBytes` 256 MiB, `InputBytes` 8 MiB (the held-result cap; 8 MiB × 24
  < 256 MiB), `OutputBytes` 4 MiB. Over-input refuses with "result is N MB, over the 8 MB script
  input limit; ask for fewer rows or columns" (read) plus `ranSuffix` for writes.
- Engine: the `*jsengine.Engine` P676 wires into `dbmcp.Config` (one per app, shared slots). If
  P676 left it API-only, Part 2 lifts the field to `Config` beside `Kept`; no second engine.
- Agent result when a script ran:
  `{"kind":"script","output":<script JSON>,"input":{"kind":"tabular","rowCount":3,"truncated":false},"kept":[{name,type,items,expiresInSeconds}]}`.
  `input` is metadata only (no cells). `kept` lists committed names (P678 Part 2 shape). zod
  `dbMcpRunQueryResultSchema` gains the `script` variant.
- Script failure: `KindSyntax` cannot occur (checked); runtime, timeout, memory, output errors
  return `run_query script <kind> error at line L, column C: <message>` as an IsError result, with
  `ranSuffix` for non-read classes. Error text goes through the P679 secret mask (secret kept reads),
  like the output. The user sees the same text in the review (when on) and the op log.
- Masked connections: input is masked already; no extra mask on output beyond P679 secrets. A
  script cannot unmask (it never had the real values).
- Kept writes: staged by `keptRun`, committed after the final point (review approved and
  `recheckHeld` passed, or right after the transform when review is off). Withhold, timeout,
  abandon, script error drop them. `keptvars.Source{Kind: script, MCP: "db", Tool: "run_query",
  Request: "<connection name>: <redacted statement>"}`; redaction through the adapter's
  `StatementRedactor` or `MaskSQLLiterals`; on `ok=false`: "<connection name>: statement withheld
  (N characters)". Scope from `keptScope(ctx)`.
- Kept reads: `keptRun` snapshot joins the same `watchKept` set as `params` uses.

### Review (Part 2): raw rows and transformed result

- When a script ran and review is on for the call, `ApprovalResponse` holds both texts: `Raw` (the
  render JSON the script read) and `Text` (the agent-bound script result). `Bytes` counts both
  against the 8 MiB per-result and 64 MiB total caps; over the cap the result is withheld unseen
  (existing texts). `Script` (source, hash) and `Keep` (P678 Part 2 staged summaries with previews)
  ride along.
- `recheckHeld` unchanged (mask set and exposure); a mask change during review withholds.
- `responsePayload` gains `scripted bool` and `rawBytes int`; snapshots never carry either text.
  `DbMcpPendingResponse` gains `raw` (text, only when scripted), `script {source, sha256}`,
  `willKeep` (P678 Part 2 shape).
- Card: P677's two-view review shape reused (assumed below). Raw view = today's `PendingResponse`
  table plus its As sent tab over `raw`, labelled as the masked rows the script received.
  Transformed view = the agent-bound JSON in a read-only `FlushEditor` (json). Script block and
  "Will keep" from P676/P678 Part 2. Unscripted results keep today's body exactly.
- Review decision is unchanged by a script: `reviewFor(summary, mode, class)` and review on request
  decide, from mode and class only.

## Risks

- pgx `QueryExecModeDescribeExec` with text result format: one extra round trip per parameterised
  statement (describe). Acceptable for agent queries. If a type fails to encode from the chosen Go
  value, the scenario shows it; fix the conversion table, never fall back to simple protocol (that
  is client-side interpolation).
- MySQL `PrepareContext` refuses statements MySQL cannot prepare (some DDL, `LOAD DATA`); the
  engine error returns as today. Tool text: params work with SELECT, INSERT, UPDATE, DELETE.
- EXPLAIN with binds may be refused by an engine form; `expensive_query` then fails closed with the
  engine text (existing behaviour); the engine flow pins which kinds pass.
- P532 parsers on placeholders and list idioms (`$1`, `?`, `{x:T}`, `JSON_TABLE`, `json_each`): a
  parse refusal only refuses (fail closed). Recorded as a Known open item if real; adding a table
  function to a parser allow set is in scope only for `json_each` (pure, reads no table).
- Offset drift for statement marks: sites are UTF-16 offsets on the exact payload statement and
  apply to As sent only; the UI spec asserts every mark's text equals its placeholder.
- Kept value echo through `SELECT $1` (decision below).
- Part 2 depends on P676/P677 shapes unknown at planning time; mitigated by "lift if local" rules
  and by Part 1 not depending on them.

## Needs a user decision

1. Echo of non-secret kept values. A bound value can come straight back (`SELECT $1`, or `WHERE id =
   ANY($1)` returning the ids). Default in this plan: parity with P678 (only secret values are
   masked in results; the card shows the statement when a card is raised; allow verdicts log labels
   only). Alternative: mask every bound non-secret value's text in agent-bound results, which also
   blanks legitimate id columns.
2. Kept-only params. Default: `params` takes kept names only; no literal bind values.
3. No SQL preparation script. Default: the statement is literal; the "prepare" ability is the
   statement plus kept params. A generated statement would bypass classification and the user's
   view.
4. MySQL/MariaDB and SQLite lists bind as one JSON-text parameter used through `JSON_TABLE` /
   `json_each`, so the executed text equals the approved text. Alternative (rejected here):
   expanding `IN (?)` to N placeholders, which changes the statement after approval.
5. No forced approval card for kept or script use. Default: verdict from mode and class only, as
   P678 decided for API requests.
