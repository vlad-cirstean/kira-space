# P676: API MCP: scripted request preparation and result transform

Planner: Opus. Implementer: one sequential Sonnet subagent. No streams: agentapi cap, dbmcp script
step, wiring, card and op log are one order-dependent chain over shared payload types.

Starts only after P675 has landed on `chapter/v0.3.18` (`internal/jsengine`, `js-worker` argv shim).
This plan is written against `plans/P675.md`'s API (`Engine.Exec`, `Run`, `Binding`, `Limits`,
`Result`, `Check`, `SourceHash`, `*Error`, `Kind`). If the landed code differs, follow the code and
note the difference in Result.

Spec row: agents use the engine to prepare an API call for the user and to post-process its result
before it returns to the AI (parse, pick, anonymise). Script visible read-only, syntax highlighted,
in the approval card next to the request and in the op log. AI receives only script output, never
the raw response unless the script returns it. Script input: status, headers, body text, parsed
JSON when valid. Failing or over-limit script: clear error to the agent, same error for the user.
Approval modes, credential redaction, existing size limits keep applying. Plan decides tool shape,
prompt-registry schema docs, settings.

## Decisions

### Tool shape: one nested argument on `api_request`

New optional argument `script` on `api_request`, not a new tool:

```json
"script": {
  "prepare":   "<JS function body>",   // optional; runs before approval, returns request fields
  "input":     <any JSON>,             // optional; prepare's `input` global; refused without prepare
  "transform": "<JS function body>"    // optional; runs on the response, its return value is the result
}
```

Why: same gate order, same `api.request` item, same approval modes, same caps, no duplicated
request schema. P680 gives `run_query` the same `script` object (transform only), so the agent
learns one shape. At least one of `prepare`/`transform` when `script` is present.

### Prepare script

- Runs in the handler before `API.Plan`, so the request the user approves (and the approval class,
  below) is the prepared one. It runs without user consent: sandboxed, no I/O, no secret in scope,
  only the agent's own data. ARCHITECTURE states this.
- Globals (`jsengine.Binding` values): `request` = the agent's request exactly as sent
  (`method, url, headers [{name,value}], query, body, contentType, form`; references stay
  `{{name}}`, nothing resolved), `input` = `script.input` (null when absent).
- Return value: an object with any of `method, url, headers, query, body, contentType, form`.
  Returned fields replace the agent's; absent fields keep them. `environmentId`, `timeoutSeconds`,
  `maxResponseBytes`, `followRedirects` are never script-settable. Rules (`applyPrepared`,
  `dbmcp/api_script.go`), each refusal "prepare script returned an invalid request: <reason>.
  Nothing was sent.":
  - not an object; unknown key (text lists the allowed ones);
  - `method`, `url`, `contentType`: string;
  - `headers`, `query`, `form`: array of `{name, value}` with string members (path named, e.g.
    `headers[2].value`);
  - `body`: string as is; object or array: compact JSON text from `Result.JSON` slice (big integers
    exact), and `contentType` becomes `application/json` unless the result or the agent set one;
    other types refused;
  - `body` and `form` both non-empty after merge: refused (same rule as the agent args).
  - Everything else (method enum, URL, 1 MiB body cap, variable names, access rules, host rules) is
    `agentapi.Plan`'s existing validation on the merged `Input`, with its existing texts.
- The merged `Input` is held in the handler goroutine and passed unchanged to `Send`, which
  re-plans it as today (`sameRequest` holds). The script never runs twice.
- Payload records `changed`: the field names the script returned, so the card says "Set by script".

### Transform script

- Runs after `Send` returns (approved or not prompted), before anything reaches the agent.
- Globals: `response` = `{status, statusText, headers [{name,value}], contentType, body, json,
  bodyBytes, truncated, binary, finalUrl, redirects [{status,url}]}`, all from the masked
  `agentapi.Result`; `request` = `{method, url}` of the plan (template URL, secrets `{{name}}`).
  `json` is the masked body bytes as a raw JSON value when `json.Valid(body)` and not truncated and
  not binary, else null (no content-type check: parsed whenever valid). The engine decodes it
  losslessly (integers above 2^53 arrive as BigInt).
- Agent result: exactly `{"result": <script output>}` (`undefined` gives null). No status, headers
  or body unless the script returns them. The wrapper object leaves room for P678 Part 2's `kept`
  sibling. Prepare alone (no transform) returns today's `agentapi.Result` shape unchanged.

### Caps and limits (existing limits keep applying)

| Limit | Value | Why |
|---|---|---|
| Script source | 64 KiB each (engine `Check`) | engine fixed cap; equals op log `maxDbCommandBytes` |
| `script.input` | 1 MiB compact JSON, depth by engine | same as the body cap |
| Prepared body | 1 MiB (existing `Plan` cap) | unchanged |
| Body given to transform | masked body up to 2 MiB (`transformBodyBytes`), also bounded by the user's client cap `MaxResponseMb` | a transform exists to reduce large responses; the agent cap applies to what the agent gets |
| Transform output | `maxResponseBytes` (default 64 KiB, max 512 KiB) as `Limits.OutputBytes` | the existing agent cap now caps the script result |
| Engine `InputBytes` | prepare: default 4 MiB; transform: 8 MiB (body text plus raw json plus headers) | 8 MiB x 24 = 192 MiB, under the 256 MiB default memory, so the engine's input sizing rule passes |
| `Timeout`, `MemoryBytes` | engine defaults (2 s, 256 MiB) | no setting, no agent argument: safety rails, not tuning |

- `agentapi.Input.ScriptBodyBytes int` (0 = no transform): `buildPlanned` copies it into an
  unexported `Planned.bodyCap`; `run` passes `bodyCap` (or `MaxResponseBytes` when 0) to
  `maskResult`. Not part of `sameRequest`. dbmcp sets it only when a transform is present.
- `agentapi.Result.Mask func(string) string \`json:"-"\``: the request's `mask.text`, so dbmcp masks
  transform output and error text with the same masker. Script input is already masked; this is
  defence in depth for later phases (P678 Part 2 secret reads, P679). After masking the output,
  `json.Valid` must hold (the mask token and `{{name}}` carry no JSON-special character); invalid
  gives `KindInternal`-style text "the script result could not be masked; nothing was returned".
- Masking can break a body's JSON validity (a secret that is a bare JSON number): `json` is then
  null. Documented.

### Approval class: decided from the request, never the script

- `needsAPIApproval(settings, plan)` and the allow-rule/deny verdict read the plan of the final
  (prepared) request: method, host, body. Neither script changes the decision. No forced prompt for
  a script: the transform only narrows what the agent sees, and prepare is equivalent to the agent
  writing that request itself. A prepared request that needs approval gets one even when the
  agent's literal request would not, and the reverse.
- With approval skipped (allow rule, `never`, auto-approved read) both scripts still run; their op
  rows are the trace.
- Denied, expired or abandoned approval: transform never runs, no `jsTransform` row.

### Binding approval to the shown script

The card's script text and the executed text are the same Go strings held by the handler goroutine
from argument decode to `Exec`; nothing can edit them in between (unlike `scriptruns`, whose file
can change, so it re-checks `Preview.Hash`). The payload carries `hash` (`jsengine.SourceHash`) per
script for the UI and tests; no re-check needed. Stated in ARCHITECTURE.

### Errors: agent and user see the same text

Every script failure records a script op row whose `error` is the exact text the agent gets:

| Case | Text (agent and op row) | Sent? | Item? |
|---|---|---|---|
| `Check` fails (syntax, source) at call start | `<stage> script: <*Error.Error()>. Nothing was sent.` | no | no |
| prepare runtime, timeout, memory, output, input | `prepare script failed: <*Error.Error()>. Nothing was sent.` | no | no |
| prepare invalid return | `prepare script returned an invalid request: <reason>. Nothing was sent.` | no | no |
| transform runtime, timeout, memory, stack | `transform script failed: <*Error.Error()>. The request was sent (HTTP <status>); its response is not returned.` | yes | as approved |
| transform output over cap | same prefix, plus ` Return less, or raise maxResponseBytes (max 524288).` | yes | |
| transform input too large (`KindInput`) | `transform script failed: the response is too large for a script (<n> bytes of input, limit 8388608). The request was sent (HTTP <status>); its response is not returned.` | yes | |
| scripts off in settings | `scripts are turned off in Kira Space's Studio MCP settings` (no row: nothing ran) | no | no |
| `script.input` without `prepare`, empty `script` | plain refusal, no row | no | no |

- The HTTP status in the transform error is kept on purpose: the request already had its side
  effect, and the agent must not retry a POST blindly. Nothing else of the response is named.
- `<*Error.Error()>` is the engine's `script <kind> error at line L, column C: <message>`; a non-
  `*Error` (internal fault) becomes "internal error" (logged once, static message, `err` key,
  `scope: "dbmcp"`).
- Transform error text passes through `Result.Mask`. Prepare error text needs no mask (no secret in
  scope).
- Check-failure row command: the source with invalid UTF-8 as U+FFFD and NUL plus bidi controls
  (U+202A to U+202E, U+2066 to U+2069) as visible `‮` escapes, so the op log never renders
  Trojan Source text. Over 64 KiB: `capCommand` truncates and sets `commandTruncated`.
- P677 shows the same text in the review; P676 alone shows it in the op log (the card is gone after
  approval).

### Op log representation

- Two new op kinds, `jsPrepare` and `jsTransform`, added to Go `model.opKinds` and
  `opKindSchema` in the same commit (else `op:start` is rejected). Generic names: P680 reuses
  `jsTransform` for SQL.
- Each script run is its own row through `ScriptOps.RunOp(ctx, adapterhost.OpSpec{Kind: …}, fn)`:
  connectionless like `http`, source `mcp` from ctx, command = the script source verbatim (fits the
  64 KiB command cap), error = the text above, duration = engine run including spawn. Order in the
  panel: `jsPrepare`, `http`, `jsTransform`.
- `OperationsPanel.codeLanguage` returns `javascript` for both kinds, so `OpLogCodeBlock` colours
  the source (read-only, existing primitive). Kind column shows the raw kind like other kinds.
- Not logged anywhere: script input values, response values, script output. The engine logs nothing
  about scripts (P675).

  `DefaultSettings`, zod `z.boolean().default(true)`), read by `bridge.apiSettings()` into
  `dbmcp.APISettings.Scripts`. No migration (missing leaf reads the default, as
  `focusOnApproval`).
- Off: `script` is removed from the `api_request` schema (`delete(sch.Properties, "script")` after

  gets the refusal above. `Server.server()` rebuild key widens from `mcpAPI bool` to
  `{api, scripts bool}` so a toggle applies without restart.
- Scripts also need `Config.JS` and `Config.ScriptOps` non-nil; nil behaves as off.
- UI: one `Switch` in `StudioMcpApiPane.vue` below the approval mode, `Field
  orientation="horizontal"` exactly like the existing API switch, testid
  `settings-db-mcp-api-scripts`, label "Agent scripts", description "Agents can attach JavaScript

  approval card and the op log." Instant patch through `useAsyncAction`, errors into the pane's
  existing error Alert.
- Default on: scripts never widen access, run sandboxed, and a transform reduces what the agent

### Code layout (dbmcp)

`dbmcp/jsscript.go` (MCP-agnostic; P680 reuses):

```go
// ScriptEngine is dbmcp's view of *jsengine.Engine.
type ScriptEngine interface {
	Exec(ctx context.Context, r jsengine.Run) (jsengine.Result, error)
}

// OpRunner records an operation row (adapterhost.Host).
type OpRunner interface {
	RunOp(ctx context.Context, spec adapterhost.OpSpec, fn func(context.Context, *adapters.OpCtx) (any, error)) (string, any, error)
}

type scriptStage string // "prepare" | "transform"

// scriptRun is one engine run. Bindings is built by appending: later phases add theirs
// (P678 Part 2 appends keptRun.Bindings()) before runScript, never by restructuring.
type scriptRun struct {
	Stage    scriptStage
	Source   string
	Bindings []jsengine.Binding
	Limits   jsengine.Limits
}

func (s *Server) scriptsOn() bool                                                      // settings && JS && ScriptOps
func (s *Server) checkScript(ctx context.Context, st scriptStage, src string) string  // "" ok; else records the row, returns text
func (s *Server) runScript(ctx context.Context, r scriptRun, describe func(*jsengine.Error) string) (jsengine.Result, string)
```

`runScript` opens the op row, sets command to the source, calls `Exec`, and on failure returns
`describe(err)` (or "internal error") as both the op error and the second return value. Exactly one
place builds the agent-facing failure text per stage.

`dbmcp/api_script.go`:

```go
type apiScriptArgs struct {
	Prepare   string          `json:"prepare,omitempty"`
	Input     json.RawMessage `json:"input,omitempty"`
	Transform string          `json:"transform,omitempty"`
}

// apiScripts is what the handler holds from decode to delivery; the card shows these strings.
type apiScripts struct {
	Prepare, Transform string
	Input              json.RawMessage
	Changed            []string // set by prepare
}

// apiOutcome is everything the final point needs: raw masked response, transform output or failure.
type apiOutcome struct {
	Raw         agentapi.Result
	Transformed json.RawMessage // nil without transform or on failure
	Failure     string          // transform failure text, "" otherwise
}

func (s *Server) prepareAPI(ctx context.Context, in agentapi.Input, sc *apiScripts) (agentapi.Input, string)
func applyPrepared(in agentapi.Input, out jsengine.Result) (agentapi.Input, []string, error) // pure, unit-tested
func (s *Server) transformAPI(ctx context.Context, plan agentapi.Planned, sc *apiScripts, raw agentapi.Result) apiOutcome
func (s *Server) deliverAPI(ctx context.Context, plan agentapi.Planned, sc *apiScripts, o apiOutcome) (*mcp.CallToolResult, any, error)
```

`apiRequest` becomes: settings and scripts-on check, decode `script`, `checkScript` both, prepare
(if any), `Plan`, approval (payload carries scripts), set `in.ScriptBodyBytes` when a transform
exists, `Send`, then without transform `jsonResult(raw)`, with transform `transformAPI` then
`deliverAPI`.

**`deliverAPI` is the one point where the agent-bound result is final.** It is the only function
that turns an `apiOutcome` into a tool result. P677 inserts its result review at its top (raw
`o.Raw`, transformed `o.Transformed`, `o.Failure`, scripts); P678 Part 2 commits staged kept values
there after review approves (or right away when review is off) and adds `kept` to the result
object. P676 keeps its body trivial: `Failure` gives `errResult(Failure)`, else
`textResult({"result": Transformed})`.

`ApprovalRequest` gains `APIScript *apiScripts` (unexported type is fine inside dbmcp; exported
`APIScriptView` only if a test outside the package needs it). `apiItemParts` takes the request (or
`*Planned` plus `*apiScripts`) and fills `apiPayload.Script`.

## Risks

- Spawn cost per script (two workers for prepare plus transform): P675 measures; if over 100 ms its
  warm-spare follow-up covers both. Flow timing assertions use generous margins.
- Monaco editors per card: two extra read-only editors per item; the dialog shows one item, so the
  cost is bounded.
- An agent could hide intent in a large prepare script: the user sees the whole script and the
  resulting request; the request, not the script, decides what is sent and whether approval is
  needed.
- Transform runs after a write already happened; a failing transform loses the result but not the
  effect. The error says the request was sent and its status.

## Needs a user decision

1. Prepare script in scope. Read of "scripted request preparation": an optional script that builds
   the request from the agent's `input` before approval. Alternative: transform only, the agent
   writes the request itself (smaller phase; P678 Part 2's read-only "before send" stage would then
   have no host). Plan assumes prepare is in.
2. `dbMcp.apiScripts` default on. Alternative: off until the user enables it.
3. Transform failure text names the HTTP status (safety against blind retries of a write). Strict
   alternative: name nothing of the response.
4. Agent result with a transform is only `{"result": …}`, no status. Alternative: add `status`.
